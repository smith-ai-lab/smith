# smith-dev-tests

What the test library and runner are is in [build-tests](../../../knowledge/build-tests.md). Run a test with the smith under test, never the installed one.

- **Tests of the docs and the release**: `tests/readme.sh` (every code block of README.md compiled, run, tested or proved by its info string, and every link resolved), `tests/skills.sh` (the `smith` blocks of the plugin's skills compiled, `smith fragment` skipped; an example in a skill is a complete block), `tests/release.sh` (scripts/release.sh with no network: the package, the pruning rule, the guard, publish and fetch against a stub `gh`), `tests/ci_tree.sh` (scripts/ci-tree.sh: the tree of a scratch repository and both branches of the skip rule), `tests/defer.sh` (scripts/defer_init.c on Mach-O objects, macOS only) and `tests/http.sh`.
- `smith test` runs the routing tests (each case through `smith cc` and through `smith-cc`; fewer for the stage0) against stub compilers, then the 532 `smith build` tests in `tests/build.sh`, the 225 `smith new` tests in `tests/new_test.smith` (the three builds, `assert(false)`, the tools on the generated project, `smith_library` under the template's flags, and the generated docs: a new project passes `smith docs` and `smith check`, breaking each rule fails it, and the verbs on a project: prove, fmt, lint, check), the 64 `smith docs` tests in `tests/docs.sh` (every rule on the small repositories of `tests/docs/fixtures/<case>`, each with the exact output in `expect.txt`, optional `args`, and `pass/expect.d`, the depfile; the options; the types the index declares; the verb needs no task) and the 27 arena tests in `tests/arena.sh` (`<smith/arena.h>` alone, its capacity stop, ASan, and a project using `smith_library`), and the io tests in `tests/io.sh` (`<smith/io.h>`, the header of the module `smith::io`: its lowering and the module compiled under the warnings, real files, console pipes, processes, timers, the seed, the lazily committed reservation, TLS connections against a server on the loopback, and the fake io with its scripted servers; sanitized and plain), the http script `tests/http.sh` (`lib/http.c` compiled under a new project's warnings; its behavior is `tests/http_test.smith`) the package tests in `tests/package.sh` (downloads on a scripted network into a real cache), the random tests in `tests/random.sh` (`<smith/random.h>`: Philox known answers, the distributions, digests across build configurations, the refusals, and a project using both libraries), the text tests in `tests/text.sh` (`<smith/text.h>`: `tests/text_test.smith` built with smith's own test library in three builds, with property tests on keys for the integers and a float parser that must equal `strtof`; `smith build text-exhaustive` parses all 2^32 float patterns and a sample of 2^24 double patterns, minutes on all cores, and is not part of `test`) the json tests in `tests/json.sh` (`<smith/json.h>`: `tests/json_test.smith` in three builds, fuzzing under ASan and UBSan, and JSONTestSuite fetched by hash into `~/.cache/smith-tests`, skipped offline), the tree-sitter tests in `tests/tree_sitter.sh` (the grammar for `.smith` in `tree-sitter/`: its corpus, samples, the #11 corpus once it exists, and every `.c` and `.h` file of smith, through `tests/tree_sitter.c` linked with the tree-sitter runtime pinned by hash; regenerate `tree-sitter/src/parser.c` with `scripts/tree-sitter.sh` after a change to `grammar.js`) the language server tests in `tests/lsp.sh` (a real `smith lsp` session driven by `tests/lsp_client.c` on a scratch project of `.smith` modules and a C file: diagnostics at the lines and columns of the text, hover, definition across modules, symbols, completion) and the Neovim tests in `tests/neovim.sh` (the plugin, `plugin/smith.lua` and `editors/neovim`, in headless Neovim; skipped without `nvim`; `SMITH_NVIM_ONLY="parser highlights"` runs some; knowledge/neovim.md), the cache tests in `tests/cache.sh` (the shared module cache, package pruning with a faked clock, `smith cache`, all in a temporary `XDG_CACHE_HOME`; never touch the real `~/.cache/smith`), the resource tests in `tests/resource.sh` (the folder of clang's embedded files written on first use, in a temporary `XDG_DATA_HOME`: its contents, `bin/clang`, `-flto`, a sanitized program run after `smith cache clean`, eight first compiles at once; skipped for the stage0) and the tests of `<smith/test.h>` and `smith_tests` in `tests/test.sh` (a scratch project whose test files fail on purpose: the failure blocks, aborts, isolation, the finding of tests, shrinking, `-Wconversion`, clangd), which need a real clang, clangd and git (and ninja only for the tests of the `SMITH_NINJA` fallback, which skip themselves without it). `smith build compare` runs 33 invocations (compiles, links with and without debug info and sanitizers, assembly, `-###`, `-v`, diagnostics with colours, response files, standard input) through clang and through smith and compares what each prints, how each exits and the bytes of the files; `REAL` defaults to the clang of the LLVM smith links, which every case must match. Homebrew's (`-DREAL=/opt/homebrew/opt/llvm/bin/clang`) says "Homebrew clang" in its version, in debug info and in bitcode, so those cases differ against it.
- **`smith prove`'s soundness tests** are `tests/prove_sound.sh` (`smith build test-prove-sound`, part of `smith test`; `smith build prove-sound-full` for 8 seeds of 50000 inputs): harnesses in `tests/prove/sound/` (one per case, with `sound.h`: random inputs filtered by the function's `requires`, `// proves:` names checked as `ok` first) and false claims in `tests/prove/unsound/`. Add a harness for every function a change makes proved, and a corpus case for every soundness bug.
- **No new test scripts.** A new test is a `.smith` test, also when it needs a process, a build of its own, a crash or a sanitizer's report: `scratch::project`, `scratch::build` and `scratch::sh` start them from the test. The scripts below are being ported; don't add a row.
- **The test scripts run side by side.** `build.c` has a table, `build_test_scripts`, one row per task `test-<task>` (the script `tests/<script>.sh`, with an optional mode and parts), and each is a test (`.test = true`, which `smith test` runs; `test-compare` is one too), so `smith test` and `smith check` run them in parallel and take about as long as the slowest. Run one alone with `smith build test-<task>` (for example `smith build test-build-0`). A new script is a new row (keep the rows in order). A script must be safe to run beside the others: its work is in `mktemp -d`, its caches in `XDG_CACHE_HOME` (and `XDG_DATA_HOME` where it starts compilers) under that folder, no fixed port (loopback tests bind port 0), no fixed temporary name, and nothing written in the repository. `tests/test.sh` takes a list of parts as its last argument (`sh tests/test.sh smith isolate shrink_list,budget`; default all), each part in a project of its own, and `build.c` runs the `--isolate` pass as several tasks (`test-isolate-main`, `-rest`, `-shrink-int`, `-shrink-list`, `-shrink-normal`) because shrinking a test in processes of their own is long. A script over about 20 s is split the same way: `tests/lsp.sh smith project|folders` (`test-lsp-project`, `test-lsp-folders`) `tests/mcp.sh smith fake-asan|fake-fast|fake-ndebug|real`, `tests/smith-lang.sh smith K/N` (`test-smith-lang-0` to `-2`: every 3rd case), `tests/test.sh smith <parts>` (`test-main`, `-reports`, `-rest`; the isolate rows likewise, and `build.c` refuses a part that is in no plain or no isolate row) and `tests/build.sh smith K/N` (`test-build-0` to `-3`: its `# 9k.` blocks dealt out by size; block 1 runs in every shard). Table first (`smith test`'s log, `.smith/log/test.log`), then split what the CPU time says is long. A row has a phase, 0 for a short task and 1 for a long one; all start at once (`prove` too: its budget is CPU time, so a busy machine slows it and never fails it). `smith build test-<task>` runs one alone. A test's time budget (about 10 s, `budget` 14 s) must hold under the load of the whole suite; a failure that appears only in `smith test` and not alone is a budget under load, so report it with numbers rather than raising it.
- **Tests of behavior are `.smith` tests on smith's own runner** (issue #31; `build_units` in build.c, the tasks `units-build` and `test-units`, part of `smith test` and `smith check`): every `*_test.smith` (a library's tests sit beside it: `lib/smith/arena_test.smith` is `module smith::arena_test;`, `lib/json_test.smith`; `tests/` holds the integration tests that start smith, `tests/build_*_test.smith` and `new_test.smith`, with `scratch.smith` and the fixtures; exported `test_*` functions, `import smith::test;`) is linked with the libraries it tests (`smith_tests` links every smith library the test files import or include, with what those need, so a new module's test needs nothing declared) into one runner built once under AddressSanitizer and UBSan, and its workers run the tests in process, one per core. Add a test file there, not a shell script, whenever the code can be called in process; run one with `build/<OS>-<arch>/units/tests --test <name>`; the heavy sizes are `--full`, and the long property runs are by hand (`--full --seeds 1000 --test test_prop_inflate_round_trips_stored_blocks`). **Tests that start smith** (`tests/build_*_test.smith`, the ported parts of tests/build.sh) use `tests/scratch.smith` (`import scratch;`): `scratch::project(io, "p", "<fixture>")` makes a folder in the test's scratch folder with `tests/build_fixtures/<fixture>/` copied in and the smith under test (`$SMITH_SELF`, set by `smith test`; set it to run the runner by hand; `smith test` also sets SMITH_OUTPUT=full, which the nested smith's verbs need to print their full output, so `tests/new_test.smith` sets it itself and a test of the quiet form unsets it) first on PATH; `scratch::build(&p, "-v")` and `scratch::sh(&p, "...")` run commands there through io's processes and return `.status`, `.out`, `.err`; `expect_contains`, `expect_text`, `expect_count` and the rest check them. Each test is its own project, so they run side by side; a long sequence is split into tests that each build what they need. `smith test` and `smith check` end with a table of each task's wall and CPU time and smith processes (`SMITH_ACCOUNT=all` or `smith check -v` lists every task): read it before choosing what to port, and when a script's number moves. The stage0 has no `.smith` compiler, so it builds no runner. The runner is a project of its own (`tests/units/build.c`, built in `build/<OS>-<arch>/units-project` with `tests` linked to ours) built and run by the smith under test, so its libraries and headers are that smith's even when an older installed smith runs the repository's build.c (a new library needs no two-step install); scripts that need the runner wait for `units-build`.
- **Writing a `.smith` test (what trips a first one).**
  - *A C file that is not a registered library* (`lib/http.c`): `tests/units/build.c` compiles it as a `SmithObject` and passes it in `.objects` of the `SmithTests`; its path comes from `$SMITH_REPO`, which `build.c` sets (the project there is `units-project`, `tests` linked to ours). The test file then has `import <smith/http.h>;` and calls `c::smith_http_get`. Without the entry the runner fails to link with an undefined symbol. Do not register a library for this: a library joins when two projects need it.
  - *`c::` errno names* (`c::ENOENT`, `c::EIO`) are macros, which `smith-preprocessor` rejects. Read each once into a constant inside `// NOLINTBEGIN(smith-preprocessor)` ... `// NOLINTEND(smith-preprocessor)`, as `lib/smith/io.smith` and `tests/io_test.smith` do (`constexpr i32 enoent = c::ENOENT;`). `snprintf` is a macro on macOS too: use `format::to`.
  - *`countof` fails on a local `T x[] = {...}`*: write the count (`const char *names[3] = {...}`, a `constexpr usize`), as `xs[:]` needs a run-time array.
  - *The lint limit of 69 lines per function applies to test files*: split a long test into `static` `check_*` helpers that exported `test_*` functions call (the same helper can run on a fake io and on the real one).
- **The protocol code is generated.** `runtime/protocol/dap.[ch]` and `mcp.[ch]` and `tests/protocol/test_protocol_dap.c` and `_mcp.c` are written by `scripts/protocol.c` (knowledge/protocol-generation.md) from DAP's and MCP's schemas, pinned by hash in build.c (`build_protocols`); never edit them. After changing the generator, `runtime/protocol/protocol.[ch]` (hand-written, what they stand on) or a pin, run `smith build protocol` and commit what it writes: `check-protocol` (a test, so `smith test` and `smith check` run it) fails on a stale file, and `tests/protocol.sh` (`smith build test-protocol`, about 14 s: three builds, the first under the sanitizers) runs the generated tests and `tests/protocol/test_protocol_samples.c`. The generated files are not formatted or linted (they are in `.clang-format-ignore`, and lint reads only what the build compiles); the hand-written ones and the generator are.
- **`smith mcp`** (`runtime/mcp*.c`, knowledge/mcp-server.md) is in the full smith only (`-DSMITH_MCP`, passed whenever clang is inside). `tests/mcp.sh` (`smith build test-mcp-real` and `test-mcp-fake-asan`, `-fast`, `-ndebug`, 10 s each) builds `tests/mcp_fake.c` three ways (the server on the fake io, a scripted client and a scripted `smith dap` child, whose frames answer the requests numbered from 1; a wrong script makes the server wait for a reply, which its alarm ends) and drives the real `smith mcp` on a C program, a `.smith` module and a project test. Build smith with the smith you just built when the installed one is older than build.c (`build/<OS>-<arch>/smith build`).
- The build executor (`runtime/executor*.c`) runs `smith build`'s manifest in place of ninja. After changing it, also run `python3 tests/ninja_compare.py build/<OS>-<arch>/smith 1 100` by hand: it builds random graphs with ninja and with the executor (`smith --smith-exec <manifest>`), edits them at random, and fails when the commands run or the files made differ. It needs ninja, so `smith test` does not run it. Comparing one project's tree from two builds: linked binaries differ in the linker's UUID and the object files' times, and a metallib is not reproducible; objects must match.
- **A new check or a new diagnostic runs the editor tests too:** `test-lsp-project`, `test-lsp-folders` and `test-neovim` pin the exact diagnostics of their sample files, so a check that fires on them fails there first. Fix the sample, not the check.
- **One full `smith check` at a time** on a machine, and say plainly what you did not run.
- **Where the per-task table is.** `smith test` and `smith check` print one line each; the table of each task (wall, CPU, processes) and every test's line are in `.smith/log/test.log`, which each run rewrites, and in CI's `check-log` artifact. To see it as it happens run with `-v` or `SMITH_OUTPUT=full` (a nested smith needs the same, so tests of smith set it).
- **The test beds in a scratch copy** ([test-beds](../../../knowledge/test-beds.md)). learner reads `../data/` (the Spleen font `data/raw/fonts/spleen-8x16.bdf`, the tokenizer `data/raw/pretrain/tokenizer/tokenizer.json`, the token shards), which git ignores, so a copy must sit beside a `data` that points at `~/Documents/virtual-cell/data`: `mkdir $S; cp -R learner $S/learner; ln -s ~/Documents/virtual-cell/data $S/data`. game writes its sessions to `$HOME/Library/Application Support/Game/sessions` (a windowed run once deleted the owner's): run it with `HOME=$(mktemp -d)`.
- **A limit that decides pass or fail is CPU time (#113).** A C client that waits for a server uses `tests/cpu_wait.h` (`cpu_wait_for(fd, pid, cpu_ms)`, a 10 minute wall backstop that fails as a hang); a program's `alarm` is a 600 s hang backstop; a runner test that wants only the CPU limit needs no `--wall-timeout` (600 by default). Wall time stays only where it is what the test is about (`--wall-timeout 1` on `sleeps`), with a comment saying so. See knowledge/machine-load.md.
- **No test asserts on wall time (#144).** Two jobs that overlap or serialise are checked by the order of marks they write (a job that must overlap waits for the other's mark), a process that must outlive an event runs until the test ends it, and a wait for something to happen polls for it up to a 600 s hang backstop; only a test of a timer or backstop uses wall time, with a comment saying so.
