# smith-dev-tests

What the test library and runner are is in [build-tests](../../../knowledge/build-tests.md). Run a test with the smith under test, never the installed one.

- **`smith prove`'s tests** are `tests/prove_test.smith`, `prove_memory_test.smith`, `prove_smith_test.smith` and `prove_misc_test.smith` (a test per case of the programs in `tests/prove/`; the shared helpers are `tests/prove_cases.smith` and the sub-projects `tests/build_fixtures/prove_cases`; the proofs are cached by content in the tests' own cache, and a budget is CPU time).
- **`smith prove`'s soundness tests** are `tests/prove_sound_test.smith` (part of `smith test`; `smith build prove-sound-full` for 8 seeds of 50000 inputs): harnesses in `tests/prove/sound/` (one per case, with `sound.h`: random inputs filtered by the function's `requires`, `// proves:` names checked as `ok` first) and false claims in `tests/prove/unsound/`. Add a harness for every function a change makes proved, and a corpus case for every soundness bug.
- **`smith test --changed`** (#441, `runtime/changed.c`, `tests/changed_test.smith`, knowledge/changed-tests.md) selects the tests a diff reaches through the imports and includes of the sources; a test that runs smith (`scratch::`) is reached by any source of smith. Run `smith test --changed --dry-run` before pushing to see what a PR needs; the tests of the feature are on scratch git repositories. **Coverage selection (#456)**: `COVERAGE=1 smith build` instruments smith, `test-units` then merges a record for each test and `smith test --coverage join` writes `.smith/coverage/coverage.tsv` (a run with `COVERAGE=1` only; CI's `ci.yml` makes none); each test also leaves `.smith/records/<test>.rec`; `tests/coverage_test.smith` tests the records, the table, the report and the selection on records it makes under coverage; `tests/record_test.smith` runs `smith test --changed` in a project of its own (`tests/build_fixtures/record_project`: a program and two tests that run it), which builds with the counters, leaves `.smith/records` and selects by them (`-DSMITH_RECORD`, the instrumented flags never reach `smith prove`, the sanitizer tests or a plain `smith test`); knowledge/coverage-selection.md.
- **Build once, copy in each test (#639).** A fixture folder every test of a file would build is built once for each smith under test in `$SMITH_TEST_CACHE` and copied, then `smith build` there is a no-op that writes the copy's paths (`generate` in `tests/new_test.smith`, `built_script` in `tests/lsp_test.smith`); several runs of one build (`tests/library_modes_test.smith`) are one test.
- **The pyramid (#646): test the smallest unit that shows the behavior.** A function with its inputs and outputs is a unit test in the runner's process; several parts together are an integration test; only a verb's wiring, the real compiler and linker, the debugger, crash reports and the sanitizers need `scratch::` (a process for each command). A new `scratch::` test says in a comment why a unit test cannot show its behavior. The runtime is reachable in process through `include/smith_core.h` (not shipped): `tests/units/build.c` compiles `smith.c` with `-DSMITH_CORE` (no `main`, the libraries and `lib/http.c` and `lib/trace.c` stay the runner's own objects) and links it; an entry point is a non-static function under `#ifdef SMITH_CORE` at the end of the runtime file it serves (`smith_core_make_translate` in `runtime/make_translate.c`) and is declared in that header, and a test imports `<smith_core.h>`. An entry point must be safe to call twice in one process: the runtime keeps its state in file-scope statics, so it resets them (`smith_make_reset`), and a test of calling twice sits beside it (`test_a_translation_does_not_remember_the_last`). The examples are `tests/make_translate_test.smith` (the Makefile reader: text in, build.c and report out, 19 tests in 1 s of CPU) and `tests/untar_readers_test.smith` (the archive readers: bytes in, the files and the refusal out through `smith_core_extract` and `smith_core_tree`, 77 tests in 0.4 s of CPU; a reader returns its error, `smith_die` is for the verb), `tests/smith_lang_lowering_test.smith` (the raw lowering: a `.smith` text in, the C, the header and the errors out through `smith_core_lower` and `smith_core_header`; it checks the corpus's `expect/lowered`, `expect/header` and `expect/lower-error` of 364 cases in 3 s, where the corpus runner started a process for each file; `smith_lang_reset` in `runtime/lang_lex.c` is what makes it safe to call twice), and a test that needs only the text of a lowering or a header takes it in process with `scratch::write_lowered` and `scratch::write_header` (`tests/random_c_test.smith`, `tests/prove_sound_test.smith`, the header rules of `tests/headers_test.smith`; twenty headers in the sanitized runner cost more than the command's processes, and a module with two C imports takes the command), beside the end-to-end `tests/make_test.smith`, which keeps what needs a real make, a compiler, lint or the verb. A test that links the core is selected by any source of smith (`runtime/changed.c`).
- **A repository file a process reads is copied first (#739).** `scratch::copy_tree(&p, "lib", "lib")` copies a file or folder of the repository into the project through `io` (the mode and links kept), and the command runs on the copy, never on `$SMITH_REPO/...`: the opens are what `smith test --changed` records, so a changed file selects the tests that copied it. `scratch::repo_text`, `repo_names`, `repo_has` and `untested_names` read the repository in the test itself. `-I "$SMITH_REPO/.smith/include"` (a build output) is the one repository path a command may name.
- **A scratch project needs no `io` (#815).** `scratch::make(name, fixture)` and `scratch::clean(&p)` work in a plain `test_x()`; what a call returns to the test (a `Run`'s text, what `read` returns) is the test's to free, and the leak check fails a test that keeps it: `defer scratch::clean(&p);`, `defer scratch::release(run.out);`. `tests/scratch_free_test.smith` is the example.
- **The pattern of a test file with no `io` (#843).** `scratch::Project p = scratch::make("name", fixture); defer scratch::clean(&p);`, then a `test::memory` arena as the current allocator around the body (`arena::Arena a = test::memory(1U << 22); arena::ArenaAllocator al = arena::allocator(&a); mem::Allocator *outside = mem::set_allocator(&al.base); defer mem::set_allocator(outside);`), so every `Run`, `read` and `capture` result goes back with the arena and no call needs `defer scratch::release`. The io-free forms: `scratch::sh`, `build`, `write`, `read`, `exists`, `lines`, `capture` (trailing newlines dropped), `sleep` (through `clock::sleep`), `copy_tree(&p, "repo/path", "name")` (cp -PR from `$SMITH_REPO`), `untested_names_free(folder, test_source, call, suffix_a, suffix_b)`, and `test::golden_free(path, actual)` (the diff and `--update` of `test::golden`, through `smith::files`). `tests/scratch_free_test.smith` is the example.
- **No new shell files is a test (#906).** `tests/no_shell_files_test.smith` fails a tracked file that ends in `.sh` or starts with a shell `#!` line, except `scripts/llvm.sh` and `scripts/release.sh` (ported by #291) and the fake programs of `tests/build_fixtures/`; the way out is a `.smith` test through `scratch::` or a task in the build file.
- **No new test scripts.** A new test is a `.smith` test, also when it needs a process, a build of its own, a crash or a sanitizer's report: `scratch::project`, `scratch::build` and `scratch::sh` start them from the test. The scripts below are being ported; don't add a row.
- **Corpus and golden tests (#292).** A table of cases whose expected output is a file is a `.smith` test per case that calls `test::golden(io, path, actual)` (`smith-test-checks`; the path is relative to the project root, `smith test --update` writes the files a run changed, read the diff). Ported so far: `tests/defaults_test.smith` (smith's default `.clang-format` and `.clang-tidy`), `tests/conventions_test.smith` (builds by convention, from the folders `tests/build_fixtures/conv_*`), `tests/lint_smith_test.smith` (`smith lint` on `.smith`, from `tests/build_fixtures/lint_smith`; the long lists of findings are goldens in `tests/lint-smith`), `tests/docs_test.smith` (a test for each folder of `tests/docs/fixtures`, golden `expect.txt`), `tests/skills_test.smith` and `tests/readme_test.smith` (the examples of the skills and of the README, which parse the fenced blocks in the test); the language corpus (`tests/smith_lang_test.smith`, a `corpus_case(io, "name")` test for each folder of `tests/smith-lang/cases`; the C rule, `tests/smith_lang_c_test.smith`; `tests/smith_fmt_test.smith`; `tests/affine_test.smith` and `tests/effects_infer_test.smith`, a test for each `tests/affine/*` and `tests/effects/*` source with its `<file>.expected`; `tests/headers_test.smith` on the fixture `tests/build_fixtures/headers`). A test that loops over many cases (the lowering shards, the fmt corpus) checks every case and fails once, listing each case that differed with its first differing line: `corpus::golden` or `corpus::golden_sections` collect, `corpus::finish` fails (`tests/corpus.smith`, #749). A folder-driven test names its cases in its source, and one test (`test_every_case_has_a_test`, `..._file_...`) lists the folder and fails for a case or file with no test, so adding one without a test is caught. Run one with `--test <name>` (the case's folder name with `_` for `-`). A test that needs the repository's files reads them from `$SMITH_REPO` through `scratch::sh`; its expectations go through `test::golden`.
- **The test scripts run side by side.** `build.c` has a table, `build_test_scripts`, one row per task `test-<task>` (the script `tests/<script>.sh`, with an optional mode), and each is a test (`.test = true`, which `smith test` runs), so `smith test` and `smith check` run them in parallel and take about as long as the slowest. Run one alone with `smith build test-<task>` (for example `smith build test-docs`). A new script is a new row (keep the rows in order). A script must be safe to run beside the others: its work is in `mktemp -d`, its caches in `XDG_CACHE_HOME` (and `XDG_DATA_HOME` where it starts compilers) under that folder, no fixed port (loopback tests bind port 0), no fixed temporary name, and nothing written in the repository. A script over about 20 s is split: and `tests/mcp.sh smith fake-asan|fake-fast|fake-ndebug|real`. Table first (`smith test`'s log, `.smith/log/test.log`), then split what the CPU time says is long. A row has a phase, 0 for a short task and 1 for a long one; all start at once (`prove` too: its budget is CPU time, so a busy machine slows it and never fails it). `smith build test-<task>` runs one alone. A test's time budget (about 10 s, `budget` 14 s) must hold under the load of the whole suite; a failure that appears only in `smith test` and not alone is a budget under load, so report it with numbers rather than raising it.
- **`SMITH_HEADERS_FROM`** names a folder of library headers (a project's `.smith/include/smith`) that a project copies instead of generating its own (about 20 `--smith-header` processes, 2 s of CPU), when the folder's `.written-by` stamp names the running smith; unset or stamped by another smith, smith generates them as usual. `tests/scratch.smith` sets it to the runner's own project's (`units-project`, prepared by the smith under test, whose stamp matches), so scratch projects start none (`tests/build_lang_test.smith` checks both ways).
- **Tests of behavior are `.smith` tests on smith's own runner** (issue #31; `build_units` in build.c, the tasks `units-build` and `test-units`, part of `smith test` and `smith check`): every `*_test.smith` (a library's tests sit beside it: `lib/smith/arena_test.smith` is `module smith::arena_test;`, `lib/json_test.smith`; `tests/` holds the integration tests that start smith, `tests/build_*_test.smith` and `new_test.smith`, with `scratch.smith` and the fixtures; exported `test_*` functions, `import smith::test;`) is linked with the libraries it tests (`smith_tests` links every smith library the test files import or include, with what those need, so a new module's test needs nothing declared) into one runner built once under AddressSanitizer and UBSan, and its workers run the tests in process, one per core. Add a test file there, not a shell script, whenever the code can be called in process; run one with `build/<OS>-<arch>/units/tests --test <name>`; the heavy sizes are `--full`, and the long property runs are by hand (`--full --seeds 1000 --test test_prop_inflate_round_trips_stored_blocks`). **Tests that start smith** (`tests/build_*_test.smith`, ported from the old shell script) use `tests/scratch.smith` (`import scratch;`): `scratch::project(io, "p", "<fixture>")` makes a folder in the test's scratch folder with `tests/build_fixtures/<fixture>/` copied in and the smith under test (`$SMITH_SELF`, set by `smith test`; set it to run the runner by hand; `smith test` also sets SMITH_OUTPUT=full, which the nested smith's verbs need to print their full output, so `tests/new_test.smith` sets it itself and a test of the quiet form unsets it) first on PATH; the commands share one data folder and one cache for the whole run and the runs before it (`$SMITH_TEST_CACHE`, else `~/.cache/smith-tests`: `data/` holds the embedded files and the programs, which macOS scans when they are new, so a test never makes its own unless it is about them: `tests/resource_test.smith` sets its own `XDG_DATA_HOME`); `scratch::build(&p, "-v")` and `scratch::sh(&p, "...")` run commands there through io's processes and return `.status`, `.out`, `.err`; `expect_contains`, `expect_text`, `expect_count` and the rest check them. Each test is its own project, so they run side by side; a long sequence is split into tests that each build what they need. `smith test` and `smith check` end with a table of each task's wall and CPU time and smith processes (`SMITH_ACCOUNT=all` or `smith check -v` lists every task): read it before choosing what to port, and when a script's number moves. The stage0 has no `.smith` compiler, so it builds no runner. The runner is a project of its own (`tests/units/build.c`, built in `build/<OS>-<arch>/units-project` with `tests` linked to ours) built and run by the smith under test, so its libraries and headers are that smith's even when an older installed smith runs the repository's build.c (a new library needs no two-step install); scripts that need the runner wait for `units-build`.
- **Writing a `.smith` test (what trips a first one).**
  - *A C file that is not a registered library* (`lib/http.c`): `tests/units/build.c` compiles it as a `SmithObject` and passes it in `.objects` of the `SmithTests`; its path comes from `$SMITH_REPO`, which `build.c` sets (the project there is `units-project`, `tests` linked to ours). The test file then has `import <smith/http.h>;` and calls `c::smith_http_get`. Without the entry the runner fails to link with an undefined symbol. Do not register a library just for a test: register it when smith ships it to other projects.
  - *`c::` errno names* (`c::ENOENT`, `c::EIO`) are macros, which `smith-preprocessor` rejects. Read each once into a constant inside `// NOLINTBEGIN(smith-preprocessor)` ... `// NOLINTEND(smith-preprocessor)`, as `lib/smith/io.smith` and `tests/io_test.smith` do (`constexpr i32 enoent = c::ENOENT;`). `snprintf` is a macro on macOS too: use `format::to`.
  - *`countof` fails on a local `T x[_] = {...}`*: write the count (`const char *names[3] = {...}`, a `constexpr usize`), as `xs[:]` needs a run-time array.
  - *The lint limit of 69 lines per function applies to test files*: split a long test into `static` `check_*` helpers that exported `test_*` functions call (the same helper can run on a fake io and on the real one).
- **The protocol code is generated, and a build output.** `.smith/protocol/dap.[ch]` and `mcp.[ch]` and `test_protocol_dap.c` and `_mcp.c` are written by `scripts/protocol.c` (knowledge/protocol-generation.md) from the schemas vendored in `schemas/`, as a step of `smith build`; never edit or commit them (a committed one fails `generated_files_test`). A change to the generator, to `runtime/protocol/protocol.[ch]` (hand-written, what they stand on) or to a schema is picked up by the next `smith build`; `tests/protocol_test.smith` (`smith test --test protocol`, needs a built tree, about 14 s: the builds, the first under the sanitizers) runs the generated tests and `tests/protocol/test_protocol_samples.c`. The generated files are not in git, so they are not formatted or linted; the hand-written ones and the generator are.
- **`smith mcp`** (`runtime/mcp*.c`, knowledge/mcp-server.md) is in the full smith only (`-DSMITH_MCP`, passed whenever clang is inside). `tests/mcp_test.smith` (`smith test --test test_mcp`, the real server and the fake io three ways, 10 s each) builds `tests/mcp_fake.c` three ways (the server on the fake io, a scripted client and a scripted `smith dap` child, whose frames answer the requests numbered from 1; a wrong script makes the server wait for a reply, which its alarm ends) and drives the real `smith mcp` on a C program, a `.smith` module and a project test. Build smith with the smith you just built when the installed one is older than build.c (`build/<OS>-<arch>/smith build`).
- The build executor (`runtime/executor*.c`) runs `smith build`'s manifest in place of ninja. After changing it, also run `python3 tests/ninja_compare.py build/<OS>-<arch>/smith 1 100` by hand: it builds random graphs with ninja and with the executor (`smith --smith-exec <manifest>`), edits them at random, and fails when the commands run or the files made differ. It needs ninja, so `smith test` does not run it. Comparing one project's tree from two builds: linked binaries differ in the linker's UUID and the object files' times, and a metallib is not reproducible; objects must match.
- **A new check or a new diagnostic runs the editor tests too:** `tests/lsp_test.smith` and `tests/neovim_test.smith` pin the exact diagnostics of their sample files, so a check that fires on them fails there first. Fix the sample, not the check.
- **Cores (#360, #567).** `smith build`, `check` and `test` draw core tokens from the host's pool (`SMITH_CORES`): one at the first heavy step, one more per further worker of the executor (`runtime/slots.c`) and of the test runner (`lib/smith/test.smith`), given back as each ends. A run that prints `waiting for a core (n of m held: ...)` is queued behind the others; a smith that a smith runs rides on its parent's token through `SMITH_SLOT_HELD`, and the runner gives every test its own `SMITH_SLOTS_DIR` (and `SMITH_CORES=4`), so the smith a test starts never waits for the host (#627). `tests/slots_test.smith` tests the pool through `smith --smith-slots PROGRAM` and `smith --smith-exec` on a manifest, with a `SMITH_SLOTS_DIR` and a `SMITH_CORES` of its own (a fake host); the test runner started by hand has no pool. See [slots](../../../knowledge/slots.md).
- **One full `smith check` at a time** on a machine, and say plainly what you did not run.
- **Where the per-task table is.** `smith test` and `smith check` print one line each; the table of each task (wall, CPU, processes) and every test's line are in `.smith/log/test.log`, which each run rewrites, and in CI's `test-log-*` artifacts. To see it as it happens run with `-v` or `SMITH_OUTPUT=full` (a nested smith needs the same, so tests of smith set it).
- **The test beds in a scratch copy** ([test-beds](../../../knowledge/test-beds.md)). learner reads `../data/` (the Spleen font `data/raw/fonts/spleen-8x16.bdf`, the tokenizer `data/raw/pretrain/tokenizer/tokenizer.json`, the token shards), which git ignores, so a copy must sit beside a `data` that points at `~/Documents/virtual-cell/data`: `mkdir $S; cp -R learner $S/learner; ln -s ~/Documents/virtual-cell/data $S/data`. game writes its sessions to `$HOME/Library/Application Support/Game/sessions` (a windowed run once deleted the owner's): run it with `HOME=$(mktemp -d)`.
- **A limit that decides pass or fail is CPU time (#113).** A C client that waits for a server uses `tests/cpu_wait.h` (`cpu_wait_for(fd, pid, cpu_ms)`, a 10 minute wall backstop that fails as a hang); a program's `alarm` is a 600 s hang backstop; a runner test that wants only the CPU limit needs no `--wall-timeout` (600 by default). Wall time stays only where it is what the test is about (`--wall-timeout 1` on `sleeps`), with a comment saying so. See knowledge/machine-load.md.
- **No test asserts on wall time (#144).** Two jobs that overlap or serialise are checked by the order of marks they write (a job that must overlap waits for the other's mark), a process that must outlive an event runs until the test ends it, and a wait for something to happen polls for it up to a 600 s hang backstop; only a test of a timer or backstop uses wall time, with a comment saying so.
