# Develop smith

[AGENTS.md](../../../AGENTS.md) holds the rules and decisions, and GitHub issues hold the planned work. This skill holds the procedures every change shares. To use smith as a compiler, load [smith](../smith/SKILL.md) instead. To edit smith's own `build.c`, load [smith-build](../smith-build/SKILL.md) as well.

## Build, test, install

smith builds itself with its own `build.c`, so the installed smith must have `smith build`. Pass `-DCC=/opt/homebrew/opt/llvm/bin/clang` to any of these to build smith with Homebrew's clang instead of the installed smith.

## The two smiths, and how to get the full one

smith has clang inside (issue #1): it compiles in its own process, by running clang's own `clang_main` (`shim/clang.cpp`, the only C++ in smith) on the arguments. Two smiths come out of one `smith.c`:
- **The stage0** is `cc -std=gnu23 smith.c -o build/stage0`: no C++, no LLVM, and it runs an external clang (`$SMITH_CLANG`, else Homebrew's). It is all a fresh clone has.
- **The full smith** has `-DSMITH_IN_PROCESS`, the shim, and the archives of our LLVM install linked in with `-Wl,-dead_strip`. `smith build` makes it when the install has `lib/libclangmain.a` (else it makes the stage0); `-DLLVM=` names another install, empty forces the stage0.

From a fresh clone: `mkdir -p build && cc -std=gnu23 smith.c -o build/stage0`, then `build/stage0 build llvm` (builds LLVM 23.1.3 into `~/.cache/smith/llvm/23.1.3/install`, about 9 minutes cold, a few seconds when it is built), then `build/stage0 build -DCC=cc` (or `... install -DCC=cc`) links the full smith; set `SMITH_CLANG=/usr/bin/clang` if Homebrew's llvm is not installed, since the stage0 compiles build.c with an external clang. Keep a copy of the stage0 outside `build/` (it survives `smith build clean`) when you work on the full one, and rebuild with the full smith: `cp build/<OS>-<arch>/smith $S/stage1 && $S/stage1 build -DCC=$S/stage1` (a smith compiles smith in its own process).
- `scripts/llvm.sh` adds `lib/smith-clang.id` (the LLVM version and a hash of the archives linked; `smith build` compiles it into smith as the identity of its clang, which `--smith-which` prints and projects' objects depend on) and `lib/libclangmain.a` to the install: the four objects of clang's driver (`driver.cpp`, `cc1`, `cc1as`, `cc1gen-reproducer`), which hold `clang_main`. Running it again is cheap. Changing it needs `smith build llvm` again.
- The driver is run as `<folder>/bin/clang` (`-no-canonical-prefixes`, in `shim/clang.cpp`), where `<folder>` is `$XDG_DATA_HOME/smith/clang/llvm-<version>-<key>` (else `~/.local/share/...`), so it finds its builtin headers, compiler-rt and `libLTO.dylib` there, with no flag in the user's command. `scripts/pack.c` packs those files from the install at build time into `build/<OS>-<arch>/clang-resource.pack` (LZFSE, per 4 MB chunk; the format is `scripts/pack.h`), smith.c `#embed`s it (`-DSMITH_CLANG_RESOURCE=`), and the first compile writes the folder (beside it, then one `rename`, so parallel first compiles are safe). The programs are not in that folder: `bin/clang`, `bin/clang++` and `bin/ld` are hard links to the running smith, in `<data>/smith/programs/<LC_UUID>/bin` (with `lib` a symlink to the runtime folder's, and `-resource-dir` passed by `shim/clang.cpp` so that rpaths name the runtime folder, never the programs folder). Smiths of one runtime key but another binary never share links; a folder idle 31 days, and a half-built one older than an hour, are removed when a new one is made. The driver runs its program again with `-cc1` for a compile with more than one step. The folder is outside the caches `smith cache clean` and pruning touch, because sanitized binaries record an rpath into it; smith never removes it. `bin/ld` is the third link: the driver looks for its linker beside its program before `PATH`, so a link it starts is smith run as `ld`, which calls lld's `lld::macho::link` in that process (`shim/lld.cpp`; `liblldMachO.a` and `liblldCommon.a` of the install). The user's command gets no flag. `SMITH_LINKER=/usr/bin/ld` runs that linker instead, and then the driver is left as Apple's `ld` wants it; with lld, `shim/clang.cpp` adds `-mlinker-version=1115.7.3`, which tells the driver there are no `objc_msgSendClass$` stubs (only Apple's current `ld` writes them), and the user's own flag wins. Never overwrite a smith that is hard-linked in place (`cp` over it kills its next run with signal 9: the kernel keeps the old signature); remove it first, as an install's rename does. `scripts/llvm.sh` hashes lld into the identity. `dsymutil` and the other tools are the system's. `SMITH_CLANG` runs an external clang as before; `compare` checks the full smith against the install's clang binary (its prefix is rewritten to the folder in the text).
- The full smith needs the install only to build: its archives to link, and the resource files to pack. To check it needs nothing at run time, build it against a copy of the install in a scratch folder (`-DLLVM=`), remove the copy, and run the tests under `sandbox-exec` with a profile that denies `~/.cache/smith/llvm` and Homebrew's llvm. `tests/resource.sh` tests the folder, the links, the lld link (frameworks, a dylib, ARC, `-dead_strip`, the signature, `SMITH_LINKER`), `-flto`, the sanitizer rpath after `smith cache clean`, and parallel first compiles.
- `smith fmt`, `smith lint` and `smith lsp` (issue #3) run clang-format, clang-tidy and clangd in process, from `shim/format.cpp`, `shim/tidy.cpp` and `shim/clangd.cpp`, one C function each (`shim/tool.h` is what they share). The tools declare their flags in global `llvm::cl::opt` objects, and LLVM aborts at load when two define the same flag (clang-format and clang-tidy both have `-fallback-style`), so `scripts/llvm.sh` makes `libsmithtools.a` (linked whole, first) of patched copies of the tools' objects: their static initializers moved out of `__mod_init_func` (`scripts/defer_init.c`) for the tool that runs to run (`smith_tool_start`), clang-format's `main` renamed, clangd's code actions copied too, and the one call in clangd and in clang-tidy that finds the resource directory by the executable's path redirected to the resource directory of the install's clang (so, until #2, they read it from `SMITH_LLVM_BIN`, as the compiler does). A change to those needs `smith build llvm` again (a few seconds), and `shim/tool.h` is the place to change when #2 moves the resource directory. clangd's XPC transport (`CLANGD_AS_XPC_SERVICE`) is left out and `shim/clangd.cpp` stubs it, because it links Foundation, whose loading cost every smith process, compiles included, about 10 ms; a plain `smith version` is the quick check of startup time (about 8 ms for the smith before #3).
- The unstripped full smith is about 127 MB (`-g`), of which 20 MB is the pack; the first compile writes about 70 MB.

- `smith symbolize` and smith run as `llvm-symbolizer` (`runtime/symbolize.c`, included by smith.c; the lookups are `shim/symbolize.cpp`, which reads the binary's debug map and the object files it names, or a matching dSYM) turn the stack traces of `<smith/trace.h>` (`lib/trace.c`, a library `smith_tests` compiles) into reports. `smith build test` sets `SMITH_SELF` for the build program, pipes the test runner (with `--trace`) through `smith symbolize`, and makes `.smith/bin/llvm-symbolizer` for the sanitizers. The stage0 has no symbolizer (`smith symbolize --available` exits 3), and the tests of reports in `tests/test.sh` skip themselves. Debug a report with `build/tests --test <name> --trace | smith symbolize`.

## Build, test, install

- `smith build` builds `build/<OS>-<arch>/smith` and the `smith-cc` and `smith-c++` links. `CC` is the installed smith, as `smith-cc`, so smith builds smith; `-DCC=/opt/homebrew/opt/llvm/bin/clang` compiles it with Homebrew's clang instead. If the installed smith is broken, use the recovery line below.
- `smith test` runs the routing tests (each case through `smith cc` and through `smith-cc`; fewer for the stage0) against stub compilers, then the 484 `smith build` tests in `tests/build.sh`, the 201 `smith new` tests in `tests/new.sh` (the three builds, `assert(false)`, the tools on the generated project, `smith_library` under the template's flags, and the generated docs: a new project passes `smith docs` and `smith check`, and breaking each rule fails it), the 61 `smith docs` tests in `tests/docs.sh` (every rule on the small repositories of `tests/docs/fixtures/<case>`, each with the exact output in `expect.txt`, optional `args`, and `pass/expect.d`, the depfile; the options; how the verb picks between the check and the project's `docs` task) and the 27 arena tests in `tests/arena.sh` (`<smith/arena.h>` alone, its capacity stop, ASan, and a project using `smith_library`), and the io tests in `tests/io.sh` (`<smith/io.h>`: real files, console pipes, processes, timers, the seed, the lazily committed reservation, TLS connections against a server on the loopback, and the fake io with its scripted servers; sanitized and plain), the http tests in `tests/http.sh` (`<smith/http.h>` on a scripted network, no internet: redirects, chunked bodies, short bodies, a stalled server, every error), the package tests in `tests/package.sh` (downloads on a scripted network into a real cache), the random tests in `tests/random.sh` (`<smith/random.h>`: Philox known answers, the distributions, digests across build configurations, the refusals, and a project using both libraries), the text tests in `tests/text.sh` (`<smith/text.h>`: `tests/text.c` built with smith's own test library in three builds, with property tests on keys for the integers and a float parser that must equal `strtof`; `smith build text-exhaustive` parses all 2^32 float patterns and a sample of 2^24 double patterns, minutes on all cores, and is not part of `test`) the json tests in `tests/json.sh` (`<smith/json.h>`: `tests/json.c` in three builds, fuzzing under ASan and UBSan, and JSONTestSuite fetched by hash into `~/.cache/smith-tests`, skipped offline), the tree-sitter tests in `tests/tree_sitter.sh` (the grammar for `.smith` in `tree-sitter/`: its corpus, samples, the #11 corpus once it exists, and every `.c` and `.h` file of smith, through `tests/tree_sitter.c` linked with the tree-sitter runtime pinned by hash; regenerate `tree-sitter/src/parser.c` with `scripts/tree-sitter.sh` after a change to `grammar.js`) the language server tests in `tests/lsp.sh` (a real `smith lsp` session driven by `tests/lsp_client.c` on a scratch project of `.smith` modules and a C file: diagnostics at the lines and columns of the text, hover, definition across modules, symbols, completion) and the Neovim tests in `tests/neovim.sh` (the plugin, `plugin/smith.lua` and `editors/neovim`, in headless Neovim; skipped without `nvim`; `SMITH_NVIM_ONLY="parser highlights"` runs some; docs/neovim.md), the cache tests in `tests/cache.sh` (the shared module cache, package pruning with a faked clock, `smith cache`, all in a temporary `XDG_CACHE_HOME`; never touch the real `~/.cache/smith`), the resource tests in `tests/resource.sh` (the folder of clang's embedded files written on first use, in a temporary `XDG_DATA_HOME`: its contents, `bin/clang`, `-flto`, a sanitized program run after `smith cache clean`, eight first compiles at once; skipped for the stage0) and the tests of `<smith/test.h>` and `smith_tests` in `tests/test.sh` (a scratch project whose test files fail on purpose: the failure blocks, aborts, isolation, the finding of tests, shrinking, `-Wconversion`, clangd), which need a real clang, clangd and git (and ninja only for the tests of the `SMITH_NINJA` fallback, which skip themselves without it). `smith build compare` runs 33 invocations (compiles, links with and without debug info and sanitizers, assembly, `-###`, `-v`, diagnostics with colours, response files, standard input) through clang and through smith and compares what each prints, how each exits and the bytes of the files; `REAL` defaults to the clang of the LLVM smith links, which every case must match. Homebrew's (`-DREAL=/opt/homebrew/opt/llvm/bin/clang`) says "Homebrew clang" in its version, in debug info and in bitcode, so those cases differ against it.
- **The test scripts run side by side.** `build.c` has a table, `build_test_scripts`, one row per task `test-<task>` (the script `tests/<script>.sh`, with an optional mode and parts), and `test` is the alias of all of them, so `smith test` and `smith check` run them in parallel and take about as long as the slowest. Run one alone with `smith build test-<task>` (for example `smith build test-build`). A new script is a new row (keep the rows in order). A script must be safe to run beside the others: its work is in `mktemp -d`, its caches in `XDG_CACHE_HOME` (and `XDG_DATA_HOME` where it starts compilers) under that folder, no fixed port (loopback tests bind port 0), no fixed temporary name, and nothing written in the repository. `tests/test.sh` takes a list of parts as its last argument (`sh tests/test.sh smith isolate shrink_list,budget`; default all), each part in a project of its own, and `build.c` runs the `--isolate` pass as several tasks (`test-isolate-main`, `-rest`, `-shrink-int`, `-shrink-list`, `-shrink-normal`) because shrinking a test in processes of their own is long. A row has a phase: 0 starts at once, 1 is a long task, 2 (`prove`, which uses every core for its proofs) waits for the phase 0 tasks, so its 10 s budget holds while the long ones run on. `smith build test-<task>` runs one alone. A test's time budget (about 10 s, `budget` 14 s) must hold under the load of the whole suite; a failure that appears only in `smith test` and not alone is a budget under load, so report it with numbers rather than raising it.
- **The protocol code is generated.** `runtime/protocol/dap.[ch]` and `mcp.[ch]` and `tests/protocol/test_protocol_dap.c` and `_mcp.c` are written by `scripts/protocol.c` (docs/protocol.md) from DAP's and MCP's schemas, pinned by hash in build.c (`build_protocols`); never edit them. After changing the generator, `runtime/protocol/protocol.[ch]` (hand-written, what they stand on) or a pin, run `smith build protocol` and commit what it writes: `smith build check-protocol` (part of `check`) fails on a stale file, and `tests/protocol.sh` (`smith build test-protocol`, about 14 s: three builds, the first under the sanitizers) runs the generated tests and `tests/protocol/test_protocol_samples.c`. The generated files are not formatted or linted (no entry in `build_format_sources` or the tidy line); the hand-written ones and the generator are.
- The build executor (`runtime/executor*.c`) runs `smith build`'s manifest in place of ninja. After changing it, also run `python3 tests/ninja_compare.py build/<OS>-<arch>/smith 1 100` by hand: it builds random graphs with ninja and with the executor (`smith --smith-exec <manifest>`), edits them at random, and fails when the commands run or the files made differ. It needs ninja, so `smith test` does not run it. Comparing one project's tree from two builds: linked binaries differ in the linker's UUID and the object files' times, and a metallib is not reproducible; objects must match.
- The files `smith new` writes live in `templates/new/` (dotfiles without their dot; `agents.md`, `knowledge-index.md`, `knowledge-program.md` and `docs-skill.md` are `AGENTS.md`, `knowledge/index.md`, `knowledge/program.md` and `.agents/skills/<name>-docs/SKILL.md`, where `@NAME@` is the program's name and `@KEBAB@` the same as a skill's name; `.claude/skills` is a link made in `smith.c`; `primes.h`, `primes.c` and `test_primes.c` are the program the template builds and tests, and `smith.c` leaves them out with `main.c` when the project has its own build) and are embedded with `#embed`. The skills are not among them: a project gets smith's skills from the smith plugin, which the `.claude/settings.json` that `smith new` writes enables. The generated project is C2y (`-std=gnu2y`), so `build.c` tidies the templates with that standard; smith itself stays C23. A test keeps the template's rules equal to smith's `.clang-format` and `.clang-tidy`; `tests/new.sh` runs with `smith build test`.
- `include/smith/build.h` and `runtime/build_runtime.c` are embedded in smith with `#embed`; keep `cc -std=gnu23 smith.c -o smith` building all of smith (a test checks it).
- `smith fmt` rewrites `smith.c`, `build.c`, `tests/stub.c`, the header and the runtime. `smith check` runs `check-format`, `lint` (`smith lint`), `test` and `compare`, and must exit 0 before you finish. They run `smith fmt` and `smith lint` of the smith they build (`check-llvm` checks they are LLVM 23), so the full smith needs no Homebrew LLVM; a stage0 runs Homebrew's. `build.c` is formatted and tidied like the rest, so each of its functions is at most 70 lines.
- Before and after a change, run `smith cc --smith-which -c a.c`, `--smith-which a.metal`, `a.metal b.c` (all after `smith cc`) and `smith version`, and compare. A refactor must not change a route, a message, an exit code or an argv.
- `smith build install` runs the tests, then replaces `~/.local/bin/smith`, which every project's build uses (`-DPREFIX=...` installs elsewhere). Do it only when the owner asks.
- If the installed smith is broken, or in a fresh clone, a C23 compiler and a clang for build.c are all it takes: `mkdir -p build && cc -std=gnu23 smith.c -o build/stage0 && build/stage0 build install -DCC=cc` installs the stage0; add the `build/stage0 build llvm` step before it for the full smith.
- `smith build clean` removes `build/`. smith keeps its own files in `.smith/`, outside `build/`, so a project's clean cannot delete them while the build runs.

## Verbs and the compiler links

- `smith.c` ends with the verb table, `smith_verbs`: one row per top-level verb, a kind that says how it runs (`smith_dispatch`), and for a verb that has not arrived the issue it waits for. `smith prove` (issue #8) and `smith dbg` (issue #7) are `SmithVerb_Later` rows that print "not available yet"; when one arrives, change its kind (`SmithVerb_ToolOrProject` if it takes a tool's arguments and runs the project's target with none, as `fmt` and `lint` do, or `SmithVerb_Project`) and add the case to `smith_dispatch` if it is a new kind. `smith docs` (`SmithVerb_Docs`, `runtime/docs.c`, included by `smith.c`) is the check itself when it has arguments, and the project's `docs` task with none when there is a build.c; it is refused as a target of `smith build`. Every other kind but Cc, Cxx, Build, New, Fetch, Cache, Docs and Tool is a project verb: `smith_project_main` builds the target of its name, passing the arguments as `-DSMITH_ARGS` (read by `smith_args`), and `smith build <name>` is refused for it (`smith_is_project_verb`).
- A bare argument (`smith foo.c`) is `smith_bare_arguments`: an error that says what to run. Do not route it to the compiler.
- `smith-cc` and `smith-c++` are links that `main` dispatches by `argv[0]`, as are `clang` and `clang++`, the names of the programs folder's links, which the driver runs again with `-cc1`; `ld` is the linker. A test that copies smith under another name and expects a compile must pass `cc`.
- `smith build`'s bootstrap manifest compiles `build.c` with `<smith> cc ...` when clang is inside smith, and with the external clang itself otherwise. `build.c` files name `smith-cc` and `smith-c++` as compilers; `"smith"` is an error in `smith_object` and `smith_program`.

## The `.smith` language

[docs/smith-lang.md](../../../docs/smith-lang.md) is the language; the plugin's `smith-lang*` skills teach it. To work on it:

- `patches/clang-format-smith.patch` (issue #25) makes clang-format read a `.smith` file as C plus `::` and the file-scope `module`/`import` lines (`Format.cpp`, `UnwrappedLineParser`, `TokenAnnotator`); `tests/smith-fmt.sh <smith>` tests it (the corpus formatted to `tests/smith-fmt/corpus.expected`, `UPDATE=1` rewrites it; every `.c` of smith and the test beds the same as `.c` and `.smith`; `throw` and `import`; `smith fmt` with no arguments in a scratch project). `scripts/llvm.sh` applies every `patches/*.patch` and keeps the applied copies in `$cache/src/.patches/`: a patch that changed is taken out (with the ones after it) and put back, so a rebuild is incremental. To iterate on a Format patch, edit the cache sources and `ninja -C ~/.cache/smith/llvm/23.1.3-r2/build clang-format` (seconds), then turn the edit into the patch.
- The clang side is `patches/clang-token-hook.patch` (the `Preprocessor`'s `TokenHook`), applied to the LLVM sources by `scripts/llvm.sh` in its marked step, and `shim/hook.cpp`. The lowering is plain C in `runtime/lang*.c` (`runtime/lang.h` is its whole interface), so changing it does not rebuild LLVM; changing the patch does. `build.c` builds the hook only when the install's headers have it (`setHookMode`).
- `tests/smith-lang.sh <smith>` runs the corpus in `tests/smith-lang/cases` (`UPDATE=1` rewrites the expectations: read the diff), and `tests/smith-lang-c.sh <smith>` compiles smith's own sources as `.c` and as `.smith` and compares the code. Both skip themselves for a smith without the hook.
- `smith cc --smith-lower x.smith` prints the lowering of the text as written, `smith cc --smith-header x.smith -o x.h` a module's header (the helpers are under `smith cc`; the top level is only verbs). `smith build` runs the header steps itself (`smith_object` of a `.smith` source, `runtime/build_runtime.c`, "`.smith` sources" in docs/build-c.md); `tests/build.sh` section 15 tests it. `SMITH_LANG_ASK=Name,struct Tag` prints what the parser answers about those types at the end of a file.
- Cost: a plain `.smith` file must compile as fast as the `.c` (the host is offered only watched identifiers). Compare with alternating runs, at least 20 each, and note the load.

## Write C

The rules are game's, in https://github.com/adam-r-kowalski/game/blob/main/knowledge/c-language.md and https://github.com/adam-r-kowalski/game/blob/main/knowledge/c-naming.md, and `.clang-format` and `.clang-tidy` are copies of game's.

- Everything has the module prefix: `smith_route_metal`, `SmithRoute`, `SmithRoute_Clang`. Functions and variables are snake_case, types PascalCase, enum values `Type_Value`, macros UPPER_SNAKE.
- Functions are at most 70 lines, nothing recurses, every loop has a bound, and there is no malloc. That is smith's C: the C++ files in `shim/` (`clang.cpp`, `lld.cpp`, `symbolize.cpp`) are thin C interfaces to LLVM and stay as small as they can; smith's C code allocates nothing, the LLVM linked into it does.
- Assert with `SMITH_ASSERT`, on in every build: arguments, buffer capacities and `snprintf` results where they must hold. An expected failure, such as a bad `$SMITH_CLANG`, is a `smith_die` message, not an assertion.
- smith's exceptions to game's rules: libc's types stay where libc takes them (`int`, `size_t`, `ssize_t`, `char *`, `uint32_t` for `_NSGetExecutablePath`), not `u32` and `u64`, so there are no casts; exit statuses are `constexpr int`, not an enum; and `SMITH_ASSERT` replaces `BASE_ASSERT`, still on in every build. smith calls libc freely, which game's base layer may not.
- Fix what clang-tidy reports in the code. Do not weaken `.clang-tidy`.

## Where docs go

- Decisions and rules, one line each: `AGENTS.md`. Planned work: GitHub issues, nowhere in the repository. Procedures: skills in `.agents/skills`. `.claude/skills` links to it.
- The `smith` and `smith-build` skills ship in the smith plugin, straight from `.agents/skills`. No project carries a copy, so change them here only.
- Code and the docs that describe it go in the same commit. Small Conventional Commits.
