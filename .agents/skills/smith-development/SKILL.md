# Develop smith

[AGENTS.md](../../../AGENTS.md) holds the rules and decisions, and GitHub issues hold the planned work. This skill holds the procedures every change shares. To use smith as a compiler, load [smith](../smith/SKILL.md) instead. To edit smith's own `build.c`, load [smith-build](../smith-build/SKILL.md) as well.

## Build, test, install

smith builds itself with its own `build.c`, so the installed smith must have `smith build`. Pass `-DCC=/opt/homebrew/opt/llvm/bin/clang` to any of these to build smith with Homebrew's clang instead of the installed smith.

## The two smiths, and how to get the full one

smith has clang inside (issue #1): it compiles in its own process, by running clang's own `clang_main` (`shim/clang.cpp`, the only C++ in smith) on the arguments. Two smiths come out of one `smith.c`:
- **The stage0** is `cc -std=gnu23 smith.c -o build/stage0`: no C++, no LLVM, and it runs an external clang (`$SMITH_CLANG`, else Homebrew's). It is all a fresh clone has.
- **The full smith** has `-DSMITH_IN_PROCESS`, the shim, and the archives of our LLVM install linked in with `-Wl,-dead_strip`. `smith build` makes it when the install has `lib/libclangmain.a` (else it makes the stage0); `-DLLVM=` names another install, empty forces the stage0.

From a fresh clone: `mkdir -p build && cc -std=gnu23 smith.c -o build/stage0`, then `build/stage0 build llvm` (builds LLVM 23.1.3 into `~/.cache/smith/llvm/23.1.3/install`, about 9 minutes cold, a few seconds when it is built), then `build/stage0 build -DCC=cc` (or `... install -DCC=cc`) links the full smith; set `SMITH_CLANG=/usr/bin/clang` if Homebrew's llvm is not installed, since the stage0 compiles build.c with an external clang. Keep a copy of the stage0 outside `build/` (it survives `smith build clean`) when you work on the full one, and rebuild with the full smith: `cp build/<OS>-<arch>/smith $S/stage1 && $S/stage1 build -DCC=$S/stage1` (a smith compiles smith in its own process).
- **Enzyme** (`scripts/enzyme.sh`, `smith build enzyme` alone, `smith build llvm` runs it last) builds `libEnzymeStatic-23.a` into `~/.cache/smith/enzyme/<version>-<LLVM name>/lib` from a patched copy of the pinned package (`patches/enzyme/*.patch`, its own folder: `scripts/llvm.sh` applies only `patches/*.patch` to LLVM), against the install's CMake config, without touching the install; the cache survives `smith build clean`. build.c links it when it exists (`-DSMITH_ENZYME`, `-exported_symbol _llvmGetPassPluginInfo`), `shim/lld.cpp` registers it, and `tests/autodiff.sh` (`smith build test-autodiff`) tests it. A new Enzyme version is the pin and the folder's name in build.c. The build runtime's `smith_autodiff_flags` is the one place the autodiff programs' flags (full LTO, no passes, ASan but no UBSan) are decided; the skill is smith-autodiff.
- `scripts/llvm.sh` adds `lib/smith-clang.id` (the LLVM version and a hash of the archives linked; `smith build` compiles it into smith as the identity of its clang, which `--smith-which` prints and projects' objects depend on) and `lib/libclangmain.a` to the install: the four objects of clang's driver (`driver.cpp`, `cc1`, `cc1as`, `cc1gen-reproducer`), which hold `clang_main`. Running it again is cheap. Changing it needs `smith build llvm` again.
- The driver is run as `<folder>/bin/clang` (`-no-canonical-prefixes`, in `shim/clang.cpp`), where `<folder>` is `$XDG_DATA_HOME/smith/clang/llvm-<version>-<key>` (else `~/.local/share/...`), so it finds its builtin headers, compiler-rt and `libLTO.dylib` there, with no flag in the user's command. `scripts/pack.c` packs those files from the install at build time into `build/<OS>-<arch>/clang-resource.pack` (LZFSE, per 4 MB chunk; the format is `scripts/pack.h`), smith.c `#embed`s it (`-DSMITH_CLANG_RESOURCE=`), and the first compile writes the folder (beside it, then one `rename`, so parallel first compiles are safe). The programs are not in that folder: `bin/clang`, `bin/clang++` and `bin/ld` are hard links to the running smith, in `<data>/smith/programs/<LC_UUID>/bin` (with `lib` a symlink to the runtime folder's, and `-resource-dir` passed by `shim/clang.cpp` so that rpaths name the runtime folder, never the programs folder). Smiths of one runtime key but another binary never share links; a folder idle 31 days, and a half-built one older than an hour, are removed when a new one is made. The driver runs its program again with `-cc1` for a compile with more than one step. The folder is outside the caches `smith cache clean` and pruning touch, because sanitized binaries record an rpath into it; smith never removes it. `bin/ld` is the third link: the driver looks for its linker beside its program before `PATH`, so a link it starts is smith run as `ld`, which calls lld's `lld::macho::link` in that process (`shim/lld.cpp`; `liblldMachO.a` and `liblldCommon.a` of the install). The user's command gets no flag. `SMITH_LINKER=/usr/bin/ld` runs that linker instead, and then the driver is left as Apple's `ld` wants it; with lld, `shim/clang.cpp` adds `-mlinker-version=1115.7.3`, which tells the driver there are no `objc_msgSendClass$` stubs (only Apple's current `ld` writes them), and the user's own flag wins. Never overwrite a smith that is hard-linked in place (`cp` over it kills its next run with signal 9: the kernel keeps the old signature); remove it first, as an install's rename does. `scripts/llvm.sh` hashes lld into the identity. `dsymutil` and the other tools are the system's. `SMITH_CLANG` runs an external clang as before; `compare` checks the full smith against the install's clang binary (its prefix is rewritten to the folder in the text).
- The full smith needs the install only to build: its archives to link, and the resource files to pack. To check it needs nothing at run time, build it against a copy of the install in a scratch folder (`-DLLVM=`), remove the copy, and run the tests under `sandbox-exec` with a profile that denies `~/.cache/smith/llvm` and Homebrew's llvm. `tests/resource.sh` tests the folder, the links, the lld link (frameworks, a dylib, ARC, `-dead_strip`, the signature, `SMITH_LINKER`), `-flto`, the sanitizer rpath after `smith cache clean`, and parallel first compiles.
- `smith fmt`, `smith lint` and `smith lsp` (issue #3) run clang-format, clang-tidy and clangd in process, from `shim/format.cpp`, `shim/tidy.cpp` and `shim/clangd.cpp`, one C function each (`shim/tool.h` is what they share). The tools declare their flags in global `llvm::cl::opt` objects, and LLVM aborts at load when two define the same flag (clang-format and clang-tidy both have `-fallback-style`), so `scripts/llvm.sh` makes `libsmithtools.a` (linked whole, first) of patched copies of the tools' objects: their static initializers moved out of `__mod_init_func` (`scripts/defer_init.c`) for the tool that runs to run (`smith_tool_start`), clang-format's `main` renamed, clangd's code actions copied too, and the one call in clangd and in clang-tidy that finds the resource directory by the executable's path redirected to the resource directory of the install's clang (so, until #2, they read it from `SMITH_LLVM_BIN`, as the compiler does). A change to those needs `smith build llvm` again (a few seconds), and `shim/tool.h` is the place to change when #2 moves the resource directory. clangd's XPC transport (`CLANGD_AS_XPC_SERVICE`) is left out and `shim/clangd.cpp` stubs it, because it links Foundation, whose loading cost every smith process, compiles included, about 10 ms; a plain `smith version` is the quick check of startup time (about 8 ms for the smith before #3).
- The unstripped full smith is about 127 MB (`-g`), of which 20 MB is the pack; the first compile writes about 70 MB.

- `smith symbolize` and smith run as `llvm-symbolizer` (`runtime/symbolize.c`, included by smith.c; the lookups are `shim/symbolize.cpp`, which reads the binary's debug map and the object files it names, or a matching dSYM) turn the stack traces of `<smith/trace.h>` (`lib/trace.c`, a library `smith_tests` compiles) into reports. `smith build test` sets `SMITH_SELF` for the build program, pipes the test runner (with `--trace`) through `smith symbolize`, and makes `.smith/bin/llvm-symbolizer` for the sanitizers. The stage0 has no symbolizer (`smith symbolize --available` exits 3), and the tests of reports in `tests/test.sh` skip themselves. Debug a report with `build/tests --test <name> --trace | smith symbolize`.

## Build, test, install

- `smith build` builds `build/<OS>-<arch>/smith` and the `smith-cc` and `smith-c++` links. `CC` is the installed smith, as `smith-cc`, so smith builds smith; `-DCC=/opt/homebrew/opt/llvm/bin/clang` compiles it with Homebrew's clang instead. If the installed smith is broken, use the recovery line below.
- `smith test` runs the routing tests (each case through `smith cc` and through `smith-cc`; fewer for the stage0) against stub compilers, then the 532 `smith build` tests in `tests/build.sh`, the 225 `smith new` tests in `tests/new.sh` (the three builds, `assert(false)`, the tools on the generated project, `smith_library` under the template's flags, and the generated docs: a new project passes `smith docs` and `smith check`, breaking each rule fails it, and the verbs on a project: prove, fmt, lint, check), the 64 `smith docs` tests in `tests/docs.sh` (every rule on the small repositories of `tests/docs/fixtures/<case>`, each with the exact output in `expect.txt`, optional `args`, and `pass/expect.d`, the depfile; the options; the types the index declares; the verb needs no task) and the 27 arena tests in `tests/arena.sh` (`<smith/arena.h>` alone, its capacity stop, ASan, and a project using `smith_library`), and the io tests in `tests/io.sh` (`<smith/io.h>`, the header of the module `smith::io`: its lowering and the module compiled under the warnings, real files, console pipes, processes, timers, the seed, the lazily committed reservation, TLS connections against a server on the loopback, and the fake io with its scripted servers; sanitized and plain), the http tests in `tests/http.sh` (`<smith/http.h>` on a scripted network, no internet: redirects, chunked bodies, short bodies, a stalled server, every error), the package tests in `tests/package.sh` (downloads on a scripted network into a real cache), the random tests in `tests/random.sh` (`<smith/random.h>`: Philox known answers, the distributions, digests across build configurations, the refusals, and a project using both libraries), the text tests in `tests/text.sh` (`<smith/text.h>`: `tests/text_test.smith` built with smith's own test library in three builds, with property tests on keys for the integers and a float parser that must equal `strtof`; `smith build text-exhaustive` parses all 2^32 float patterns and a sample of 2^24 double patterns, minutes on all cores, and is not part of `test`) the json tests in `tests/json.sh` (`<smith/json.h>`: `tests/json_test.smith` in three builds, fuzzing under ASan and UBSan, and JSONTestSuite fetched by hash into `~/.cache/smith-tests`, skipped offline), the tree-sitter tests in `tests/tree_sitter.sh` (the grammar for `.smith` in `tree-sitter/`: its corpus, samples, the #11 corpus once it exists, and every `.c` and `.h` file of smith, through `tests/tree_sitter.c` linked with the tree-sitter runtime pinned by hash; regenerate `tree-sitter/src/parser.c` with `scripts/tree-sitter.sh` after a change to `grammar.js`) the language server tests in `tests/lsp.sh` (a real `smith lsp` session driven by `tests/lsp_client.c` on a scratch project of `.smith` modules and a C file: diagnostics at the lines and columns of the text, hover, definition across modules, symbols, completion) and the Neovim tests in `tests/neovim.sh` (the plugin, `plugin/smith.lua` and `editors/neovim`, in headless Neovim; skipped without `nvim`; `SMITH_NVIM_ONLY="parser highlights"` runs some; docs/neovim.md), the cache tests in `tests/cache.sh` (the shared module cache, package pruning with a faked clock, `smith cache`, all in a temporary `XDG_CACHE_HOME`; never touch the real `~/.cache/smith`), the resource tests in `tests/resource.sh` (the folder of clang's embedded files written on first use, in a temporary `XDG_DATA_HOME`: its contents, `bin/clang`, `-flto`, a sanitized program run after `smith cache clean`, eight first compiles at once; skipped for the stage0) and the tests of `<smith/test.h>` and `smith_tests` in `tests/test.sh` (a scratch project whose test files fail on purpose: the failure blocks, aborts, isolation, the finding of tests, shrinking, `-Wconversion`, clangd), which need a real clang, clangd and git (and ninja only for the tests of the `SMITH_NINJA` fallback, which skip themselves without it). `smith build compare` runs 33 invocations (compiles, links with and without debug info and sanitizers, assembly, `-###`, `-v`, diagnostics with colours, response files, standard input) through clang and through smith and compares what each prints, how each exits and the bytes of the files; `REAL` defaults to the clang of the LLVM smith links, which every case must match. Homebrew's (`-DREAL=/opt/homebrew/opt/llvm/bin/clang`) says "Homebrew clang" in its version, in debug info and in bitcode, so those cases differ against it.
- **The test scripts run side by side.** `build.c` has a table, `build_test_scripts`, one row per task `test-<task>` (the script `tests/<script>.sh`, with an optional mode and parts), and each is a test (`.test = true`, which `smith test` runs; `test-compare` is one too), so `smith test` and `smith check` run them in parallel and take about as long as the slowest. Run one alone with `smith build test-<task>` (for example `smith build test-build`). A new script is a new row (keep the rows in order). A script must be safe to run beside the others: its work is in `mktemp -d`, its caches in `XDG_CACHE_HOME` (and `XDG_DATA_HOME` where it starts compilers) under that folder, no fixed port (loopback tests bind port 0), no fixed temporary name, and nothing written in the repository. `tests/test.sh` takes a list of parts as its last argument (`sh tests/test.sh smith isolate shrink_list,budget`; default all), each part in a project of its own, and `build.c` runs the `--isolate` pass as several tasks (`test-isolate-main`, `-rest`, `-shrink-int`, `-shrink-list`, `-shrink-normal`) because shrinking a test in processes of their own is long. A row has a phase, 0 for a short task and 1 for a long one; all start at once (`prove` too: its budget is CPU time, so a busy machine slows it and never fails it). `smith build test-<task>` runs one alone. A test's time budget (about 10 s, `budget` 14 s) must hold under the load of the whole suite; a failure that appears only in `smith test` and not alone is a budget under load, so report it with numbers rather than raising it.
- **Tests of behavior are `.smith` tests on smith's own runner** (issue #31; `build_units` in build.c, the task `test-units`, part of `smith test` and `smith check`): every `tests/*_test.smith` (`module <x>_test;`, exported `test_*` functions, `import smith::test;`) is linked with the libraries it tests (`smith_tests` links every smith library the test files import or include, with what those need, so a new module's test needs nothing declared) into one runner built once under AddressSanitizer and UBSan, compiled by the smith under test (`<folder>/smith-cc`), and its workers run the tests in process, one per core. Add a test file there, not a shell script, whenever the code can be called in process; run one with `build/<OS>-<arch>/units/tests --test <name>`; the heavy sizes are `--full`, and the long property runs are by hand (`--full --seeds 1000 --test test_prop_inflate_round_trips_stored_blocks`). **Tests that start smith** (`tests/build_*_test.smith`, the ported parts of tests/build.sh) use `tests/scratch.smith` (`import scratch;`): `scratch::project(io, "p", "<fixture>")` makes a folder in the test's scratch folder with `tests/build_fixtures/<fixture>/` copied in and the smith under test (`$SMITH_SELF`, set by `smith test`; set it to run the runner by hand) first on PATH; `scratch::build(&p, "-v")` and `scratch::sh(&p, "...")` run commands there through io's processes and return `.status`, `.out`, `.err`; `expect_contains`, `expect_text`, `expect_count` and the rest check them. Each test is its own project, so they run side by side; a long sequence is split into tests that each build what they need. A script stays for what needs a process or a build of its own (a stop, a sanitizer's catch, a build mode, a project built with `smith_library`). `smith test` and `smith check` end with a table of each task's wall and CPU time and smith processes (`SMITH_ACCOUNT=all` or `smith check -v` lists every task): read it before choosing what to port, and when a script's number moves. The stage0 has no `.smith` compiler, so it builds no runner.
- **The protocol code is generated.** `runtime/protocol/dap.[ch]` and `mcp.[ch]` and `tests/protocol/test_protocol_dap.c` and `_mcp.c` are written by `scripts/protocol.c` (docs/protocol.md) from DAP's and MCP's schemas, pinned by hash in build.c (`build_protocols`); never edit them. After changing the generator, `runtime/protocol/protocol.[ch]` (hand-written, what they stand on) or a pin, run `smith build protocol` and commit what it writes: `check-protocol` (a test, so `smith test` and `smith check` run it) fails on a stale file, and `tests/protocol.sh` (`smith build test-protocol`, about 14 s: three builds, the first under the sanitizers) runs the generated tests and `tests/protocol/test_protocol_samples.c`. The generated files are not formatted or linted (they are in `.clang-format-ignore`, and lint reads only what the build compiles); the hand-written ones and the generator are.
- **`smith mcp`** (`runtime/mcp*.c`, docs/mcp.md) is in the full smith only (`-DSMITH_MCP`, passed whenever clang is inside). `tests/mcp.sh` (`smith build test-mcp`, about 25 s) builds `tests/mcp_fake.c` three ways (the server on the fake io, a scripted client and a scripted `smith dap` child, whose frames answer the requests numbered from 1; a wrong script makes the server wait for a reply, which its alarm ends) and drives the real `smith mcp` on a C program, a `.smith` module and a project test. Build smith with the smith you just built when the installed one is older than build.c (`build/<OS>-<arch>/smith build`).
- The build executor (`runtime/executor*.c`) runs `smith build`'s manifest in place of ninja. After changing it, also run `python3 tests/ninja_compare.py build/<OS>-<arch>/smith 1 100` by hand: it builds random graphs with ninja and with the executor (`smith --smith-exec <manifest>`), edits them at random, and fails when the commands run or the files made differ. It needs ninja, so `smith test` does not run it. Comparing one project's tree from two builds: linked binaries differ in the linker's UUID and the object files' times, and a metallib is not reproducible; objects must match.
- The files `smith new` writes live in `templates/new/` (dotfiles without their dot; `agents.md`, `knowledge-index.md`, `knowledge-program.md` (the `.smith` project's concept; `knowledge-program-c.md` is the C one's) and `docs-skill.md` are `AGENTS.md`, `knowledge/index.md`, `knowledge/program.md` and `.agents/skills/<name>-docs/SKILL.md`, where `@NAME@` is the program's name and `@KEBAB@` the same as a skill's name; `.claude/skills` is a link made in `smith.c`; `main.smith`, `primes.smith` and `test_primes.smith`, or `main.c`, `primes.c`, `primes.h` and `test_primes.c`, are the program, one set for each `--language` (a row of `smith_new_files` says which), and `smith.c` leaves them out when the project has its own build file, another build system or a `main` of the other language) and are embedded with `#embed`. There is no build file and no config file among them: smith builds by convention, and smith's own `.clang-format` and `.clang-tidy`, which `smith fmt` and `smith lint` use where a project has none, are `templates/defaults/clang-format` and `clang-tidy`. The skills are not among them: a project gets smith's skills from the smith plugin, which the `.claude/settings.json` that `smith new` writes enables. A test keeps the defaults' rules equal to smith's `.clang-format` and `.clang-tidy`; `tests/new.sh` runs with `smith build test-new`.
- `include/smith/build.h` and `runtime/build_runtime.c` are embedded in smith with `#embed`; keep `cc -std=gnu23 smith.c -o smith` building all of smith (a test checks it).
- `smith fmt` rewrites every C, C++, Objective-C and `.smith` file git sees except what `.clang-format-ignore` names (generated parsers, the fixtures of the tests). `smith check` is the standard check: fmt (dry run), docs, lint (clang-tidy over the compiles in `.smith/build.info`; `build.c` declares the libraries' and tests' sources with `smith_compile_command`; `shim/.clang-tidy` has the C++ glue's rules), test and prove, each reported, and must exit 0 before you finish. They run the tools of the smith that runs them (a full smith: its own LLVM 23; a stage0: Homebrew's). `build.c` is formatted and tidied like the rest, so each of its functions is at most 70 lines.
- Before and after a change, run `smith cc --smith-which -c a.c`, `--smith-which a.metal`, `a.metal b.c` (all after `smith cc`) and `smith version`, and compare. A refactor must not change a route, a message, an exit code or an argv.
- `smith build install` runs the tests, then replaces `~/.local/bin/smith`, which every project's build uses (`-DPREFIX=...` installs elsewhere). Do it only when the owner asks.
- If the installed smith is broken, or in a fresh clone, a C23 compiler and a clang for build.c are all it takes: `mkdir -p build && cc -std=gnu23 smith.c -o build/stage0 && build/stage0 build install -DCC=cc` installs the stage0; add the `build/stage0 build llvm` step before it for the full smith.
- `smith build clean` removes `build/`. smith keeps its own files in `.smith/`, outside `build/`, so a project's clean cannot delete them while the build runs.

## Rules for an agent working on smith

- **Test the smith under test.** Run a change's tests with `build/<OS>-<arch>/smith`, not the installed `smith`, when the change is to the language, a library or the build. A test that builds a project puts the tested smith's folder (its `smith-cc` and `smith-c++`) first on `PATH`, so nothing in it compiles with the installed smith.
- **Regenerate after a merge that changes a library module or the lowering.** When `lib/smith/*.smith` or `runtime/lang*.c` changed on either side, run `smith build headers` and `smith build bootstrap`; `check-headers` and `check-bootstrap` fail until it is done. A merge of docs or skills alone needs neither.
- **Scratch folders are your own.** Make each with `mktemp -d` (under your scratchpad when you have one), never a fixed name such as `proj`: another agent may be using it.
- **A change to LLVM is a new configuration, never an edit of the one in use.** When a change needs LLVM rebuilt (a new patch in `patches/`, a changed `scripts/llvm.sh`), bump the configuration (`23.1.3-rN` to `-rN+1` in build.c, `scripts/llvm.sh` and the scripts that name it) and build it beside the old one with `smith build llvm`, about 10 minutes and 11 GB. The installed smith and every other worktree keep using the old one until the change merges, so nothing breaks while it builds. Say in your report that you built one, and why.
- **Write idiomatic Smith, not C renamed.** In a `.smith` file: sized types (`u64`, `usize`, `f64`), `import <h>;` with `c::` names, modules that import modules, generics where a type was passed as `sizeof` and `alignof`, and no preprocessor. Count them before and after a port: a module with a standard C type, an `#include` or an `#if` left is not done.
- **Effects come through capabilities.** No raw call to the world outside a capability's own module (`smith-effects`); a function takes the part of `io::Io` (`SmithIo` in C) it needs as a parameter.
- **Never signal a process that is not your own unwaited child**, and never `pkill` or `killall`: a reparented pid may already be another test's compile.
- **A new check or a new diagnostic runs the editor tests too:** `test-lsp` and `test-neovim` pin the exact diagnostics of their sample files, so a check that fires on them fails there first. Fix the sample, not the check.
- **When `smith build headers` or `bootstrap` cannot build smith** (it embeds the stale bootstrap file after a header change), regenerate that module's bootstrap by hand, `sh scripts/bootstrap.sh <smith> lib/smith/<name>.smith bootstrap/lib/smith/<name>.c`, then build.
- **`host->read_header` returns a buffer valid only until the next read**, and the lowering's own lookups read others: copy what you need before calling anything that may read a header.
- **A change to a library's header or its smith.c row in the same commit:** the branch's smith embeds the old header, so rebuild it with the installed smith (`smith build`), then regenerate (`build/<OS>-<arch>/smith build headers`, `... bootstrap`), then build again.
- **One full `smith check` at a time** on a machine, and say plainly what you did not run.
- **Report friction when you finish.** Besides what you did, say what slowed you down or misled you: a skill that was wrong, missing or hard to find, an error message that did not say the fix, a rule you had to guess, a check that caught you (and whether its message was enough). Name the skill, message or check. Each report is how the skills and the checks get better, and whether a change to them helped shows in the next agent's report.

## Verbs and the compiler links

- `smith.c` ends with the verb table, `smith_verbs`: one row per top-level verb, a kind that says how it runs (`smith_dispatch`) and, for a project verb, the function that does it (`runtime/verbs.c`, included by `smith.c`). `SmithVerb_ToolOrProject` (`fmt`, `lint`, `prove`) is the tool with arguments and the project action with none; `SmithVerb_Project` (`run`, `test`) and `SmithVerb_ProjectBare` (`check`) are the action alone. `smith docs` (`SmithVerb_Docs`, `runtime/docs.c`) is always the check, with the types of `knowledge/index.md`. The actions read `.smith/build.info` (written by every run of build.c, `runtime/build_runtime.c`: `smith_put_build_info`) and build the manifest's `smith_needs` or `smith_tests`; `smith build <verb>` is refused for the seven fixed names (`smith_is_project_verb`), and `smith_task` and `smith_alias` refuse them (`smith_verb_names` in the runtime). A new verb is a row and a function.
- A bare argument (`smith foo.c`) is `smith_bare_arguments`: an error that says what to run. Do not route it to the compiler.
- `smith-cc` and `smith-c++` are links that `main` dispatches by `argv[0]`, as are `clang` and `clang++`, the names of the programs folder's links, which the driver runs again with `-cc1`; `ld` is the linker. A test that copies smith under another name and expects a compile must pass `cc`.
- `smith build`'s bootstrap manifest compiles `build.c` with `<smith> cc ...` when clang is inside smith, and with the external clang itself otherwise. `build.c` files name `smith-cc` and `smith-c++` as compilers; `"smith"` is an error in `smith_object` and `smith_program`.

## The `.smith` language

[docs/smith-lang.md](../../../docs/smith-lang.md) is the language; the plugin's `smith-lang*` skills teach it. To work on it:

- `patches/clang-format-smith.patch` (issue #25) makes clang-format read a `.smith` file as C plus `::` and the file-scope `module`/`import` lines (`Format.cpp`, `UnwrappedLineParser`, `TokenAnnotator`); `tests/smith-fmt.sh <smith>` tests it (the corpus formatted to `tests/smith-fmt/corpus.expected`, `UPDATE=1` rewrites it; every `.c` of smith and the test beds the same as `.c` and `.smith`; `throw` and `import`; `smith fmt` with no arguments in a scratch project). `scripts/llvm.sh` applies every `patches/*.patch` and keeps the applied copies in `$cache/src/.patches/`: a patch that changed is taken out (with the ones after it) and put back, so a rebuild is incremental. To iterate on a Format patch, edit the cache sources and `ninja -C ~/.cache/smith/llvm/23.1.3-r4/build clang-format` (seconds), then turn the edit into the patch.
- **The other LLVM patches, applied after those above (a patch's name sorts it, and it must apply to the sources as the earlier ones left them).** A patch changes the configuration, so it is a new folder (`23.1.3-r4` is the third): build it with `smith build llvm` from your branch, and only your branch's `build.c` points at it, never at the shared one that installed smiths link. `patches/smith-editor-defaults.patch`: a fallback style written `file:<path>` in `format::getStyle`, and `clang::clangd::FallbackTidyConfigFile` in `provideClangTidyFiles`; `smith lsp` sets both (`smith_lsp_defaults` in smith.c, `smith_clangd_defaults` in shim/clangd.cpp), tested in `tests/lsp.sh`. `patches/smith-format-source-extension.patch`: `.smith` is a source file in clang-format's main-include rule, so `foo.smith` sorts `foo.h` first as `foo.c` does (`tests/smith-fmt.sh`). `patches/smith-command-hook.patch`: `clang::CommandHook`, asked by `createInvocation` (clangd) and `getStripPluginsAdjuster` (clang-tidy), which the shims set to `smith_lang_command` (shim/tool.h); `build.c` treats an install without it (`CLANG_HAS_COMMAND_HOOK`) as not linkable.
- The clang side is `patches/clang-token-hook.patch` (the `Preprocessor`'s `TokenHook`), applied to the LLVM sources by `scripts/llvm.sh` in its marked step, and `shim/hook.cpp`. The lowering is plain C in `runtime/lang*.c` (`runtime/lang.h` is its whole interface), so changing it does not rebuild LLVM; changing the patch does. `build.c` builds the hook only when the install's headers have it (`setHookMode`).
- `tests/smith-lang.sh <smith>` runs the corpus in `tests/smith-lang/cases` (`UPDATE=1` rewrites the expectations: read the diff), and `tests/smith-lang-c.sh <smith>` compiles smith's own sources as `.c` and as `.smith` and compares the code. Both skip themselves for a smith without the hook.
- `smith cc --smith-lower x.smith` prints the lowering of the text as written, `smith cc --smith-header x.smith -o x.h` a module's header (the helpers are under `smith cc`; the top level is only verbs). `smith build` runs the header steps itself (`smith_object` of a `.smith` source, `runtime/build_runtime.c`, "`.smith` sources" in docs/build-c.md); `tests/build.sh` section 15 tests it. `SMITH_LANG_ASK=Name,struct Tag` prints what the parser answers about those types at the end of a file (`?const char *` asks about a type written as tokens, the question generics use).
- Cost: a plain `.smith` file must compile as fast as the `.c` (the host is offered only watched identifiers). Compare with alternating runs, at least 20 each, and note the load.
- **What the hook offers the lowering:** identifiers it watches, and braces or every token only in the modes that ask for them. Keywords (`if`, `else`, `constexpr`) are never offered as such, and the hook's fast path handles file-scope keywords without calling the lowering; a feature that must see a keyword asks for every token in the file (as `if constexpr` does for a file whose text has it).
- **`smith_lang_keep_aside` holds one saved state:** reading another module's interface while one is set aside corrupts the caller. Read imported modules first (`smith_raw_prefetch`), never nested.
- **A smith-lang corpus case is read by three tests:** after adding or changing one, run `UPDATE=1 sh tests/smith-lang.sh <smith>` and `UPDATE=1 sh tests/smith-fmt.sh <smith>` and read both diffs, and run `test-tree_sitter`: the editor's grammar must parse every case, so new syntax may need `tree-sitter/grammar.js` (then `sh scripts/tree-sitter.sh corpus`).
- **Generics today:** an instance is compiled where it is called, outside its module's file, but `smith-effects` counts it as its generic's module (a raw call in a capability module's generic is the module's own); an exported generic's body names only exports; an instance's tokens begin the lines the generic's did (a braceless `if` in a generic is fine under `-Wmisleading-indentation`). An exported enum's constants are `<CType>_<Value>` in C (`SmithTestKind_Equal`), passing C's `Type_Value` naming rule, when the enum has a C name (`[[smith::c_name]]` or a tag).
- **A module the bootstrap lowers writes its generics' types out** (`arena::push_array(arena, f64, n)`): the header pass and `--smith-lower` have no parser, so they cannot type an argument (a bootstrapped module calls no `auto` function: random calls the builtins), and the error ("the raw lowering has no compiler to type it") means exactly that.
- **The tests include the bootstrap lowering** (`tests/random.c` includes `bootstrap/lib/smith/random.c`), so a change to what a module imports can break a test's compile: run `smith lint`, which compiles them.

## Libraries in C and in `.smith`

**Adding a library to the registry touches, in one commit:** its row in `smith_libraries` and its embeds in smith.c (with any flags it declares, as random's `-ffp-contract=off`); the lists in build.c that name the libraries (sources, headers, bootstrap, lint compiles); `scripts/bootstrap.sh`'s list when it is a `.smith` module; runtime/package.c if the build runtime compiles it; the test scripts that build smith's libraries by hand; its skill and the smith map. A module that only a body imports becomes a relative `#include` in the bootstrap lowering, so the stage0's one-command build still finds it.

- A library is a row of `smith_libraries` in `smith.c` (`SMITH_LIBRARY(name, lang)`), its two `#embed`s just above (the header
  `include/smith/<name>.h` and the source), and its name in `build_smith_inputs` and `build_format_sources` in `build.c`. The source
  is C (`lib/<name>.c`, written to `.smith/lib/<name>.c`) or, with `lang` true, a `.smith` module (`lib/smith/<name>.smith`,
  `module smith::<name>;`, written to `.smith/lib/smith/<name>.smith`, which is where its path rule puts it).
  `smith_library(b, "<name>")` finds either; a project compiles it like any source.
- **Porting a library from C to `.smith`:** `git mv lib/<name>.c lib/smith/<name>.smith` and convert it (drop the
  `smith_<name>_` prefix, `[[smith::c_name("smith_<name>_x")]] export` on each function so the symbols stay, `[[smith::c_name("SmithX")]]` on
  each type; comments above an export are the header's, written with the Smith names, the first one saying how a C name follows from them); change the `#embed` path and the row's
  `false` to `true` in `smith.c`; add the name to `build_generated_headers` in `build.c` and remove the library from `build_tidy` (it has
  no `.smith` support yet); `smith build headers` writes `include/smith/<name>.h` (commit it); a library that uses another is a module that imports it, `import smith::arena;` (see `smith::random`): the header includes it relative to itself (`#include "arena.h"`), so smith's own build, the stage0 and a user project find it with no include path, and the bootstrap lowering reads its source (docs/smith-lang.md "The header", "The bootstrap");
  point the library's own test script at the `.smith` source. Compare the old and new header's declarations and `nm -gU` of an
  object from each: they must match. A module `import`s C headers (`import <string.h>;`), never `#include`s them, has no preprocessor directive and no `c::` name that is a C macro (`smith-preprocessor`: `contract::assert`, `math::max(usize)`, `__builtin_memset`), and a flag it needs is `SMITH_LIBRARY_FLAGS` in smith.c, not a `#pragma`, and uses the sized types (`u64`, `usize`, `f64`) and `arena::push(&a, T)` for a typed push.
- **The bootstrap (`bootstrap/`).** A `.smith` source that smith's own build compiles is compiled from its committed
  lowering, `bootstrap/<path>.c` (`bootstrap/lib/smith/text.c`), with `config->cc`, so the stage0 and an older installed
  smith need no knowledge of the language and a fresh clone builds with `cc`. List the source in `build_bootstrap_sources`
  (build.c), run `smith build bootstrap`, commit the file, and have the build compile the `.c` (as `build_protocol` does
  for text). `check-bootstrap` (part of `check`) lowers again and fails naming the stale file, so change a `.smith` that
  is listed, run `smith build bootstrap`, commit both. `scripts/bootstrap.sh` writes the file: an include of the module's header, then `smith cc --smith-lower` (no compiler, so the stage0
  writes the same bytes) less what the header says; smith's runtime (`runtime/package.c`) includes `bootstrap/lib/smith/contract.c`, `arena.c`, `io.c` and `random.c` (and `lib/trace.c`, which arena's stop and contract call), embedded in smith.c and written to `.smith/bootstrap/lib/smith/`, because `io` needs the others, and so does `tests/mcp_fake.c`; the executor's growing buffer is its own (`SmithGrow` in `runtime/executor.c`), since io's is private; a test that reaches a module's private names (`tests/random.c`) includes the lowering; it has no comments, but keeps `#include`, `#define`, `#pragma`, `#error` and `#if`
  chains as written (every branch is lowered; a `#define` body with `::` or a sized type is an error). The lowering has no parser, so a generic call in a listed module writes its type (`arena::push_array(arena, f64, count)`) and calls no `auto` function, and uses no `if constexpr` that asks about a type; it does read a module it imports, so `arena::Arena` is `SmithArena`. `tests/bootstrap.sh`
  (`smith build test-bootstrap`) checks the files, the stage0's bytes, the lowering in an empty environment, and the C under
  `/usr/bin/clang` and `cc`. docs/smith-lang.md, "The bootstrap".
- **What a port of a C library with system calls (io) needed, and how it was done:**
  - A C macro the module needs (`ENOENT`, `O_CREAT`, `EV_ADD`) is read once into a `constexpr` of the module inside one `// NOLINTBEGIN(smith-preprocessor, bugprone-signed-bitwise)` block, and flags that are OR-ed together are one constant (`open_replace`), since `smith-preprocessor` reports each `c::` macro and `bugprone-signed-bitwise` an OR of named `i32`s. `errno` is `*c::__error()`; a wait status, a file's kind and a `sigset_t` are decoded from their bits (the SDK's macros for them are octal literals, which C2y deprecates, and `<signal.h>`'s are macros); `EV_SET` is a `struct c::kevent` initializer; `dlsym`'s address is copied with `__builtin_memcpy`, not converted to a function pointer (`-Wpedantic`).
  - A name that a C header declares cannot be a local or a parameter even where it is not called (`wait`, `read`, `exit`, `link`, `signal` as a *field* is fine): the error says `write c::name`.
  - An exported struct with an attribute between `struct` and its tag (`struct [[clang::annotate("smith::capability")]] SmithOp {`) keeps its tag as written, so write the C tag there and in its self-references (`struct SmithOp *next`); an opaque exported type is `[[smith::c_name("SmithLoop")]] export typedef struct SmithLoop Loop;` and its body is a private `struct Loop { ... };` later in the module (the private tag lowers to the typedef's C name).
  - An exported enum's constants are written short (`Replace`, C's `SmithWrite_Replace`), which the naming check refuses (it wants `Type_Value`), so the enum sits between `// NOLINTBEGIN(readability-identifier-naming)` and `END` with a blank line after the BEGIN (a comment right above an export is its doc comment).
  - A module has no forward declarations: order private functions so each comes after what it calls (io's scripted network is before the loop that calls it). `_Countof` is C2y, which the stage0's `-std=gnu23` build of the lowering refuses: write `sizeof a / sizeof a[0]`.
- **`smith::build` is a module with no bodies** (`lib/smith/build.smith`): it declares the build API with module names, each export `[[smith::c_name("smith_x")]]`, defined in C by `runtime/build_runtime.c`. Its generated header IS `include/smith/build.h` (what every build.c includes and smith embeds), so it is in `build_generated_headers` but is no library row and has no bootstrap file. Add a call to the API in `lib/smith/build.smith` (with its doc comment above the export, in Smith names: `build::task`), run `smith build headers`, and commit the header. A type must come after what it uses (the module has no forward declarations).
- A stage0 cannot compile a `.smith` library (no hook), so a project that calls `smith_library(b, "text")` needs the full
  smith; the header alone (C code that only includes it) works anywhere.
- **One header, written twice with the same bytes.** C includers and `import smith::<name>;` both read `.smith/include/smith/<name>.h`. `smith build` writes the embedded generated header there (`smith_write_library_header` in `smith.c` swaps the first line's `from lib/smith/<name>.smith` for the `.smith/lib/...` path the project's header step generates from), and `smith_object` of the library's source (`.smith/lib/smith/…`) adds no header step, because the committed header is formatted with `.clang-format` (`smith build headers` and `check-headers` run `smith fmt --style=file:.clang-format` on the generator's output; the stage0 formats with Homebrew's clang-format) and a step would write it again unformatted, the two taking turns. The header carries the `smith-module` line, so no "not a header smith wrote" error arises. While a library is still C, its hand-written header at `.smith/include/smith/<name>.h` is refused as a module's header (a project module `smith::<name>` collides), which ends when the library is ported. `tests/text.sh` builds a project with `smith_library(b, "text")`, a C file and a `.smith` importer.
- `check-headers` (part of `check`) regenerates every committed generated header and compares the bytes.

## Write C

The rules are game's, in https://github.com/adam-r-kowalski/game/blob/main/knowledge/c-language.md and https://github.com/adam-r-kowalski/game/blob/main/knowledge/c-naming.md, and `.clang-format` and `.clang-tidy` are copies of game's.

- Everything has the module prefix: `smith_route_metal`, `SmithRoute`, `SmithRoute_Clang`. Functions and variables are snake_case, types PascalCase, enum values `Type_Value`, macros UPPER_SNAKE.
- Functions are at most 70 lines, nothing recurses, every loop has a bound, and there is no malloc. That is smith's C: the C++ files in `shim/` (`clang.cpp`, `lld.cpp`, `symbolize.cpp`) are thin C interfaces to LLVM and stay as small as they can; smith's C code allocates nothing, the LLVM linked into it does.
- Assert with `SMITH_ASSERT`, on in every build: arguments, buffer capacities and `snprintf` results where they must hold. An expected failure, such as a bad `$SMITH_CLANG`, is a `smith_die` message, not an assertion.
- smith's exceptions to game's rules: libc's types stay where libc takes them (`int`, `size_t`, `ssize_t`, `char *`, `uint32_t` for `_NSGetExecutablePath`), not `u32` and `u64`, so there are no casts; exit statuses are `constexpr int`, not an enum; and `SMITH_ASSERT` replaces `BASE_ASSERT`, still on in every build. smith calls libc freely, which game's base layer may not.
- Fix what clang-tidy reports in the code. Do not weaken `.clang-tidy`.
