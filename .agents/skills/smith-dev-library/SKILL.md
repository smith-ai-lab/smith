# smith-dev-library

What a library is and may contain is in [libraries](../../../knowledge/libraries.md).

**Adding a library to the registry touches, in one commit:** its row in `smith_libraries` and its embeds in smith.c (with any flags it declares, as random's `-ffp-contract=off`); the lists in build.c that name the libraries (sources, headers, linked libraries, lint compiles); `smith_build_program_libraries` in smith.c when the build runtime links it (runtime/package.c); the test scripts that build smith's libraries by hand; its skill and the smith map.
- A library is a row of `smith_libraries` in `smith.c` (`SMITH_LIBRARY(name, lang)`), its `#embed`s just above (the source, and for a C library its hand-written header `include/smith/<name>.h`; a `.smith` module has no header in git), and its name in `build_smith_inputs` and `build_format_sources` in `build.c`. The source
  is C (`lib/<name>.c`, written to `.smith/lib/<name>.c`) or, with `lang` true, a `.smith` module (`lib/smith/<name>.smith`,
  `module smith::<name>;`, written to `.smith/lib/smith/<name>.smith`, which is where its path rule puts it).
  `smith_library(b, "<name>")` finds either; a project compiles it like any source.
- **Porting a library from C to `.smith`:** `git mv lib/<name>.c lib/smith/<name>.smith` and convert it (drop the
  `smith_<name>_` prefix, `[[smith::c_name("smith_<name>_x")]] export` on each function so the symbols stay, `[[smith::c_name("SmithX")]]` on
  each type; comments above an export are the header's, written with the Smith names, the first one saying how a C name follows from them); change the `#embed` path and the row's
  `false` to `true` in `smith.c`; add the name to `build_header_modules` in `build.c` (a module no smith_object compiles gets its header step there) and remove the library from `build_tidy` (it has
  no `.smith` support yet); its header is a build output, written to `.smith/include/smith/<name>.h` (never commit it); a library that uses another is a module that imports it, `import smith::arena;` (see `smith::random`): the header includes it relative to itself (`#include "arena.h"`), so smith's own build and a user project find it with no include path (knowledge/smith-language.md "The header");
  point the library's own test script at the `.smith` source. Compare the old and new header's declarations and `nm -gU` of an
  object from each: they must match. A module `import`s C headers (`import <string.h>;`), never `#include`s them, has no preprocessor directive and no `c::` name that is a C macro (`smith-preprocessor`: `contract::assert`, `math::max(usize)`, `__builtin_snprintf`), and a flag it needs is `SMITH_LIBRARY_FLAGS` in smith.c, not a `#pragma`, and uses the sized types (`u64`, `usize`, `f64`) and `arena::push(&a, T)` for a typed push.
- **What a port of a C library with system calls (io) needed, and how it was done:**
  - A C macro the module needs (`ENOENT`, `O_CREAT`, `EV_ADD`) is read once into a `constexpr` of the module inside one `// NOLINTBEGIN(smith-preprocessor, bugprone-signed-bitwise)` block, and flags that are OR-ed together are one constant (`open_replace`), since `smith-preprocessor` reports each `c::` macro and `bugprone-signed-bitwise` an OR of named `i32`s. `errno` is `*c::__error()`; a wait status, a file's kind and a `sigset_t` are decoded from their bits (the SDK's macros for them are octal literals, which C2y deprecates, and `<signal.h>`'s are macros); `EV_SET` is a `struct c::kevent` initializer; `dlsym`'s address is copied with `__builtin_memcpy`, not converted to a function pointer (`-Wpedantic`).
  - A name that a C header declares cannot be a local or a parameter even where it is not called (`wait`, `read`, `exit`, `link`, `signal` as a *field* is fine): the error says `write c::name`.
  - An exported struct with an attribute between `struct` and its tag (`struct [[clang::annotate("smith::capability")]] SmithOp {`) keeps its tag as written, so write the C tag there and in its self-references (`struct SmithOp *next`); an opaque exported type is `[[smith::c_name("SmithLoop")]] export typedef struct SmithLoop Loop;` and its body is a private `struct Loop { ... };` later in the module (the private tag lowers to the typedef's C name).
  - An exported enum's constants are written short (`Replace`, C's `SmithWrite_Replace`), which the naming check refuses (it wants `Type_Value`), so the enum sits between `// NOLINTBEGIN(readability-identifier-naming)` and `END` with a blank line after the BEGIN (a comment right above an export is its doc comment).
  - A module has no forward declarations: order private functions so each comes after what it calls (io's scripted network is before the loop that calls it). `_Countof` is C2y; a build that compiles the module as `-std=gnu23` refuses it: write `sizeof a / sizeof a[0]`.
- **`smith::build` is a module with no bodies** (`lib/smith/build.smith`): it declares the build API with module names, each export `[[smith::c_name("smith_x")]]`, defined in C by `runtime/build_runtime.c`. Its generated header IS `include/smith/build.h` (what every build.c includes and smith embeds), so it is in `build_header_modules` but is no library row. Add a call to the API in `lib/smith/build.smith` (with its doc comment above the export, in Smith names: `build::task`) and run `smith build`: the header is made again (no header is committed; build.c itself is compiled with the installed smith's, so it can call the new function only after the next install: the lag rule). A type must come after what it uses (the module has no forward declarations).
- A library smith links itself (arena, contract, format, inflate, io, random) is compiled by the smith that builds smith, so it may use only what that smith compiles (the lag rule, skill smith-dev-build).
- **One header, one writer.** C includers and `import smith::<name>;` both read `.smith/include/smith/<name>.h`, never in git. `smith build` (any smith) writes the embedded source of each `.smith` library to `.smith/lib/smith/<name>.smith` and its header beside it with the same binary, in parallel (`smith_write_lang_headers` in smith.c; the stamp `.smith/include/smith/.written-by` is the binary's size and mtime, so a new binary writes them again and an old one nothing), so a header is always in the format of the smith that reads it; `smith_object` of the library's source (`.smith/lib/smith/...`) adds no header step because of that. In smith's own tree build.c's steps (`build_header_steps`, smith_object's) write them from `lib/smith/*.smith` with the previous release, and smith.c, `-I .smith/include`, waits for them. `tests/library_modes_test.smith` builds a project with `smith_library(b, "text")`, a C file and a `.smith` importer.
- Hand-written headers (`include/smith/{handlers,http,json,trace}.h`) include a generated one as `<smith/arena.h>`, never `"arena.h"`: they are not beside it.
- **After editing a library's `.smith` (a generic above all), run `smith build`, then the test.** The header is made again by the build when its bytes change; nothing else regenerates it, and a test that reads `$SMITH_REPO/.smith/include` needs the build first. A stale header (a `check_equal` on the wrong types, "too many types" at a call) cannot happen now unless the build was skipped.
