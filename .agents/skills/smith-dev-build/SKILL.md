# smith-dev-build

Change smith itself with the rules in [smith-dev](../smith-dev/SKILL.md); what the compiler, linker and caches are is in [one-compiler](../../../knowledge/one-compiler.md); why smith is built this way is in [smith-bootstrap](../../../knowledge/smith-bootstrap.md).

smith builds itself with its own `build.c`, **with the smith before it**: the installed one, or in a clone with no smith the release of the newest ancestor commit. `smith.c` is one C23 file that links clang, lld and the tools from our LLVM, and the libraries it uses (`arena`, `contract`, `inflate`, `random`, `text`) are `.smith` modules that `build.c` compiles to objects with `smith-cc` (the default `CC`); there is no copy of them as C and no build by one `cc` command.

## The lag rule
Code compiled into smith itself (`smith.c`, `runtime/`, `build.c`, those libraries and `lib/trace.c`) can use a language feature or build API call only once it is on main, because the smith that builds your branch is a release of an earlier commit. A branch cannot use, in that code, the feature it adds itself: add the feature, merge it, and use it in the next change. A new library API follows the same rule; `lib/std/format`, `math`, `autodiff`, `test` and `tests/*.smith` are built by the smith under test and use a feature at once. If a build fails on syntax the branch just added, that is the rule.

## From a clone with no smith
`mkdir -p .smith && clang -std=c23 -x c scripts/stage0.c -o .smith/stage0-tool && .smith/stage0-tool` (plain C23, no shell; needs `git`, `curl`, `tar`, the network; no `gh` login, the release is fetched over plain HTTPS): finds the release `stage0-<commit>` of the newest ancestor of HEAD, downloads and checks it into `.smith/stage0/`, and runs its `smith build` with its `bin/` first on `PATH`; pass `smith build` arguments after it (`.smith/stage0-tool install`). It needs LLVM built already: `.smith/stage0/bin/smith build llvm` (about 9 minutes once, into `~/.cache/smith/llvm/23.1.3-r9`). Without it the default target stops and says so; `llvm`, `enzyme` and `clean` still run. `tests/stage0_test.smith` tests the tool with a stand-in `curl`. In a shared container, log to a per-worktree path (`.smith/stage0.log`), not a fixed `/tmp` name; the first build can take about 40 minutes on shared cores (#1216). A clone older than the retained releases pulls main first; `SMITH_STAGE0_RELEASE=<tag>` picks a release.

## Build, test, install
- `smith build` builds `build/<OS>-<arch>/smith` and the `smith-cc` and `smith-c++` links. `CC` is `smith-cc` from `PATH`; `-DCC=<path>/smith-cc` names another smith (an external clang cannot compile the libraries). If the installed smith is broken, use the recovery line below.
- `lib/std/build.smith`, the library sources and `runtime/build_runtime.c` are embedded in smith with `#embed`; the headers of the `.smith` modules are not in git: the smith that builds smith writes them (build.c's header steps, `.smith/include/smith/`), and an installed smith writes them from the embedded sources at first use (about 80 ms). `smith.c` compiles with `-I include -I .smith/include` (`include/` holds only hand-written headers). No task regenerates headers and no check compares them: edit a module, run `smith build`, and its header is made again when its bytes change. `tests/generated_files_test.smith` fails a tracked file with a generator's marker, under `.smith/` or at an ignored path.
- `smith fmt` rewrites every C, C++, Objective-C and `.smith` file git sees except what `.clang-format-ignore` names (the generated parser, the fixtures of the tests). `smith check` is the standard check: fmt (dry run), docs, lint (clang-tidy over the compiles in `.smith/build.info`; `build.c` declares the libraries' and tests' sources with `smith_compile_command`; `shim/.clang-tidy` has the C++ glue's rules), test and prove, each reported, and must exit 0 before you finish. `build.c` is formatted and tidied like the rest, so each of its functions is at most 70 lines.
- Before and after a change, run `smith cc --smith-which -c a.c`, `--smith-which a.metal`, `a.metal b.c` (all after `smith cc`) and `smith version`, and compare. A refactor must not change a route, a message, an exit code or an argv.
- `smith test` runs the routing tests against stub compilers (each through `smith cc` and through `smith-cc`), then the `smith build` tests with a real clang (`tests/build_*_test.smith`); they all run side by side in one runner (skill smith-dev-tests). `tests/compare_test.smith` runs the same invocations through the clang of the LLVM smith links (`SMITH_REAL` names another) and through smith.
- `smith build install` runs the tests, then copies smith and the `smith-cc` and `smith-c++` links to `$PREFIX/bin` (and removes an old `smith++` there) (`-DPREFIX=...`, default `~/.local/bin`); a build uses it when CC names smith. A broken install breaks every build, smith's included. The way back is `.smith/stage0-tool install`. Only CI's `install` job installs, after the release of a push to main; an agent never does (owner, 2026-10-27).
- The heavy verbs draw cores from a pool of the host (`runtime/slots.c`, [slots](../../../knowledge/slots.md)): `smith build`, `check` and `test` take one token at the first heavy step and one more for each further worker (executor job, test runner worker), so a small run does not wait behind big ones; `SMITH_CORES` is the pool's size, `SMITH_SLOTS=0` is for a machine you own alone, and CI sets `SMITH_PRIORITY=ci` to go first and keep most cores.
- `smith build clean` removes `build/`. smith keeps its own files in `.smith/`, outside `build/`, so a project's clean cannot delete them while the build runs (`.smith/stage0/` is the downloaded release).
- A fresh `build/` has no `smith-cc` yet, so its first build leaves out the lint objects of the `*_test.smith` files (they need the smith under test for their headers); the second build adds them.
- `smith build release` (CI only: the `release` job after install) publishes the built smith as the release `stage0-<commit>` (`smith-<os>-<arch>.tar.xz` and `.sha256`) and prunes old ones; `scripts/release.sh` refuses by hand unless HEAD is main's tip. `tests/release_test.smith` tests it with a stub `gh` (publish) and `curl` (fetch). See [release](../../../knowledge/release.md).
- No shell in the build (#291): `smith build friction -Dsince=<date>` prints the `## Friction` sections of merged PRs; the tree-sitter parser is generated by every `smith build` into `tree-sitter/src/` (gitignored), compiled to a shared library and embedded in smith, and `smith build tree-sitter -Dcorpus` also runs the grammar's corpus tests (a CLI pinned per platform, Linux included); Ninja, Z3, Alive2, Bitwuzla and Enzyme are `build_*_make` functions in `build.c` that `smith build llvm` runs, through `build_spawn` (a program, its folder, environment and log, no shell). A new build step is a function there, never a `.sh` file.
- `smith build bench [-Dfull=1] [-Dsmith=<path>]` (#639, `scripts/bench.c`) measures the budget lines of the speed table with the smith this build made (or `-Dsmith`): build with nothing changed, after a one-file change to `runtime/slots.c` (restored), in a fresh `git worktree` of HEAD, `fmt` of the files the last commit changed, `fmt --dry-run`, `lint --changed=HEAD~1`, the whole `lint` and `docs`, a generated 1,000-line `.smith` module's compile (budget TBD), and with the option the full `smith test` (CPU). It prints step, wall s, CPU s (user plus system of the command and its children), budget and ok/over, and the load average (the Mac is shared: read CPU beside wall), and writes `.smith/bench.tsv` (name, wall, cpu, budget, verdict, load). No CI job runs it: run it by hand.
- `smith build ci-times [-Dn=10] [-Devent=pull_request|merge_group|push]` (#360) reports where CI's time goes: it downloads the last n green runs of `ci.yml` with `gh` into `.smith/ci-times/<run id>` (kept) and `scripts/ci_times.c` prints the steps of every job with the runner `queued` wait, the CPU of each part of the test matrix (how balanced the split is) and the tests of 2 CPU seconds or more, from the `test-log-*` artifacts. A run with no test logs (documents only, or the artifacts expired) is counted apart.
