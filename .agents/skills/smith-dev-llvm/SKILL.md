# smith-dev-llvm

What the LLVM build produces is in [llvm-build](../../../knowledge/llvm-build.md), the embedded files in [embedded-files-and-programs-folders](../../../knowledge/embedded-files-and-programs-folders.md) and Enzyme in [autodiff](../../../knowledge/autodiff.md).

- **Enzyme** (`build_enzyme_make` in `build.c`, `smith build enzyme` alone, `smith build llvm` runs it last) builds `libEnzymeStatic-23.a` into `~/.cache/smith/enzyme/<version>-<LLVM name>/lib` from a patched copy of the pinned package (`patches/enzyme/*.patch`, its own folder: `scripts/llvm.sh` applies only `patches/*.patch` to LLVM), against the install's CMake config, without touching the install; the cache survives `smith build clean`. build.c links it when it exists (`-DSMITH_ENZYME`, `-exported_symbol _llvmGetPassPluginInfo`), `shim/lld.cpp` registers it, and `tests/autodiff.sh` (`smith build test-autodiff`) tests it. A new Enzyme version is the pin and the folder's name in build.c. The build runtime's `smith_autodiff_flags` is the one place the autodiff programs' flags (full LTO, no passes, ASan but no UBSan) are decided; the skill is smith-autodiff.
- `scripts/llvm.sh` adds `lib/smith-clang.id` (the LLVM version and a hash of the archives linked; `smith build` compiles it into smith as the identity of its clang, which `--smith-which` prints and projects' objects depend on) and `lib/libclangmain.a` to the install: the four objects of clang's driver (`driver.cpp`, `cc1`, `cc1as`, `cc1gen-reproducer`), which hold `clang_main`. Running it again is cheap. Changing it needs `smith build llvm` again.
- The driver is run as `<folder>/bin/clang` (`-no-canonical-prefixes`, in `shim/clang.cpp`), where `<folder>` is `$XDG_DATA_HOME/smith/clang/llvm-<version>-<key>` (else `~/.local/share/...`), so it finds its builtin headers, compiler-rt and `libLTO.dylib` there, with no flag in the user's command. `scripts/pack.c` packs those files from the install at build time into `build/<OS>-<arch>/clang-resource.pack` (LZFSE, per 4 MB chunk; the format is `scripts/pack.h`), smith.c `#embed`s it (`-DSMITH_CLANG_RESOURCE=`), and the first compile writes the folder (beside it, then one `rename`, so parallel first compiles are safe). The programs are not in that folder: `bin/clang`, `bin/clang++` and `bin/ld` are clones of the running smith (`clonefile`, never hard links: issue #48), in `<data>/smith/programs/<LC_UUID>/bin` (with `lib` a symlink to the runtime folder's, and `-resource-dir` passed by `shim/clang.cpp` so that rpaths name the runtime folder, never the programs folder). Smiths of one runtime key but another binary never share links; a folder idle 31 days, and a half-built one older than an hour, are removed when a new one is made. The driver runs its program again with `-cc1` for a compile with more than one step. The folder is outside the caches `smith cache clean` and pruning touch, because sanitized binaries record an rpath into it; smith never removes it. `bin/ld` is the third link: the driver looks for its linker beside its program before `PATH`, so a link it starts is smith run as `ld`, which calls lld's `lld::macho::link` in that process (`shim/lld.cpp`; `liblldMachO.a` and `liblldCommon.a` of the install). The user's command gets no flag. `SMITH_LINKER=/usr/bin/ld` runs that linker instead, and then the driver is left as Apple's `ld` wants it; with lld, `shim/clang.cpp` adds `-mlinker-version=1115.7.3`, which tells the driver there are no `objc_msgSendClass$` stubs (only Apple's current `ld` writes them), and the user's own flag wins. Never overwrite a smith that is hard-linked in place (`cp` over it kills its next run with signal 9: the kernel keeps the old signature); remove it first, as an install's rename does. `scripts/llvm.sh` hashes lld into the identity. `dsymutil` and the other tools are the system's. `SMITH_CLANG` runs an external clang as before; `compare` checks the full smith against the install's clang binary (its prefix is rewritten to the folder in the text).
- The full smith needs the install only to build: its archives to link, and the resource files to pack. To check it needs nothing at run time, build it against a copy of the install in a scratch folder (`-DLLVM=`), remove the copy, and run the tests under `sandbox-exec` with a profile that denies `~/.cache/smith/llvm` and Homebrew's llvm. `tests/resource_test.smith` tests the folder, the links, the lld link (frameworks, a dylib, ARC, `-dead_strip`, the signature, `SMITH_LINKER`), `-flto`, the sanitizer rpath after `smith cache clean`, and parallel first compiles.
- `smith fmt`, `smith lint` and `smith lsp` (issue #3) run clang-format, clang-tidy and clangd in process, from `shim/format.cpp`, `shim/tidy.cpp` and `shim/clangd.cpp`, one C function each (`shim/tool.h` is what they share). The tools declare their flags in global `llvm::cl::opt` objects, and LLVM aborts at load when two define the same flag (clang-format and clang-tidy both have `-fallback-style`), so `scripts/llvm.sh` makes `libsmithtools.a` (linked whole, first) of patched copies of the tools' objects: their static initializers moved out of `__mod_init_func` (`scripts/defer_init.c`) for the tool that runs to run (`smith_tool_start`), clang-format's `main` renamed, clangd's code actions copied too, and the one call in clangd and in clang-tidy that finds the resource directory by the executable's path redirected to the resource directory of the install's clang (so, until #2, they read it from `SMITH_LLVM_BIN`, as the compiler does). A change to those needs `smith build llvm` again (a few seconds), and `shim/tool.h` is the place to change when #2 moves the resource directory. clangd's XPC transport (`CLANGD_AS_XPC_SERVICE`) is left out and `shim/clangd.cpp` stubs it, because it links Foundation, whose loading cost every smith process, compiles included, about 10 ms; a plain `smith version` is the quick check of startup time (about 8 ms for the smith before #3).
- The unstripped full smith is about 127 MB (`-g`), of which 20 MB is the pack; the first compile writes about 70 MB.
- `smith symbolize` and smith run as `llvm-symbolizer` (`runtime/symbolize.c`, included by smith.c; the lookups are `shim/symbolize.cpp`, which reads the binary's debug map and the object files it names, or a matching dSYM) turn the stack traces of `<smith/trace.h>` (`lib/trace.c`, a library `smith_tests` compiles) into reports. `smith build test` sets `SMITH_SELF` for the build program, pipes the test runner (with `--trace`) through `smith symbolize`, and makes `.smith/bin/llvm-symbolizer` for the sanitizers. The stage0 has no symbolizer (`smith symbolize --available` exits 3), and the tests of reports in `tests/test.sh` skip themselves. Debug a report with `build/tests --test <name> --trace | smith symbolize`.
- **A change to LLVM is a new configuration, never an edit of the one in use.** When a change needs LLVM rebuilt (a new patch in `patches/`, a changed `scripts/llvm.sh`), bump the configuration (`23.1.3-rN` to `-rN+1` in build.c, `scripts/llvm.sh` and the scripts that name it) and build it beside the old one with `smith build llvm`, about 10 minutes and 11 GB. The installed smith and every other worktree keep using the old one until the change merges, so nothing breaks while it builds. Say in your report that you built one, and why.
- **The other LLVM patches, applied after those above (a patch's name sorts it, and it must apply to the sources as the earlier ones left them).** A patch changes the configuration, so it is a new folder (`23.1.3-r6` is the sixth): build it with `smith build llvm` from your branch, and only your branch's `build.c` points at it, never at the shared one that installed smiths link. `patches/smith-editor-defaults.patch`: a fallback style written `file:<path>` in `format::getStyle`, and `clang::clangd::FallbackTidyConfigFile` in `provideClangTidyFiles`; `smith lsp` sets both (`smith_lsp_defaults` in smith.c, `smith_clangd_defaults` in shim/clangd.cpp), tested in `tests/lsp.sh`. `patches/smith-format-source-extension.patch`: `.smith` is a source file in clang-format's main-include rule, so `foo.smith` sorts `foo.h` first as `foo.c` does (`tests/smith_fmt_test.smith`). `patches/smith-command-hook.patch`: `clang::CommandHook`, asked by `createInvocation` (clangd) and `getStripPluginsAdjuster` (clang-tidy), which the shims set to `smith_lang_command` (shim/tool.h); `build.c` treats an install without it (`CLANG_HAS_COMMAND_HOOK`) as not linkable. `patches/clang-constexpr-c.patch` (#97): `LangOptions::SmithConstexprC`, set by `makeHook` in shim/hook.cpp for a `.smith` main file, and the gate `SmithCEval` in `ExprConstant.cpp` (a constant context that is not quiet folding); test: `tests/smith_lang_c_test.smith`. `patches/clang-constexpr-fold.patch` (#166, r7, sorts after it): `Sema::VerifyIntegerConstantExpression`, past its check of a caller that forbids folding (a block-scope array bound stays a VLA), returns an evaluation with no notes without `-Wgnu-folding-constant` when `SmithConstexprC` is on and it holds a call or an element of a `constexpr` array (`SmithFoldsLikeConstexpr`: other GNU folding keeps its warning, as in C) (corpus `constexpr-c-pedantic`). `patches/smith-lang-format-enum.patch` (#215, LLVM r8, applies last to the Format files): a payload enum (a `;` between its braces) is parsed like a struct (`isSmithPayloadEnum`), and a `.` after `case`, `return`, `==`, `!=`, `=`, `?`, `&&` or `||` has an operand's space; `tests/smith-fmt/payload_enum.smith`. `patches/clang-plugin-attr-args.patch` (#207, LLVM r9): `hasAttribute` also asks a plugin by `scope::name`, so the parser reads the arguments of `[[smith::effects(...)]]` (it skipped them for an attribute it did not know without plugins), and a plugin that sets `ParsedAttrInfo::HasVariadicIdentifierArg` gets bare identifiers as arguments (`alloc, net`); test `tests/effects/effects_args.c`.
- **lldb formatters** (`shim/lldb_slices.cpp`, `T xs[:]`) use lldb's internal C++ classes through the installed headers (`lldb/DataFormatters/*`), as lldb's own `std::span` provider does (its source is in `~/.cache/smith/llvm/<name>/src/lldb/source/Plugins/Language/CPlusPlus/`, read it for the pattern); the install lacks `FormatterBytecode.def`, so `shim/lldb/FormatterBytecode.def` is a copy of LLVM's, found by `-isystem shim/lldb`. A new LLVM may change those classes' signatures. Register them after `smith_tool_start`.
