# Build with smith build

`build.c` describes the build in C, explicitly and with no defaults. `smith build` compiles it, runs it, and runs the manifest it writes (a ninja-language file) with its own executor; no ninja is needed. The API is `.smith/include/smith/build.h` and its implementation is `.smith/runtime.c`. Every `smith build` writes both, and they match the installed smith exactly, so read them first. The source's home is https://github.com/smith-ai-lab/smith (`include/smith/build.h`, `runtime/build_runtime.c`), and the design and its reasons are in `docs/build-c.md` there. The repository is private, so read it with `gh`, for example `gh api repos/smith-ai-lab/smith/contents/knowledge/build-file.md -H 'Accept: application/vnd.github.raw'`.

## No build file: the conventions

A folder with no `build.c` and a `main.smith` or `main.c` at its root builds, runs and tests with no build file: `smith build`, `run`, `test`, `lint`, `prove` and `check` run an embedded build program (`.smith/conventions.c`) that is nothing but `smith_app(b, &(SmithApp){}); smith_app_tests(b, &(SmithAppTests){});`. Read this first in any project that has neither file; do not write a build.c unless the conventions fall short.

- **The program:** `main.smith` or `main.c` (both is an error), named after the folder, built to `build/debug/<name>` (the default: `-g -O0`, address and undefined sanitizers), `build/release/<name>` (`smith build release`: `-O2`) and `build/fast/<name>` (`smith build fast`: `-O2 -DNDEBUG`; contracts and bounds checks still run in all three). `release` and `fast` compile and link with ThinLTO (`-flto=thin`: inlining across files, no unity files). Every profile has `-std=gnu2y` with the warnings and `-Werror`, `-ffp-contract=off`, `-mcpu=apple-m1` on Apple silicon, and Clang modules.
- **What is compiled is what `main` reaches.** `.smith`: every `import a::b;` is found at `a/b.smith` and followed transitively; a module nothing imports is not compiled. C and Objective-C: every quoted `#include "foo.h"` (or `#import`) is followed to the `foo.c` (else `foo.m`) beside the header, transitively (the including file's folder, then the root, then the folders of the `-I` and `-iquote` flags of `build::defaults` and `.flags`). The scan is lexical: a conditional include is followed anyway, an include built by a macro is missed, and a `.c` file that no header names is not compiled. When a source is missed, write a build file (below) or rename to `.smith`.
- **A program that reaches `smith::autodiff`** (Enzyme's derivatives, the smith-autodiff skill) is built in every profile with full LTO instead of ThinLTO, each file compiled with `-Xclang -disable-llvm-passes`, AddressSanitizer (run after Enzyme) but no UBSan in debug, and its objects in `build/<profile>/autodiff/`; every other program is built as described here.
- **smith's libraries need no declaration:** `#include <smith/text.h>` (or `import <smith/text.h>;`), or `import smith::text;`, compiles and links that library and what it needs.
- **Tests:** every `*_test.smith` and `*_test.c` file below the root (beside the module it tests, or in `tests/` for integration tests), built with the debug flags and linked with the code they reach (what they include or import) and with the helpers, the other `.c` files directly in `tests/`; `smith test` runs them (the smith-test skill).
- **Several programs, shared settings** (all in `build.smith`/`build.c`): one `build::app` per program (`.entry` names each; `.tool = true` for one `smith build` does not build by default: `smith build tools`, `release`, `fast`, or its file `build/debug/<name>` build it); a source or library two programs share is compiled once per profile. `build::defaults(b, &(build::Defaults){.flags, .folder_flags, .link_flags})`, called first, gives every compile and link the project's flags, and `{"src/base", flags, inputs}` rows give the sources below a folder their flags and the files their compiles wait for (a baked table they embed) (smith's libraries are `.smith/lib`). For a low-level step that starts from the conventions: `build::profile_flags(b, "debug")`, `build::profile_link_flags`, `build::source_flags(b, "debug", source)`, `build::sources(b, "src/base")`, `build::objects(b, "debug", "src/base")` (the objects are `build/<profile>/<source without extension>.o`). Two programs compiling one source with different flags is an error; put the flags in `build::defaults`. `docs/build-c.md` "Several programs".
- **No packages.** `smith_package` needs a build file.
- **A folder with neither** (say a Makefile and no main) is an error that says what smith looked for. `CC = smith-cc` in the Makefile builds it unchanged; a `build.c` replaces it (below).
- **A failed step** prints `FAILED:` with its command and at most 30 lines of what it printed from the first error, then `smith: N more lines of this output; the full output is in .smith/log/<output path, / as _>.log`; `smith build -v` prints it whole.
- **Making it explicit:** `smith build --dump-config > build.smith` (a `main.smith` project) or `> build.c` (a `main.c` one) prints the build file that does exactly what the conventions do, in the highest-level API, with the defaults as fields (`.entry`, `.name`, the tests' `.folder`); building with it gives the same commands as with no file. On a project that already has a build file it says so on stderr, prints nothing and exits 0. Or write a `build.c` with the two calls above (the fields are `.entry`, `.name`, `.flags`, `.link_flags`, `.libraries` for the program and `.folder` for the tests; `docs/build-c.md` shows each call's expansion into `smith_object`, `smith_program`, `smith_tests`), then replace a call with its expansion where you need control. `smith_app` makes the profiles, the aliases `release` and `fast` and the default, so a build.c that calls it declares no `smith_default` of its own; call `smith_compile_commands` after it if another tool wants a root `compile_commands.json` (the editor and the verbs read `.smith/compile_commands.json`).

## Run it

- `smith build` builds the defaults. `smith build <name>...` builds those targets or runs those tasks. Run it from the folder that holds `build.c`.
- **The verbs read what build.c declares; they are not tasks.** `smith run` runs the one program `smith_default` names, `smith test` runs what `smith_tests` declares, `smith lint` acts on the sources `smith_object` (and `smith_compile_command`) compile, with their flags, and `smith prove` on the C sources of each `smith_program`, and `smith fmt`, `smith docs` and `smith check` need nothing from build.c. So a build.c writes no task for them, and `smith_task` and `smith_alias` refuse the names `fmt`, `lint`, `docs`, `prove`, `check`, `run` and `test`; anything of your own is a task with another name, run with `smith build <task>`. `-D` options work on a verb as on `smith build`; every other argument is the verb's (`--` ends the `-D` options, so `smith run -- -Dx` passes `-Dx` to the program; the test runner's reach build.c as `smith_args(b)`). `smith build run` and the other verb names are refused, so there is one way to run each. Every run of build.c writes `.smith/build.info` and `.smith/compile_commands.json` for the verbs, and the manifest has the targets `smith_needs` and `smith_tests` ([build-file](../../../knowledge/build-file.md)).
- `-Dname` and `-Dname=value` set build.c's options for this call only. An option build.c does not declare is an error that lists the declared ones.
- Every other argument is the executor's, and works as ninja's did: `-j N` (default: cores + 2), `-n`, `-v`, `-k N` (keep going until N jobs fail; `-k 0` never stops), `--quiet`, and `-t <tool>`: `targets [all]`, `clean [-g] [targets]` (removes every declared output), `compdb [rules]` (prints compile commands), `commands <targets>`, `deps [targets]` (what each output read last time), `cleandead`. `-d explain` says why each step is dirty. `-f` and `-C` are refused; `-l`, `-w` and other `-d` modes are ignored. A job prints its output whole when it ends, Ctrl-C stops the jobs and exits 130.
- Each call compiles `build.c` into `.smith/program` when build.c, a file it includes or smith changed, runs it, which writes `.smith/build.ninja` when its bytes changed, and then runs that manifest. So globs, environment variables and options are read fresh every time. A no-op takes a few milliseconds.
- `.smith/` is smith's own folder and ignores itself in git. Never edit it. `rm -rf .smith` is always safe; the next build recompiles build.c and reruns every step.
- **Cores.** `smith build`, `smith test` and `smith check` draw from a pool of core tokens shared by every smith on the machine (`SMITH_CORES` tokens, default the core count; its folder is `$SMITH_SLOTS_DIR`, else `/tmp/smith-slots-<uid>`, never `$TMPDIR`, which differs between a shell and a service): one token when they start their first compile, link or test (an up-to-date build waits for nothing), one more for each further worker, given back as it ends, so a one-test run takes one core and a full run grows as cores free up. `smith: waiting for a core (n of m held: ...)` means the others hold them all: wait, do not start the job another way. A smith that a smith runs rides on its parent's token. `SMITH_CORES=n` sets the size, `SMITH_SLOTS=0` turns the limit off, `SMITH_PRIORITY=ci` makes a waiting job go first and leaves CI most cores; a CI run (or `SMITH_SLOTS_LOG=1`) ends with a `smith: pool:` line: its wait for the base core, its workers and the attempts that found no core; a holder that died or lost its parent loses its tokens. [slots](../../../knowledge/slots.md)
- **Compiles are cached** across folders and builds in `~/.cache/smith/steps` (`$XDG_CACHE_HOME/smith/steps`): a compile whose command, compiler, environment and inputs were seen before is cloned from the cache, not run, and `smith build` shows `(cached)` after it. `release` and `fast` objects are shared by every folder; a debug (`-g`) object names the folder it was compiled in, so it is shared by builds in that folder only. A compile that printed a warning is never cached. `SMITH_STEP_CACHE=0` turns it off; `smith cache clean steps` empties it.
- `SMITH_VERBOSE=1` prints the commands smith runs. `SMITH_NINJA=<path to ninja>` runs the manifest with that ninja instead of smith's executor (a fallback; ninja keeps its own logs, so each tool rebuilds what the other never built).

## Start a project

- `smith new [--language smith|c] [<name>]` (`smith` is the default; with no name, the current folder) creates a project that builds by convention, so it has **no build file, no `.clang-format`, no `.clang-tidy` and no root `compile_commands.json`**: smith's defaults cover them. A `.smith` project has `main.smith`, the module `primes.smith` (no header) and `tests/test_primes.smith`; with `--language c`, `main.c`, `primes.c`, `primes.h` and `tests/test_primes.c`. Both have `.gitignore` and what agents need: `.claude/settings.json`, which enables the smith plugin (it carries these skills), `knowledge/` with a first concept, the project's own skill `.agents/skills/<name>-docs`, the `.claude/skills` link, all checked by `smith docs` (which `smith check` runs: see `smith-docs`). It then builds once and commits on `main`. It never overwrites: a file that exists is kept, and a folder with a `main`, a build file or a Makefile, a `CMakeLists.txt` keeps its own program (beside another build system it also does not build). Any other value of `--language` is an error naming both. `smith new --help` shows the usage.
- The project builds three ways, each into `build/<name>/<project>`: `smith build` is debug (`-O0`, sanitizers), `smith build release` is `-O2`, and `smith build fast` is `-O2 -DNDEBUG`; every profile keeps the contracts and bounds checks (only `smith prove` removes one). Its sources are C2y (`-std=gnu2y`, for `_Countof`), a draft standard that Apple clang and upstream clang 21 or later accept.
- To change a default, make it the project's first: `smith fmt --dump-config > .clang-format`, `smith lint --dump-config > .clang-tidy`, `smith build --dump-config > build.smith` (or `build.c` in a C project). Nothing changes until the file is edited.

## When something goes wrong

- `smith: build.c: <step or task>: <message>` is a mistake in build.c. Fix build.c.
- A compiler error in build.c means build.c does not compile; the failed step prints clang's message.
- `smith: error: ...` is the executor's own, for example an input that no step makes and that does not exist, a dependency cycle, or a manifest it cannot read.
- `smith: no build.c in this folder, and no main.smith or main.c to build by convention`: run from the project's root, add a `main.smith` or `main.c`, or write a build.c. `smith: cannot find ninja` appears only with `SMITH_NINJA` set to something that is not ninja.
- If smith build itself seems wrong, or smith is missing or broken, stop. Run the command again with `SMITH_VERBOSE=1` and report it to the owner. Do not work around it.
