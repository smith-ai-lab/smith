# smith check, fmt, lint and lsp

This skill ships in the smith plugin, from `.agents/skills/smith-check/SKILL.md` in https://github.com/adam-r-kowalski/smith. Change it there.

`smith fmt`, `smith lint` and `smith lsp` are clang-format, clang-tidy and clangd, linked into smith from the same LLVM as the compiler, so every machine formats and lints alike.

## On the project: no arguments

The verbs mean the same in every project and read what its `build.c` declares; a project writes no task for them.
- `smith fmt` rewrites every C, C++, Objective-C and `.smith` file git sees (tracked, and untracked but not ignored; `.c .h .m .mm .cpp .cc .cxx .hpp .hh .smith .metal`) to `.clang-format` (a `.metal` file is formatted as C++, the language clang-format gives an extension it does not know). `smith fmt --dry-run` (or `-n`, with `--Werror` or `-i`) and `smith lint --quiet` are the project forms too: options alone, no file names, so they never wait for standard input; any other option, or a file name, makes them the tools (`smith fmt --assume-filename=x.c` reads standard input). A file named in `.clang-format-ignore` (clang-format reads it itself: a generated `parser.c`, a fixture) is left alone. Outside a git repository it says to name the files (`smith fmt -i <files>`).
- `smith lint` builds what the compiles read (generated headers), then runs clang-tidy with `.clang-tidy` on the project's own sources among the build's compiles (`smith_object`, and `smith_compile_command` for sources the build never compiles), side by side. Not `.smith/`, `build/` outputs or packages, and not `.smith` sources. A `.clang-tidy` in a folder (such as `InheritParentConfig: true` with other checks) applies there.
- `smith docs` checks AGENTS.md, `knowledge/` and the skills (`smith-docs`).
- `smith check` runs fmt (clang-format's dry run), docs, lint, test and prove, in that order, and does not stop at a failure: each part prints `smith check: <part> ok` or `FAILED (status N)` after its own output, and the last line is `smith check: ok` or `smith check: failed: <parts>`; the exit status is 1 when any failed. It takes no arguments but `-D` options.
- Before committing: `smith fmt`, then `smith check`.
- A task of your own (a custom check, a generator) is `smith_task` in build.c and runs with `smith build <task>`; no task or alias may be named `fmt`, `lint`, `docs`, `prove`, `check`, `run` or `test`. `smith build check` and the other verb names are refused: use the verb.

## On files: with arguments

clang-tidy's analyzer (`clang-analyzer-*`) reads `smith_requires`, `smith_ensures`, `smith_invariant` and `smith_assert` of `<smith/contract.h>` as assumptions (`target::static_analyzer`), so an index a contract bounds is not reported by `clang-analyzer-security.ArrayBound`.

smith's default `.clang-tidy` turns off two analyzer checks that were noise (on game, learner and smith: 546 of 616 findings): `clang-analyzer-security.insecureAPI.DeprecatedOrUnsafeBufferHandling` (every `memcpy`) and `clang-analyzer-optin.performance.Padding`. Turn one back on in the project's own `.clang-tidy` (`smith lint --dump-config > .clang-tidy` writes the effective file) by deleting its `-clang-analyzer-...` line.

With arguments they are the tools, unchanged: `smith fmt -i main.c`, `smith fmt --dry-run --Werror main.c`, `smith lint --quiet main.c -- <flags>`, `smith lsp --check=main.c`. A project's `.clang-format` and `.clang-tidy` apply. A stage0 smith runs Homebrew's tools, or `$SMITH_CLANG_FORMAT`, `$SMITH_CLANG_TIDY`, `$SMITH_CLANGD`.

**smith's defaults, where a project has no file** (issue #43). A project with no `.clang-format` (or `_clang-format`) and no `.clang-tidy`, looked up from each file's folder and up as clang-format and clang-tidy do, is formatted and linted with smith's own, embedded in smith (the files `smith new` writes today); there is nothing to write. A file in the project replaces smith's whole, never merged, and an explicit `--style` (or `--fallback-style`), `--config` or `--config-file` wins. With standard input, `--assume-filename` names where to look. Naming files with and without a project file in one command works (smith runs the second kind as another process). `smith fmt --dump-config > .clang-format` and `smith lint --dump-config > .clang-tidy` print the effective one (the project's, else smith's), so a project takes the defaults over by dumping them and edits what it wants; the defaults change rarely and on purpose, so a project that wants them fixed dumps them. smith writes its copy to `$XDG_DATA_HOME/smith/defaults/` (else `~/.local/share/...`). `smith cc` is never affected: it stays a pure passthrough.

## smith-effects

smith's default `.clang-tidy` lists the check `smith-effects` beside bugprone, misc-no-recursion, readability-function-size and readability-identifier-naming: a program may touch the world only through capabilities (`io::Io` and its parts) that `main` passes down, so `printf`, `fopen`, `time`, `malloc` and the like are reported with the capability to take instead (`io::Console *`, `io::Files *`, `io::Clock *`, `arena::Arena *`; `SmithConsole *` and the like in C). `smith lint` and the editor both run it, on `.smith` files with names as written (`c::fopen`). `smith lint --dump-config > .clang-tidy` shows it; a project that does not want it deletes it from `Checks`, and `smith-effects.CFiles: false` makes it read `.smith` files only. The rules, how to mark a project's own capability and how to fix each finding are in [smith-io](../smith-io/SKILL.md).

## smith-preprocessor

smith's default `.clang-tidy` also lists `smith-preprocessor`: **a `.smith` file has no preprocessor.** In a `.smith` file it reports every directive (`#define`, `#undef`, `#include`, `#if` and its kin, `#pragma`, `#error`, `#warning`, `#line`, `#embed`) and `_Pragma`, and every `c::` name that is a C macro, each with what to write instead: `#include` becomes `import`, `#define` of a constant `constexpr`, `#if` `if constexpr` with `target::`, `#pragma` a flag the library declares, `#error` `static_assert(false, ...)`; `c::assert` becomes `contract::assert`, `c::isfinite` `math::is_finite`, `c::SIZE_MAX` `math::max(usize)`, `c::INFINITY` and `c::NAN` `math::infinity(f64)` and `math::nan(f32)`; any other macro is the module that wraps the C API's to provide (`smith-lang-c-interop`). A `.c` file is left alone. The directives are read from the file's text, so those in a branch the compiler did not take count, and the `c::` names are the macros the file's imports defined (the lowering's own test, so `c::memset` is a macro in a fortified SDK: write `__builtin_memset`). The editor shows it too. A line that must keep one says `// NOLINT(smith-preprocessor)` (or `NOLINTBEGIN`/`NOLINTEND`); deleting `smith-preprocessor` from `Checks` opts a project out.

## The idiom checks

smith's default `.clang-tidy` lists five more `smith-*` checks (issue #47), each message naming the fix; the editor shows them too. They are how `smith check` steers a first draft to idiomatic Smith ([smith-idiom](../smith-idiom/SKILL.md) has the rules and a port):

| Check | Files | Reports | Says |
|---|---|---|---|
| `smith-sized-types` | `.smith` | `uint8_t` to `uint64_t`, `int8_t` to `int64_t`, `size_t`, `ptrdiff_t`, `float`, `double`, `unsigned`, `long`, `short`, `signed` and `int` (not `char`; `main` too: `i32 main(i32 argc, char *argv[])`; a renamed `int main(int argc, char **argv)` compiles and is reported) | the sized type: ``write `u64` `` |
| `smith-module-library` | `.smith` | a library that is a module, used through its C header: `import <smith/arena.h>;`, `c::smith_arena_push(...)`, `c::SmithArena` (the generated header's `// smith-module:` line says it is one) | `import smith::arena;` and the module's name, `arena::push_raw`, `arena::Arena` |
| `smith-bounded-loop` | `.smith` and C | a loop with no condition or a constant one (`for (;;)`, `while (true)`, `do ... while (1)`) outside `main` | bound it by a count; only `main` runs forever |
| `smith-c23` | `.smith` and C | `NULL`, `_Bool`, `_Noreturn`, `_Static_assert`, `_Alignas`, `_Alignof`, `<stdbool.h>`, `{0}` as an initializer of a struct or array, and `__attribute__((noreturn))`, `unused`, `warn_unused_result`, `deprecated`, `fallthrough` | `nullptr`, `bool`, `{}`, `[[noreturn]]`, `[[maybe_unused]]`, `[[nodiscard]]` |
| `smith-constexpr` | `.smith` and C | a file-scope `const` object (arithmetic, enum, or an array or struct of them; not a float, a pointer or an external one in C) with a constant initializer | `constexpr` |

One more is off by default, because it is a style a project chooses (`Checks: smith-designated-init` turns it on): `smith-designated-init` (`.smith`) reports a positional initializer of two or more values for a struct that another file defines (`(text::Text){bytes, length}`, `{"src/base", fast}` for a `build::Folder`), which breaks, or shifts its values, when that struct gains a field. It says to name the fields: ``{.path = "src/base", .fast = fast}``. A struct the file defines itself, a system header's and a one-value initializer are left alone.

`// NOLINT(smith-c23)` (or `NOLINTBEGIN`/`NOLINTEND`) opts a line out, and deleting a check from `Checks` opts a project out. The C checks read C files and `.smith`, never C++.

## `.smith` files

`smith fmt x.smith` (and `-i`, `--dry-run`, standard input with `--assume-filename=x.smith`) formats a `.smith` file as C, with its `::` paths, `module a::b;` and `import a::b as x;` lines and `import <sys/wait.h>;` kept whole; `smith fmt` with no arguments formats the project's `.smith` files too (git sees them). `import` and `module` inside a function are names, as in C. Needs a smith whose clang-format has the `.smith` patch (a stage0 runs Homebrew's, which reads `.smith` as C++ and so misreads C names that are C++ keywords, such as `throw`). clangd formats `.smith` files the same way.

`smith lint x.smith -- <flags>` (clang-tidy, with the project's `.clang-tidy`) lints a `.smith` file as `smith cc` reads it (`-x c`, and `-std=gnu2y` unless you name a standard; a compile database's own command is used as it is) and reports as the source is written: findings, notes and fix-its at the lines and columns of the `.smith` text, with the names as written (`area` and `Box` in the module, `box::area` where it is imported, never `geometry_box_area`). `readability-identifier-naming` judges the written name of a module's file-scope names, so the template's rules (snake_case functions and variables, PascalCase types) apply to `area` and `Box`, and `--fix` rewrites the token in the source; the sized types (`u32`, `i32`), the lowering's copies of prototypes and the headers `smith build` writes are never reported. A finding about an export is reported in the module's file, not in each importer, and a fix there does not rename the importers. Other checks show the written names in their messages, but a check that compares the name itself (a length or a reserved-name check, say) still reads the lowered one. Needs a smith whose clang has the token hook (`smith cc --smith-which x.smith` says `token-hook yes`); a stage0 runs Homebrew's clang-tidy, which cannot read `.smith`.

## The editor

- Point clangd at the command `smith lsp`, with no `--query-driver` (with it clangd cannot build the SDK's modules). It reads the project's `compile_commands.json`, which `smith build` writes, whose commands name `smith-cc`.
- **No root `compile_commands.json` needed.** When the current folder, or one above it, has `.smith/compile_commands.json` (which `smith build` writes) and neither it nor its `build/` has a `compile_commands.json`, `smith lsp` adds `--compile-commands-dir=<that folder>/.smith`, so clangd uses it; a root file, or your own `--compile-commands-dir`, wins. Start the editor's clangd in the project folder. **The editor has smith's defaults too.** In a project with no `.clang-format`, the editor's formatting (`textDocument/formatting`, range formatting, include insertion) uses smith's style, and with no `.clang-tidy`, clangd's built-in clang-tidy runs smith's checks and shows the findings as diagnostics (the slow checks clangd leaves out for every project stay out). A project's file replaces smith's whole, and clangd's own `--fallback-style` wins over smith's style. A smith without clang inside (the stage0) runs Homebrew's clangd, which has neither; `smith fmt --dump-config > .clang-format` gives the editor smith's style there.
- VS Code: `"clangd.path": "smith", "clangd.arguments": ["lsp"]`. Neovim: the plugin below, or `vim.lsp.config('clangd', { cmd = { 'smith', 'lsp' } })`. Helix: `command = "smith"`, `args = ["lsp"]`. Zed: `"lsp": {"clangd": {"binary": {"path": "smith", "arguments": ["lsp"]}}}`. Emacs eglot: `("smith" "lsp")` for c-mode, c++-mode, objc-mode.
- Neovim 0.12 with smith's plugin: `vim.pack.add({ "git@github.com:adam-r-kowalski/smith" })` (HTTPS once public), then `vim.lsp.enable("smith")`. The repository root holds `plugin/smith.lua`, which registers the `.smith` file type, compiles the tree-sitter parser on first use with `smith cc -shared` (highlighting of `module`, `import`, `export` and `a::b` paths, with C's own highlights, folds and indents inherited), defines the `smith` LSP config (`smith lsp` for c, cpp, objc, objcpp and smith; root markers `build.c`, `build.smith`, `main.smith`, `main.c`, `compile_commands.json` and `.git`), registers a `smith` nvim-dap adapter (`smith dap`) when nvim-dap is installed, and warns once when its commit differs from the one `smith version` prints. It enables nothing and replaces no setting of yours. `smith fmt` formats `.smith` files (below). The language server for them is below. See docs/neovim.md.
- Claude Code: the smith plugin declares `smith lsp` for `.c`, `.h`, `.m`, `.mm`, `.cpp`, `.cc`, `.hpp` and `.smith`, so an agent gets definitions, references, symbols and diagnostics after each edit. `smith` must be on the PATH of the shell that starts Claude Code; disable the official `clangd-lsp` plugin if both are on.
- **`.smith` files** work in `smith lsp` as C files do, in any editor: the hook that lowers `.smith` runs in clangd's own parses (the open file, the preamble, the background index), so positions are those of the text as written. What works: diagnostics, including the lowering's own (``printf` is a C name; write `c::printf``) and clang's, at the line and column of the .smith source; hover; go-to-definition and references across modules (from `box::area(b)` to its definition in `geometry/box.smith`, once the background index has the module; before that the answer is the generated header `.smith/include/geometry/box.h`); document symbols; completion of the name being typed. Names are the ones written: `box::area` in an importing file, `area` in the module itself, in hover, symbols, completion, signature help and clang's messages (also in `smith cc`), and `box::` offers the module's exports, inserted after the typed `box::`; a layer between the editor and clangd does it (`SMITH_LSP_RAW=1` turns it off and shows the compiler's `geometry_box_area`), and leaves the generated headers out of references and renames. A "did you mean" note is at the declaration in the module's `.smith`. What does not work: a rename of an exported name edits only what clangd's index knows (the importers it has seen); hover in an importer shows the declaration as the header gives it (`int32_t`, not the module's `i32`; the symbol's `asm(...)` label is left out); completion offers `#include` edits for C names. **What the editor needs.** Nothing for a single file or a few modules in one folder: with no `build.c` and no `compile_commands.json`, every command clangd uses for a `.smith` file (the fallback, a hand-written database, a command borrowed from a `.c` entry) gets what `smith cc` gives it, `-x c` and `-std=gnu2y` unless the command names a standard, and `import foo` is found by `foo.smith` beside the importing file, as `smith cc main.smith foo.smith` finds it; so what `smith cc` accepts, the editor accepts, with go-to-definition from `foo::f` into `foo.smith`. For a real project, the `compile_commands.json` that its `build.c` writes (`smith build` writes it, with `-x c -std=gnu2y` for `.smith` sources): the flags and include paths of the build, and a new file is read with the command of a similar one until the next `smith build`. In a project the modules' headers (`.smith/include`) must have been built once by `smith build`, or `import` reports that it cannot find the module. Only one `.smith` file is lowered at a time in a clangd, so a project of many modules opens a little slower than the same in C.
- clangd keeps its index in `.cache/clangd`; "Error while reading shard" once after a Homebrew clangd is harmless (delete the folder to start clean).
