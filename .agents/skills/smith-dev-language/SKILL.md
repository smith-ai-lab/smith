# smith-dev-language

The language is in [smith-language](../../../knowledge/smith-language.md), its lowering in [smith-lowering-internals](../../../knowledge/smith-lowering-internals.md); the plugin's smith-lang skills teach it.

- `patches/clang-format-smith.patch` (issue #25) makes clang-format read a `.smith` file as C plus `::` and the file-scope `module`/`import` lines (`Format.cpp`, `UnwrappedLineParser`, `TokenAnnotator`); `tests/smith_fmt_test.smith` tests it (the corpus formatted to the golden file `tests/smith-fmt/corpus.expected`, `smith test --update` rewrites it; every `.c` of smith and the test beds the same as `.c` and `.smith`; `throw` and `import`; `smith fmt` with no arguments in a scratch project). `scripts/llvm.sh` applies every `patches/*.patch` and keeps the applied copies in `$cache/src/.patches/`: a patch that changed is taken out (with the ones after it) and put back, so a rebuild is incremental. To iterate on a Format patch, edit the cache sources and `ninja -C ~/.cache/smith/llvm/23.1.3-r9/build clang-format` (seconds), then turn the edit into the patch.
- The clang side is `patches/clang-token-hook.patch` (the `Preprocessor`'s `TokenHook`), applied to the LLVM sources by `scripts/llvm.sh` in its marked step, and `shim/hook.cpp`. The lowering is plain C in `runtime/lang*.c` (`runtime/lang.h` is its whole interface), so changing it does not rebuild LLVM; changing the patch does. `build.c` builds the hook only when the install's headers have it (`setHookMode`).
- `tests/smith_lang_test.smith` runs the corpus in `tests/smith-lang/cases` (one test per case, `corpus_case(io, "name")`: the build, the errors the compile reports, the output, the symbols and the generic instances; the expectations are golden files, `smith test --update` rewrites the ones a case holds, and writes everything for a case with no `expect` folder: read the diff), and `tests/smith_lang_c_test.smith` compiles smith's own sources as `.c` and as `.smith` and compares the code, then builds and runs the programs of `tests/smith-lang-c/` both ways (the C rule, [smith-language](../../../knowledge/smith-language.md): add a program there for each construct whose meaning a feature could touch). A new case needs its test: `test_every_case_has_a_test` names it. The text the raw lowering gives is checked in process, not by the case's build: `tests/smith_lang_lowering_test.smith` reads every case's `src/` through `smith_core_lower` and `smith_core_header` (`include/smith_core.h`) and compares `expect/lowered/`, `expect/header/` and `expect/lower-error` (four shards, 3 s for the corpus), so a case needs no test there; a header that needs the compiler's answer (several C imports; the function does not ask) is in `header_by_command` in both tests and checked by `smith_lang_test.smith` through `smith cc --smith-header`. The lowering is safe to run twice in a process because `smith_lang_reset` (`runtime/lang_lex.c`) puts back its counters and caches: state a lowering keeps in the process is reset there (a new counter or cache goes in it), and `test_lowering_twice_is_the_same` lowers the corpus both ways round.
- `smith cc --smith-lower x.smith` prints the lowering of the text as written, `smith cc --smith-header x.smith -o x.h` a module's header (the helpers are under `smith cc`; the top level is only verbs). `smith build` runs the header steps itself (`smith_object` of a `.smith` source, `runtime/build_runtime.c`, "`.smith` sources" in knowledge/build-file.md); `tests/build_tail_test.smith` tests it. `SMITH_LANG_ASK=Name,struct Tag` prints what the parser answers about those types at the end of a file (`?const char *` asks about a type written as tokens, the question generics use). `!expr` asks `value_query` and prints the value tree (`!grid.cells`, `!f(3)`; no commas in it).
- Cost: a plain `.smith` file must compile as fast as the `.c` (the host is offered only watched identifiers). Compare with alternating runs, at least 20 each, and note the load.
- **What the hook offers the lowering:** identifiers it watches, and braces or every token only in the modes that ask for them. Keywords (`if`, `else`, `constexpr`) are never offered as such, and the hook's fast path handles file-scope keywords without calling the lowering; a feature that must see a keyword asks for every token in the file (as `if constexpr` does for a file whose text has it).
- **`smith_lang_keep_aside` holds one saved state:** reading another module's interface while one is set aside corrupts the caller. Read imported modules first (`smith_raw_prefetch`), never nested.
- **A smith-lang corpus case is read by three tests:** after adding or changing one, add its `corpus_case` test to `tests/smith_lang_test.smith`, run `smith test --update` with the smith under test, or `--test smith_lang_test` and then `--test smith_fmt_test` (both golden files: read the diffs), and run `test-tree_sitter`: the editor's grammar must parse every case, so new syntax may need `tree-sitter/grammar.js` (then `smith build tree-sitter -Dcorpus`).
- **Generics today:** an instance is compiled where it is called, outside its module's file, but effect inference attributes it to the generic's module; an exported generic's body names only exports; an instance's tokens begin the lines the generic's did (a braceless `if` in a generic is fine under `-Wmisleading-indentation`), and the call as written begins its line when its first token did (`SmithLangCallFrame.start_line`, #787: `if (x) continue;` then `test::check_less(a, b);`). An exported enum's constants are `<CType>_<Value>` in C (`SmithTestKind_Equal`), passing C's `Type_Value` naming rule, when the enum has a C name (`[[std::c_name]]` or a tag).
- **The raw lowering (`--smith-lower`, the header pass) writes a generic's types out** (`arena::push(arena, F64)`; the raw `push_array_raw(arena, sizeof(F64), n, alignof(F64))` for a size): the header pass and `--smith-lower` have no parser, so they cannot type an argument (a module that goes through it calls no `auto` function: random calls the builtins), and the error ("the raw lowering has no compiler to type it") means exactly that.
- **Two white-box tests include a module's raw lowering** (`tests/random.c`, `tests/prove/sound/smith_*.c`; their scripts write it with `smith cc --smith-lower`), so a change to what a module imports can break a test's compile: run `smith lint`, which compiles them.
- **Where a new kind of compile-time parameter goes** (`constexpr Type T`, `auto x`, `constexpr auto f`, `auto... rest` are the four): `runtime/lang_generic.c` is in the sections its `// ----` headings name, and a kind touches these, in this order. (1) `SmithLangSlot` in `runtime/lang.c` and `smith_lang_param_is_*` plus `smith_lang_generic_params` (the classification, "Seeing that a declaration is generic"). (2) `smith_lang_generic_scan` ("Recording the definition": it fills `type_kind[]`, `type_token[]`, `type_position[]`) and the record in the header ("The record in a module's header", written and read back: a new kind is a new line in every generated header, so the corpus' `expect/header` changes; the library headers are build outputs and follow on the next `smith build`). (3) What an instance takes from an argument ("The types an instance was asked for", `smith_lang_infer_*`, "The type of an `auto` parameter, from its argument"; the conversion check of the later arguments is `smith_lang_converts_to` and `smith_lang_convert_ok`, "A later argument converts to..."). (4) What the instance's signature and call write ("Writing a signature and a call", "Writing the instances", `smith_lang_call_types` and `smith_lang_call_arity` for reading a call). (5) What the body may use (`runtime/lang_constexpr.c`, included in the middle of the file: `if constexpr` queries; "Built lists and `for constexpr`" for the loop). Messages for each step are in the same sections: `grep -n 'smith_lang_error' runtime/lang_generic.c` lists them.
- **A generic passed as `constexpr auto f`** (issue #669): the name is one pool token `module::name` (`smith_lang_generic_as_argument`, only as a whole argument of a call being read), accepted by `smith_lang_infer_function`, refused by `smith_lang_infer_auto`, `smith_lang_replay_plain` and `smith_lang_gen_put_arg`; a call of the parameter in the body is replayed by `smith_lang_replay_function_call`. Corpus: `generic-function-generic`, `generic-function-generic-error`.
- **`fields(T)`** is `runtime/lang_fields.c` (included by `lang_constexpr.c`, listed in `build.c`), asked at each token of an instance's body by `smith_lang_fields_replay` and in `smith_lang_pack_expand_range`, and in conditions through `smith_lang_fields_typeof_end` (a type), `smith_lang_fields_countof_at` (a number) and the host's `type_field`. A new construct on it needs both write paths, the condition and `smith_lang_fields_begins`. Corpus: `generic-fields`, `generic-fields-error`, `generic-fields-doc` (doc comments, enums), `error-fields-enum-member`. `Field` and `smith_field_make` (issue #100) are written raw by `smith_lang_fields_define`, after the last `import` line (`smith_lang_field_after_imports`, runtime/lang_type.c) or where the first instance needs them; `smith_lang_fields_alias` and `smith_lang_fields_cx_piece` make a `constexpr Field f` readable to a condition (the parser has not read the instance's body); the shim's `value_query` reads a pointer to a whole string literal as its characters. A function body cannot be queued as tokens (its `}` is lost in the sparse body). Corpus: `generic-fields-values`, `generic-fields-import`.
- **The hook's text gating** (`shim/hook.cpp`): a file with the words `if constexpr` or `for constexpr` (`hasIfConstexpr`, a scan of the buffer for `constexpr` after `if` or `for`) is offered every token of a body, as `tryFastSparse` says; any other file only braces and watched names. A new construct that needs to see a keyword the hook does not offer must extend that scan (or add its own word to it), or the lowering never sees it, with no error: it fails as the construct "not working in plain files". The corpus case that covers it needs a file whose only use of the construct is in a body.
- Private names in an exported generic's body (issue #75) are `runtime/lang_private.c`: the header pass tees each private declaration (`private_active`, routed in `smith_lang_header_token`), `smith_lang_priv_resolve` marks what the exported generics reach, and the header's `#ifdef SMITH_INSTANCES` section, `// smith-linked:` and `// smith-hidden:` lines come from it; the module's own compile reads `smith-linked` at its `module` line (`smith_lang_linked_read`). A call in a call's arguments inside an instance is typed from captured tokens by the replay's `TypedStart`/`TypedFinish` frames (no recursion). A header with a section is guarded (`#ifndef SMITH_HEADER_<module>` first, `#define` at the end of the declarations, a second guard for the section; `smith_lang_priv_open`, `_close`, `_section`) instead of `#pragma once`, so a plain include first cannot hide the section; the aligned form keeps the opening to one line. Corpus: `generic-private-names`, `generic-private-generic`, `generic-private-included-first`, `generic-nested-argument` and the two `error-generic-private-*` cases.
- **Tuples** (`runtime/lang_tuple.c`, skill `smith-lang-tuples`): `smith_lang_tuple_begin` runs in `smith_lang_process` at a `struct` token and rewrites the queue (the tokens up to the `}` become the tag, the braces and `A _0;` fields), so no state of the lowering knows tuples; the tokens it makes are `synthetic` (a token counted as source made clangd hang), and a head holds a tuple's braces as parentheses (`tuple_brace`). `t[0]`, `countof(t)` and `return {...}` ask the compiler (`expr_type`, `return_type`), so they exist only where the host has a parser and the token goes through `smith_lang_process` (not in a generic's replay); a token the lowering takes from a generic call's arguments sets `advance_skip` so the call's depth stays balanced. The hook offers every token of a file with a tuple in its text (`hasTuple`, `maybe_tuple`) or whose import's header has `// smith-tuples`. The spelling rule is one function used by every pass (`smith_lang_tuple_spell`): change it and every header and `expect/lowered` changes, and an old header disagrees with a new compile.
- **Type values** (`runtime/lang_type.c`, skill `smith-lang-type-values`, issue #99): `smith_lang_ty_token` is the first thing `smith_lang_process` does for a token of a file with `maybe_type_value` (the hook sets it, `hasTypeValue`; it also turns off the hook's fast path for sized names and `smith_lang_fast`'s, since a type name is read with its neighbours). It rewrites the queue like the tuples do (the tokens it makes are `synthetic`; the tokens it copies from the source, a `sizeof(t)`'s chain, are skipped by `passthrough`), and it follows the file's shape in `SmithLangTy` (static, reset in `smith_lang_new`: frames, names, regions). A handle is a 128-bit number to clang (issue #143: the lower half is `smith_lang_ty_pack`, a pointer's upper half its pointee's lower half, `smith_lang_ty_pieces` writes it, `smith_lang_ty_pointee` reads `typeof(*(t)nullptr)`; the lowering keeps the lower half, as `value_query` returns it); a generic's `if constexpr` writes `T` as one in `smith_lang_cx_text`. The generic scan (`smith_lang_generic_ahead`) takes a bare `Type t` as a type parameter only when the head uses `t` as a type (`smith_lang_bare_type_used`); `decl.generic` keeps the hook out of a generic's head. A `.smith` corpus case that uses `kinds[1] x;` does not parse in the tree-sitter grammar: write `constexpr Type k = kinds[1]; k x;`. `host->constant` reads a variable's value with `evaluateValue()` and crashes on a declaration whose initializer is not attached yet: use `value_query` for a name just declared.
- **Slices** (`runtime/lang_slice.c`, skill `smith-lang-arrays`, issue #82): a declaration is rewritten at its **first token** (`SmithLang.slice.after_boundary`), a subscript chain at its first token too, never at the `;` before, because everything the lowering peeks is processed in the same batch while the parser still lacks the declarations before it: a question to the compiler (`expr_type`) is right only at a token the parser has just consumed, and peeking one token too far (a `)`, a `=`) can pull a later statement's type question into a stale batch. A `c::` name's next token must be peeked unexpanded first (`smith_lang_peek(..., 1, true)`), so a scan that starts at `c` stops at the `::`. The struct's tokens are `synthetic` (`data`, `count` declare nothing in a head), its braces `tuple_brace`; a tag already defined at file scope is written bare, with the definition in `header_text`. Statement expressions are `__extension__`. `SmithExprType.is_array` and `array_size` say what `expr_type` hides (it decays arrays). State that must survive a module read aside is in `SmithLang.slice`.
  A generic that returns a slice (`arena::push_slice`): its head's tag `smith_array_T_n` is flagged `g` in the header line (`smith_lang_slice_tag_param`, `smith_lang_gen_put_slice_tag`) and spelled per instance; its body names `struct smith_array_T_n` itself (a body is recorded before T is known, so `T xs[:]` and `typeof(T[:])` there stay raw); `smith_lang_slice_flag` does not set `slices_seen` in a generic's head, or every importer of arena would be in slice mode (which `for (...)` bodies and `contract::assert`, `[[gnu::format(printf...)]]` and `T *map(` heads were never exercised under: mass slice mode needs those chains fixed first).
  More dimensions (issue #105): `SmithLangSliceDims` (runtime/fixed per dimension) is read from the tag's end (`smith_lang_slice_dims_parse`), so a tag is `smith_array_<elem>[_e]_n_2`; a run of `xs[i][j]` is one pattern (`smith_lang_slice_rows`) and `smith_lang_slice_cur_max`/the queue hold its size (a nested row per index overflowed 256 tokens); `Cur.sliced` makes `xs[a:b][c:d]` an error; a generic's head cannot return a multi-dimension slice yet. An error that drops a subscript with a trailing `//` comment on its line can print a cascade (the trivia follows token counts).
- **A slice passed to a generic** (issue #119, knowledge/smith-generics.md): the instance and the call define the slice's struct (`smith_lang_instance_define_slices`) from `SmithLangInstance.slices` (`slot`, tag, data type, count per slice type of the instance), and the body's `countof(xs)`, `xs[i]`, `xs[a:b]` of a parameter are written by `smith_lang_slice_replay` (runtime/lang_slice.c; `SmithLangFrame.words` is a frame of words). The compiler has read nothing of an instance when its body is replayed at the end of the file (its parameters, a struct defined in a function): a question to it there sees only what was parsed before, which is why a typed argument (`replay->typing`) is written as a value of the element's type. `is_slice(T)` is in `smith_lang_cx_builtin` and, for a type value, the handle's depth bits (`smith_lang_ty_question`). A file with no `module` line has no `in_function`: `smith_lang_slice_define` asks `host->return_type`. The slice scan (`hasSlice`, `smith_lang_text_has_slice`) skips comments, strings and character literals (issue #121); a pointer to an array (`T (*)[N]`) goes to a generic as `__typeof__(...)`. The library headers hold a generic's tokens and are made again by `smith build` when it changes.
- **Functions over `type` and slice types** (issue #107, knowledge/smith-generics.md): a handle is `index (bits 0-11) | slice depth (12-15) | kinds | align | size`; `t[:]` is `smith_lang_ty_slice_op` (an expression over the handle, `smith_lang_ty_slice_make` the same arithmetic in C, `smith_lang_ty_from_tag` reads `typeof(xs)` of a slice back), and a `type` function is a plain generic (`SmithLangGeneric.plain`, kinds `f` and `g` in the record, `smith_lang_plain_ahead`). The header pass and the raw lowering record it (a placeholder for C), a compile writes it private and an importer defines it after its last import (`smith_lang_types_define`, tokens marked `replay`, bypassing the lowering in `smith_lang_process` but for the type values; `smith_lang_ty_qualified` makes `m::f(` a call that takes types). Things that bit: a token read past the import line enters the include after the next, in its middle; a definition between imports is a declaration before an import (`imports come before any declaration`); a token made by `smith_lang_synth` keeps `replay` from its model; `smith_lang_tuple_keep` is a ring (keep what you queue); `-E` prints a made token's characters from its place, so its output of replay tokens is garbled while the compile is not; `smith_lang_ty_identifier` must keep `ident0` (the function a head declares) before its early returns; a keyword macro (`static_assert` of assert.h) reaches the lowering as no token.
- **A computed result type** (issue #102, `runtime/lang_constexpr.c` last section, knowledge/smith-generics.md): `export slice_of(T, countof(rest)) f(...)`. `smith_lang_generic_ahead` ends the result's call (`generic_result_call`, `decl.result_call` so the parser takes the name after it as the declared one); the signature writer asks `value_query` for it and caches the spelling in the instance. The called function is the file's own or an exported function over `type` of an import (below). A non-static, non-exported `Type f(...)` in a file with `import <h>;` is not read as a type function: write `static`. Corpus: `generic-return-type`, `error-generic-return-type`.
- **Body files (issue #107, [body-files](../../../knowledge/body-files.md)).** `runtime/lang_body.c` writes (`SMITH_LANG_BODY=path`: the compile keeps every token it writes, so the fast path and the sparse body are off) and reads (`smith_lang_body_use`, at the last `import`) the `.body` of a module; `shim/hook.cpp` has `readBody` (finds or makes the file: it runs `$SMITH_LANG_SELF cc -fsyntax-only` of the source with `SMITH_LANG_FLAGS`, both set by the driver, because the process may be a clone called `clang`), `mentionsName` (the statements that need a constant) and `includeText` (the copies, a system buffer called `<smith-bodies>`, which `shim/effects.h` knows). The buffer is a system file, so `smith_body_depend` (`runtime/lang_body.c`) names each body, source and C header in it with `__has_include`, or `-MMD` would drop them. What bit: the host's header buffer is reused by the next `read_header` (copy what you keep), `SMITH_LANG_DUMP` alone is sparse (a body's tokens the host decided are not written), a project's build uses the installed `smith-cc` (put the branch's `build/<OS>-<arch>` first in `PATH` to try it), and a header change moves every `expect/header` of the corpus (`UPDATE=1`).
- **After editing a library generic or the lowering**, run `smith build`: the headers it includes are made by the previous release's writer (the lag rule), and an installed smith writes its own from its embedded sources.
- **Lambda forms in the editor tools** (#316, #954): `tree-sitter/grammar.js` has `lambda_expression`, `lambda_capture_list`, `trailing_call_expression` and `lambda_type` (corpus `tree-sitter/test/corpus/lambdas.txt`); clang-format already lays out the lambda forms (tests in `tests/smith_fmt_test.smith`), except a trailing `f(args) [](T *a) {...}`, which needs a clang-format patch (an LLVM rebuild).
- **Front lexer goldens** (`front/lex.smith`, `tests/front/lex/*.tokens`; `grep -l type_name` finds them): the lexer makes ANY identifier whose first character is an uppercase letter a `type_name`, whatever it names (`Arena`, `X`, `Foo_bar`). Each golden holds the `line:column` of every token, so an edit or rename that shifts a column changes it.
- **A header's `// smith-generic:` record** (`runtime/lang_generic.c`) holds `@line:col` for each token of a generic's body, relative to its first line, so the same edit also moves the `expect/header` goldens (`UPDATE=1` rewrites them).
