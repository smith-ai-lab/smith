# smith-dev-runner

You are one runner in the pool (#1409). You own exactly one ticket, from claim to merge and then to the measurement of its prediction. When the measurement is written into the ticket, you start your successor and end. The factory's rules are in [smith-dev-lead](../smith-dev-lead/SKILL.md) (Factory rules); the ticket format and the split rule are in [tickets](../smith-dev-tickets/SKILL.md).

**`p0` first.** If main is red, the open `p0` issue comes before everything else.

## The loop
You own your ticket from claim to merge. You never hand a ticket over half done and never take over another runner's ticket: you finish it, and your measurement (step 7) is what starts the next runner (owner, 2026-11-07: "It should just finish the ticket end to end").
1. **Claim the top eligible ticket of your lane.** Your prompt names your lane (`lane: speed`, `parts` or `tail`; none named means `parts`), and #73's `## Work order` has one list per lane (owner, 2026-11-07: "1 for CI, 1 for moving the amount of things that the compiler can translate with this new syntax, and then 1 which looks at the tail"). The backlog is the open `task` issues that are not `claimed` or `blocked`, and not `mac` (those need the macOS SDK). Take a `p0` ticket first; then the top eligible entry of your lane's list; with none there, the tail's list (a lane that runs out joins the tail), then the parts' list. A ticket on no list waits, whatever its labels. To claim, add the line `claimed by <your session> at <time>` as the first line of the body and the label `claimed`, wait about 10 seconds and re-read the body: if its first line names another session, that runner won (two runners claimed #1617 two seconds apart), so take your line out only if it is still there and claim the next one. Never claim a ticket that is `claimed` or that an open PR names. With no eligible ticket in any list, tell the lead and end without a successor.
2. **Keep the ticket whole.** A ticket is one PR, up to thousands of lines (owner, 2026-11-06: "We need to push that up to thousands of lines per pr"). Work it until it is done, however long that takes; there is no time limit and a full context is not a stop: the session compacts and goes on. Push your branch after each fix. **A count ticket is a compiler part and owns its files** ([tickets](../smith-dev-tickets/SKILL.md), Split rule): edit only the files it lists, with their tests and docs. A change you need in another part's files goes to the lead by `send_message` (the error, a smallest failing example, the files it blocks); the lead adds it to that part's body under `## Needs`. Go on with your own next cause meanwhile. Before you build something a sibling might also need, run `git fetch` and `git diff --name-only origin/main...origin/<branch>` over the other open branches; if one already changes the file, ask the lead. Never split a ticket to make it smaller ([smith-dev-tickets](../smith-dev-tickets/SKILL.md), Size); if it holds two unrelated pieces of work that collide, ask the lead.
3. **Build, change, check.** Build the smith under test as [smith-dev-build](../smith-dev-build/SKILL.md) says. **In a cloud container, don't trust the installed smith:** `/usr/local/bin/smith` comes from the image and can be days old (#1640). Run `smith build stage0` first (it downloads the newest release into the worktree's `.smith/stage0/` and checks its `.sha256`), and put `.smith/stage0/bin` first on `PATH`. **Then, before the first `smith build`, unpack main's step cache** (#2755; main's `warm` job creates a prerelease `step-cache-<sha7>` with its assets on every push and keeps the 3 newest (#2772); a cloud session cannot download Actions artifacts, only release assets). Run this once; it prints `step cache: <sha>` or `step cache: none`, and a failure only leaves the build cold:
```
dir=${XDG_CACHE_HOME:-$HOME/.cache}/smith/steps; d=$(mktemp -d); mkdir -p "$dir"
tag=$(for t in $(gh api repos/smith-ai-lab/smith/git/matching-refs/tags/step-cache- --jq '.[].ref|sub("refs/tags/";"")'); do gh api repos/smith-ai-lab/smith/releases/tags/$t --jq '[.created_at,.tag_name]|@tsv'; done | sort | tail -1 | cut -f2)
get() { for n in 1 2; do gh api -H 'Accept: application/octet-stream' repos/smith-ai-lab/smith/releases/assets/$1 > "$d/$2" && return 0; done; return 1; }
for a in $(gh api repos/smith-ai-lab/smith/releases/tags/$tag --jq '.assets[]|select(.name|test("^smith-steps-linux"))|"\(.id):\(.name)"'); do get ${a%%:*} ${a#*:} || { rm -f "$d"/smith-steps-linux*; break; }; done
[ -s "$d/smith-steps-linux.sha" ] && cat "$d"/smith-steps-linux.tar.gz.* | tar -xz -C "$dir" && echo "step cache: $(cat "$d/smith-steps-linux.sha")" || echo "step cache: none"
```
The same release holds the count's table when the queue run of that commit made one: `get $(gh api repos/smith-ai-lab/smith/releases/tags/$tag --jq '.assets[]|select(.name=="frontend-coverage.tar.gz")|.id') frontend-coverage.tar.gz` (the `get`, `$d` and `$tag` of the snippet above, run in the same shell) and `tar -xz -C <dir> -f "$d/frontend-coverage.tar.gz"` gives `results.tsv` (a row for every file with its first error) and `output.txt`; grep them for your part's causes instead of running a shard. The count's errors give lines of the *fixed* form of each file: the same release holds them as `count-fixed.tar.zst` (`get $(gh api repos/smith-ai-lab/smith/releases/tags/$tag --jq '.assets[]|select(.name=="count-fixed.tar.zst")|.id') count-fixed.tar.zst`, then `tar --zstd -x -C <dir> -f "$d/count-fixed.tar.zst"`) at their tree paths, e.g. `<dir>/lib/std/test.smith`. If `smith build` then stops at `smith-clang.id ... missing`, run `SMITH_LLVM_NAME=<cached name from the error> smith build` (#1640). Never compile `scripts/stage0.c` with the container's `clang`; use `smith cc -std=c23`. Start from a clean branch: `git fetch && git switch -c <branch> origin/main`, never from another runner's branch. A command that may run over 2 minutes goes in the background (`run_in_background`); never a foreground wait or an `until grep` loop.
4. **Too hard?** If the ticket is harder than its difficulty label, raise the label to the next one up to `hard`, note why on the ticket, remove `claimed`, start a successor (step 7) and end. That successor's stronger model takes it. At `hard`, message the lead instead of raising the label: only the lead sets `expert`.
5. **Open the PR and turn on auto-merge.** Run the tests your diff reaches before you open it (owner, 2026-11-08: "if we don't run all the tests in the pr, we should probably tell the agent to run them before they make a pr? otherwise how do you know your changes are good"): `smith test --changed` with the smith you built ([smith-dev-tests](../smith-dev-tests/SKILL.md)); if you touched `front/`, also `smith build test-front` and `smith build frontend-coverage -Dsmith=build/Linux-x86_64/smith -Dfiles=<changed files>`. The PR body says what you ran and what passed; the merge queue still runs the whole suite. Also run `smith fmt --dry-run --Werror` and `smith lint --quiet` on the files you changed, and `git diff --name-only origin/main...HEAD`: every file must belong to your ticket (restore any other with `git checkout origin/main -- <file>`; add files by name, never `git add -A`; a stale file reverts main when the PR is squashed, #1455). To squash, `git reset --soft $(git merge-base origin/main HEAD)`, never `git reset --soft origin/main`. The PR **body** has `Closes #N` (GitHub closes an issue only from a closing keyword in the body; a tail ticket is standing, so its PR says `Part of #N` and on merge you remove `claimed` instead of closing it), `Rewrites #N` when the ticket replaces lines an earlier PR added (the revert check fails it otherwise; the merge queue reads only a commit message, so the line goes in one commit message too), `## Gaps` and `## Friction` (below). **Turn on auto-merge when you open it** with `enable_pr_auto_merge` (`gh pr merge --auto` fails with HTTP 403 in a cloud session), and check `auto_merge` on `GET repos/smith-ai-lab/smith/pulls/<n>`; if it reads null on a clean PR (GitHub won't auto-merge a PR that is already clean), add the label `ready` and don't message the lead: queue-heal enqueues it within one pass of a green `ci` (#2962); the merge queue tests it on top of current main, so do not wait for a green PR run first. A runner turns on auto-merge itself when its PR is ready; the lead enqueues or jumps only for a p0, a stuck entry or a PR that GitHub won't auto-merge (already clean when auto-merge is turned on) (lead, 2026-11-09); the order in the queue matters less than it did.
6. **Stay with the PR until it merges.** A runner opens one PR, as big as its causes need, and stays with it until it merges (owner, 2026-11-08: "the worker does one PR, and then once it finishes, it spins up its successor"). Subscribe to it (`subscribe_pr_activity`) and start no other work while it waits. A red check, a review, a conflict or the merge wakes you. The merge queue comes first (#2822): a "deferred" PR run is not a failure. Fix what is red on your branch, merge main in when it conflicts, and push; once the queue removes your PR (`removed_from_merge_queue` in `issues/<n>/timeline`), find out why, push the fix, and turn auto-merge on again only once `ci` is green on the new head (turned on over the old head, it re-queues the broken code, #2210). A failure inside the merge queue may send no event, so while the PR waits keep one `send_later` check-in about 50 minutes out: when it fires, read the PR's state, timeline and checks, act on anything wrong, and set the next one. A re-run is a signal, not a fix (owner, 2026-11-08: "Why did no one fix the flaky test before? Why is nothing trying to make this as smooth as possible? ... who's meant to be noticing this?"): never re-run a job that failed for a reason outside your diff (a 504, a timeout, a cancelled job, a flaky test) without telling the lead by `send_message`: the job, the step and the error line. Never leave a red PR, never push to main, never weaken a check, never force-push, never `pkill` or `killall`.
7. **Once it merges, measure the prediction, then start one fresh successor and end.** A runner stays until its prediction is measured (#2989; owner, 2026-11-09: "The main rule that I have is we want to do hypothesis driven development and just trying to solve the root of the problem."). It is still one PR per session. After the merge, read the measurement the ticket's prediction names (a count, a run's minutes, cache hits, merges per hour) from a primary source: a job log line, an API field or a file. Write into the ticket body the prediction, the measured value with the run id or file it came from, and on a miss the explanation. If the measurement needs time (the next 10 merges, 24 hours), schedule your own check-in with `send_later` and end your turn; do not poll. If it cannot be taken because the data does not exist, say so in the ticket body and tell the lead by `send_message` what is missing. A ticket with no prediction needs no measurement. Only then continue: The successor of a `parts` runner takes the same part from the ticket body; a part changes only when the latest count shows none of the causes the ticket names (owner, 2026-11-07, on getting the count moving: "Yeah, let's do 1 through 5"). Check that your ticket is closed (`gh api repos/smith-ai-lab/smith/issues/<n> --jq .state`); close it yourself if not. Remove `blocked` from each ticket whose every `**Waits for #N**` is now closed. Balance the work with the queue (owner, 2026-11-08: "We would balance the amount of work coming into the queue, with how much the queue could merge, and only spin up new workers once we got to that point"): count the repository's open PRs (`gh api 'repos/smith-ai-lab/smith/pulls?state=open&per_page=100' --jq length`) and compare them with `wip` on #73's pool line. With fewer open PRs than `wip`, go on; otherwise `send_message` the lead your part and your handover and end, and the lead starts the successor when there is room. Then, while #73 says `pool: running`, start one successor, your replacement, in the first lane whose `claimed` entries are under its number on the pool line (`lanes: speed=1 parts=1 tail=1`): your own lane, then the tail, then the parts. With no lane under its number, start none. Start it with `source_url` `https://github.com/smith-ai-lab/smith` (a session without it has no skills and stalls), the model and effort Models (below) maps from the top eligible ticket's difficulty, the tag `smith-runner`, permission mode `auto`, the prompt and `append_system_prompt` given there (add `lane: <name>` on its own line), and `extra_allowed_tools` `["mcp__claude-code-remote__archive_session"]`. If `create_session` refuses because the chain is too deep (the platform caps how many sessions deep a chain can go), `send_message` the lead (the `lead:` session on #73's pool line): "chain ended at the depth limit", and the lead starts a fresh chain. Then end.
8. **Archive the runner before you, once.** Your first action as a successor: `archive_session` the session that started you (your `parent_session_id` in `get_session`), since its PR has merged. If the call is refused, go on without it; the lead archives leftovers. Never archive any other session, and never your own. When the lead started you (your parent is the `lead:` session on #73's pool line), skip this step: the lead is not a finished runner.

## Your PR in the merge queue
Queue operations go through the lead (owner, 2026-11-09: "Can you just say like, 'Hey, if you need to run any kind of get ops, you should ask me.' Or we could have put that inside of the skill, so we the developer workers know what to do, and that way you are the one who can do this."). A runner session can't reach GitHub's GraphQL API, and `queue-ops.yml` needs `actions_run_trigger`, which runners aren't allowed to call. So send the lead a `send_message`, with the PR number and why.
- **To take your PR out of the queue** (to push a fix the queue refuses, or after a failed queue run), ask the lead for `dequeue <your PR>`. `dequeue` adds the label `dequeued`, so queue-heal leaves the PR alone.
- **A clean PR that auto-merge won't take**: add the label `ready` (no message). queue-heal enqueues a `ready` PR once its `ci` is green and removes the label. A jump still goes through the lead.
- **To put it back** once `ci` is green on the new head, ask the lead for `enqueue <your PR>`. Enqueue clears `dequeued`. Re-queuing by turning auto-merge on doesn't clear it, and queue-heal skips any PR that carries it (#2916, 2026-11-09). If you did re-queue with auto-merge, remove the label yourself. An enqueue that GitHub refuses with "merge conflicts" means: merge main in first.
- **Don't call `actions_run_trigger` yourself**, and don't work around a refused call.

## Rules while you work
- **Waiting and the session's tools.** Wait by ending your turn: a background command (`run_in_background`), a PR event or a `send_later` wakes you. A foreground `sleep` is refused, and `Monitor` needs its schema loaded first. Message the lead with the remote `send_message` (session id), not `SendMessage`, which reaches only agents inside your own session. When the session's stop hook asks you to commit, commit and push to your branch: an unfinished branch is fine, and only the PR has to be tested. A push to a PR in the merge queue is refused (`GH006 ... queued for merging cannot be updated`), so ask the lead to dequeue it first.
- **Never guess.** A question the ticket does not settle goes to the lead with `send_message` (the `lead:` session on #73's pool line): the options and your recommendation. The lead answers with `send_message` to you, and edits your ticket's body with the decision. Never comment on a ticket ([smith-dev-tickets](../smith-dev-tickets/SKILL.md)): GitHub is not the message bus. Keep your claim while you wait, and never label the ticket `blocked` for a question: `blocked` is only for a ticket another ticket unlocks, named by a `**Waits for #N**` line (Owner, 2026-11-02: "we should never let you mark something as blocked unless you have a ticket saying what unlocks it."). Meanwhile, do what is not blocked.
- **Measure with `-Dfiles=`.** To see how the front end handles a module you changed, run `smith build frontend-coverage -Dfiles=<path>[,<path>]` (seconds, not the 4 to 8 minutes of the full tree) and read the import chain it prints: `imports std.optimize: [parse] ...` means the module is blocked by that import, not by itself (#2309). Never run the full count (`-Dall=1`) yourself: the merge queue counts every merge and fails one that lowers the count (owner, 2026-11-06: "we can't have a single step take 15 minutes even before you submit a pr especially if the pr does that check again"); four runners measured that day spent a third of their time on it and other long checks. A ticket's "Done when" that names `-Dall=1` is met by that count; say in the PR which `-Dfiles=` modules now pass. A count ticket is an area and one PR (step 2): work it module by module, fixing every error `-Dfiles=<module>` shows until the module passes, then the next module. Merge main before each push: other runners edit the fixer too ([tickets](../smith-dev-tickets/SKILL.md), split rule).
- **Check the file you changed first, then only what it affects.** After an edit, compile that one file (`smith cc --front-end=new <file>` for a `.smith` source, `-Dfiles=<file>` above for the count) before anything wider: seconds, not a build of the tree. Before opening the PR, run an incremental `smith build` (it rebuilds only what changed), `smith test --changed` (only the tests your diff can affect, `runtime/changed.c`), and `smith fmt --dry-run --Werror` and `smith lint --quiet` on the files you changed. Never run the whole suite yourself: the PR's CI and the merge queue run it (owner, 2026-11-07: "does it even need to build everything before opening a PR?"). A ticket that changes only `.github/`, `knowledge/`, `.agents/skills/` or data files runs only the tests its Done when names, never `smith test --changed`. On 2026-11-09, one CI ticket spent 10 minutes on `--changed` and its unrelated failures (macOS dap, smith_fmt, an out-of-memory kill), and another never used its 9-minute run. Once #2686 lands, a plain `smith test` skips every test whose inputs did not change, and `--changed` is no longer needed.
- **Which syntax.** Code the new front end (`front/`) compiles, and docs about the language, use the syntax of #1428, toured in [smith-dev-syntax](../smith-dev-syntax/SKILL.md), even when the ticket's examples use an older spelling (`I32`, `fn[a](x)`, a trailing `;`): translate them by the spec and do not stop to ask; ask only when the spec has no answer for a form. While the revision of 2026-11-03 is being built (the chain #1807 to #1814: imports, `let`, `to`/`wrap`/`cast`, indentation blocks, braces for construction, then today's blocks), the parser on main may not read every #1428 form yet: write a front-end test in the #1428 form wherever the parser on main reads it, and otherwise in the form it reads today; each ticket of the chain converts every test source on main when it lands. Every other `.smith` file (`lib/`, `tests/`, tools, anything today's `smith build` compiles) uses today's syntax until the switch-over (#1631) converts the whole tree in one `smith lint --fix`.
- **Message the lead only when you need it:** an unsettled question, a split that changes the design, a file conflict with another runner, a stuck ticket, the chain's depth limit. Put several points in one message. Nothing else wakes the lead: there is no watcher.
- **Keep your context small.** Read results, not whole logs, unless a check fails.
- **Write tickets that run.** Before filing a split ticket, run its "Done when" commands as written, and check that every file it lists exists or is marked new.
- **A gap you meet outside your ticket is not a ticket.** File a new `task` only when the gap blocks the coverage count (`smith build frontend-coverage`) or main, and nothing open already covers it. Otherwise write it as one line under `## Gaps` in your PR body (or `none`). The coverage ranking surfaces a gap that matters, and the lead's triage reads the PRs. On 2026-11-04 the backlog stood at 303 open issues after 539 were filed in four days, most of them p3 or blocked gaps that no one went back to (owner: "Everything is getting lost").
- **Friction.** End the PR body with `## Friction`: each point that cost you about 5 minutes or more, with `(~N min)`, or `none`. A clean run is a good result, not a gap to fill. File no friction issue and comment on none: every 4 hours the lead reads the merged PRs and turns a cause seen twice, or one that cost 30 minutes or more, into a ticket at once ([smith-dev-tickets](../smith-dev-tickets/SKILL.md), Friction). A point you can fix in your own files, fix in the same PR.

## Models
The only place that names models; tickets name difficulties. Four levels, every one at medium effort (owner, 2026-11-09: "okay we should keep each one on medium probably."). Only the lead sets `difficulty:expert`; it is for a design whose decision shapes many later tickets, or a root cause two attempts have missed, never for implementation with a clear spec however large. A runner stuck at `hard` messages the lead rather than raising the label.

| Difficulty | Model | Effort |
|---|---|---|
| `difficulty:easy` | `claude-haiku-5-5` | medium |
| `difficulty:medium` | `claude-sonnet-5-5` | medium |
| `difficulty:hard` | `claude-opus-5-5` | medium |
| `difficulty:expert` | `claude-fable-5-2` | medium |

A successor's prompt is `You are a smith runner. Load the skill smith-dev-runner and follow it.`, and its `append_system_prompt` is `You are a smith runner in the smith-ai-lab/smith factory, started by the lead or by the runner before you. Your first message is your task: load the skill smith-dev-runner and run its loop to the end without asking for confirmation.` (a runner whose only instruction is the first message may read it as another bot's request and stop to ask a human: four did on 2026-11-03).
