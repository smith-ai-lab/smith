# smith-dev-runner

You are one runner in the pool (#1409). You own exactly one ticket. When it is merged and handed over, you end. The rules are in [smith-dev-factory](../smith-dev-factory/SKILL.md); the ticket format is in [smith-dev-ticket](../smith-dev-ticket/SKILL.md).

## Modes
- **Backlog mode** (the default): the loop below.
- **Friction mode**: your prompt says "friction mode". Follow the loop below, but step 1 takes a released PR first (as in backlog mode), then the open `friction` issue that is not `claimed` with the most comments, ties oldest first: `gh api 'repos/smith-ai-lab/smith/issues?labels=friction&state=open&sort=comments&direction=desc'`. Fix the cause where it lives: in the skill, message, check or code that caused it. Your PR closes the issue. Your successor also runs in friction mode, except while #73 has a `**Chain first` focus: then start no friction successor and end, since the next chain merge starts runners for what it unlocks (2026-11-03: eight friction runners in a row while two chain PRs sat red). If no friction issue is open, the chain stops: do not idle and do not start a successor.
- **`p0` first, in both modes.** If main is red, the open `p0` issue comes before everything else.
- **A focus on #73 narrows the backlog.** When #73 has a paragraph that starts `**Chain first`, the backlog is only the tickets that paragraph names, unless the ticket the paragraph says ends it is closed: then the paragraph no longer applies and the work order is the backlog again, with no lead needed. Every other ticket waits, even one that is unblocked, `p2` or `p3`. With none of them eligible, first take over an open PR of one of those tickets that is red or conflicted with no push for 30 minutes, even without a release (its runner has ended): comment `Taking over PR #N: red or conflicted for 30 minutes with no push` on the ticket, then work it as a released PR. Only then take friction that slows those tickets (friction mode for one issue), never other work.
- **The Mac runner** takes `mac` tickets first, then the normal backlog ([smith-dev-mac-runner](../smith-dev-mac-runner/SKILL.md)). Cloud runners skip every `mac` ticket: it needs the macOS SDK.

## The loop
1. **Claim the top eligible ticket. A released PR comes first:** a ticket whose last claim comment starts `Claim released (lead` and has an open PR is finished before any new ticket, whatever its priority (finish what is open before starting new work). The backlog is the open `task` issues that are not `claimed` or `blocked`, and not `mac` unless you are the Mac runner. Take a `p0` ticket first; then the top eligible entry of `## Work order` on #73 (ranked by the files each ticket unblocks in the latest count); with no eligible entry there, the highest priority label (`p1` to `p3`), then the oldest. Label it `claimed` and comment `claimed by <your session> at <time>`. Post the claim comment first, then the label, wait about 10 seconds and re-read the ticket's comments: the earliest claim comment wins (two runners claimed #1617 two seconds apart and one wasted 35 minutes). If yours is not the earliest, remove nothing, stop before building and claim the next one. Never claim a ticket that is `claimed` or has an open pull request without auto-merge on, whatever the claim's age. A part's ticket whose PR waits in the queue with auto-merge on may be claimed: start with a cause that PR does not touch, and merge main in once it lands (an area runs for hours; only the lead releases a claim) (in a cloud session `gh pr list` and `gh pr merge` fail with HTTP 403, they need GraphQL: use `gh api -X GET search/issues -f q='repo:smith-ai-lab/smith is:pr is:open <n>'`, or `gh api 'repos/smith-ai-lab/smith/pulls?state=open'`), unless the lead released it (a comment starting `Claim released (lead`): then take that PR over whatever its state (red, conflicted, or green but needing rework). Check out its branch, merge main in, do what the release says, and push. Never open a second PR. **No eligible ticket? Take friction instead of ending:** follow friction mode for this one issue (the open unclaimed `friction` issue with the most comments). End only when there is neither an eligible ticket nor an unclaimed friction issue (2026-11-02: five fresh runners ended in a minute with 53 friction issues open).
2. **Check the size. Keep the ticket whole by default:** a ticket is an area, one PR of thousands of lines, committed and pushed as you go (owner, 2026-11-06: "We need to push that up to thousands of lines per pr"; 2026-11-04: fewer, bigger tickets that each move the count). Work it until it is done or about 3 hours have passed, then open the PR. A full context is not a stop: push the branch, and the session compacts its context and goes on (2026-11-06: area A's runner stopped at two thirds after 32 minutes and 117 lines; its context was the system prompt, skills, its own reasoning and many mid-size tool results, with no single large one). **A count ticket is a compiler part and owns its files** ([smith-dev-ticket](../smith-dev-ticket/SKILL.md), Split rule): edit only the files it lists, with their tests and docs. A change you need in another part's files goes to that part's ticket as a `Needs:` comment (the error, a smallest failing example, the files it blocks). You never make it on your branch, and you go on with your own part's next cause meanwhile (2026-11-06: `?*T` was built on three branches at once). Before you build something a sibling might also need, run `git fetch` and `git diff --name-only origin/main...origin/<branch>` over the other open branches. If one already changes the file, ask the lead. A part's ticket stays open: your PR says `Part of #N`, and at hand-over (step 6) remove `claimed` yourself so the next runner takes the part. Split only when the work holds two separate causes that would collide in one PR. Then file new `task` tickets, each with its files listed, no two sharing a file, and each with one difficulty label and the same priority label. Make the parent a checklist of them, and take the first piece.
3. **Build, change, check, open the PR.** Build the smith under test as [smith-dev-build](../smith-dev-build/SKILL.md) says. **In a cloud container, don't trust the installed smith:** `/usr/local/bin/smith` comes from the image and can be days old, too old to build main (#1640). Download the newest release first (`curl -fsSL -o smith.tar.xz https://github.com/smith-ai-lab/smith/releases/latest/download/smith-linux-x86_64.tar.xz`, the same with `.sha256` and check it, unpack it into the worktree's `.smith/stage0/`, and put its `bin/` first on `PATH`). If `smith build` then stops at `smith-clang.id ... missing` (the container has pack r12, the tree wants r14), run `SMITH_LLVM_NAME=<cached name from the error> smith build`: it builds a smith under test for any change that does not touch the LLVM pack or a patch (#1640). Never compile `scripts/stage0.c` with the container's `clang` (20 errors); use `smith cc -std=c23`. A step that still cannot run goes in the PR as not run, and CI decides). The repository is public, so no login is needed. Then make the change, and run the checks the ticket's "Done when" names. Push your branch after each fix, and run `date -u` when you claim so you know when 3 hours are up. **Open the PR only when the area is done or about 3 hours have passed (step 2), never when one module passes**: opening it starts steps 5 to 7, which end the session (2026-11-06: four of five area runners opened after one module and ended at 35 to 50 minutes with PRs of 25 to 316 lines, one saying "I stopped at about an hour of the 3 hours the ticket asked for"). A short time or a small diff is not a reason to stop; neither is a passing module, a CI question or a large context. Before opening it, run `smith fmt --dry-run --Werror` and `smith lint --quiet` on the files you changed: a minute here saves a red CI run and the 25 minutes two runners spent fixing one on 2026-11-06. Once the PR is open, push to it only to fix CI: every push re-runs it on runners all of the pool share. A command that may run over 2 minutes goes in the background (`run_in_background`) while you keep working; never a foreground wait or an `until grep` loop (each one hit the 10-minute Bash timeout in the 2026-11-06 measurement). Start from a clean branch: `git fetch && git switch -c <branch> origin/main` in a clean worktree, never from another runner's branch (#1460 stacked on #1455's). Open the PR from that branch. The PR **body** (not only the title) has a line `Closes #N` for the ticket, or `Part of #N` for a piece: GitHub closes an issue only from a closing keyword in the body or a commit message, and a ticket left open keeps its dependents `blocked` (#1862 left #1858 open for two hours). When the ticket deliberately replaces lines that an earlier PR added (a later piece of a chain, a rewrite), the body also has `Rewrites #N` naming that PR, or the revert check (`scripts/revert_check.c`) fails it in the queue. The PR ends with `## Gaps` (below) and `## Friction`: one bullet per point, each ending `(~N min)`, or `none`.
4. **Too hard?** If the ticket is harder than its difficulty label, raise the label to the next one, note why on the ticket, and end. A stronger runner takes it.
5. **Merge through the queue.** Before opening the PR, run `git diff --name-only origin/main...HEAD` and check that every file belongs to your ticket; restore any other with `git checkout origin/main -- <file>`, and add files by name, never `git add -A`. To squash, `git reset --soft $(git merge-base origin/main HEAD)`, never `git reset --soft origin/main` once main has moved: the commit keeps your older tree and reverts what merged meanwhile. A stale file outside the ticket reverts main when the PR is squashed (#1455). **Turn on auto-merge when you open the PR** (owner, 2026-11-06: "perfect, yeah let's do this"): the merge queue tests every PR on top of current main, so there is no retest before it and no wait for a green PR run. Use `enable_pr_auto_merge`, or `gh api -X PUT repos/smith-ai-lab/smith/pulls/<n>/ccr/auto_merge` (`gh pr merge --auto` fails with HTTP 403 in a cloud session), and check that `auto_merge` is set on `GET repos/smith-ai-lab/smith/pulls/<n>`. Without it, the PR never enters the queue. Waiting for green and retesting when main moved cost runners about a third of their time (2026-11-06); the risk it guarded, a PR that fails the queue and drops its group (#2148), is what fmt, lint and the tests you run before opening are for. If the queue removes your PR (`removed_from_merge_queue` in `issues/<n>/timeline`), find out why, push the fix, and turn auto-merge on again only once `ci` is green on the new head: turned on over the old green head, it re-queues the broken code (#2210, 2026-11-04). The queue merges it once the required check `ci` passes. **Do not wait for CI before steps 6 and 7:** once auto-merge is set, hand over and start your successor right away, then stay subscribed to your PR (`subscribe_pr_activity`) and end your turn; a red check or a review wakes you, and you fix it on your branch. **Once the PR enters the merge queue** (the `pull_request.enqueued` event, or `added_to_merge_queue` in `issues/<n>/timeline`), call `unsubscribe_pr_activity`. If about 3 hours have passed since your claim, end: your part is done. If not (a small PR the lead asked for ahead of the rest, such as a fix that unmasks many files), do not end. Run `git fetch && git switch -c <new-branch> origin/main` and go on with your part's next cause until the 3 hours are up; the next PR is the one at the end (2026-11-06: the parser runner ended at 32 minutes after the small PR it was asked for, with its part's other causes untouched). A queue failure after that goes to a fresh runner the lead starts, which costs about $0.20; a runner kept alive for the queue re-read its whole context on every queue event and cost $4 to $7 (2026-11-04: 38 runners lived over 6 hours and spent 37% of the night's $368). Waiting cost each pool slot about half its time on 2026-11-02 (35 minutes of work, then 30 to 40 idle for CI and the queue). In a bash loop (`SMITH_RUNNER_LOOP=1`) you cannot be woken: end, and the lead's watcher releases a PR that stays red for an hour to the next runner. Never leave a red PR you can still fix: six PRs sat red overnight on 2026-11-02 with no one to fix them. Never push to main, never weaken a check, never force-push, never `pkill` or `killall`.
6. **Hand over.** Check that your ticket is closed once the PR merges (`gh api repos/smith-ai-lab/smith/issues/<n> --jq .state`); if it is not, close it yourself. Comment on the ticket in a few lines: what merged, what is open, what a successor needs, and the friction total as bullets ending `(~N min)` plus the total.
7. **Start at most one successor, your own replacement**, and only while #73 says `pool: running` and both limits on #73 have room: the runners working (every `claimed` ticket that no open PR names) are under `runners=`, and the open pull requests (`gh api -X GET search/issues -f q='repo:smith-ai-lab/smith is:pr is:open' --jq .total_count`) are under `waiting=`. A PR waiting for CI or the queue does not take a runner's slot (owner, 2026-11-06: "perfect, yeah let's do this"; it held one for 34 of each PR's 83 minutes), and the cap on open PRs keeps production no faster than the queue consumes (owner, 2026-11-04; on 2026-11-03 a successor per eligible ticket grew the pool to 20 while the queue merged 5 an hour and 64 PRs piled up). Without room, start none and end: the lead's watcher starts runners when room opens. Before counting, remove `blocked` from each ticket whose every `**Waits for #N**` is now closed (your merge may be what unlocked it). In friction mode the successor is also in friction mode, if an open unclaimed `friction` issue exists. Start it with `source_url` `https://github.com/smith-ai-lab/smith` (a session without it has no skills and stalls) and the model that [providers/anthropic.md](../smith-dev-factory/providers/anthropic.md) maps from the top eligible ticket's difficulty, and the prompt "load `smith-dev-runner`" (add "friction mode" in friction mode), with the same instruction in `append_system_prompt` as [providers/anthropic.md](../smith-dev-factory/providers/anthropic.md) gives it, so the successor runs without stopping to ask. If `create_session` refuses because the chain is too deep (a limit of 8 sessions), post `@lead: chain ended at the depth limit` on #1406 so the lead starts a fresh chain. Then end. If `SMITH_RUNNER_LOOP=1` is set, skip this step: a bash loop starts the next runner ([smith-dev-mac-runner](../smith-dev-mac-runner/SKILL.md)), so a crash costs one ticket, not the chain.
8. **Never archive a session, your own included.** The lead archives you once your PR merges: the watcher names each merged PR's runner. A runner's `archive_session` is denied by its permission check (2026-11-04 test), which leaves it asking for input, and the old rule (a successor archives its predecessor) left 73 finished runners in the owner's sidebar on 2026-11-04: the predecessor's PR was still in the queue when the successor checked, and a paused pool starts no successor.

## Rules while you work
- **Never guess.** A question the ticket does not settle goes to the lead with the options and your recommendation, as an `@lead:` comment on #1406 (that wakes the lead within a minute). The answer comes on your ticket, as a comment starting `Lead:`; read the ticket's comments before you decide, and so does a successor who takes it over. Keep your claim while you wait, and never label the ticket `blocked` for a question: `blocked` is only for a ticket another ticket unlocks, named by a `**Waits for #N**` line (Owner, 2026-11-02: "we should never let you mark something as blocked unless you have a ticket saying what unlocks it."). Meanwhile, do what is not blocked.
- **Measure with `-Dfiles=`.** To see how the front end handles a module you changed, run `smith build frontend-coverage -Dfiles=<path>[,<path>]` (seconds, not the 4 to 8 minutes of the full tree) and read the import chain it prints: `imports std.optimize: [parse] ...` means the module is blocked by that import, not by itself (#2309). Never run the full count (`-Dall=1`) yourself: the merge queue counts every merge and fails one that lowers the count (owner, 2026-11-06: "we can't have a single step take 15 minutes even before you submit a pr especially if the pr does that check again"); four runners measured that day spent a third of their time on it and other long checks. A ticket's "Done when" that names `-Dall=1` is met by that count; say in the PR which `-Dfiles=` modules now pass. A count ticket is an area and one PR (step 2): work it module by module, fixing every error `-Dfiles=<module>` shows until the module passes, then the next module. Merge main before each push: other runners edit the fixer too ([smith-dev-ticket](../smith-dev-ticket/SKILL.md), split rule).
- **Check the file you changed first, then only what it affects.** After an edit, compile that one file (`smith cc --front-end=new <file>` for a `.smith` source, `-Dfiles=<file>` above for the count) before anything wider: seconds, not a build of the tree. Before opening the PR, run an incremental `smith build` (it rebuilds only what changed), `smith test --changed` (only the tests your diff can affect, `runtime/changed.c`), and `smith fmt --dry-run --Werror` and `smith lint --quiet` on the files you changed. Never run the whole suite yourself: the PR's CI and the merge queue run it (owner, 2026-11-07: "does it even need to build everything before opening a PR?"). Once #2686 lands, a plain `smith test` skips every test whose inputs did not change, and `--changed` is no longer needed.
- **Which syntax.** Code the new front end (`front/`) compiles, and docs about the language, use the syntax of #1428, toured in [smith-dev-syntax](../smith-dev-syntax/SKILL.md), even when the ticket's examples use an older spelling (`I32`, `fn[a](x)`, a trailing `;`): translate them by the spec and do not stop to ask; ask only when the spec has no answer for a form. While the revision of 2026-11-03 is being built (the chain #1807 to #1814: imports, `let`, `to`/`wrap`/`cast`, indentation blocks, braces for construction, then today's blocks), the parser on main may not read every #1428 form yet: write a front-end test in the #1428 form wherever the parser on main reads it, and otherwise in the form it reads today; each ticket of the chain converts every test source on main when it lands. Every other `.smith` file (`lib/`, `tests/`, tools, anything today's `smith build` compiles) uses today's syntax until the switch-over (#1631) converts the whole tree in one `smith lint --fix`.
- **Message the lead only when you need it:** an unsettled question, a split that changes the design, a file conflict with another runner, a stuck ticket. Put several non-urgent points in one message.
- **Keep your context small.** Read results, not whole logs, unless a check fails.
- **Write tickets that run.** Before filing a split ticket, run its "Done when" commands as written, and check that every file it lists exists or is marked new.
- **A gap you meet outside your ticket is not a ticket.** File a new `task` only when the gap blocks the coverage count (`smith build frontend-coverage`) or main, and nothing open already covers it. Otherwise write it as one line under `## Gaps` in your PR body (or `none`). The coverage ranking surfaces a gap that matters, and the lead's triage reads the PRs. On 2026-11-04 the backlog stood at 303 open issues after 539 were filed in four days, most of them p3 or blocked gaps that no one went back to (owner: "Everything is getting lost").
- **Friction.** Report only what cost you about 5 minutes or more; otherwise write `none`. A clean run is a good result, not a gap to fill. For each `## Friction` bullet, find an open `friction` issue with the same cause. If one exists, add a comment: `Hit this too: #PR (~N min) — <one line>`. Each comment raises the issue in the friction ranking. If none exists, open a new issue labelled `friction` ([smith-dev-ticket](../smith-dev-ticket/SKILL.md)). A point you can fix in your own files, fix in the same PR.
