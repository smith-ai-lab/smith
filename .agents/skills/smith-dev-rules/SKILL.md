# smith-dev-rules

The decisions are in [decisions](../../../knowledge/decisions.md); these are the habits.

- **Test the smith under test.** Run a change's tests with `build/<OS>-<arch>/smith`, not the installed `smith`, when the change is to the language, a library or the build. A test that builds a project puts the tested smith's folder (its `smith-cc` and `smith-c++`) first on `PATH`, so nothing in it compiles with the installed smith. In a fresh worktree or a cloud session there is none yet, and the installed smith is older than main and cannot build the tree: get one before you push, so your targeted test runs here and not first in CI. Try in order: (1) a prebuilt `build/Linux-x86_64/smith` in the main checkout `/home/user/smith` (it builds a recent main in about 3 minutes): `PATH=/home/user/smith/build/Linux-x86_64:$PATH smith build ...`; (2) if it predates main and fails (e.g. "this verb was given arguments"), stage0: `smith cc -std=c23 scripts/stage0.c -o .smith/stage0-tool && .smith/stage0-tool` (it fetches the LLVM pack itself when the cache has none, about 1.6 GB, then builds: measured 4 cores and 15 GB, about 80 s plus the pack download, and peak 2.2 GB of memory, but a shared container can take much longer; a step killed by a signal is reported by name with "probably out of memory" for 9, and running the same command again resumes from the steps that are done; the container's system clang is too old for `stage0.c`, so compile it with the installed `smith cc`; [smith-dev-build](../smith-dev-build/SKILL.md)), then `PATH=$PWD/build/Linux-x86_64:$PATH smith test --test <name>::`; (3) if stage0 stops because no LLVM pack is published for the configuration (a branch that bumped it waits for its CI's pack), do not start the source build by hand: say so, run the checks that need no smith under test (`smith fmt --dry-run --Werror`, `smith docs`, clang-tidy with the prebuilt), name in the pull request what was not run, and let CI run the tests; but when the cache holds an older pack (the error lists the names under `~/.cache/smith/llvm/`), `SMITH_LLVM_NAME=<cached name> smith build ...` still builds a smith under test, enough for any change that does not touch the LLVM pack or a patch (those need the real one). A worktree under the main checkout hides a missing `compile_commands.json` (clang-tidy finds the main checkout's): reproduce lint problems from a path outside it.
- **Scratch folders are your own.** Make each with `mktemp -d` (under your scratchpad when you have one), never a fixed name such as `proj`: another agent may be using it.
- **Write idiomatic Smith, not C renamed.** In a `.smith` file: sized types (`U64`, `Usize`, `F64`), `import <h>;` with `c::` names, modules that import modules, generics where a type was passed as `sizeof` and `alignof`, and no preprocessor. Count them before and after a port: a module with a standard C type, an `#include` or an `#if` left is not done.
- **Effects are inferred, not passed down.** A program calls the C library and smith's direct modules (`files`, `process`, `net`, `clock`, `console`, `env`) from anywhere; effects are inferred from what a function calls (#207), and tests and arenas control them through handlers (#239); no `io` value is passed down from `main`.
- **Never signal a process that is not your own unwaited child**, and never `pkill` or `killall`: a reparented pid may already be another test's compile.
- **`host->read_header` returns a buffer valid only until the next read**, and the lowering's own lookups read others: copy what you need before calling anything that may read a header.
- **Edit `.c`, `.h` and `.smith` sources with Edit or Write, not shell edits (`sed`, heredocs), and read the diagnostics that come back** (Claude Code passes `smith lsp`'s diagnostics only after Edit or Write); find a symbol's definition and uses with the LSP tool (hover, goToDefinition, findReferences) or from the shell with `smith lsp def`, `refs` and `hover` (one query a line on stdin with `smith lsp -`), not grep; after an edit made outside Edit or Write, `smith lsp diag FILE`. Shell edits stay fine for generated files and expected outputs.
- **Never read `tree-sitter/src/`** (`parser.c` is about 185,000 lines, `grammar.json` and `node-types.json` thousands): `smith build` generates them (gitignored) from `tree-sitter/grammar.js`, which is the file to read and edit. To check one rule, `grep` the generated file for a line.
- **CI runs the full `smith check`; you run targeted tests.** Work on your own branch, push it and open a pull request with `gh pr create`, the issue linked (`Closes #N`); run `smith fmt`, `smith lint` and `smith docs` first, then only the tests for what you changed (the corpus for the lowering, `--test prove_` for the prover, one script or `--test` for a library). Never run the full `smith check` locally: GitHub's hosted runners run it on the pull request (the check `ci`). When it is green, add the pull request to the merge queue (`gh pr merge N --auto`); the queue checks it again on top of main and merges it. A red `ci` is yours to fix on the branch: merge main into it if it conflicts (never rebase or force-push). Never `smith build install`. See [ci](../../../knowledge/ci.md). In a cloud session where `gh pr create` fails with HTTP 403 (it needs GraphQL), open the pull request with the GitHub MCP `create_pull_request`, or `gh api -X POST repos/smith-ai-lab/smith/pulls -f title=... -f head=BRANCH -f base=main -f body=...`. In a cloud session `gh pr view` and `gh pr edit` fail with HTTP 403 too (they need GraphQL): read and update the pull request with the GitHub MCP `pull_request_read` and `update_pull_request`, and use `gh` only for search.
- **Reading a failed CI job in a cloud session:** `get_job_logs` returns one very long line (JSON with `\n` escapes), so pass `tail_lines` (about 400) and take the `FAILED TESTS of this shard:` block near the end; the FAILED lines above it name the test.
- **A full check by hand** (rarely) is `lockf /private/tmp/smith-full-check.lock build/Darwin-arm64/smith check`, one at a time, its output in a file; say plainly what you did not run.
- **An implementer never runs `smith build llvm` by hand and never touches `~/.cache/smith/llvm`**; stage0 fetches the published pack for them (it never starts a source build unless `SMITH_STAGE0_LLVM=build`).
- **A test's limits count CPU time, never wall time**: the machine is shared and its load reaches 100 or more; give a test of a CPU limit a large `--wall-timeout`. See [machine-load](../../../knowledge/machine-load.md).
- **Shell traps on this Mac.** `sed -i` needs an argument (`sed -i '' 's/a/b/' f`), and a failure in the middle of an `&&` chain is easy to miss: end a chain with a check you read. zsh does not split `$F` into words: use an array (`a=(x y); cmd "${a[@]}"`) or `while read -r line`. Edit and Write are for sources; a short script file is for bulk edits.
- **When the command guard says "too complex to verify"**, write the commands to a script file and run it, one command per call; wait for a condition with Monitor and an until-loop, never `sleep`.
- **Stopping your own hung child:** `kill <pid>` of the process you started (`$!`, or `pgrep -P $$`), never `pkill`. A plain `timeout` does not stop a hung `smith lsp --check`; use `timeout -s KILL 60 smith lsp --check=...`.
- **The git stash is shared by every worktree**: never a bare `git stash` (commit instead, or `git stash push <path>`); check that `git worktree add` printed `HEAD is now at` before working in the folder.
- **Reach for `smith dbg --crash PROG` (or `--at FILE:LINE PROG`) before adding prints** to learn why a program crashed or what its variables hold at a line; see [smith-debug](../smith-debug/SKILL.md).
- **Report friction when you finish, in the pull request's body under a last heading `## Friction`** (`none` when nothing; the same text in your report). Besides what you did, say what slowed you down or misled you: a skill that was wrong, missing or hard to find, an error message that did not say the fix, a rule you had to guess, a check that caught you (and whether its message was enough), a `smith lsp` or `smith dbg` answer you had to replace with grep or prints (and the issue you filed). Name the skill, message or check. Each report is how the skills and the checks get better, and whether a change to them helped shows in the next agent's report.
- **Small Conventional Commits.** The commit that finishes an issue says `Closes #N`, a partial step `Part of #N`. Push `main` after every merge: the plugin's skills come from GitHub, so other agents learn a feature only once it is pushed.
- **No new shell files** (owner, 2026-10-25): a test that starts a process is a `.smith` test through `scratch::`; a download or a tool's build is a task in the build file.
- **Fix what clang-tidy reports; do not weaken `.clang-tidy`.** Generated files are build outputs, never committed; `tests/generated_files_test.smith` fails a tracked one.
- **smith's own tools come before grep and prints:** `smith lsp` for code, `smith dbg` for a crash. When one gives wrong, missing or slow answers, keep going with grep or prints and make the tool right too: fix it when it is in your ticket's area, else file an issue naming the query, what it said and what it should have said (owner: "if they're ever not good enough, fix them.").
- **Hand work to subagents whenever possible, on Sonnet 5.5 at medium reasoning effort.** A feature a user reaches for (a language feature, a library, a verb) gets a short README section with one example in the same PR, which `tests/readme.sh` compiles; internal changes don't.
- **Read [module-in-one-page](../../../knowledge/module-in-one-page.md) before designing or building a module rule.**
