# smith-dev-rules

The decisions are in [decisions](../../../knowledge/decisions.md); these are the habits.

- **The pre-push hook runs the check on your machine (#3132).** `.smith/hooks/pre-push` (written by `smith build`, never tracked; active once core.hooksPath is `.smith/hooks`, which the first `smith build` in a clone sets) runs `smith build pre-push` on the commits being pushed, which runs `smith check --changed --base <merge-base with origin/main>` (#3163): the one command that is the whole check (fmt, docs, prove, lint, test; lint and the tests only for what the change reaches), with the smith built from the tree (it builds one first when there is none). A push that changes only `knowledge/`, `.agents/` or `*.md` runs nothing, and a base that cannot be resolved here is not checked. On a failure it prints the command to run it again and the log (`.smith/pre-push-check.log`). The hook has no list of stages or files of its own (`build_pre_push` in build.c only builds the command); the owner's end state is the queue's exact command with no selection (#3294), which is one constant (`pre_push_changed_only`) away. `git push --no-verify` skips it and is never used except on the lead's word; the merge queue still decides.
- **Test the smith under test.** Run a change's tests with `build/<OS>-<arch>/smith`, not the installed `smith`, when the change is to the language, a library or the build. A test that builds a project puts the tested smith's folder (its `smith-cc` and `smith-c++`) first on `PATH`, so nothing in it compiles with the installed smith. In a fresh worktree or a cloud session there is none yet, and the installed smith is older than main and cannot build the tree: get one before you push, so your targeted test runs here and not first in CI. Try in order: (1) a prebuilt `build/Linux-x86_64/smith` in the main checkout `/home/user/smith` (it builds a recent main in about 3 minutes): `PATH=/home/user/smith/build/Linux-x86_64:$PATH smith build ...`; (2) if it predates main and fails (e.g. "this verb was given arguments"), or there is none (a cloud container often has none; #1384), download the newest release (README, Install; `.github/actions/fetch-smith` is the same download), put its `bin/` first on `PATH`, `smith build llvm` (fetches the LLVM pack, about 1.6 GB) and `smith build`: measured 4 cores and 15 GB, about 80 s plus the pack download, and peak 2.2 GB of memory, but a shared container can take much longer; a step killed by a signal is reported by name with "probably out of memory" for 9, and running the same command again resumes from the steps that are done; [smith-dev-build](../smith-dev-build/SKILL.md)), then `PATH=$PWD/build/Linux-x86_64:$PATH smith test --test <name>::`; (3) if `smith build llvm` stops because no LLVM pack is published for the configuration (a branch that bumped it waits for its CI's pack), do not start the source build by hand: say so, run the checks that need no smith under test (`smith fmt --dry-run --Werror`, `smith docs`, clang-tidy with the prebuilt), name in the pull request what was not run, and let CI run the tests; but when the cache holds an older pack (the error lists the names under `~/.cache/smith/llvm/`), `SMITH_LLVM_NAME=<cached name> smith build ...` still builds a smith under test, enough for any change that does not touch the LLVM pack or a patch (those need the real one). A worktree under the main checkout hides a missing `compile_commands.json` (clang-tidy finds the main checkout's): reproduce lint problems from a path outside it.
- **Waiting for stage0 (#1384):** start it in the background with its output to `.smith/stage0.log` (not a shared `/tmp` name), then wait with Monitor on that log (an until-loop), never `sleep`, which the command guard refuses. A first stage0 in a shared cloud container took about 30 minutes; do the checks that need no smith meanwhile.
- **Commands run from a script file in a cloud session:** in auto mode the command guard refuses compound commands (`&&`), heredocs and `PATH=` / `$PWD` prefixes (#1364), so write each command to a script in your own per-ticket scratch folder (never a shared name: one was clobbered in #1333) and run it, one per call, calling the smith under test by its absolute path.
- **A worktree that is behind starts from `origin/main`:** `git fetch origin main`, then `git checkout -b <branch> origin/main` for new work; never rebase or force-push a branch someone else may hold (#1301, #1316).
- **Scratch folders are your own.** Make each with `mktemp -d` (under your scratchpad when you have one), never a fixed name such as `proj`: another agent may be using it.
- **Write idiomatic Smith, not C renamed.** In a `.smith` file: sized types (`U64`, `Usize`, `F64`), `import <h>;` with `c::` names, modules that import modules, generics where a type was passed as `sizeof` and `alignof`, and no preprocessor. Count them before and after a port: a module with a standard C type, an `#include` or an `#if` left is not done.
- **Effects are inferred, not passed down.** A program calls the C library and smith's direct modules (`files`, `process`, `net`, `clock`, `console`, `env`) from anywhere; effects are inferred from what a function calls (#207), and tests and arenas control them through handlers (#239); no `io` value is passed down from `main`.
- **Never signal a process that is not your own unwaited child**, and never `pkill` or `killall`: a reparented pid may already be another test's compile.
- **`host->read_header` returns a buffer valid only until the next read**, and the lowering's own lookups read others: copy what you need before calling anything that may read a header.
- **Edit `.c`, `.h` and `.smith` sources with Edit or Write, not shell edits (`sed`, heredocs), and read the diagnostics that come back** (Claude Code passes `smith lsp`'s diagnostics only after Edit or Write); find a symbol's definition and uses with the LSP tool (hover, goToDefinition, findReferences) or from the shell with `smith lsp def`, `refs` and `hover` (one query a line on stdin with `smith lsp -`), not grep; after an edit made outside Edit or Write, `smith lsp diag FILE`. Shell edits stay fine for generated files and expected outputs.
- **Never read `tree-sitter/src/`** (`parser.c` is about 185,000 lines, `grammar.json` and `node-types.json` thousands): `smith build` generates them (gitignored) from `tree-sitter/grammar.js`, which is the file to read and edit. To check one rule, `grep` the generated file for a line.
- **CI runs the full `smith check`; you run targeted tests.** Work on your own branch, push it and open a pull request with `gh pr create`, the issue linked (`Closes #N`); run `smith fmt`, `smith lint` and `smith docs` first, then only the tests for what you changed (the corpus for the lowering, `--test prove_` for the prover, one script or `--test` for a library). Never run the full `smith check` locally: GitHub's hosted runners run it on the pull request (the check `ci`). When it is green, add the pull request to the merge queue (`gh pr merge N --auto`); the queue checks it again on top of main and merges it. A red `ci` is yours to fix on the branch: merge main into it if it conflicts (never rebase or force-push). Never `smith build install`. See [ci](../../../knowledge/ci.md). In a cloud session where `gh pr create` fails with HTTP 403 (it needs GraphQL), open the pull request with the GitHub MCP `create_pull_request`, or `gh api -X POST repos/smith-ai-lab/smith/pulls -f title=... -f head=BRANCH -f base=main -f body=...`. In a cloud session `gh pr view` and `gh pr edit` fail with HTTP 403 too (they need GraphQL): read and update the pull request with the GitHub MCP `pull_request_read` and `update_pull_request`, and use `gh` only for search. `gh pr list` fails the same way: list pull requests with `gh api 'repos/smith-ai-lab/smith/pulls?state=open'` (one PR: `.../pulls/<n>`, its `auto_merge` field), and turn on auto-merge with `enable_pr_auto_merge` or `gh api -X PUT repos/smith-ai-lab/smith/pulls/<n>/ccr/auto_merge`.
- **Reading a failed CI job in a cloud session:** `get_job_logs` returns one very long line (JSON with `\n` escapes), so pass `tail_lines` (about 400) and take the `FAILED TESTS of this shard:` block near the end; the FAILED lines above it name the test.
- **A full check by hand** (rarely) is `lockf /private/tmp/smith-full-check.lock build/Darwin-arm64/smith check`, one at a time, its output in a file; say plainly what you did not run.
- **A runner never runs `smith build llvm` by hand and never touches `~/.cache/smith/llvm`**; stage0 fetches the published pack for them (it never starts a source build unless `SMITH_STAGE0_LLVM=build`).
- **A test's limits count CPU time, never wall time**: the machine is shared and its load reaches 100 or more; give a test of a CPU limit a large `--wall-timeout`. See [machine-load](../../../knowledge/machine-load.md).
- **Shell traps on this Mac.** `sed -i` needs an argument (`sed -i '' 's/a/b/' f`), and a failure in the middle of an `&&` chain is easy to miss: end a chain with a check you read. zsh does not split `$F` into words: use an array (`a=(x y); cmd "${a[@]}"`) or `while read -r line`. Edit and Write are for sources; a short script file is for bulk edits.
- **When the command guard says "too complex to verify"**, write the commands to a script file and run it, one command per call; wait for a condition with Monitor and an until-loop, never `sleep`.
- **Stopping your own hung child:** `kill <pid>` of the process you started (`$!`, or `pgrep -P $$`), never `pkill`. A plain `timeout` does not stop a hung `smith lsp --check`; use `timeout -s KILL 60 smith lsp --check=...`.
- **The git stash is shared by every worktree**: never a bare `git stash` (commit instead, or `git stash push <path>`); check that `git worktree add` printed `HEAD is now at` before working in the folder.
- **Reach for `smith dbg --crash PROG` (or `--at FILE:LINE PROG`) before adding prints** to learn why a program crashed or what its variables hold at a line; see [smith-debug](../smith-debug/SKILL.md).
- **Timing a change** (a speed ticket's before/after table; #2899 lost about 35 minutes to the two mistakes below): (1) copy each binary under test to its own path in a scratch folder before timing (`cp build/Linux-x86_64/smith $scratch/smith-after`) and run the copies, so a rebuild during a run never touches them (#2899 rebuilt `build/Linux-x86_64/smith` under a running comparison and killed it); (2) build "before" and "after" the same way, both with `smith build` from a worktree at each commit and the same profile, never a release stage0 against a dev build (#2899's first table set the optimized stage0 against its own -O0 build); (3) run each side at least twice, on the same machine in the same session, and report the pairs on one line, because the machine's speed drifts and only pairs on the same line compare (#2889's re-measure ran on a slower machine); cold means an empty cache folder, warm means the same folder again; (4) the PR body gives the command, the commit of each side and the wall time.
- **Small Conventional Commits.** The commit that finishes an issue says `Closes #N`, a partial step `Part of #N`.
- **Never merge a broken build** (owner, 2026-10-25: "We should just have the discipline to not merge broken builds"): every change is a pull request from its own branch; GitHub's hosted runners run the full check on it (`ci.yml`), and GitHub's merge queue merges it, squashed, only when the required check `ci` passes on it together with main and the entries ahead of it; nobody pushes to main, and there are no exceptions for known failures (owner, 2026-10-29: "they make a pr when ready, those are running on github runners, not the self hosted one, once the ci passes, we merge into main"). See [ci](../../../knowledge/ci.md).
- **No new shell files** (owner, 2026-10-25): a test that starts a process is a `.smith` test through `scratch::`; a download or a tool's build is a task in the build file.
- **Fix what clang-tidy reports; do not weaken `.clang-tidy`.** Generated files are build outputs, never committed; `tests/generated_files_test.smith` fails a tracked one.
- **smith's own tools come before grep and prints:** `smith lsp` for code, `smith dbg` for a crash. When one gives wrong, missing or slow answers, keep going with grep or prints and make the tool right too: fix it when it is in your ticket's area, else file an issue naming the query, what it said and what it should have said (owner: "if they're ever not good enough, fix them.").
- **Hand work to subagents whenever possible, at medium reasoning effort, on the cheapest model the ticket needs:** Haiku 5.5 for docs, a README or a change the ticket spells out line by line; Sonnet 5.5 for code and for orchestrators (owner, 2026-10-31: "If it's like a documentation change, why are we using Sonnet, right? Or like an update to a README? That seems crazy.").
- **Read [module-in-one-page](../../../knowledge/module-in-one-page.md) before designing or building a module rule.** Its design was the pinned issue #450, kept current by the lead: a decision that changes one of its rows updates it in the same turn (owner, 2026-10-26: "Our documentation needs to be world class").
- **The compiler may recurse** (owner, 2026-11-07: "In our own compiler we should be able to use the full Smith language ... recursion"): in `.smith` code built by the new front end (#2710, knowledge/recursion.md) recursion needs no workaround and no work stack. The code the old front end still builds (`front/`, `lib/` today) keeps its explicit stacks until the switch-over (#1631), and the C files keep smith-dev-c.
