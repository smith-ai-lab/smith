# smith-dev-factory

- **One work order, ranked by the count (owner, 2026-11-06).** The order of work is the numbered list under `## Work order` on #73: tickets ranked by the files each unblocks in the latest count (the `frontend-coverage` job of the merge queue, `smith build frontend-coverage -Dall=1`), each cause ranked by the files whose first error it is, since a file moves only when its first error is fixed (owner, 2026-11-04: "ordering by files unblocked is a great idea"). A runner takes the top entry that is not `claimed`, `blocked` or `mac`. The lead rewrites the list after every new count: each entry shows the files it unblocks, and a top-5 cause with no ticket gets one. Owner, 2026-11-06: "We should tell them to go fix off the top unclaimed ticket in that list, and then you can update that list every time we get a new count." Labels no longer rank the work: `p0` (main is red, or the count is unmeasured) comes before the list, and only when the list has no eligible entry do the labels order the backlog (`p1`, `p2`, `p3`, the oldest first within a label). Until 2026-11-06 the labels were the order; with 28 tickets at `p1` the order fell back to the oldest, and the ticket that blocked 334 files waited behind older ones. A ticket that moves no count waits below one that does, unless it unblocks the flow (CI, the queue). Until #1377 is done, the backlog holds only its work: the new front end (#1112) to the switch-over, the `.smith` tools, upstream LLVM (#1376), the patch deletions, and what speeds those up.
- **`mac` label:** a ticket that needs the macOS SDK carries `mac` (#1124, #1127, #1130). Cloud runners skip `mac` tickets. The Mac runner takes `mac` tickets first, then the normal backlog ([smith-dev-mac-runner](../smith-dev-mac-runner/SKILL.md)).
- **Dependencies:** "Waits for #N" in the ticket plus the `blocked` label, until #N closes; then the lead removes `blocked`. `blocked` always names the ticket that unlocks it; never for a question, a split or a parked idea (owner, 2026-11-02).
- **Difficulty:** one label per ticket, `difficulty:easy`, `difficulty:medium` or `difficulty:hard`, set by whoever files it ([smith-dev-ticket](../smith-dev-ticket/SKILL.md)). Which model runs which difficulty is in [providers/anthropic.md](providers/anthropic.md), the only file that names models.
- **The pool line on #73:** `pool: running · runners=5 · waiting=4` or `pool: paused`. #73 holds the current goal, that line and the lead's handovers; it keeps no lane list. Paused: running tickets finish, and no runner starts another.
- **Work in progress has a limit, not the pool** (owner, 2026-11-04: "we don't want to produce more than the queue can consume"). Two limits on #73's pool line since 2026-11-06 (owner: "perfect, yeah let's do this"): `runners=` caps the runners working (claimed tickets with no open PR) and `waiting=` caps the open PRs; new work starts only when both have room. A waiting PR no longer takes a runner's slot (it held one for 34 of each PR's 83 minutes). The lead tunes `waiting=` to about what the queue merges in 40 minutes: raise it when the queue sits empty, lower it when PRs wait over an hour. A fixed pool kept producing while the queue was full: 2026-11-03 opened 27 PRs in an hour, merged 5 and reached 64 open.
- **Runners** are fresh sessions, one ticket each, that start at most one successor, their own replacement, when they hand over and work in progress is under the limit; only the lead adds runners, when the watcher reports room ([smith-dev-runner](../smith-dev-runner/SKILL.md)). Runners are launched as [providers/anthropic.md](providers/anthropic.md) says. The lead runs the pool ([smith-dev-lead](../smith-dev-lead/SKILL.md)).
- **Stale claims:** a claim with no push, comment or PR activity for 30 minutes is checked by the lead, who releases it when its runner's session has ended. A claim is never released by age alone: a part runs for hours.
- **Friction is a runner job, ranked by comments (owner, 2026-11-01: "we're just constantly chasing friction down from highest priority to lowest priority based on the number of comments on those friction tickets").** Every pull request ends with `## Friction`, each bullet ending `(~N min)`, the author's estimate. A runner comments `Hit this too: #PR (~N min)` on the open `friction` issue with the same cause, or opens one ([smith-dev-runner](../smith-dev-runner/SKILL.md)). The friction-mode runner takes the issue with the most comments, oldest first on a tie, fixes the cause in the skill, message, check or code that caused it, and closes it with its PR; its successor takes the next. `smith build friction -Dsince=<date>` still prints the minutes as a report. Only `p0` (main red) comes before friction.
- **Finish open issues before new work;** a new idea becomes an issue, not a branch, placed by its label.
- **Fundamentals before features.** When the factory has friction (a gate failing for reasons outside a pull request's code, red trains, slow builds, checks or tests, a growing queue), runners start no new feature work and spare capacity fixes the friction first; the lead lifts the freeze when it is fixed (owner, 2026-10-27: "we really need to stop adding new features and fix all of these fundamental things first").
- **Chase the bottleneck.** The one item the most work waits on (a blocker of tickets, CI, the merge queue) gets every spare runner, split or swarmed; no runner starts work that only queues behind it. The lead names it at every check (owner, 2026-10-28: "How do we make sure we are always chasing the bottleneck").
- **Test beds** ([test-beds](../../../knowledge/test-beds.md)): `~/Documents/checkers`, `~/Documents/virtual-cell/learner` and `~/Documents/game`. Read them and run the installed smith on them in place; build, test or prove them with a smith under test only in a scratch copy, so runners never share a `.smith/`. They follow smith: when smith changes its idiom or breaks their code, change them to match (they are the owner's own projects for trying smith: commit and push to their main freely). The commit says what changed and why, naming the smith issue; their own docs carry no change log.
- **Merge discipline:** every change is a pull request from its own branch, and nobody pushes to main. Push `main` after every merge: the plugin's skills come from GitHub, so other agents learn a feature only once it is pushed. The rule and its check are in [smith-dev-rules](../smith-dev-rules/SKILL.md).
- **Known gaps:** [known-gaps](../../../knowledge/known-gaps.md).

## On the owner's Mac (the lead only)
- Never `pkill` or `killall`.
- Nobody runs `smith build install` or `smith build llvm` by hand: CI's `install` job puts each new stage0 release in the owner's `~/.local/bin` (owner, 2026-10-27; from the release since 2026-10-29).
