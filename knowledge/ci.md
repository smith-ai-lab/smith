# CI runs the full check on the owner's Mac

`.github/workflows/check.yml` runs on every push to `main` and to `train` (never on a pull request), on the owner's self-hosted runner (`self-hosted, macOS, ARM64`), which runs as the owner's user: it shares `~/.cache/smith/llvm` and the installed smith. The service reads no shell profile, so the job puts `~/.local/bin` on `PATH` itself.

**The job.** It builds smith from the checked-out commit with the installed smith (`smith build`), then runs `build/Darwin-arm64/smith check` in its own clone, with no shared lock: the agents' local checks hold `/private/tmp/smith-full-check.lock`, and CI queuing behind them timed out idle. The full output is streamed to the job log and to the `check-log` artifact (with `.smith/log` and a process list taken at the end, so a timeout names the stuck process); the last lines are the job summary, and `SMITH_ACCOUNT=all` puts the per-task table (wall, cpu, processes) in `smith-log/test.log` of the artifact. A new push to `train` cancels its older run; runs on `main` never cancel each other. When the check fails, the job ends with "what failed": every `FAILED:` task and `FAIL` case from the output and `.smith/log` (also at the top of the job summary), so a long log cut short still names the cause.

**LLVM is never built here.** If `~/.cache/smith/llvm/<name>` is missing for the pinned name, the job fails and says the lead must run `smith build llvm`.

**On `main`,** after a green check the `install` job runs `smith build install`, so the installed smith is the merged commit; the `release` job then publishes it ([release](release.md)). The install job runs `smith build install -DNOTESTS` (the check job already ran the suite on this tree; a local `smith build install` still runs the tests), and `release` runs none. With two runners two main pushes can run at once, so `install` and `release` share one concurrency group (`main-install`, a newer pending run replaces an older pending one) and each skips itself unless its commit is still the head of `main`, so an older commit never installs or becomes the latest release after a newer one.

**A tree is checked once.** A green Full check (a train's, or a push's that ran it) uploads a tiny artifact `tree-<tree sha>` (7 days), and a push to `main` whose `git rev-parse HEAD^{tree}` has a live one skips "Debugger permission", "Build smith" and "Full check" (the job stays green, so `install` and `release` go on, and a notice names the run); a tree main moved under (or an expired artifact) runs the full check; `scripts/ci-tree.sh` holds the rule, `tests/ci_tree.sh` tests it. The lookup fails safe: any error, empty or malformed answer from `gh` means "not checked" and the full check runs; only a single run id from a live artifact skips.

**Mechanical checks first (#360).** "Mechanical checks first" runs right after "Build smith" and before any test, with the smith just built from the batch: `$smith fmt --dry-run --Werror` on each file the batch changed, `smith docs`, and, when a source or `.clang-tidy` or `build.c` changed, `smith lint` (which builds the headers it reads and checks every source). A failure ends in `FAIL fmt|lint|docs <file>`, so a mechanical red costs about a minute, not a tested run. It uses the built smith, not the installed one: a batch that changes a library's API or a check is judged by its own headers and rules (the installed smith rejected a correct json change, runs 40572148103 and 40572354319).

**Changed tests first (#506).** Before the Full check, "Changed tests first" runs `smith test --changed --base origin/main --fail-fast`: the tests the batch's changes select (records of main's latest green run, brought by the build file's `coverage-fetch` task with `gh`; with none, the build graph), stopping at the first failure, so a broken batch is red in minutes. The Full check after it still names every failure; a green batch pays for the selected tests twice. A wide selection still runs, with `--cheapest-first` and a 4-minute watchdog on the process group (a timeout is a pass), since the cheap tests catch most breakage.

**Coverage.** The Full check builds smith with `COVERAGE=1` and, when green, uploads `coverage-<commit sha>` (the table and `coverage-report.txt`) and `smith-records` (the per-test records), 7 days, beside the `tree-` artifact; the report's totals go to the job summary. See [coverage-selection](coverage-selection.md).

**The layers of the tests (#646).** Most of a full check's CPU was tests that start smith (39,216 processes, about 2,400 CPU-s in one train run). The suite is a pyramid: unit tests call a function in the runner's process (the runtime is linked as a library, `include/smith_core.h`, from `smith.c` compiled with `-DSMITH_CORE`), integration tests put several parts together in process, and a thin end-to-end top runs each verb once with the real compiler, linker, debugger and sanitizers. A migration keeps the file's coverage and posts its CPU and processes before and after; the rule and the mechanism are in the smith-dev-tests skill.

**Where the time goes.** `smith build ci-times` downloads the `check-log` artifacts and job steps of the last green runs (`gh`, no shell; `scripts/ci_times.c` makes the report) and prints the wall and CPU of each job step, stage and test task, the slowest tests and a 2-way split of the tasks by CPU. It is how the time budget of CI is read: the runners share one Mac, so CPU time is the cost and wall time is the load.

**The process: the merge train.** An implementer pushes its branch, opens a pull request with `gh pr create` linking the issue, and runs only `smith fmt`, `smith lint`, `smith docs` and the tests for what it changed; it then runs `smith build preflight` (a task of build.c: builds, fmt, docs, `smith lint --changed` and `smith test --changed` with the smith it built, on a clean tree; it posts the commit status `smith/preflight` on the head's SHA, success with the counts or failure naming the steps, through `gh api`, which smith itself never runs). Its test step is `test --changed --cheapest-first --fail-fast` capped at 10 minutes in a process group of its own, like CI's "Changed tests first": a timeout is a pass (the status description says "capped at 10 min"), only a failed test is red, and the train's full check stays the gate (`SMITH_PREFLIGHT_CAP=<seconds>` shortens the cap). Preflight builds in the worktree it is run in (`smith build`, incremental: "clean" means `git status` is clean, not a fresh build folder), prints the time of each step and puts them in the status description (`ok: build 41s, fmt 3s, docs 2s, lint 28s, tests 3m capped (N passed)`, under GitHub's 140 characters) so the 5-minute budget (#638) is visible on every PR. The train takes only a `ready` pull request whose head has that status as success; a new head (a push, a rebase) has none, so what rides was checked as it is. Its orchestrator then labels the pull request `ready` and pushes to it no more. Nobody runs the full check locally: the train's run is the only full check (owner, 2026-10-26: "lanes stop local full checks now, label ready after fmt, lint, docs and their own tests, and the train's check is the only full one"). Five full checks at once on one Mac took 16 to 50 minutes each, against about 6 for one. The lander is a script with no agent, run on the lead's Mac as a LaunchAgent from its own clone. It takes up to four ready pull requests, oldest first, rebases their commits onto `main` one after another and pushes the stack to `train`. A pull request with no `## Friction`, or one that conflicts with `main`, is rejected with a comment and loses `ready`; one that conflicts only with the pull requests ahead of it waits for the next batch. If the `check` job is green, each pull request's branch is moved to its place in the stack and `main` is fast-forwarded to the top, so GitHub shows every one as merged and the tree that was checked is the tree on `main` (whose own run then skips). If it is red only in tests known to fail under load (the debugger tests, the timed diagonals proofs), the run is rerun once; otherwise the lander tries the first half of the batch, down to one pull request, which then gets the failure as a comment and loses `ready`. A rejected pull request is its lane's to fix and label again. Only the lander pushes to `main`.

**Cores.** The Full check step and the install job set `SMITH_PRIORITY=ci`: `smith build`, `check` and `test` on the host draw core tokens from a host-wide pool, a waiting CI job gets the next free token before any local job, and while it runs the local runs leave it a quarter of the pool ([slots](slots.md)). This replaces the lanes' rule of one heavy build at a time.

**Limits.** The check job has `timeout-minutes: 50`, its Full check step 45. The DAP test client fails with "the debugger is waiting for permission (Developer Tools)" when neither `smith dap` nor its children use CPU for 60 s (the service user lacks the permission), instead of waiting out the 600 s backstop.

**Adding a runner.** CI can run on several runners on this machine (two today: `~/actions-runner` and `~/actions-runner2`), all as the owner's user. GitHub's `svc.sh install` writes the LaunchAgent with `SessionCreate = true`, which puts the runner in its own security session where debugserver refuses to attach ("non-interactive debug session"). After installing, set it false (`plutil -replace SessionCreate -Bool false <plist>`) and restart the agent (`launchctl bootout`, wait, `bootstrap`); the user must also be in the `_developer` group (once per user). The "Debugger permission" step of the workflow fails in seconds when a runner cannot debug. Setting these up is the owner's job, not an agent's.
