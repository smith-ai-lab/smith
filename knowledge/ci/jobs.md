# CI jobs, scope and the split

**A typical queue run (#2870)** is a change whose untested tests fit in one part (a parts PR). Its heavy jobs, at most 5 at once on Linux (the count runs after each code merge to main and by hand, in `count.yml`, not here: [count](count.md)):

| job | runs | why it is its own job |
|---|---|---|
| `changes` | first, light | the scope, the matrix, the macOS runner |
| `build-linux` | the dev build, the sizing, and the one test part | the tree every Linux check restores; the part runs here, on the tree just built, when the misses fit in one part |
| `check-fmt-prove`, `check-lint` | after `build-linux` | two jobs so neither is longer than the other path (lead, 2026-11-08, #2833); their `Checks` step prints where the time went (#2985): lint's `linted N files (R run, C cached, T s, setup S s: build info, needs, plan and hash)`, prove's `G groups, build B s, proofs P s` and its count of functions reused from the cache |
| `macos` | not in a queue run: the push to main and the nightly run | the macOS job (#1709): the `--macos-only` tests (its own test store) |
| `macos-lint` | not in a queue run: the push to main and the nightly run | `smith lint` of the code only the Mac sees (#3045): its own job and tree, since lint and the tests cannot share one (`.smith/build.ninja`); it builds smith, not the tests |
| `release-pack-linux` | a queue run, beside the others | the Linux release tarball of the commit main moves to ([release](../release.md)), #3052 |
| `ci` | last, light | the verdict |

More parts (a change to `lib/std/test.smith`, the nightly's empty store) run in `test-linux`, one job per part on the build `build-linux` uploads, and a pull request's part runs there too, beside `check-fmt-prove`, so its checks are not behind its tests. No job gathers the test stores: each job that runs tests publishes its own ([caches](caches.md)). Until #2870 a typical run also had `build-linux-release` (now in `frontend-coverage-fix`, #2890), `test-linux` (now in `build-linux` for one part) and `save-test-cache` (now in each test job; the `macos` job's store upload of #2867 became its own `test-cache/save`): before, the batch heads 42558311503 and 42559604613 ran 9 jobs outside the count.

**The jobs.** `changes` decides the scope (below) and the Linux matrix. `macos-lint` (#3045) lints on the Mac in its own job: it builds smith, not the tests. `macos` is the macOS job for the tests (#1709): it builds smith and the tests (`.github/actions/setup-smith`: the newest release downloaded by `.github/actions/fetch-smith` ([smith-bootstrap](../smith-bootstrap.md)), the LLVM pack, `smith build`, then `smith test --list`), then runs `smith test --macos-only` (a documents-only change: `docs` and `--test readme_test,skills_test`). Each stage is reported with `took <stage> <n>s (exit <code>)`, and a failure ends in `FAIL <stage>` with the failed tests as annotations. Stages in one job share one tree one at a time, since two verbs at once collide on `.smith/build.ninja`. **Where each check runs** (#2234): `fmt`, `docs` and `prove` run in `check-fmt-prove`, and `lint` in `check-lint`, two Linux jobs that restore the build of `build-linux` like a test shard and run beside the 8 parts, on pull requests too (so a formatting or lint mistake fails the PR, not the queue). `macos-lint` also lints on the Mac, because each platform lints code the other can't see: `@when(target.os == .macos)` code, Objective-C and Metal only on the Mac, glibc's macros only on Linux. On the Mac, prove took 163 s and fmt 11 s of the 9 minutes of checks (run 41766089451: `setup-smith` 5 min, `fmt` 11 s, `docs` 0 s, `lint` 193 s, `prove` 163 s, `test` 158 s), so the Mac job is about 11 minutes until lint is cached (#2236, #2237). A documents-only change (`docs` scope) builds no Linux artifact, so `docs` and its tests stay on the Mac. Until #1709 these were five jobs (`build`, `mechanical`, `prove`, `test`, `docs`) handing the build over as an artifact; four of them filled four of the five hosted macOS slots the free plan allows, so a second run queued behind the first, and a job that waited past its time limit was cancelled with no test failing. One job takes one slot, so five runs proceed at once, and nothing is packed or downloaded. `test-linux` is 8 hosted shards of `--skip-macos`, each `smith test --shard i/8 --costs .github/shard-costs.tsv`, each restoring the build of the one `build-linux` job (`setup-smith` with `artifact: build-linux`, #1758). A failing test is named in the job summary and as an annotation (`FAIL <name>`). `ci` gathers them and is the one check branch protection and the merge queue name. `ci` also fails a job that was owed and skipped: `full` owes `test-linux`, `check-fmt-prove` and `check-lint`, the two macOS jobs where they run (the nightly run, #3172), and `docs` owes `docs-linux`, so a skipped ancestor can't drop a gate unseen (#1139). `ci` does not run on a push to `main` (#3172): no required check reads that run.

**Scope.** On a pull request or merge queue entry, the files changed against the base decide: only `LICENSE*`, `CONTRIBUTING.md` and root images (documents no build reads) run nothing and `ci` passes; only those and `README.md`, `knowledge/` and `.agents/` run `build` and `docs`; anything else, a push to `main` and a diff that cannot be read run everything (a push to `main` runs the release jobs).

**What a pull request runs, and what the queue runs** (#754, #2234). A pull request and a queue entry run the same tests: the full suite in 8 Linux parts (`--skip-macos`, `--shard i/8`) and the Linux checks (`check-fmt-prove`, `check-lint`), because from 2026-11-03 the queue was the first place a change was fully tested, 74 of 100 failed queue builds failed in `test-linux`, and each failure fails every build behind it (owner, 2026-11-04). The test mode `--changed` is no longer used in CI. The macOS jobs are not in a queue run: they run on the push to main and in the nightly run, and gate nothing (#3172). A change of documents only keeps its scope (nothing, or `docs`), and one that changes only other workflows (`llvm.yml`) runs nothing. A `push` to `main` runs no test part (the queue tested that exact commit, #1139; `test-linux` is skipped, and `release` and `release-linux` need only `changes`, and `warm` waits for `publish` so it builds with the stage0 of its own commit, the one the jobs after it fetch). Linux is required: `ci` gathers `test-linux` like every other job, with no `continue-on-error`.

**`check-new`: `smith check` beside the old jobs (#3163).** One Linux job on main's push run (scope `release`, so a documents-only push runs none), `continue-on-error`, in the `check-new` concurrency group (one at a time; a push waiting behind it is replaced by a newer one). It builds smith and the tests, restores the test store, and runs `smith check --require fmt,docs,lint,test,prove` (the whole suite: no `--changed`); its summary has the stage lines and `compare: smith check <pass|fail>, queue run <id> <pass|fail>: agree|DISAGREE`, against the queue run of the same commit that `changes` finds. It runs after the merge, so a queue run gains no time from it, and it takes the 20th of the 20 Linux runners (queue 9, push run 2, count 8). No verdict reads it; the compared pushes are written into the body of #3163, and no old job is deleted before 20 agree.

**A pull request runs no check of its own; the merge queue runs the full suite (#3170, replacing the light check of #2822).** The checks are two: the pre-push hook on the runner's machine (`smith build pre-push`: fmt, lint and the changed files' own tests, #3132) and the merge queue's run of `ci.yml` on top of current main (everything below). On a `pull_request` event only `ci-pr.yml` runs: one job, `ci`, which succeeds at once (a few seconds on one runner), so the required context `ci` is met and the PR can enter the queue; it builds, tests and lints nothing. `ci.yml` has no pull request path: no `--changed` selection, no part budget, no yield to the queue, no commit status, no dry run of `warm`. On `merge_group` everything runs as before: 8 `test-linux` parts (or the sizing of `build-linux`), the release jobs. **A green pull request therefore says nothing about the code**: the queue run is the first full test, and a change the hook missed is ejected from the queue and its runner fixes it. A documents-only diff (`gated` in the `Scope` step) runs in the queue exactly as before: scope `docs` and `docs-linux`, nothing else. The LLVM pack (`pack` job, llvm.yml) is not built by a queue run, which would hold the one queue run for the whole LLVM build: a PR that bumps the configuration has its pack made BEFORE it enters the queue, by starting llvm.yml with `workflow_dispatch` on the PR's branch; a queue run whose pack is missing fails in `changes` in seconds, naming that dispatch (lead ruling, #3170; the same rule as the tools release in #3161).

Measured (#818, before Linux carried CI): a full run (a workflow change) took 12.0 min to the `ci` verdict with 4 macOS test parts of 6 to 9.5 min; a one-test-file pull request took 6.6 min. On Linux (main's run 41142406495) the build takes 3.5 min and each of the 6 shards 3 to 6 min.

**The split** is `--shard i/n` of the runner ([build-tests](../build-tests.md)): a test file stays whole in one part, files go heaviest first to the lightest part, and the weight of a file is the CPU seconds `.github/shard-costs.tsv` gives its tests (0.4 for a test it does not name, so a new test needs no entry). The file holds every test of both runners (#2927: with only the tests of 2 s or more, the 0.4 s default made the 1842 front tests weigh 737 s against 58 s measured), from the `cpu` lines (`SMITH_TEST_STATS=1`) of a nightly run's `test-linux` parts, which run every test: refresh it with `for j in <the parts' job ids>; do gh api repos/smith-ai-lab/smith/actions/jobs/$j/logs; done | sed -n 's/^[^ ]* \(cpu\t[0-9.]*\t.*\)$/\1/p' | tr -d '\r' | LC_ALL=C sort -t"$(printf '\t')" -k3,3 -u`, keeping the rows of the macOS-only tests (the `macos` job prints no `cpu` lines), when a part is much slower than the others. The count is chosen with the hosted limit in mind: the organisation gets at most 5 macOS jobs at once, and a job over the limit waits in a queue shared by every pull request, so a run that takes 6 jobs takes the slots of a second run.

**The handoff is an artifact, not the cache, on a hosted runner; on the owner's Mac it is its disk.** Restoring the 376 MB build from the cache took 8 s against 27 s for the artifact, but every job's restore counts against the account's cache egress limit, and a day of runs used it up (2026-10-30: `Egress is over the account limit`, every job that needed the build failed). So the build is uploaded with `upload-artifact` (zip level 1, which takes the 1.1 GB tar to about 0.4 GB: the tree is mostly binaries and a precompiled header; kept a day) as `smith-tree-<os>` and downloaded by each job. The LLVM pack and step caches stay: a restore that fails falls back (`smith build llvm` downloads the pack from its release; a missing step cache only means more compiles).

**Times** (wall clock of one `macos-26` job; numbers from #809): before, every job built smith: `setup` took 2.2 min (fetch 15 to 25 s, build 100 to 120 s) in each of 7 jobs, and a green merge queue run took 21.5 min (mechanical 5.8, docs 4.5, the five test parts 7.5 to 14). Now: `build` 2.4 min with warm caches (restore 14 s, stage0 13 s, smith 57 s, the tests 41 s, pack and save 8 s) and 2.3 to 2.9 min with empty ones (the step cache saves little); a job that takes the build starts its work after 18 s (the caches 12 s, unpack 2 s) and `smith test` then runs a chain of about 55 s before the first test (a build of a just-built tree is not a no-op, #816); `mechanical` 2.9 to 4.8 min; 4 test parts 6.2 to 8.8 min (the runner 261 to 357 s for 440 to 840 tests). The verdict of a run with free slots is about 11.5 min (changes 9 s, build 143 s, the slowest part 528 s), 14.6 min with empty caches and the old runner, against 21.5. The 5-minute target is not reached: 4 parts of about 4.4 min of tests on 3-core runners are the floor of what 5 jobs at once can do, and the tests need either less CPU or more cores. Under load the queue decides: one run waited 16 min for its `build` and 20 min for its last part behind other pull requests' jobs, and the parts differ by 2 min because `.github/shard-costs.tsv` is older than the tests (refresh it from the `test-log-*` artifacts, which this workflow had stopped uploading: `.smith` is hidden).

**How many parts.** Linux parts each add about 1.7 min of start to their share of the tests (about 17 min of runner time in all), so the count changes the latency and hardly the load. The macOS side is one job per run (#1709), so the hosted macOS cap of 5 is five runs at once, not one.

**Not covered by a hosted run:** the debugger tests need a runner that may debug (they do nothing for an account that may not, [debugger](../debugger.md)); the editor tests need `nvim`, which only the Linux jobs have (from the repository's own tools cache); a macOS job installs nothing, so a Mac without `nvim` skips them (#3161: the queue's path reaches GitHub only).

**One build is handed to the Linux shards** (#1758). The `macos` job builds and checks in its own checkout and hands nothing over (#1709); `build-linux` packs its tree (zstd) and the shards download it. Storage egress was over the limit 2026-10-30, when 10 shards each downloaded the uncompressed ~1 GB tree: watch it.
