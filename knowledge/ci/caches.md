# CI caches, downloads and the step cache

**What a job's setup restores and builds** (#2242). Run 41766089451 spent 5 minutes in the Mac's `setup-smith`, 71 s of it fetching and building smith; the rest was restoring the 1.5 GB step cache and compiling every test, though the Mac runs only `--macos-only`. So `setup-smith` takes `test-flags`: the `macos` job and the Mac's `warm` pass `--macos-only --shard 1/1 --costs <file>` (a `--shard` is what makes the scan list one part, so the runner and test programs built are those of the part, and the run in `macos_tests` gives the same options so nothing is rebuilt); the Linux jobs build every test once in `build-linux`. The Mac's saved cache then holds what the Mac builds, not the Linux-sized one (the keys were already per OS). A job with `artifact:` (the test parts, `check-fmt-prove`, `check-lint`) restores no step cache, since it compiles nothing. On a hosted Linux runner the first step removes the image's unused toolchains (`/usr/local/lib/android`, `/usr/share/dotnet`, `/opt/ghc`, boost, CodeQL, swift) in the background while the caches restore, and the last step waits until `/` has 40 GB free or the removal has ended, whichever comes first (#2255; waiting for the whole removal cost about 127 s per job), and prints `disk wait: N s, M GB free` and `disk: <df -h />` in the job summary; this applies to every job that uses `setup-smith` (`build-linux`, the parts, `release-linux`, `warm`, `frontend-coverage`) after a part and `release-linux` died with "No space left on device" (2026-11-04). The numbers after the change are in the PR's runs, not here yet.

**The lint and proof caches** (#2237). Every queue run linted and proved the whole tree (193 s and 163 s, run 41766089451), since `~/.cache/smith/lint` and `~/.cache/smith/proofs` started empty. `check-lint` restores the first and `check-fmt-prove` the second with `actions/cache/restore`, keyed `smith-lintprove-<os>-<commit>` with the newest entry of the OS as the restore key, like the step cache. Only the Linux `warm` job on a push to `main` fills them: after the step cache it restores the last entry, runs `smith lint` and `smith prove` once (so only what the merge changed runs), and saves both folders under the new commit's key (`continue-on-error`, saved `always()`, so a failure there never fails main's push; its summary prints the `linted N files (R run, C cached, ...)` line and the folder sizes). A cache saved from a queue or pull request ref is invisible to other refs, so main must fill them. `check-lint` prints the same `linted N files` line in its summary. **Every restore names the same two paths as `warm`'s save** (#2954): `actions/cache` hashes the path list into the cache version, so a restore of only `~/.cache/smith/proofs` or only `~/.cache/smith/lint` found nothing, not even by the prefix, and every PR check linted and proved from cold (run 42660438704: 128 s prove, 187 s lint). `check-fmt-prove` and `check-lint` now restore both folders. `prove` and `lint` stay one after the other: two smith verbs in one tree race on `.smith/build.ninja` ("cannot replace", runs 42667056557 and 42668129884), and with the caches hitting lint takes about 15 s. A cache never changes a result: a lint entry is keyed by the lint identity and the file's content (#2236), a proof by the IR the prover checks plus the prover and LLVM versions (`shim/prove.cpp`), neither by the smith binary. The Mac's `macos` job keeps linting cold, since its tree differs from Linux's and only Linux `warm` saves.

**The cache** ([caches](../caches.md)). The LLVM pack is `~/.cache/smith/llvm` and `enzyme` under one immutable key, `smith-llvm-<os>-<arch>-<configuration name>`: restoring it takes about 4 s for 194 MB, downloading the pack from its release 12 to 22 s. The compiles of smith and of the tests are the step cache, with the packages (the tree-sitter CLI) and tools: `smith-steps-<os>-<commit>` with the newest entry of the OS as the restore key, 71 MB; `step-cache-max` of `setup-smith` (`SMITH_CACHE_MAX`, 300M, least recently used first, manifests with their results) keeps it from growing, since a restore carries the whole folder forward. **The cap must be set on the first smith verb of the job** (#3045): the prune runs once an hour at the start of the first verb and stamps the time, and `setup-smith`'s "Fetch the LLVM pack" step (`smith build llvm`) ran first with no cap, so it pruned at the 10 GB default and the builds' 300M never ran; every `macos` and `build-linux` job restored 9.8 GB (3 GB gzip, 113 to 147 s on the Mac) of which a build reads about 20 MB. Only `warm` (a push to `main`, one job on macOS and one on Linux: the Linux shards restored no step cache until it saved one) saves it, so there are few entries and every branch and queue entry restores main's (a cache saved on a branch is seen only by that branch). `warm` starts after `publish` (#2833): a compile step's key holds the digest of the smith that runs it, and `warm` used to run beside `release`, so it built with the stage0 before its commit's while every later job fetched the new one, and `build-linux` hit 23 of 319 steps. It now fetches its own commit's stage0, about 14 minutes later, by name (`setup-smith` input `stage0`, fetch-smith's `tag`), and, when `publish` did not succeed, `warm` fails at once with one line naming `publish` and the release jobs' results instead of waiting 6 minutes (#2976; `publish` now also runs when only the Linux job succeeded, so a macOS timeout no longer keeps the step cache from being saved), and every job's "newest" is `releases/latest`: fetch-smith took the newest of the first 30 listed releases, but the list puts the drafts first (24 stale `stage0-*` drafts) and the rest in no order of date, so on 2026-11-09 `warm` got `stage0-d6bcd6c` 2 s after `stage0-78a4f9a` was published (run 42601821786) and the next `build-linux` hit 24 of 321; a job in the 4 or 5 minutes between `publish` and the save still misses. Pinning the jobs to the cache's stage0 instead would wait for nothing but break the lag rule ([smith-bootstrap](../smith-bootstrap.md)). A compile through a precompiled header is served like any other (the header is keyed by the content of what it was made from, `-fvalidate-ast-input-files-content`): `pch.h` and the four shims that use it (`hook`, `tidy`, `affine`, `effects_infer`) were `(cached)` in a build-linux after a warm (#2833). `smith.c` has the same rule as every smith-cc step: it is served only to a build whose stage0 is the one the cache was warmed with, which `warm` after `publish` now arranges; locally a second build serves it. **Cloud runners get the same folder** (#2690): the Actions cache cannot be read outside Actions, so a cloud session also cannot download an Actions artifact (the zip is served from `productionresultssa<N>.blob.core.windows.net`, which its proxy refuses), so the Linux `warm` job publishes `~/.cache/smith/steps` as `smith-steps-linux.tar.gz` (+ `smith-steps-linux.sha`, the commit) and the count's table as `frontend-coverage.tar.gz` to the rolling prerelease `step-cache` (#2755, replaced on every push to main, never `stage0-*`, so `releases/latest` is unchanged), and step 3 of the runner skill downloads them with `curl` before the first `smith build`. The artifact `smith-steps-linux-<commit>` of #2690 stays for CI. Measured in a fresh container: first `smith build` 94 s cold, 20 s with the folder restored (376 MB, no absolute path inside any entry). The build graph is not a no-op after a build (the restored tree-sitter object keeps its old mtime and is dirty again, which relinks smith and rebuilds what uses it): see #816.

**The step cache for cloud sessions (#2755, #2772).** A cloud session cannot download an Actions artifact, only a release asset. Releases here are immutable: a release takes its assets when it is created and never again (`HTTP 422: Cannot upload assets to an immutable release`). So each push to main makes its own prerelease `step-cache-<sha7>` in one `gh release create` call, with `smith-steps-linux.tar.gz.NN` (the step folder, gzip, cut in parts of at most 1900 MB since an asset may hold 2 GiB; join them in order), `smith-steps-linux.sha` (the commit) and, when that commit's queue run saved the count, `frontend-coverage.tar.gz`. The same step deletes all but the 3 newest `step-cache-*` releases. A reader takes the newest by `createdAt`: see step 3 of the runner skill for the commands.

**The test-result store (#2833).** `smith test` caches each passed test by the content of what it read ([build-tests](../build-tests.md), #2686), and `--shard` uses that cache: the plan is split first, then each part drops its own unchanged tests, so a part's split never depends on what is cached. Measured on part 1 of 8: 97 s cold, 17 s with the store warm. The store (`~/.cache/smith/tests`, about 25 MB for the whole suite) travels like the step cache: in a merge queue run each job that runs tests (every `test-linux` part, and `macos`) publishes its own store as the prerelease `test-cache-<sha7>-<job>` (`linux-2of3`, `macos`) with `.github/actions/test-cache/save` (immutable; the stores of the 10 newest commits kept, since a merge queue's groups are newer than main's commit and 3 let them delete main's (#2938); entries unused for 14 days dropped), and the action `.github/actions/test-cache` restores every store of the newest commit that published one for its OS: it tries the commit under test and its first parents, at most 20, by their tags, so in a queue a group reads the groups ahead of it and then main (REST, no page of releases; a failure leaves the store empty and every test runs). The whole store of a commit is one part's (below), so a commit with another part missing still restores whole. Until #2870 a job `save-test-cache` gathered the parts' stores as artifacts and published one release; it waited for `macos`, and it was one more job in every queue run. **Key:** the test's code, every file it read, the runner's options and, for a test that runs smith, the smith under test, so a change to `smith.c` or `runtime/` reruns the tests that run smith and a change to `lib/std/test.smith` reruns everything that imports it. **Always runs:** a failing test (nothing but a pass is stored), a test marked `// smith-test: uncached` or whose inputs `smith test` cannot list. **Only queue runs and the nightly save**; a pull request run reads. A push to main only publishes. **Nightly:** a `schedule` run restores nothing, so every test runs and the run stores them all; a test that fails there while the cache said pass is a p0 bug in a key. **Part count (#3061):** fixed, 8 parts of the units runner and 1 of the front runner ([jobs](jobs.md)); until then `build-linux` sized it with `smith test --misses`, which needs the tests built before any part starts. **Whole and delta stores (#3061):** the front part publishes the whole store (what it restored plus its own entries) and the import cache; each units part publishes only the entries it added since the restore (`delta` of `test-cache/save`: files newer than the restore's marker), so a restore downloads one whole store and 8 small ones, not 9 copies of the whole. A commit whose front part published nothing restores only the deltas, and the tests it lacks run once more. **macOS (#2833):** the `macos` job restores `smith-tests-macos.tar.gz` of the same release (`test-cache` with `os: macos`), so `--macos-only` runs only the tests whose inputs changed, publishes its own store (`test-cache-<sha7>-macos`) on queue and nightly runs. A commit with no macOS store leaves the newest older one that has one (with none, every macOS test runs).

**Downloads from GitHub retry for about two minutes (#2792).** A release download answers `504` now and then; `curl --retry 3` gave up after a few seconds and failed `build-linux` (and a rerun, too). `fetch-smith` retries by itself (`--retry 10`, the asset API with `--retry-all-errors`, #2796), the `install` job asks the asset API first and the download URL second, and tries again for about 6 minutes (24 tries, 15 s apart, job limit 10 minutes), because a release published seconds ago answered `504` to every try of 40 s of curl on 2026-11-09 (run 42567390515), and smith's own package download (`smith_package_download` in `runtime/package.c`, which fetches Neovim for the editor tests and the tree-sitter CLI for the parser) tries an https URL 8 times, 5 s apart, on any error and says so on stderr (`SMITH_DOWNLOAD_TRIES` and `SMITH_DOWNLOAD_DELAY` override the numbers; `tests/package.c`, whose network is scripted and answers each server once, sets 1 try). When smith gives up after retrying it prints one line, `external: <url> <status> after <n> tries` (#2825), so a failure that is GitHub's or the network's greps apart from smith's own.

**Where packages come from in CI (#2825).** A GitHub 504 hour on 2026-11-08 failed the `test-linux` shards of #2798 on `GET https://github.com/tree-sitter/tree-sitter/releases/download/...` and kept it out of the queue for hours, though main's cache held that package: a job with `artifact:` (the test parts, `check-fmt-prove`, `check-lint`, `release-linux`) restores no step cache, so `~/.cache/smith/packages` and `~/.cache/smith/tools` started empty and the tests fetched the tree-sitter CLI and Neovim. Now the Linux `warm` job fetches both (`smith build nvim`, which fetches Neovim for Linux x86_64 only and fails on a Mac, so the Mac `warm` job skips the step, 2026-11-09) and saves the two folders apart, about 60 MB, as `smith-tools-Linux-<commit>`, and `setup-smith` restores the newest entry in a job with `artifact:`. The `warm` matrix has `fail-fast: false`, so one OS failing never cancels the other's cache save. A job reaches github.com for a package only when that cache lacks it. `fetch-smith` retries its two requests on any error (10 tries) and a request that still fails prints `external: <url> curl exit <n> after 10 tries`: a line starting `external:` means GitHub, not the diff; re-run the job. The download inside smith (`smith_package_download`) retries in the same way, 8 tries, 5 s apart (#2792).

**The import cache (#2891).** std's parse trees and the C headers' declarations that `smith cc --front-end=new` keeps (`~/.cache/smith/imports/<identity>/`, [front end](../front-end.md), From disk) travel with the test store: `.github/actions/test-cache/save` adds the job's cache to its release as `smith-imports-<os>.tar.gz` (also when the job ran no test), merged from `~/.cache/smith/imports` and the folder a smith run inside a test writes (`~/.cache/smith-tests/xdg/smith/imports`, the scratch projects' `XDG_CACHE_HOME`), and `.github/actions/test-cache` extracts every such asset of the newest commit that has one into both; `tests: "false"` restores or publishes only the import cache, which `frontend-coverage-fix` and the count's shards use (they publish as `count` and `count-<k>`, so they need `contents: write`). A test job's set is a few MB; a count shard's holds the module trees of its files, 40 to 90 MB, about 490 MB for a commit's nine count sets, so each job restores only the sets it can use (`imports-from`, #2939): a shard its own `count-<k>` and the fix job's `count`, the fix job `count`, a Linux test job `linux-*` (the dev smith's identity; the count's sets are the release smith's). Each pattern restores only the newest set it names (#2978): a set holds what its job restored plus what it stored, so `linux-*` named six sets of 613 MB with the same ~6460 entries (5.3 minutes); one is enough. The restore prints a line per set (`import cache: set <job>: <n> entries, <MB> MB, <s> s`, or `FAILED at <download|extract>: ...`) and `df` before and after. The restore sets `SMITH_IMPORT_CACHE_LOG`, and `.github/actions/test-cache/report` (run by the save) prints `import cache: <n> processes, headers <h> hits <m> misses, modules <h> hits <m> misses`. Queue runs and the nightly publish; `fresh: true` (the nightly) restores none. A session restores it with the command in the skill smith-dev-build (The import cache).

**A cache that misses says so, and says why (#2876).** Three PRs on 2026-11-09 lost an hour each to a cache that missed silently (the count's cache, an environment variable in the test keys, the `--list` step's progress). Now every cached step prints one line of the same form in the job summary, `cache <name>: <hits> of <total> (<percent>%)`, by the action `.github/actions/cache-report` (inputs `name`, `log`, `inputs`): `steps` (the `smith build` of `setup-smith`: `[n/m]` steps and those ending in `(cached)`), `tests-built` (the `--list` step) and `test-store` (the test-result store: the `build-linux` sizing step and each `test-linux` part; `smith test` prints one line per runner, front and units, and the script adds them). **A warning** (`::warning::`, never a failure) is printed when a *merge queue* run hits under 50% and `git diff` against the queue's base touches none of the cache's inputs (the regex in the call: `runtime/`, `lib/std/test.smith`, `smith.c`, `build.c`, `.github/` for the test store; `build.c`, `patches/`, `llvm/` for the step cache). The warning means a key moved without a reason: read the miss lines above it. **A miss says why** (the test store only; first 5 per runner, `cache test-store: miss <test>: <reason>`): `smith test` (when `CI` is set, or `SMITH_RESULT_CACHE=why` or `=report`) saves the inputs every key holds, apart from the test's files, as `<store>/base/<digest>` (the runner's options, its path, each keyed `SMITH_*` variable, the build files, the smith under test) and compares them on a miss with the stored run that shares the most lines: `the nearest stored run differs in environment SMITH_TEST_STATS is new` names a variable (its name, never its value), `... smith under test (SMITH_SELF) differs` the compiler or smith, `... build file build.c differs` a build file. `<file> changed since the entry was stored` is a test whose entry exists but whose recorded read changed. `no entry, though a stored run had this environment` means the base is not the cause: the test is new, never passed, or its own files changed. The step cache's misses give no reason yet: its keys are in `runtime/executor_cache.c` (#2833), so run `smith build -d explain` on a step that should have hit; a hook there would let this report name the input. Seed a miss to see it: run any `SMITH_X=1 smith test --misses` after a run without it.
