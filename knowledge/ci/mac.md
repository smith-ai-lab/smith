# The owner's Mac in CI

**GitHub's runners come first; the owner's Mac is overflow** (#1141, owner 2026-10-31: "I would prefer to prioritize GitHub runners so that way my MacBook can be off. And if it happens to be on, great, we can use it. But if it's not on, we shouldn't stop working. And also, I would prefer to be able to not have my MacBook fans constantly running"; this replaces #754's Mac-first rule). `changes` outputs `mac`, the `runs-on` of every macOS job (`macos`, and llvm.yml's packs), picked per run by `.github/actions/pick-mac` (`ci.yml` and `llvm.yml` both use it, #1064). The default is `"macos-26"`. It picks `["self-hosted","macOS","ARM64"]` only when both hold: (1) at least one such runner is `online` and not busy (`GET /repos/smith-ai-lab/smith/actions/runners` with the repository secret `RUNNER_STATUS_TOKEN`, a fine-grained token, Administration read-only), and (2) the hosted macOS pool is saturated. The job's own token (`actions: read`; `llvm.yml` declares it) sees that: it lists the repository's runs that are `queued` or `in_progress`, and their jobs with their labels; the pool is saturated when another run has a `macos-26` job `queued` (a job waiting for a slot) or 5 are `in_progress` (the free plan's macOS cap), or a `macos-26` job of a run completed in the last hour was cancelled with no `runner_name` (abandoned: on 2026-11-04 hosted jobs sat 15 minutes with no runner while this repository ran nothing else, and every pull request's `ci` failed on it). It cannot see other repositories of the organisation, which share that cap, so the count is a lower bound; a pick made at the start of a run is a forecast, and jobs the run starts later may still queue. It also outputs `"macos-26"` for a `pull_request` whose head repository is not this one (code from outside never runs on the owner's machine), when a token is missing and when a call fails, so a Mac that is off never stalls a run, and the summary of `changes` says which runner was picked and why. Free resources only: no paid runner. Three runners (`Adams-MacBook-Pro`, `...Pro2`, `...Pro3`) share the machine, each with its own `_work` folder and the owner's own `~/.cache/smith`; nothing there is deleted. A runner takes one job at a time, and overflow may use all three runners at once (owner, 2026-10-31, #1141: no cap on the Mac; three runs' `macos` jobs can reach all three); the Mac is the backup, so its fans run rarely. Each macOS job on the Mac gets `SMITH_CORES=5` (16 / 3, rounded down; 3 on a hosted runner, 4 on Linux) so three at once do not oversubscribe it. `release`, `warm`, `release-linux` and `publish` run hosted. The tools (`nvim`, `gtimeout`) are installed with Homebrew only when missing.

**Does fetch-smith work on the owner's Mac?** (#2835) `mac-fetch-check.yml` (`workflow_dispatch`) runs only `fetch-smith` and `smith version` on `[self-hosted, macOS, ARM64]`, with a 5-minute limit that also covers the wait for a runner, so a Mac that is off ends the run (cancelled) instead of holding it. It passed on 2026-11-09 (run 42524525697), so the macOS jobs pick like any other run: the temporary hosted-only rule of `pick-mac` is gone.

**A Mac that does not start a job costs 3 minutes, not the run** (#2835, lead 2026-11-09). A job queued for `[self-hosted, macOS, ARM64]` waits for a runner that never comes when the Mac is off, asleep or hung though the runners call says `online`, and the run waits for it. So `macos` is not queued on the Mac blind. When `pick-mac` picks the Mac, `mac-probe` (a job with one `echo`, which nothing needs) is queued on it, and `watch`, a hosted Linux job that starts with it, looks at the run's jobs every 10 s for 3 minutes: if `mac-probe` is `in_progress` or `completed`, `macos` runs on the Mac (`runs-on` is `watch`'s `runner` output, not `changes`'s `mac`); otherwise, or when the call fails, `macos` runs on hosted `macos-26` and `mac-probe-end` cancels the probe by taking its concurrency group (`mac-probe-<run>`, `cancel-in-progress`, which cancels a pending job too). Hosted was picked: `watch` answers at once. The price: a run whose Mac did not answer ends `cancelled` (the probe) though every job it owed passed, `ci` is green, and one hosted Linux minute or three per macOS run goes to `watch`. To test it, dispatch `ci.yml` by hand on a branch with `mac: mac` (the Mac, whatever the pool looks like) or `mac: dead` (a runner label nothing carries, as a Mac that is off): the step summary of `watch` says where `macos` ran and why.

**The Mac's Linux runners are overflow too** (#1140, owner 2026-11-02: "I can add Linux jobs to my Mac. That's totally fine with me."), **chosen when the jobs are about to start** (#2259). Picked once in `changes` at the start of a run, the choice almost never saw the pool saturated: in the queue runs of 2026-11-04 13:19 to 13:35 every Linux job ran hosted while test parts waited up to 5.3 minutes for a slot. Now the last step of `build-linux` (no extra job, no extra slot, about 10 s) calls `pick-mac` with `linux-jobs: 10`, the 8 test parts, `check-fmt-prove` and `check-lint` that start next. Hosted comes first: it counts the `ubuntu-latest` jobs of other runs that are `in_progress` or `queued` (this run's own `build-linux` ends right after, so it counts as free), and the jobs that do not fit in the 20 hosted slots, at least 1 when another run's job is already queued, go to the Mac's Linux runners, at most as many as are online and idle (two). The order is parts 8, 7, ..., then `check-lint`, then `check-fmt-prove`. `build-linux` outputs the test matrix with a `runner` per part, and `runner-lint` and `runner-fmt-prove`; the jobs read them as `runs-on`. A fork, a missing token, a failed call or no idle Mac runner gives 0: every job hosted, so a Mac that is off never stalls a run. The runners are OrbStack containers (already installed, nothing else goes on the Mac), `linux/amd64` through Rosetta, so they use the same LLVM pack as hosted Linux and no `linux-arm64` pack exists. Two of them, 4 cores and 12 GB each, each with its own `_work` and cache folder inside its container: they never see the owner's `~/.cache/smith`. A job on one gets `SMITH_CORES=4`, as on hosted Linux. The summary of `build-linux` says how many jobs went to the Mac and why.

Setup by the owner, once per runner (never `sudo`; the token is pasted into the command and nowhere else, since it must not appear in a comment, a file, a log or a transcript, and it expires after an hour):
1. In GitHub, Settings, Actions, Runners, New self-hosted runner, Linux, X64: copy the registration token.
2. Start the container with the token in the command: `orb`/`docker run --platform linux/amd64 --cpus 4 --memory 12g -d --restart unless-stopped --name smith-linux-1 -e REPO_URL=https://github.com/smith-ai-lab/smith -e RUNNER_NAME=mac-linux-1 -e LABELS=self-hosted,Linux,X64 -e RUNNER_TOKEN=<the token> <a runner image that carries the build tools of ubuntu-latest>`.
3. Repeat with a fresh token and `smith-linux-2` / `mac-linux-2` for the second runner.
4. Check Settings, Actions, Runners: both show `Idle` with the labels `self-hosted`, `Linux`, `X64`.
To stop, `docker stop smith-linux-1 smith-linux-2`: CI then runs hosted only.
