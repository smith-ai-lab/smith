# The front-end coverage count in CI

**The front-end coverage count** (#2073). On every push to main whose merge changed more than documents (README, `knowledge/`, the skills, images), the jobs `frontend-coverage-fix`, `frontend-coverage-shard` and `frontend-coverage` run `smith build frontend-coverage` over every tracked `.smith` file on `ubuntu-latest`, with the release smith the fix job builds for that very commit (the other two restore it as the artifact `build-linux-release`). A batch of the queue is one push, so it gets one count. **It runs after the merge and gates nothing** (#3052; owner, 2026-11-11: "Do we need the count job? ... We mostly need to figure out what to work on with translation next. And we want a rough idea of how much work is left."): from 2026-11-06 it gated every queue entry, and it was 11 to 13 minutes of every queue run and the end of its critical path. No PR check and no queue run counts; `ci` neither needs nor owes it. **The alarm.** The last step of `frontend-coverage`, `Gate`, compares the count with main's last one: the `frontend-coverage-<sha>` artifact of the newest commit before the push, on main's first-parent line, whose count job passed. It compares like with like: the passes on the files both tables have, so files that leave the total (#3037) or are new move neither side. When the count fell, the step fails the job (the push run of `ci.yml` is red) and lists the merges since that count (`git log --first-parent <that sha>..HEAD`) and the files that went from pass to fail. Nothing else is opened or posted: the lead reads the result on an hourly check (owner, 2026-11-11: "Can you somewhat just subscribe to that job automatically? So every time we get a new count you find out?"). **Where to read it:** workflow `ci.yml`, event `push`, job `frontend-coverage`, step `Gate`, one line in the log and the job summary, `frontend-coverage-change: <sha> <state> <main's passes> <this count's passes> <files both have> <main's sha>` with state `up`, `same`, `fell`, `fell-meant` (a merge said `Count drop:`), `unmeasured` or `no-base` (`-` where there is no number). The same line, followed by the lines `count: pass->fail <path>`, `count: fail->pass <path>` and (on a fall) `count: merge since <sha7> <subject>`, is the file `change.txt` of the artifact `frontend-coverage-<sha>` and of `frontend-coverage.tar.gz` in the release `count-fixed-<sha7>`. A count that fell is no base (its job failed), so every later push compares with the last count that did not fall and stays red, naming every merge since, until the count is back. A merge that means to lower the count says why in its PR body, a line `Count drop: <why>`: the step reads the bodies of the merges in the range and warns instead. A count that could not be made (the log says `unmeasured`) also fails the job, and so does finding no count to compare with on main's last 20 commits: the gate passed silently on nothing for a day when every download of main's count was corrupt (#3052, gh_retry dropped the zip's NUL bytes). Its job summary has `N of M files pass`, the failures per stage and the top 20 causes, ranked by the files each stops first (the files whose first diagnostic it is, #2247); the artifact `frontend-coverage-<sha>` (kept 30 days) has `output.txt` and `results.tsv`; the step log has one line, `frontend-coverage: <sha> <passed> <total>`, which the lead's watcher reads, followed by 20 lines `frontend-cause: <first> <files> <count> <cause>` (the lead reads them from the job's log with `gh api repos/smith-ai-lab/smith/actions/jobs/<id>/logs`) (`.agents/skills/smith-dev-lead/reference/watch.md`); a worker reads the table from the release `count-fixed-<sha7>` (below).

**How the count is cached (#2832).** The count's slow part is the fixer (a file reads modules that must already be in the new syntax, so the tree is fixed before it is compiled): 1798 s of 1867 s on one shard cold, 275 s with the fixed files restored (4 cores). So the job `frontend-coverage-fix` builds the release smith itself (no `build-linux-release` job, #2832), fixes the tree once, and the `frontend-coverage-shard` jobs only restore its artifact `count-fixed-<sha>` and compile. The job starts from main's fixed files: the newest `count-fixed-<sha7>` release (below). A fixed file is cached under a key of everything its result depends on: the file, every module it imports, the C headers and the objects the fixer is built from (#2309, #2632); a stale or missing entry is only fixed again, so the cache never changes a result. A fix that fails by a plain failure (status 1 to 126) is cached as `<key>.fail` beside the entry and replayed as the same `[fixer]` row (14 files, about 220 s each in the fix job and each shard before); a signal or ulimit kill depends on the machine and is never cached. **Never hash an object that embeds the commit** (#2842): the key hashes the objects of the smith folder, and `commit.o` is compiled with `-DSMITH_COMMIT=<HEAD>`, so for the first day every commit had a new key and main's cached files could never be reused; the key skips `commit.o`, and any object or file added to it must be the same bytes for the same sources. **The release `count-fixed-<sha7>`** (#2832, #3052). The job `count-fixed-save` of the push run (needs the fix job, and runs after the count) publishes the count of that commit as one prerelease, its assets all in one `gh release create` (releases here are immutable): `count-fixed.tar.gz` (the fixed files and the rows the parts measured), `frontend-coverage.tar.gz` (`results.tsv`, `output.txt` and `sha`, when the count was measured) and `count-fixed.tar.zst` (the fixed tree, #2942, below). The 3 newest stay. The fix job unpacks `count-fixed.tar.gz` from one of them found by tag (#2974): along the first parents of `HEAD`, up to 20 commits, the first `count-fixed-<sha7>` release with the asset (the release list is in no order of date and held none in its first 30 of 569); the `count-fixed.tar.zst` beside it is the tree, never restored as fixed files. Two pushes close together run their counts at once, so the second may start from the count before the first. It prints `fixed files: <n> restored from <tag> (<k> commits back)` or `fixed files: none in the last 20 commits`. The first queue run after #2837 was cold (fix job 26 min, shards 5 min each); a warm one should fix in a few minutes. The step `Gate` prints, in the log of the `frontend-coverage` job's `Gate` step and in its job summary, the files that went from pass to fail or back against main's last count (#2879, an `awk` in the step over the two `results.tsv`; a file only one table has is not listed): one line `count: pass->fail <path>` or `count: fail->pass <path>` per file, then `count: N files changed (P pass->fail, F fail->pass)`, or `count: no file changed against main <sha7>`, or `count: no main results to compare (<reason>)`. A cloud session cannot download the artifact, but it reads this with `get_job_logs` (grep `^count:`); a drop names its files, and a fixer PR can quote the ones it fixed. **The fixed files for sessions (#2942).** The errors of the count give lines of the fixed form of a file, and the artifact `count-fixed-<sha>` cannot be downloaded in a cloud session. The fix job also packs the fixed tree (`.smith/frontend-coverage/tree`, at its tree paths, `compile_commands.json` left out) as artifact `count-fixed-tree-<sha>`, and `count-fixed-save` attaches it as `count-fixed.tar.zst` to the release `count-fixed-<sha7>`, next to `frontend-coverage.tar.gz`: by REST, as step 3 of the runner skill does for `frontend-coverage.tar.gz` (the asset named `count-fixed.tar.zst`), then `tar --zstd -x -C <dir>`. **The row cache (#2832).** A row of the table (the stage and message of one file) is cached too, as `<key>.row` beside the fixed files, so a file whose compile inputs did not change is not compiled again. The key is *include by default, exclude by name*: the file, every module it imports, the C headers, the fixer, and every link input of the smith program (`build.c`'s graph: `smith.o`, the runtime `rt_*.o`, the library, shim and pack objects, the front-end objects `front_*`), plus the embedded std sources and headers and the identity of clang and LLVM. Left out, with the reason: `commit.o` (embeds HEAD in `-DSMITH_COMMIT`, so it differs on every commit and cannot change a compile), `lint_identity.o` (only `smith lint` reads it, never a fix or a compile) and, because a runtime edit made #2854's queue run fix all 1609 files again, the objects that hold only another verb's code: `rt_runtime_docs.o` (`smith docs`), `rt_smith_protocol_dap.o`, `rt_smith_protocol_mcp.o` and `rt_runtime_mcp*.o` (the MCP server and its debug session: `smith mcp`), `lldb_dap_shim.o` and `lldb_server_shim.o` (`smith dap`, the debug server) and `front_lsp_*.o` (the language server's modules: `smith lsp`). A step of the fix job ("Check the objects the count's key leaves out") runs `nm` on them and fails when an object outside `smith.o` and `rt_runtime_verbs.o`, which dispatch the verbs, calls a symbol one of them defines. Kept in the key, because the startup, a crash trace or the lint path reaches them: `rt_runtime_test_cache.o` (it was left out as `smith test`'s cache until #2869 made the executor's step cache call `smith_self_digest` from it, the digest that keys every compile step; the check above caught that), `rt_runtime_account.o`, `rt_runtime_changed.o`, `rt_runtime_coverage.o`, `rt_runtime_explain.o`, `rt_runtime_symbolize.o`, `rt_runtime_lint_cache.o`, `lldb_shim.o`, `lsp_shim.o`. Anything not on that list is in the key, so a new object is hashed until someone shows it cannot affect a compile. The nightly count without the cache (#2955, below) is the check: a row that differs there is a key that left something out. The fix job prints `rows to measure: M of T` (rows with no entry) and sizes the shards from it: `ceil(8 * M / T)` parts, 1 to 8, so a warm count is 3 jobs against 10 before: the fix job, which also measures the rows left when that is one part or none (as part 1 of 1, no shard job), the merge and `count-fixed-save`; two or more parts run as `frontend-coverage-shard` jobs (a cold run: the count is 1 + up to 8 + 2 jobs on the build the fix job packs as artifact `build-linux-release`). The rows that miss are compiled together (#2888): one `smith cc --front-end=new` per group of up to 32 files of one project folder, so the modules and C headers a group imports are read once (the file a group's process leaves no result for, after a crash or the 6 GB cap, is compiled again alone); the table is byte-identical to compiling each file alone, and the compile phase of 41 test files went from 6.7 s to 2.6 s, of 14 files of `front/` from 10.7 s to 5.2 s. Each part uploads its new rows as `count-rows-<sha>-<k>`. The rows go back the same way: `count-fixed-save` also downloads the parts' `count-rows-<sha>-*` artifacts into the folder before it packs `count-fixed.tar.gz`, so the next run starts with every row measured; `warm` no longer attaches its own `count-fixed.tar.gz` (a copy without the rows would be restored as often as the one with them).

**The count in a pull request's check (#2914), until #3052.** From 2026-11-09 a PR check whose diff touched `front/`, `lib/std/`, `shim/cimport*`, `runtime/front*`, `runtime/lang*` or `build.c` counted a sample (the fix job and 2 of the parts), after #2808 sent about 73 files from pass to `fixer` and, as the front queue entry, failed every group behind it for over an hour. With the count after the merge (#3052), no PR check counts: a PR that touches the front end checks the files it changes with `smith build frontend-coverage -Dfiles=<paths>` before it is opened (the runner skill), and a loss on main is the alarm above.

**The nightly count with no cache (#2955).** Every cache above names the nightly count as its soundness check, and until #2955 that count never ran (every count job's `if:` named only `merge_group`). Now the `schedule` run, and a `workflow_dispatch` of `ci.yml` with `uncached` set (by hand), counts with no cache: the fix job restores no fixed files (so no row either: the rows live beside them), the import cache is restored `fresh` (nothing), the shards are all 8. Its `frontend-coverage` job then compares its `results.tsv` with the table of the cached count of the same commit (the artifact `frontend-coverage-<sha>` of the newest commit on the first-parent line from the run's own that has a passing one): it logs `nightly count: N files pass (cached: M, ...)`, then one line `nightly count: differs <path>: cached [<first row that differs>] uncached [...]` per file whose rows differ (or that only one table has), and fails when any differs or the totals differ, so a red nightly is the signal and each file named is a cache bug. Not cleared: the step cache (`~/.cache/smith/steps`) that `setup-smith` restores to build the release smith in the fix job; the count measures with that smith, and a stale step there would show as the same difference in both tables only if the queue's smith had the same stale step. The run uses the same queue yielding as other runs.
