# The front-end coverage count in CI

**The front-end coverage count** (#2073). In every `merge_group` run whose scope is `full` (#2433) the job `frontend-coverage` runs `smith build frontend-coverage -Dall=1 -Dsmith=<smith>` on `ubuntu-latest`, with the smith of that run's `build-linux` (it `needs: build-linux` and restores the artifact like the test shards, no second build), so every merge main takes is counted, on the very commit it is fast-forwarded to (a group of 2 or 3 PRs gets one count; a group the queue cancels cancels it). A push to main and a pull request run no count. It gates the merge (owner, 2026-11-06, after the count went unmeasured for five hours while PRs kept merging): it is in `ci`'s `needs` and owed by a full merge group, and its last step, `Gate`, fails when the count could not be made (the log says `unmeasured`) or when it is below main's last count, read from the `frontend-coverage-<sha>` artifact of the newest commit on main that has one. A PR that must lower the count says why in a body line `Count drop: <why>`, and the lead agrees on the PR. Its job summary has `N of M files pass`, the failures per stage and the top 20 causes, ranked by the files each stops first (the files whose first diagnostic it is, #2247); the artifact `frontend-coverage-<sha>` (kept 30 days) has `output.txt` and `results.tsv`; the step log has one line, `frontend-coverage: <sha> <passed> <total>`, which the lead's watcher reads, followed by 20 lines `frontend-cause: <first> <files> <count> <cause>` (the lead reads them from the job's log with `gh api repos/smith-ai-lab/smith/actions/jobs/<id>/logs`) (`.agents/skills/smith-dev-lead/reference/watch.md`). `timeout-minutes: 20` counts queue time.

**How the count is cached (#2832).** The count's slow part is the fixer (a file reads modules that must already be in the new syntax, so the tree is fixed before it is compiled): 1798 s of 1867 s on one shard cold, 275 s with the fixed files restored (4 cores). So the job `frontend-coverage-fix` (merge queue, scope `full`) builds the release smith itself (no `build-linux-release` job, #2832), fixes the tree once, and the `frontend-coverage-shard` jobs only restore its artifact `count-fixed-<sha>` and compile. The job starts from main's fixed files: `warm` attaches `count-fixed.tar.gz` to each `step-cache-<sha7>` release, and the job unpacks the newest one that has it. A fixed file is cached under a key of everything its result depends on: the file, every module it imports, the C headers and the objects the fixer is built from (#2309, #2632); a stale or missing entry is only fixed again, so the cache never changes a result. A fix that fails by a plain failure (status 1 to 126) is cached as `<key>.fail` beside the entry and replayed as the same `[fixer]` row (14 files, about 220 s each in the fix job and each shard before); a signal or ulimit kill depends on the machine and is never cached. **Never hash an object that embeds the commit** (#2842): the key hashes the objects of the smith folder, and `commit.o` is compiled with `-DSMITH_COMMIT=<HEAD>`, so for the first day every commit had a new key and main's cached files could never be reused; the key skips `commit.o`, and any object or file added to it must be the same bytes for the same sources. Main's `warm` publishes the fixed files about 11 minutes after a merge, so the next queue run used to start cold; the job `count-fixed-save` (needs `ci` green and the fix job) now puts the group's `count-fixed` artifact in a prerelease `count-fixed-<sha7>` (the 3 newest stay), and the fix job unpacks the newest of the `step-cache-*` and `count-fixed-*` releases that has one. The first queue run after #2837 was cold (fix job 26 min, shards 5 min each); a warm one should fix in a few minutes. The gate prints, in the log of the `frontend-coverage` job's `Gate` step and in its job summary, the files that went from pass to fail or back against main's last passing count (#2879, an `awk` in the step over the two `results.tsv`): one line `count: pass->fail <path>` or `count: fail->pass <path>` per file, then `count: N files changed (P pass->fail, F fail->pass)`, or `count: no file changed against main <sha7>`, or `count: no main results to compare (<reason>)`. A cloud session cannot download the artifact, but it reads this with `get_job_logs` (grep `^count:`); a drop names its files, and a fixer PR can quote the ones it fixed. The comparison is output only: it never fails the job and never changes the count. **The row cache (#2832).** A row of the table (the stage and message of one file) is cached too, as `<key>.row` beside the fixed files, so a file whose compile inputs did not change is not compiled again. The key is *include by default, exclude by name*: the file, every module it imports, the C headers, the fixer, and every link input of the smith program (`build.c`'s graph: `smith.o`, the runtime `rt_*.o`, the library, shim and pack objects, the front-end objects `front_*`), plus the embedded std sources and headers and the identity of clang and LLVM. Left out, with the reason: `commit.o` (embeds HEAD in `-DSMITH_COMMIT`, so it differs on every commit and cannot change a compile), `lint_identity.o` (only `smith lint` reads it, never a fix or a compile) and, because a runtime edit made #2854's queue run fix all 1609 files again, the objects that hold only another verb's code: `rt_runtime_docs.o` (`smith docs`), `rt_smith_protocol_dap.o`, `rt_smith_protocol_mcp.o` and `rt_runtime_mcp*.o` (the MCP server and its debug session: `smith mcp`), `lldb_dap_shim.o` and `lldb_server_shim.o` (`smith dap`, the debug server) and `front_lsp_*.o` (the language server's modules: `smith lsp`). A step of the fix job ("Check the objects the count's key leaves out") runs `nm` on them and fails when an object outside `smith.o` and `rt_runtime_verbs.o`, which dispatch the verbs, calls a symbol one of them defines. Kept in the key, because the startup, a crash trace or the lint path reaches them: `rt_runtime_test_cache.o` (it was left out as `smith test`'s cache until #2869 made the executor's step cache call `smith_self_digest` from it, the digest that keys every compile step; the check above caught that), `rt_runtime_account.o`, `rt_runtime_changed.o`, `rt_runtime_coverage.o`, `rt_runtime_explain.o`, `rt_runtime_symbolize.o`, `rt_runtime_lint_cache.o`, `lldb_shim.o`, `lsp_shim.o`. Anything not on that list is in the key, so a new object is hashed until someone shows it cannot affect a compile. The nightly count without the cache (#2833) is the check: a row that differs there is a key that left something out. The fix job prints `rows to measure: M of T` (rows with no entry) and sizes the shards from it: `ceil(8 * M / T)` parts, 1 to 8, so a warm queue run is 3 count jobs against 10 before: the fix job, which also measures the rows left when that is one part or none (as part 1 of 1, no shard job), the merge and `count-fixed-save`; two or more parts run as `frontend-coverage-shard` jobs (a cold run: the fix job packs the build as artifact `build-linux-release` for them, and the count is 1 + up to 8 + 2 jobs). Each part uploads its new rows as `count-rows-<sha>-<k>`. The rows go back the same way: `count-fixed-save` also downloads the parts' `count-rows-<sha>-*` artifacts into the folder before it packs `count-fixed.tar.gz`, so the next run starts with every row measured; `warm` no longer attaches its own `count-fixed.tar.gz` (a copy without the rows would be restored as often as the one with them).
