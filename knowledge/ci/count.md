# The front-end coverage count in CI

**The front-end coverage count** (#2073). `.github/workflows/count.yml` runs `smith build frontend-coverage` over every tracked `.smith` file after every push to `main` that changes code (the push trigger's `paths` are the code paths: not `knowledge/`, `.agents/`, `.claude/skills/`, top-level `*.md`, images or other workflows), and by `workflow_dispatch`. The job `frontend-coverage-build` builds the release smith for that commit, the 8 `frontend-coverage-shard` jobs each fix the files they own and the modules those import (a quarter of the tree for an eighth of its files, #3369: the fix was one serial job of 6 to 9 minutes before the shards) and compile them, and `frontend-coverage` prints the result. Every count starts from nothing: no cache, no fixed files restored. No pull request or queue run counts (#3052), and nothing gates on it.

**One count at a time (#3196).** The workflow has the concurrency group `count` with `cancel-in-progress: false`, on the workflow (no job has a group of its own, so no shard is cancelled alone): a running count is never cancelled and finishes. A merge that lands meanwhile waits, and a newer merge replaces a count that is still waiting (one running, one pending). With `cancel-in-progress: true` every count was cancelled just before it finished (merges land every ~9 minutes, a count takes 9 to 10: runs 43122712382, 43123859041, 43125081029), so none finished. Under steady merges a count now finishes about every 10 minutes, for the newest commit that was waiting. It is a workflow of its own so that this concurrency does not touch the post-merge jobs of `ci.yml` (publish, warm, release, macos). The nightly cron is gone: the number is at most one count behind `main` plus the waiting one. Runner budget: a queue run peaks at 9 Linux jobs, a push run of `ci.yml` at 2, the count at 8 shards (about 2 minutes, after a 6-minute single job), so 19 of the owner's 20 (owner, 2026-11-11: "we want to be using as much of our free resources as possible").

**What it prints.** The step log has one line `frontend-coverage: <sha> <passed> <total>`, which the lead's watcher reads, then the lines `frontend-regressed-count: <n>` and one `frontend-regressed: <file>` for each file that passed in the last finished count on `main` (the newest successful run of `count.yml` before this one; its artifact `frontend-coverage-<sha>` is the stored result) and fails now (`frontend-regressed-count: unknown` when that table cannot be found). A count above 0 acts (#3296): after the table is saved, the last step reopens the issue each commit of the range (last finished count, exclusive, to this commit) closes through its pull request, adds the label `regressed` (no comment, no body edit), prints `frontend-regressed-by: <sha7> #<pr> #<issue>` and ends red, so the commit on `main` shows a failed `count`. At 0 or unknown it does nothing, and a later green count closes nothing: the worker closes its ticket once its fix's count shows 0. A manual run with `rehearse` true tests this path without changing an issue, `frontend-errors`, `frontend-cause` (20 lines: `<first> <files> <count> <cause>`), `frontend-pair`, `frontend-name` and `frontend-fail` (#3271: one line per failing file, `<path> <stage> <n> <cause> [; <cause> ...]`, every distinct cause of the file in order of first appearance, up to 8 then `; +<k> more`, sorted by path, excluded files left out; the job log holds the per-file table, so `grep -c 'frontend-fail:'` is the total minus the passed). The lead reads them with `gh api repos/smith-ai-lab/smith/actions/jobs/<id>/logs` (`.agents/skills/smith-dev-lead/reference/watch.md`). The job summary has `N of M files pass`, the failures per stage and the top 20 causes, ranked by the files each stops first (#2247). The artifact `frontend-coverage-<sha>` (kept 30 days) has `output.txt` and `results.tsv`.

**What it measures.** A file reads modules that must already be in the new syntax, so the fixer runs on the whole tree before anything is compiled; the shards then compile the fixed files, 8 parts in all.

**History.** The count gated every queue entry, then ran on each push to main with an alarm until #3052, then nightly (#3172, 8 parts), and since #3196 runs after every code merge (8 parts).
