# The front-end coverage count in CI

**The front-end coverage count** (#2073). In every `merge_group` run whose scope is `full` (#2433) the job `frontend-coverage` runs `smith build frontend-coverage -Dall=1 -Dsmith=<smith>` on `ubuntu-latest`, with the smith of that run's `build-linux` (it `needs: build-linux` and restores the artifact like the test shards, no second build), so every merge main takes is counted, on the very commit it is fast-forwarded to (a group of 2 or 3 PRs gets one count; a group the queue cancels cancels it). A push to main and a pull request run no count. It gates the merge (owner, 2026-11-06, after the count went unmeasured for five hours while PRs kept merging): it is in `ci`'s `needs` and owed by a full merge group, and its last step, `Gate`, fails when the count could not be made (the log says `unmeasured`) or when it is below main's last count, read from the `frontend-coverage-<sha>` artifact of the newest commit on main that has one. A PR that must lower the count says why in a body line `Count drop: <why>`, and the lead agrees on the PR. Its job summary has `N of M files pass`, the failures per stage and the top 20 causes, ranked by the files each stops first (the files whose first diagnostic it is, #2247); the artifact `frontend-coverage-<sha>` (kept 30 days) has `output.txt` and `results.tsv`; the step log has one line, `frontend-coverage: <sha> <passed> <total>`, which the lead's watcher reads, followed by 20 lines `frontend-cause: <first> <files> <count> <cause>` (the lead reads them from the job's log with `gh api repos/smith-ai-lab/smith/actions/jobs/<id>/logs`) (`.agents/skills/smith-dev-lead/reference/watch.md`). `timeout-minutes: 20` counts queue time.

**How the count is cached (#2832).** The count's slow part is the fixer (a file reads modules that must already be in the new syntax, so the tree is fixed before it is compiled): 1798 s of 1867 s on one shard cold, 275 s with the fixed files restored (4 cores). So the job `frontend-coverage-fix` (merge queue, scope `full`) builds the release profile of smith (the artifact `build-linux-release` the shards restore; a job of its own until #2870), fixes the tree once and the eight `frontend-coverage-shard` jobs only restore its artifact `count-fixed-<sha>` and compile. The job starts from main's fixed files: `warm` attaches `count-fixed.tar.gz` to each `step-cache-<sha7>` release, and the job unpacks the newest one that has it. A fixed file is cached under a key of everything its result depends on: the file, every module it imports, the C headers and the objects the fixer is built from (#2309, #2632); a stale or missing entry is only fixed again, so the cache never changes a result. A fix that fails by a plain failure (status 1 to 126) is cached as `<key>.fail` beside the entry and replayed as the same `[fixer]` row (14 files, about 220 s each in the fix job and each shard before); a signal or ulimit kill depends on the machine and is never cached. **Never hash an object that embeds the commit** (#2842): the key hashes the objects of the smith folder, and `commit.o` is compiled with `-DSMITH_COMMIT=<HEAD>`, so for the first day every commit had a new key and main's cached files could never be reused; the key skips `commit.o`, and any object or file added to it must be the same bytes for the same sources. Main's `warm` publishes the fixed files about 11 minutes after a merge, so the next queue run used to start cold; the job `count-fixed-save` (needs `ci` green and the fix job) now puts the group's `count-fixed` artifact in a prerelease `count-fixed-<sha7>` (the 3 newest stay), and the fix job unpacks the newest of the `step-cache-*` and `count-fixed-*` releases that has one. The first queue run after #2837 was cold (fix job 26 min, shards 5 min each); a warm one should fix in a few minutes. The gate prints, under main's last count, the files whose result changed against main (path, main's stage, this run's stage; `-` is a file one table lacks), so a drop names its files.
