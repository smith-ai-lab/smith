# The front-end coverage count in CI

**One mechanism, one place (#3369).** The count (`smith build frontend-coverage`: how many original-syntax `.smith` files the new front end compiles after the fixer) runs in the merge queue's run of `ci.yml` (`merge_group`, scope `full`), on the commit the queue would merge, and **refuses the entry** when a file that passed on the base no longer passes. `count.yml` is gone: nothing runs the count after a merge, and nothing reopens a ticket (on 2026-11-12 #3355 lowered it from 1179 to 1047 of 1565, five counts failed in a row after the merge, and the step that acted on it reopened the ticket of the last PR to merge, which was not the cause). There is no hand dispatch: a worker reads the count of its own merge in the log of its queue run.

**The jobs.** `release-pack-linux` builds the release profile of the commit (-O2, #2684) and packs `build` and `.smith` as the artifact `build-linux-release`, so the count builds nothing of its own; it ends there (about 2 minutes into the run). `release-package-linux` restores that build, packages the release tarball and checks the objects the count's key leaves out, off the count's path (in the first queue run with the count the shards waited 4.4 minutes for a job whose last 2.3 minutes were the packaging). `count-shard` (8 jobs, `needs: release-pack-linux`) restores that build; shard k of 8 fixes the files whose path hashes to k - 1 modulo 8 **and the modules they import, transitively** (not the whole tree: the fix of the tree was one serial job of 6 to 9 of the 13 to 15 minutes of the count, #3369; the rows of a file made from its closure are the rows of a full run, the same as `run ... FILES`, #2309) and compiles them, and saves its table. `count` joins the tables in the order of the files (a file in no part or in two is an error), compares with the base, prints the lines below, publishes the table and fails the run on a regression. `ci` owes `count-shard` and `count` in a full queue run, so an unmeasured count (a shard that failed or hung: the count step is killed at 420 s, a shard takes 3 to 4.5 minutes, and the job at 10 minutes, so a hang costs the queue little more than a normal run; a shard whose runner is lost, as in run 43313009698, is GitHub's to time out and `fail-fast` cannot run) refuses the entry too. A shard fails the run at once (`fail-fast`, #3051).

**The base.** The table of the newest commit among the first 20 first parents of the commit under test that a queue run published: the prerelease `test-cache-<sha7>-count-table` (asset `frontend-coverage-table.tsv`, one release for the commit, made whole by `gh release create` in the step "Publish the table", only after the gate passed; the same ten-newest-commits rule as the test stores prunes it, [caches](caches.md)). None found: `frontend-regressed-count: unknown` and a warning, the run passes, and its table is the base of the next. **A regression** is a file whose stage was `pass` on the base and is not `pass` now, and which is still in the tree; a file removed is not one, a new file that does not pass yet is not one. Each is printed as `frontend-regressed: <file> (<stage>: <first cause>)` and as an `::error file=` line, so the failure names the file and its first cause. **The rule (owner, 2026-11-12: "yeah do your recommendation please", the recommendation being to refuse any change that makes a passing file fail, not only one that lowers the total):** a change that fixes three files and breaks three is refused. There are two ways out, and the failure says both: fix the file, or, for a file that should no longer be measured, list it in `scripts/frontend_coverage/excluded.txt` with a valid reason ([the count's excluded files](../front-end/driver.md)); a listed file has no row in the table, so it is not a newly failing file, and the tool refuses a bad line or a listed file that compiles. A file that starts to pass is always allowed. The comparison is `frontend_coverage regressed BASE NOW` (the count's tool, no shell file) (a test in `tests/frontend_coverage_test.smith` shows that a file listed in `excluded.txt` or gone from the tree is not named, and that the table compared with is the base's, not an older green run's).

**The gate's version, and a new gate that only reports (#3443).** On 2026-11-12 the gate merged with two bugs, refused healthy pull requests and stalled the queue for over an hour. Now a gate that has not run enough queue runs cannot refuse. The gate has a version (`gate_version` in `scripts/frontend_coverage/main.smith`), bumped by any change to the comparison: the text of `regressed` between the `gate-begin` and `gate-end` lines of the tool, and the lines of the gate step of `ci.yml` between its own `gate-begin` and `gate-end`. `gate_fingerprint` is the hash of that text, which `frontend_coverage gate-check SOURCE CI` computes (nobody hashes by hand), and the test `the_gate_version_moves_with_the_comparison` fails, printing the fingerprint to write, when the text changed and the number did not. Each queue run publishes, next to its table in the same release, `frontend-gate.tsv`: `version TAB run TAB would-refuse TAB dirty TAB mode`, where `run` counts the finished queue runs of that version (1 for the first run of a new version), `would-refuse` is what the comparison named and `dirty` is 1 when one of the version's first 10 runs would have refused. The next run reads only the base's row. **A version refuses from its 11th run, and only when `dirty` is 0**; before that, and for good when `dirty` is 1, the step is report-only: it prints `frontend-would-refuse: <file> (<stage>: <cause>)` for each file and `frontend-would-refuse: <n>`, and the job succeeds. No input, flag or label turns it off; the first version (the gate after #3427) starts report-only like any other. **Where a stuck gate shows:** a gate that stays report-only because a dry run would have refused prints the line `frontend-gate: <version> <run> <would> <dirty> report-only` and a `::warning::` that says `stays report-only: one of its first 10 queue runs would have refused`, and the job summary opens with **The gate is report-only**; the stall alarm reads that warning. The way out is a new gate version.

**The gate demotes itself (#3443, item 5; owner, 2026-11-12: "I trust you").** The release `count-gate-log` (asset `gate-log.tsv`, the last 50 queue runs, one line each: pull request, gate version, status `refused`, `ok`, `report` or `demoted`, and the files the comparison named as `,a,b,`) is read by every run and appended to by it. A run whose gate is about to refuse, and whose last three log lines are all `refused`, for three different pull requests, with a file in all three sets, does not refuse: three unrelated pull requests cannot all have broken the same file, so the fault is the gate's or main's. That run only reports and prints `frontend-gate: demoted (<files>)` (the line the stall alarm, #3444, lists) and a warning; its verdict row has run 0, so the gate counts 10 queue runs again and returns to refusing only by the rule above. Three refusals with no shared file, from one pull request, or with a run that passed in between, keep refusing. The log lives outside the first-parent history because a refused entry never reaches main.

**What it prints.** In the log of `count` (a worker reads its prediction from the queue run of its merge, and from the run before it): `frontend-coverage: <sha> <passed> <total>`, `frontend-errors: <sha> <errors> <files failing>`, `frontend-excluded: <sha> <n>`, `frontend-cause` (20 lines: `<alone> <first> <files> <count> <cause>`), `frontend-pair`, `frontend-name`, `frontend-fail` (#3271: one line per failing file, `<path> <stage> <n> <cause> [; <cause> ...]`, every distinct cause of the file in order of first appearance, up to 8 then `; +<k> more`, sorted by path, excluded files left out; `grep -c 'frontend-fail:'` is the total minus the passed), `frontend-base: <sha7>`, `frontend-gate: <version> <run> <would> <dirty> <mode>`, `frontend-would-refuse: <n>` and `frontend-regressed-count: <n>`. The job summary has `N of M files pass`, the failures per stage and the top 20 causes, ranked by the files each stops first (#2247). The artifact `frontend-coverage-<sha>` (kept 30 days) has `output.txt` and `results.tsv`. Read the log with `gh api repos/smith-ai-lab/smith/actions/jobs/<id>/logs`.

**What it measures.** A file reads modules that must already be in the new syntax, so each shard fixes the files it owns and the modules they import before anything is compiled, then compiles the fixed files.

**Times (#3369).** Before: one fix job of 8.5 to 12 minutes (the release build 2, the fix of the tree 6 to 9), the shards 3.5, the merge 1: 12 to 17 minutes after the merge, behind a queue run of 380 to 470 s. See the ticket for the measured times of each step of the change.

**History.** The count gated every queue entry, then ran on each push to main with an alarm until #3052, then nightly (#3172, 8 parts), after every code merge (#3196, #3296: the regression step reopened tickets) and since #3369 it is part of the queue run again, with the fix spread over the shards and a gate on the base's table.
