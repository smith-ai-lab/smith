# CI and the merge queue

**A pull request runs no check; the queue gets every runner** (#3170, replacing the budgeted dispatch of #2856, owner 2026-11-11: "the individual PRs are not doing checks anymore. We're just doing the merge queue. So all the resources are going towards that."). On 2026-11-11 at 15:52Z the queue run of #3093 was created and its build and test jobs started at 16:07Z to 16:14Z, while about 17 runners' pushes ran their PR checks: the only thing that merges waited behind checks that merge nothing. Now `.github/workflows/ci-pr.yml` runs on `pull_request` and has one job, `ci`, that succeeds at once; the `main` ruleset requires context `ci` from GitHub Actions (15368) and counts a check run from a `pull_request` run, so the PR can enter the queue. There is no dispatcher, no budget, no yield to the queue, no commit status and no self-cancel; `ci-dispatch.yml` and the `yield-to-queue` action are gone. `ci.yml` runs on `merge_group`, `push` to main, the nightly schedule and by hand. A runner whose clone has no pre-push hook (a fresh container before its first `smith build`) is not noticed at the push: the hook installs on the first build, so the gap is a push before any build; the queue run catches what the hook would have, at the cost of a queue run. The `cancel-pr-runs` op of queue-ops cancels nothing now. Prediction (#3170): a queue run's jobs start within 60 s of its creation, runner minutes per merged PR fall by a third, and 9 of 10 queue runs still merge; below that, make the hook's selection equal to the queue's for the changed files, never bring the PR run back.

**A PR the queue lost is queued again by `.github/workflows/queue-heal.yml`** (#2900; every 10 minutes and by hand): it lists the queue's entries on `main` and, for each open PR whose last merge-queue event is `added_to_merge_queue`, older than 15 minutes, with no entry in that list (as #2885 on 2026-11-09, 75 minutes unseen), dequeues and enqueues it as queue-ops does, with `QUEUE_OPS_TOKEN` or else `GITHUB_TOKEN`. It skips a PR labelled `dequeued`: queue-ops' `dequeue` sets that label (an API dequeue leaves no timeline event, #2886 on 2026-11-09), and `enqueue`, `enqueue-many` and `jump` clear it. It logs `queue-heal: #N lost since <time>, re-queued at position P`, or `queue-heal: none lost (Q entries)`. **A second pass dequeues a failed front entry** (#2902): the front PR's group is main plus itself, so when the newest `merge_group` run of ci for its branch, created at or after the entry's `enqueuedAt`, has `conclusion` failure it fails alone (an older run on a `pr-<N>-` branch belongs to an earlier entry of the same PR and is never judged: on 2026-11-11 #3129 and #3056 were dequeued the moment they re-entered, on the run of their first failure; with no run of its own yet the front is "no run yet"); HEADGREEN would keep it and fail every later group (#2808, 2026-11-09, over an hour stopped). It dequeues it with the `dequeued` label and logs `queue-heal: #N dequeued, its own group failed (run <id>, job <name>)`, else `queue-heal: front #N ok (run <id> <status>)`; a cancelled or running front run is left alone. **A fourth pass dequeues a queued PR that conflicts with main** (#2948; #2926 sat 90 minutes in the queue while it conflicted, and nothing woke its runner): for each queue entry it reads `GET pulls/<n>`, and when `mergeable` is `false` or `mergeable_state` is `dirty` it dequeues the PR, labels it `dequeued` and logs `queue-heal: dequeued #N (conflicts with main)`, so its `removed_from_merge_queue` event wakes the runner, who merges main in and asks the lead to enqueue. A `mergeable` of `null` (GitHub is still computing it) is skipped, never dequeued. With nothing conflicting it logs `queue-heal: none conflicting (Q entries)`; a dry run logs `dry-run: would dequeue #N (conflicts with main)`. It runs before the second pass, which then judges the front entry without the PRs it dequeued. queue-heal also runs on `workflow_run` of ci (the cron rarely fires), one run at a time, a new one cancelling the old.

**A stale PR with auto-merge is updated or flagged by queue-heal** (#3200; on 2026-11-11 nothing merged for 54 minutes while #3197 and #3195, both `dirty`, sat out of the queue and nobody was told). A sixth pass of `queue-heal.yml` runs after every push to `main` (a `push` trigger, added because `workflow_run` of ci also fires for `merge_group` runs and for a push only when its slow macOS jobs end, so a merge could go unseen), and looks at each open PR with auto-merge on that is not in the queue. Behind main without a conflict (`compare` says `behind_by` > 0): `PUT pulls/<n>/update-branch`, a merge commit, with `QUEUE_OPS_TOKEN` because an event caused by `GITHUB_TOKEN` starts no workflow and the new head would never get `ci-pr`; the check runs again and auto-merge queues it. Conflicting: a failing check run `conflict` on the head ("This branch conflicts with main. Merge origin/main into it, resolve, push.", made with `GITHUB_TOKEN` and `checks: write`, since a personal token cannot create check runs); the red check wakes the worker that follows the PR, and its next push has a new head without it. `conflict` is not a required check. A PR without auto-merge is left alone; a `mergeable` of `null` waits for the next pass. It logs `queue-heal: #N was K behind main, branch updated`, `queue-heal: #N conflicts with main, check conflict set red on <sha>` or `queue-heal: none stale`.

**Queue operations are a workflow** (#2828). A Claude Code session cannot reach GitHub's GraphQL API, and jumping or dequeuing a queue entry exists only there, so `.github/workflows/queue-ops.yml` (`workflow_dispatch`, inputs `op`, `pr`, `value`) does it from a runner: `jump`, `dequeue`, `enqueue`, `enqueue-many` (`pr` a list of numbers separated by spaces, enqueued 3 s apart in one job, #2851), `cancel-pr-runs` (force-cancels the queued PR checks of `ci`, except PRs that touch `.github/`; ci-dispatch starts them again), `rerun-failed` and `set-group-size` (1, 2, 4 or 8 on the `main` ruleset; nothing else writes it, and a write cancels the group being built, #3286; the second pass of queue-heal needs it at 1). It tries `GITHUB_TOKEN` first and the repo secret `QUEUE_OPS_TOKEN` (fine-grained, this repo only: pull requests write, actions write, administration write) only when GitHub refuses; every run writes one line per op to its job summary (op, PR, result, actor). **Several ops in one dispatch (#2872).** The input `ops` is a list, one `<op> <pr>` per line or separated by `;` (`jump 2864` / `dequeue 2784`; `enqueue-many 1 2 3`; `set-group-size 2`); when set it replaces `op` and `pr` (`op` is no longer required, and `op`/`pr` alone is a list of one). The ops run in order inside the one job, each with the same token fallback, and one that fails does not stop the ones after it. The summary ends with `queue-ops: N op(s), M failed` and the step fails when M is not 0, so the run is red exactly when an op failed and its summary line names the op and GitHub's message. `run-name` is `queue-ops: <the ops>` (or `<op> <pr>`), so the run list shows what each run did. The `queue-ops` concurrency group still keeps one pending run, so send one list instead of several dispatches. **A PR that changes a workflow file is enqueued only when it is based on the current main** (2026-11-09: #2855 was refused at 01:23Z): `QUEUE_OPS_TOKEN` has no workflow scope, so merge main into such a branch before enqueuing it. The owner is never asked to run a command for the queue. **Both workflows take a `dry_run` input** (#2934): dispatched with `dry_run: true`, every read runs as usual, every write (enqueue, dequeue, jump, label changes, force-cancel, rerun, the ruleset PUT) is skipped and printed as `dry-run: would <op> <args>`, so a PR that changes either file is tested by dispatching it on its own branch (`ref: <branch>`); `schedule` and `workflow_run` events never dry-run.

**`jump` reports before the queue shows it** (#2843 and #2842, 2026-11-08). The `jump` entry prints `jump=true`, but the position it prints and `queue_order` can still show the old order, even 10 s later. Judge a jump by which entry's `ci` run starts first, not by the printed position.

**A queue run whose group left the queue cancels itself** (#2241). When the queue reorders (a jump to the front, a removal, a failure ahead), GitHub deletes the old group's branch `gh-readonly-queue/main/pr-<N>-<sha>` but does not cancel its run, so the stale run kept holding hosted runners (2026-11-04: five stale runs, one with about 11 of the 20 slots, merges fell to 3 to 4 an hour). `concurrency` can't replace it, since an expression can't cut `pr-<N>` out of the ref. No job waits for it (#2256, which replaces the polling job #2245 added: the polling job held a hosted slot for the whole run, 904 s in #2245's queue run, so a queue run took 12 Linux jobs instead of 11). The composite action `.github/actions/queue-guard` runs in each job of a `merge_group` run (`build-linux`, the test parts, `check-fmt-prove`, `check-lint`) right after checkout, before the long steps: it checks once with `git ls-remote --exit-code` that the run's own ref still exists (exit 2 twice, 5 s apart; any other failure is not a miss) and runs `gh run cancel` (`actions: write` on those jobs, nothing else). A dropped group's run is cancelled by the next job to start, within about a minute, since the jobs start one after another. A live group's branch exists until the queue merges or drops it, so a live run is never cancelled. Nobody cancels stale runs by hand.

**The queue builds one group at a time, and the group is one pull request** (#3131, #3286; owner 2026-11-11: "we should not do speculative runs. because that means we are consuming github runners and we have a limit of 20 of those."). GitHub's ruleset `main` does it all: `max_entries_to_build` 1 (a group is created only when the run ahead has finished, so nothing is built on an unfinished entry and no job waits), `min_entries_to_merge` 1, `max_entries_to_merge` 1 and `grouping_strategy` ALLGREEN. Nothing in `ci.yml` waits or batches: a queue run is the full check of its own tree. **The size is fixed and nothing writes it** (#3286, 2026-11-12). A third pass of `queue-heal.yml` (#3131) used to set the size (1, 2, 4, 8) by the health of the last 10 runs, and it never produced a group of more than one: of the 600 `merge_group` runs of `ci` from 2026-11-06 to 2026-11-12, the 304 that failed or were cancelled and a sample of 40 that passed were all one pull request (`ahead_by` 1). Its only effect was to cancel runs: every write to the ruleset makes GitHub cancel the group being built, and the pass read that cancelled run as bad health and wrote again (04:22:42Z, the size set from 1 to 4: run 43153506621 cancelled and #3268 removed from the queue, then the write back to 1 cancelled run 43154633643 too; 03:35:48Z to 03:50:05Z the same from 1 to 2). So the pass is deleted; `queue-ops`' `set-group-size` stays as the one way to write the setting by hand, and it cancels the running group when used. **The second pass of queue-heal depends on size 1**: it dequeues the front entry whose run failed because "its group is main plus that PR alone"; with a group of more than one that would dequeue the first PR of a group it did not break. What GitHub does with a failed group of more than one is not in our history, so it is unread. **Merging several pull requests per run is not done yet.** With about 7 real failures per 100 runs a group of 4 fails about one time in four, and telling the four apart needs the size written down to 1 and up again, which is the brittle thing removed here. It comes back as a fixed size with no rule once the pre-push hook runs the queue's exact command (after the store series, #3176 to #3179) and a failure in the queue is rare. **A group made at the front by `GITHUB_TOKEN` gets no run** (found 2026-11-11: `jump 3130` sat 56 minutes, 20 PRs enqueued into an empty queue sat 8, while auto-merge by a user token started a run in 20 s): GitHub starts no workflow for an event that `GITHUB_TOKEN` caused. So queue-ops' `jump`, `enqueue` and `enqueue-many` use `QUEUE_OPS_TOKEN` first, and queue-heal logs `queue-heal: FAULT front #N has no merge_group run after M min` and re-queues the front PR with that token when its entry is older than 5 minutes. A PR that GitHub removes with a failed group and that has no fault of its own is queued again with the label `ready` (below).
**A failure does not end the run.** Every job runs to completion and `ci` (`if: always()`) is red when any job failed or was cancelled; see [ci](../ci.md).

**Main's runs do not cancel each other (#2792).** The workflow's concurrency group keeps one running and one *pending* run; a newer run replaces the pending one. With one group for `refs/heads/main` and the merge queue landing a PR every ~30 minutes, a run still pending when the next push arrived was cancelled with no job started, so from 02:21Z on 2026-11-08 `warm` (and with it the `step-cache-<sha7>` release) did not run for 18 of 30 pushes. A push to main now has the group `ci-<sha>`: every main push runs `warm` for its own commit, in parallel with the others (the repository is public, so hosted minutes are free). Only the stage0 release stays one at a time, in `release-macos` and `release-linux`, where skipping a commit in between is fine because the next release has the newer tree. A pull request still has `ci-<number>` (a new push replaces its run) and a merge-queue entry its own ref.

**A runner turns on auto-merge when its PR is ready** (lead, 2026-11-09). The lead enqueues or jumps only for a p0, a stuck entry or a PR that GitHub won't auto-merge (already clean when auto-merge is turned on) is labelled `ready` by its runner instead (below): the order of entries in the queue matters less now that a group tests several entries in one run. A conflict that drops a PR from the queue is the runner's to fix and re-enable.

**A PR labelled `ready` is enqueued by queue-heal** (#2962, owner 2026-11-09: "We want these things to be autonomous."). GitHub won't turn on auto-merge for a PR that is already clean: the call succeeds, `auto_merge` stays null and nothing queues it (#2935, #2940), and a runner can't call `actions_run_trigger`. So when `auto_merge` reads null after `enable_pr_auto_merge`, the runner adds the label `ready`. A fifth pass of `queue-heal.yml` (it runs after every ci completion and every 10 minutes) enqueues each open PR to main with that label that is not in the queue, is mergeable, is not labelled `dequeued`, and whose `ci` check on the current head is `success`, as queue-ops' `enqueue` does; it removes `ready` and logs `queue-heal: enqueued #N (ready) at position P`. A PR whose `ci` is not green yet keeps the label (`queue-heal: #N (ready) ci is <state>, kept`) and is tried on the next pass, so it is queued within one pass of `ready` plus a green `ci` (at most 10 minutes, usually under 2). A dry run logs `dry-run: would enqueue #N (ready)`. A jump stays with the lead.

**The REST quota, and the budget lines** (#2986, 2026-11-09). Every `gh api` call a workflow makes with `GITHUB_TOKEN` counts against one hourly pool for the whole repository, shared by every job of every run (the budget lines of run 42704853134 read 5,000 an hour, and about 870 requests went in about 10 minutes beside one PR check). At 21:33Z it ran out: `gh: API rate limit exceeded for installation` failed two queue runs, a PR check's `changes` and two `ci-dispatch` runs. Four rules follow. (1) Every job prints `api budget: <job> <remaining> of <limit>, resets in <s> s` first and last (`.github/actions/api-budget`; `GET /rate_limit` is free), so a job's spend is the difference less what ran beside it. (2) A call a verdict depends on goes through `gh_retry` (the `api-budget` action (it defines `gh_retry` for the later steps of the job through BASH_ENV)): on a rate-limit error it reads `/rate_limit`, logs `api budget: waiting <s> s for the quota`, sleeps to the reset (at most 20 minutes) and tries again; a wait is not a failure, and when the wait runs out the job fails as before. (3) Reads use the token of the read-only GitHub App `smith-ci-reader` (`.github/actions/ci-reader`; repository variable `CI_READER_APP_ID`, secret `CI_READER_PRIVATE_KEY`; its own 5,000 an hour), exported as `READ_GH_TOKEN`; writes (the commit status `ci`, release creation, run cancel, dispatch) stay on `GITHUB_TOKEN`, and the reader falls back to it with `api budget: reader token unavailable, using the workflow token`. (4) Prefer a call that costs nothing: `git ls-remote`, a release asset by its direct URL.

**What the budget reserved in the saturated hour** (#3069, the dispatch logs of 01:40Z to 02:25Z on 2026-11-11 set against the jobs API). From 02:02Z to 02:13Z the budget was 2 (`queue` 17 to 38) and all 20 slots were in use with 6 to 21 jobs queued, 15 to 20 of them the queue's: the rule did not over-reserve, the queue asked for more than the account has (the entries stacked on #3053's failed head, #3051). Outside that window the error was the other way: it counted only `ubuntu-latest` jobs, so with 5 hosted macOS jobs running at 01:56Z it budgeted 9 when 3 slots were free. It now counts every `ubuntu-*` and `macos-*` job.
