# CI and the merge queue

**A pull request's check runs under a budget, and never ahead of the merge queue** (#2856, replacing the defer of #2822 and the wait of #2356; owner 2026-11-08: "How do we solve this once and for all"). GitHub has no job priority and hands runners out first come, first served, and a wait inside a job holds the runner it waits on. On 2026-11-08 at 23:21 about 25 pull request runs started within minutes, each passing the one check at its start, and two minutes later their jobs held all 20 Linux runners while a queue run's coverage shards waited over 15 minutes. So no `pull_request` event starts a check. `.github/workflows/ci-dispatch.yml` does: one job of seconds, one pass at a time (`concurrency`), on every pull request event, when any `ci` run ends (room freed), every 5 minutes as the backstop and by hand. Each pass scans every open PR to `main`, so a dropped pass loses nothing. It force-cancels a live check whose sha is no PR's head any more (a push replaced it). Then, longest-waiting PR first (`updated` ascending), it starts `ci.yml` with `workflow_dispatch` (input `pr`) on the PR's head branch for every PR whose head has no `ci` check run and no live check. It does so only while **no merge queue job waits** (a `merge_group` run `queued`, or one of its jobs `queued`: a job is listed only once the jobs it needs are done, so `queued` means it waits for a runner) and while **the Linux jobs of the live PR checks plus the new one fit the budget**: `BUDGET` in ci-dispatch.yml, 6 of the 20 (a constant: changing it is a one-line PR, lead 2026-11-08). A live check counts as its live `ubuntu-latest` jobs, and at least 2, the most a PR check runs at once. A PR that cannot start now holds no runner and starts on a later pass; nobody pushes, re-runs or types anything. After its dispatches a pass waits (every 5 s, at most 90 s) until each sha it started shows a live `workflow_dispatch` run, because a dispatched run is listed only about 20 s later and a pass inside that window would dispatch the head a second time and cancel the first run (#2882); if it is not listed by then the pass prints `dispatch: <pr> <sha7> not listed after 90 s`, ends and dispatches nothing again. The dispatcher only runs the checks: the runner turns on auto-merge (below), and GitHub enqueues the PR once its `ci` is green. **How the check reaches the ruleset**: the `main` ruleset requires context `ci` from integration 15368 (GitHub Actions); a `workflow_dispatch` run on the PR's head branch runs on its head sha, and its last job, `ci`, leaves a check run `ci` there, but the ruleset does not count a check run from a `workflow_dispatch` run (2026-11-09: #2857 stayed `blocked` with it green, while #2855, green from a `pull_request` run, was `clean`). So that job also posts its verdict as the **commit status** `ci` on the PR head with `GITHUB_TOKEN`, created by GitHub Actions (15368); its description and link name the run. It posts only when every job before it ran: a cancelled run posts nothing, and a skipped job that was owed fails the verdict it posts. `ci.yml` has no `pull_request` trigger at all: a run whose jobs were all skipped would leave a skipped `ci`, which counts as passing. `GITHUB_TOKEN` can start the run (`workflow_dispatch` is the exception to "a token's events start no workflow"). **A started check gives its runner back to the queue**: every heavy Linux job of a PR check (`changes`, `build-linux`, `test-linux`, `check-fmt-prove`) first calls `.github/actions/yield-to-queue`, one check and no waiting. If a merge queue job waits, it **force-cancels** its own run and ci-dispatch starts the check again once there is room. It is a force-cancel because a plain cancel still runs the `always()` job `ci`, which fails: a red `ci` on the PR head (run 42537002372), while a force-cancelled run leaves no `ci` check run at all (run 42537065604). **A self-cancelled run is never a result**: its head has no `ci`, so the next pass starts it again, and the dispatcher counts a `cancelled` or `skipped` `ci` as none. A check started by hand with `no_yield: true` skips the self-cancel; the dispatcher never sets it (used once, for #2857's own check, while the queue was never idle). A PR from a fork is noted in the pass's summary and skipped: `workflow_dispatch` needs a ref in this repository (every PR comes from the runners; push a fork's branch here to check it). The only runner a PR takes ahead of a queue job is the dispatcher's own job of seconds. `merge_group` and `push` runs are unchanged.

**A queue run yields to the groups ahead of it (#2833).** The same action, on a `merge_group` run, waits in `changes` (only there: `queue-wait: "true"`; the other jobs that call it, for a PR check's yield, never wait) while an earlier `merge_group` run of `ci.yml` (created before this one, not finished) has a job in status `queued` (a job is listed only once the jobs it needs are done, so `queued` means it waits for a runner). Evidence: on 2026-11-08 at 17:48 the front group (run 42505988647) had 2 jobs running and 18 queued while the two speculative groups behind it held 17 of the 20 runners. The front group never waits (no earlier run); the next waits for the front group's queued jobs to get runners, and so on. The cap is 10 minutes (`queue-cap-minutes`), after which the run goes ahead and says so; an API failure counts as no wait. A group that waits holds one small runner (`changes`).

**A PR the queue lost is queued again by `.github/workflows/queue-heal.yml`** (#2900; every 10 minutes and by hand): it lists the queue's entries on `main` and, for each open PR whose last merge-queue event is `added_to_merge_queue`, older than 15 minutes, with no entry in that list (as #2885 on 2026-11-09, 75 minutes unseen), dequeues and enqueues it as queue-ops does, with `QUEUE_OPS_TOKEN` or else `GITHUB_TOKEN`. It skips a PR labelled `dequeued`: queue-ops' `dequeue` sets that label (an API dequeue leaves no timeline event, #2886 on 2026-11-09), and `enqueue`, `enqueue-many` and `jump` clear it. It logs `queue-heal: #N lost since <time>, re-queued at position P`, or `queue-heal: none lost (Q entries)`. **A second pass dequeues a failed front entry** (#2902): the front PR's group is main plus itself, so when the newest `merge_group` run of ci for its branch has `conclusion` failure it fails alone; HEADGREEN would keep it and fail every later group (#2808, 2026-11-09, over an hour stopped). It dequeues it with the `dequeued` label and logs `queue-heal: #N dequeued, its own group failed (run <id>, job <name>)`, else `queue-heal: front #N ok (run <id> <status>)`; a cancelled or running front run is left alone. **A fourth pass dequeues a queued PR that conflicts with main** (#2948; #2926 sat 90 minutes in the queue while it conflicted, and nothing woke its runner): for each queue entry it reads `GET pulls/<n>`, and when `mergeable` is `false` or `mergeable_state` is `dirty` it dequeues the PR, labels it `dequeued` and logs `queue-heal: dequeued #N (conflicts with main)`, so its `removed_from_merge_queue` event wakes the runner, who merges main in and asks the lead to enqueue. A `mergeable` of `null` (GitHub is still computing it) is skipped, never dequeued. With nothing conflicting it logs `queue-heal: none conflicting (Q entries)`; a dry run logs `dry-run: would dequeue #N (conflicts with main)`. It runs before the second pass, which then judges the front entry without the PRs it dequeued. queue-heal also runs on `workflow_run` of ci (the cron rarely fires), one run at a time, a new one cancelling the old.

**Queue operations are a workflow** (#2828). A Claude Code session cannot reach GitHub's GraphQL API, and jumping or dequeuing a queue entry exists only there, so `.github/workflows/queue-ops.yml` (`workflow_dispatch`, inputs `op`, `pr`, `value`) does it from a runner: `jump`, `dequeue`, `enqueue`, `enqueue-many` (`pr` a list of numbers separated by spaces, enqueued 3 s apart in one job, #2851), `cancel-pr-runs` (force-cancels the queued PR checks of `ci`, except PRs that touch `.github/`; ci-dispatch starts them again), `rerun-failed` and `set-build-entries` (1 to 10 on the `main` ruleset; since #2922 queue-heal sets the value itself, so use it only to override). It tries `GITHUB_TOKEN` first and the repo secret `QUEUE_OPS_TOKEN` (fine-grained, this repo only: pull requests write, actions write, administration write) only when GitHub refuses; every run writes one line per op to its job summary (op, PR, result, actor). **Several ops in one dispatch (#2872).** The input `ops` is a list, one `<op> <pr>` per line or separated by `;` (`jump 2864` / `dequeue 2784`; `enqueue-many 1 2 3`; `set-build-entries 5`); when set it replaces `op` and `pr` (`op` is no longer required, and `op`/`pr` alone is a list of one). The ops run in order inside the one job, each with the same token fallback, and one that fails does not stop the ones after it. The summary ends with `queue-ops: N op(s), M failed` and the step fails when M is not 0, so the run is red exactly when an op failed and its summary line names the op and GitHub's message. `run-name` is `queue-ops: <the ops>` (or `<op> <pr>`), so the run list shows what each run did. The `queue-ops` concurrency group still keeps one pending run, so send one list instead of several dispatches. **A PR that changes a workflow file is enqueued only when it is based on the current main** (2026-11-09: #2855 was refused at 01:23Z): `QUEUE_OPS_TOKEN` has no workflow scope, so merge main into such a branch before enqueuing it. The owner is never asked to run a command for the queue. **Both workflows take a `dry_run` input** (#2934): dispatched with `dry_run: true`, every read runs as usual, every write (enqueue, dequeue, jump, label changes, force-cancel, rerun, the ruleset PUT) is skipped and printed as `dry-run: would <op> <args>`, so a PR that changes either file is tested by dispatching it on its own branch (`ref: <branch>`); `schedule` and `workflow_run` events never dry-run.

**`jump` reports before the queue shows it** (#2843 and #2842, 2026-11-08). The `jump` entry prints `jump=true`, but the position it prints and `queue_order` can still show the old order, even 10 s later. Judge a jump by which entry's `ci` run starts first, not by the printed position.

**A queue run whose group left the queue cancels itself** (#2241). When the queue reorders (a jump to the front, a removal, a failure ahead), GitHub deletes the old group's branch `gh-readonly-queue/main/pr-<N>-<sha>` but does not cancel its run, so the stale run kept holding hosted runners (2026-11-04: five stale runs, one with about 11 of the 20 slots, merges fell to 3 to 4 an hour). `concurrency` can't replace it, since an expression can't cut `pr-<N>` out of the ref. No job waits for it (#2256, which replaces the polling job #2245 added: the polling job held a hosted slot for the whole run, 904 s in #2245's queue run, so a queue run took 12 Linux jobs instead of 11). The composite action `.github/actions/queue-guard` runs in each job of a `merge_group` run (`build-linux`, the test parts, `check-fmt-prove`, `check-lint`, `macos`) right after checkout, before the long steps: it checks once with `git ls-remote --exit-code` that the run's own ref still exists (exit 2 twice, 5 s apart; any other failure is not a miss) and runs `gh run cancel` (`actions: write` on those jobs, nothing else). A dropped group's run is cancelled by the next job to start, within about a minute, since the jobs start one after another. A live group's branch exists until the queue merges or drops it, so a live run is never cancelled. Nobody cancels stale runs by hand.

**The queue's build entries follow its health** (#2922, owner 2026-11-09: "is there a way to make it so that the queue automatically grows the concurrency limit or shrinks based on how healthy it's been?"). The third pass of `queue-heal.yml` reads `max_entries_to_build` (B) and the `updated_at` (T) of the ruleset `main`, and counts the completed `merge_group` runs of `ci.yml` created after T. Any `failure` halves B (minimum 1); otherwise 3 or more `success` runs double it (maximum 8, the steps are 1, 2, 4, 8, matching the about 20 Linux runners); cancelled runs count for neither. A change sets a new T, so each level starts counting again. It uses the PUT of `set-build-entries` with the same token fallback and logs one line per run: `queue-heal: build entries B -> B' (<n> passed, <m> failed since T)` or `queue-heal: build entries B kept (...)`.

**The queue tests a batch with one full run** (#2851, owner 2026-11-08: "I thought with a merge queue multiple prs get merged at once?"). The ruleset builds up to 10 entries at once (Build concurrency, set with queue-ops `set-build-entries`; merge max is 10). A batch of 10 is one full run, which peaks at 10 Linux jobs at once (run of #2842), plus 9 waiting `changes` jobs: 19 of the about 20 Linux runners with grouping HEADGREEN: entry *k*'s group is main plus entries 1 to *k*, and when its run passes, entries 1 to *k* all merge with it. So only the last entry being built needs the full checks. A group's branch is `gh-readonly-queue/main/pr-<N>-<sha>`, where `<sha>` is the head of the group ahead of it (or main's commit), so a later group is being built on an entry exactly when a branch `pr-*-<its head sha>` exists. The second step of `changes`, `.github/actions/batch-wait` (`scripts/batch_wait.c`), checks that with `git ls-remote` every 30 s, after a **batching window**: a group that is last waits for its **batch's deadline** (#2925; owner, 2026-11-09: "We don't want the time constantly restarting ... Whatever gets in gets in. We wait no more then n minutes then we start."): the batch is the groups in a row ahead of it that have not started their full build (a job other than `changes` in progress or done), the deadline is the creation of the batch's first merge_group run plus 1 minute (`window_seconds` in `scripts/batch_wait.c`, 60 s; owner, 2026-11-09: "If there is a 1 minute window and the ci takes 10 minutes that doesn't seem too bad?"), and it never restarts, so a PR that arrives after the full build started starts the next batch with its own deadline; the step logs `batch: deadline <time> (batch from <ref>)` and `batch: deadline reached, building`; with `max_entries_to_build` at 1 on the `main` ruleset no later group can exist, so it skips the window and the polling and logs `batch: alone (build entries 1)` (a failed ruleset read counts as 2 or more and waits) for later groups before it decides it is alone, since entries are enqueued in bursts and the queue creates their groups one after another (2026-11-09, the first run at concurrency 10: of a burst of 4 groups, 3 started while last and built in full; a lone entry pays the window; PRs go green minutes apart, not seconds, so at 60 s 4 entries 2.5 to 13 minutes apart made 4 full runs on 2026-11-09 01:25–01:47Z; the lead shortens the window to 1 or 2 minutes once a full run is 5 to 10 minutes (owner, 2026-11-09: "If there is a 1 minute window and the ci takes 10 minutes that doesn't seem too bad?"); the lead enqueues a burst with queue-ops `enqueue-many`). It checks, not the GraphQL queue position, which lags after a jump. While a later group exists, the run waits on that one runner and every heavy job, all of which need `changes`, waits with it. When the later group's run passes, the entry merges and its branch goes: the wait cancels the run. When no later group is left (the later ones failed or left the queue), the wait returns and the same run builds the full checks of the entry's own tree, so the `ci` the ruleset counts is that run's own, as before. **The safety rule**: no PR merges unless a passing full run tested a tree that contains it. The wait never makes `ci` pass; it only holds the full checks back. A stale read can only cost runners: one that misses a later group builds the full checks for nothing, and one that sees a gone group waits one more poll. A failed read builds. The wait is capped at 60 minutes (then it builds anyway), so a wait and a full run stay under the ruleset's 120-minute check timeout; `changes` has `timeout-minutes: 75`. **A later group whose run has a failed job ends the wait at once** (#2903): each poll also reads the latest merge_group run of every later group's branch and its jobs (`gh api`), and a job with `conclusion` `failure` means that group cannot merge this entry, so the run prints `batch: waited`, logs `later group <ref> failed (job <name>), building now` and builds its own tree. On 2026-11-09 the later groups all held a bad entry (#2808, #2886), failed one after another and each failure made the queue build new groups, so the waiting runs (42582094132, 42582096340) never saw "no later group" and waited the whole cap, then four built together and took the runners for 40 minutes. A read of the run or its jobs that fails counts as no failure and the wait goes on; the 60-minute cap stays the last resort. A failing entry is removed and the entries behind it rebuilt, as GitHub always does; the entries ahead of it, waiting, then find no later group and build their own trees, the last of them first. Finding the culprit needs no bisection: each group's run tests its own tree. The step logs one line per change of state (`waiting on <ref>`, `now last; running full checks`, `... is gone`), so a batch reads from the logs; a jump recreates every group branch, so a waiting run whose branch vanished cancels itself and the new group starts its own run. `changes` and `ci` print `batch: alone|waited|capped` and `tests: <the PRs on top of main>`. A group whose full build started before a later group existed keeps building, so a front entry queued alone merges by itself. The logic is `scripts/batch_wait.c`; `tests/batch_wait_test.smith` tests it against made-up branches.

**A failure does not end the run.** Every job runs to completion and `ci` (`if: always()`) is red when any job failed or was cancelled; see [ci](../ci.md).

**Main's runs do not cancel each other (#2792).** The workflow's concurrency group keeps one running and one *pending* run; a newer run replaces the pending one. With one group for `refs/heads/main` and the merge queue landing a PR every ~30 minutes, a run still pending when the next push arrived was cancelled with no job started, so from 02:21Z on 2026-11-08 `warm` (and with it the `step-cache-<sha7>` release) did not run for 18 of 30 pushes. A push to main now has the group `ci-<sha>`: every main push runs `warm` for its own commit, in parallel with the others (the repository is public, so hosted minutes are free). Only the stage0 release stays one at a time, in `release-macos` and `release-linux`, where skipping a commit in between is fine because the next release has the newer tree. A pull request still has `ci-<number>` (a new push replaces its run) and a merge-queue entry its own ref.

**A runner turns on auto-merge when its PR is ready** (lead, 2026-11-09). The lead enqueues or jumps only for a p0, a stuck entry or a PR that GitHub won't auto-merge (already clean when auto-merge is turned on): the order of entries in the queue matters less now that a group tests a batch with one full run. A conflict that drops a PR from the queue is the runner's to fix and re-enable.
