# CI and the merge queue

**A pull request's run yields to the merge queue** (#2356, owner 2026-11-05). GitHub has no job priority, and a pull request's run takes 9 Linux runners (`test-linux` 8 parts and `check-lint`, after `build-linux`); on 2026-11-05 between 04:30 and 04:50 UTC the queue's runs for #2346 and #2350 waited 20+ minutes for a runner while two pull request runs held them, and every minute a queue run waits delays every pull request behind it. So the first step of `changes` is `.github/actions/yield-to-queue`: on a `pull_request` run it checks every 30 s (`GET actions/workflows/ci.yml/runs?event=merge_group`, `status=queued` and `status=waiting`) and waits until no `merge_group` run of this workflow is queued or waiting. `build-linux`, the parts, the checks and `macos` all need `changes`, so none of them starts, and the waiting run holds one small runner. The wait is capped at 20 minutes (`timeout-minutes` of `changes` is 25): after that the run goes ahead and its summary says so, so a stuck queue never stalls pull requests for ever. With an empty queue it is one pair of API calls. `merge_group` and `push` runs never wait, a fork's run waits the same way (the read-only `github.token` is enough), a failed API call counts as an empty queue, and a new push cancels a waiting run (`concurrency`). No check is dropped and no part count changes. The summary of `changes` says how long the run waited.

**A queue run yields to the groups ahead of it (#2833).** The same action, on a `merge_group` run, waits in `changes` while an earlier `merge_group` run of `ci.yml` (created before this one, not finished) has a job in status `queued` (a job is listed only once the jobs it needs are done, so `queued` means it waits for a runner). Evidence: on 2026-11-08 at 17:48 the front group (run 42505988647) had 2 jobs running and 18 queued while the two speculative groups behind it held 17 of the 20 runners. The front group never waits (no earlier run); the next waits for the front group's queued jobs to get runners, and so on. The cap is 10 minutes (`queue-cap-minutes`), after which the run goes ahead and says so; an API failure counts as no wait. A group that waits holds one small runner (`changes`).

**Queue operations are a workflow** (#2828). A Claude Code session cannot reach GitHub's GraphQL API, and jumping or dequeuing a queue entry exists only there, so `.github/workflows/queue-ops.yml` (`workflow_dispatch`, inputs `op`, `pr`, `value`) does it from a runner: `jump`, `dequeue`, `enqueue`, `enqueue-many` (`pr` a list of numbers separated by spaces, enqueued 3 s apart in one job, #2851), `cancel-pr-runs` (queued `pull_request` runs of `ci`, except PRs that touch `.github/`), `rerun-failed` and `set-build-entries` (1 to 10 on the `main` ruleset). It tries `GITHUB_TOKEN` first and the repo secret `QUEUE_OPS_TOKEN` (fine-grained, this repo only: pull requests write, actions write, administration write) only when GitHub refuses; every run writes one line to its job summary (op, PR, result, actor). **A PR that changes a workflow file is enqueued only when it is based on the current main** (2026-11-09: #2855 was refused at 01:23Z): `QUEUE_OPS_TOKEN` has no workflow scope, so merge main into such a branch before enqueuing it. The owner is never asked to run a command for the queue.

**`jump` reports before the queue shows it** (#2843 and #2842, 2026-11-08). The `jump` entry prints `jump=true`, but the position it prints and `queue_order` can still show the old order, even 10 s later. Judge a jump by which entry's `ci` run starts first, not by the printed position.

**A queue run whose group left the queue cancels itself** (#2241). When the queue reorders (a jump to the front, a removal, a failure ahead), GitHub deletes the old group's branch `gh-readonly-queue/main/pr-<N>-<sha>` but does not cancel its run, so the stale run kept holding hosted runners (2026-11-04: five stale runs, one with about 11 of the 20 slots, merges fell to 3 to 4 an hour). `concurrency` can't replace it, since an expression can't cut `pr-<N>` out of the ref. No job waits for it (#2256, which replaces the polling job #2245 added: the polling job held a hosted slot for the whole run, 904 s in #2245's queue run, so a queue run took 12 Linux jobs instead of 11). The composite action `.github/actions/queue-guard` runs in each job of a `merge_group` run (`build-linux`, the test parts, `check-fmt-prove`, `check-lint`, `macos`) right after checkout, before the long steps: it checks once with `git ls-remote --exit-code` that the run's own ref still exists (exit 2 twice, 5 s apart; any other failure is not a miss) and runs `gh run cancel` (`actions: write` on those jobs, nothing else). A dropped group's run is cancelled by the next job to start, within about a minute, since the jobs start one after another. A live group's branch exists until the queue merges or drops it, so a live run is never cancelled. Nobody cancels stale runs by hand.

**The queue tests a batch with one full run** (#2851, owner 2026-11-08: "I thought with a merge queue multiple prs get merged at once?"). The ruleset builds up to 10 entries at once (Build concurrency, set with queue-ops `set-build-entries`; merge max is 10). A batch of 10 is one full run, which peaks at 10 Linux jobs at once (run of #2842), plus 9 waiting `changes` jobs: 19 of the about 20 Linux runners with grouping HEADGREEN: entry *k*'s group is main plus entries 1 to *k*, and when its run passes, entries 1 to *k* all merge with it. So only the last entry being built needs the full checks. A group's branch is `gh-readonly-queue/main/pr-<N>-<sha>`, where `<sha>` is the head of the group ahead of it (or main's commit), so a later group is being built on an entry exactly when a branch `pr-*-<its head sha>` exists. The second step of `changes`, `.github/actions/batch-wait` (`scripts/batch_wait.c`), checks that with `git ls-remote` every 30 s, after a **batching window**: a group that is last waits 60 s (`window_seconds` in `scripts/batch_wait.c`) for later groups before it decides it is alone, since entries are enqueued in bursts and the queue creates their groups one after another (2026-11-09, the first run at concurrency 10: of a burst of 4 groups, 3 started while last and built in full; a lone entry pays the minute; the lead enqueues a burst with queue-ops `enqueue-many`). It checks, not the GraphQL queue position, which lags after a jump. While a later group exists, the run waits on that one runner and every heavy job, all of which need `changes`, waits with it. When the later group's run passes, the entry merges and its branch goes: the wait cancels the run. When no later group is left (the later ones failed or left the queue), the wait returns and the same run builds the full checks of the entry's own tree, so the `ci` the ruleset counts is that run's own, as before. **The safety rule**: no PR merges unless a passing full run tested a tree that contains it. The wait never makes `ci` pass; it only holds the full checks back. A stale read can only cost runners: one that misses a later group builds the full checks for nothing, and one that sees a gone group waits one more poll. A failed read builds. The wait is capped at 60 minutes (then it builds anyway), so a wait and a full run stay under the ruleset's 120-minute check timeout; `changes` has `timeout-minutes: 75`. A failing entry is removed and the entries behind it rebuilt, as GitHub always does; the entries ahead of it, waiting, then find no later group and build their own trees, the last of them first. Finding the culprit needs no bisection: each group's run tests its own tree. The step logs one line per change of state (`waiting on <ref>`, `now last; running full checks`, `... is gone`), so a batch reads from the logs; a jump recreates every group branch, so a waiting run whose branch vanished cancels itself and the new group starts its own run. `changes` and `ci` print `batch: alone|waited|capped` and `tests: <the PRs on top of main>`. A group whose full build started before a later group existed keeps building, so a front entry queued alone merges by itself. The logic is `scripts/batch_wait.c`; `tests/batch_wait_test.smith` tests it against made-up branches.

**A failure does not end the run.** Every job runs to completion and `ci` (`if: always()`) is red when any job failed or was cancelled; see [ci](../ci.md).

**Main's runs do not cancel each other (#2792).** The workflow's concurrency group keeps one running and one *pending* run; a newer run replaces the pending one. With one group for `refs/heads/main` and the merge queue landing a PR every ~30 minutes, a run still pending when the next push arrived was cancelled with no job started, so from 02:21Z on 2026-11-08 `warm` (and with it the `step-cache-<sha7>` release) did not run for 18 of 30 pushes. A push to main now has the group `ci-<sha>`: every main push runs `warm` for its own commit, in parallel with the others (the repository is public, so hosted minutes are free). Only the stage0 release stays one at a time, in `release-macos` and `release-linux`, where skipping a commit in between is fine because the next release has the newer tree. A pull request still has `ci-<number>` (a new push replaces its run) and a merge-queue entry its own ref.

**A runner turns on auto-merge when its PR is ready** (lead, 2026-11-09). The lead enqueues or jumps only for a p0, a stuck entry or a PR that GitHub won't auto-merge (already clean when auto-merge is turned on): the order of entries in the queue matters less now that a group tests a batch with one full run. A conflict that drops a PR from the queue is the runner's to fix and re-enable.
