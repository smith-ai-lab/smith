# CI on GitHub's hosted runners, one build and sharded tests

`.github/workflows/ci.yml` (#798) runs on `pull_request`, `merge_group` and `push` to `main`, on hosted runners only (`macos-26` and `ubuntu-latest`), never self-hosted; how a change merges is [ci](ci.md). Nothing runs on a developer's machine on push: there is no git hook. A push to `main` is a commit the merge queue already checked: it runs only `release` and `release-linux` (they publish the stage0 release for each platform, [release](release.md)), `warm` (saves the cache) and `install`. The Linux parts join by themselves once a Linux release exists (#799): without one, stage0 builds smith from source for hours.

**The jobs.** `changes` decides the scope (below) and the matrices. `build` builds smith once and the tests too (`.github/actions/setup-smith`: the stage0 release of the newest ancestor commit fetched by `scripts/stage0.c` ([smith-bootstrap](smith-bootstrap.md)), the LLVM pack, `smith build`, then `smith test --list`, which builds the runner and every test program and runs none), packs everything the build made (git's ignored files, minus the downloaded stage0: `build/`, `.smith/`, the generated headers and parser) into one zstd tar and uploads it as the artifact `tree-<os>` (`.github/actions/pack-smith`). `mechanical`, `test` and `docs` start when it ends and each takes the build instead of making it (`.github/actions/use-smith`: the LLVM pack from the cache, the artifact, unpacked over the checkout). `mechanical` runs `fmt --dry-run --Werror`, `docs`, `lint` and `prove` (each reported, every one run, a failure ends in `FAIL <stage>`); `test` is a matrix of macOS parts, plus 2 Linux parts when `changes` finds an ancestor release with `smith-linux-x86_64.tar.xz` (it writes both matrices as outputs and says which in the summary), each `smith test --shard i/n --costs .github/shard-costs.tsv`; `docs` runs `smith docs` and `--test readme_test,skills_test`. A failing test is named in the job summary and as an annotation (`FAIL <name>`). `ci` gathers them and is the one check branch protection and the merge queue name.

**The first failure ends the run.** Each job's last step, `if: failure()`, runs `gh run cancel` (the workflow has `actions: write`); `ci` runs whatever happens (`if: always()`), sees a failed or cancelled job and is red at once, instead of after the slowest part. A Linux part (`continue-on-error`) never cancels.

**The cache** ([caches](caches.md)). The LLVM pack is `~/.cache/smith/llvm` and `enzyme` under one immutable key, `smith-llvm-<os>-<arch>-<configuration name>`: restoring it takes about 4 s for 194 MB, downloading the pack from its release 12 to 22 s. The compiles of smith and of the tests are the step cache, with the packages (the tree-sitter CLI) and tools: `smith-steps-<os>-<commit>` with the newest entry of the OS as the restore key, 71 MB; `SMITH_CACHE_MAX=1G` keeps it from growing, since a restore carries the whole folder forward. Only `warm` (a push to `main`) saves it, so there are few entries and every branch and queue entry restores main's (a cache saved on a branch is seen only by that branch). What it buys is small: compiles that go through a precompiled header (`smith.c`, five shims) are never served from the step cache, so a warm `build` still takes about 50 s of the 90 a cold one does. The build graph is not a no-op after a build (the restored tree-sitter object keeps its old mtime and is dirty again, which relinks smith and rebuilds what uses it): see Friction in #809.

**Scope.** On a pull request or merge queue entry, the files changed against the base decide: only `LICENSE*`, `CONTRIBUTING.md` and root images (documents no build reads) run nothing and `ci` passes; only those and `README.md`, `AGENTS.md`, `knowledge/` and `.agents/` run `build` and `docs`; anything else, a push to `main` and a diff that cannot be read run everything (a push to `main` runs the release jobs).

**The split** is `--shard i/n` of the runner ([build-tests](build-tests.md)): a test file stays whole in one part, files go heaviest first to the lightest part, and the weight of a file is the CPU seconds `.github/shard-costs.tsv` gives its tests (0.4 for a test it does not name, so a new test needs no entry). The file holds the tests of 2 CPU seconds or more from a green run's `.smith/log/test.log` (a `test-log-*` artifact of this workflow, which runs with `SMITH_TEST_STATS=1`; `smith build ci-times` reads them): refresh it from there when a part is much slower than the others. The count is chosen with the hosted limit in mind: the organisation gets at most 5 macOS jobs at once, and a job over the limit waits in a queue shared by every pull request, so a run that takes 6 jobs takes the slots of a second run.

**Times** (one hosted `macos-26` job each; numbers are from runs of #809, see its description for the table): see the pull request.

**Not covered by a hosted run:** the debugger tests need a runner that may debug (they do nothing for an account that may not, [debugger](debugger.md)); the editor tests need `nvim`, which the macOS jobs install with Homebrew while the build downloads.
