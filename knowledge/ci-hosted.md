# CI on GitHub's hosted runners, one build and sharded tests

`.github/workflows/ci.yml` (#798) runs on `pull_request`, `merge_group` and `push` to `main`, on `ubuntu-latest` for Linux and, for macOS, on hosted `macos-26`, with the owner's Mac (three self-hosted runners, `[self-hosted, macOS, ARM64]`) only as overflow when the hosted pool is saturated, picked per run;  how a change merges is [ci](ci.md). Nothing runs on a developer's machine on push: there is no git hook. A push to `main` is a commit the merge queue already checked: it runs `release` and `release-linux` (they publish the stage0 release for each platform, [release](release.md)), `warm` (saves the cache, on macOS and on Linux) and `install`. Linux carries the tests and the checks (fmt, docs, lint, prove) and is required (#73): the Mac runs only what macOS alone can.

**The jobs.** `changes` decides the scope (below) and the Linux matrix. `macos` is the one macOS job of a run (#1709): it builds smith and the tests (`.github/actions/setup-smith`: the newest release downloaded by `.github/actions/fetch-smith` ([smith-bootstrap](smith-bootstrap.md)), the LLVM pack, `smith build`, then `smith test --list`), then runs `smith lint` and `smith test --macos-only` (a documents-only change: `docs` and `--test readme_test,skills_test`). Each stage is reported with `took <stage> <n>s (exit <code>)`, and a failure ends in `FAIL <stage>` with the failed tests as annotations. Stages in one job share one tree one at a time, since two verbs at once collide on `.smith/build.ninja`. **Where each check runs** (#2234): `fmt`, `docs` and `prove` run in `check-fmt-prove`, and `lint` in `check-lint`, two Linux jobs that restore the build of `build-linux` like a test shard and run beside the 8 parts, on pull requests too (so a formatting or lint mistake fails the PR, not the queue). `lint` also stays on the Mac, because each platform lints code the other can't see: `@when(target.os == .macos)` code, Objective-C and Metal only on the Mac, glibc's macros only on Linux. On the Mac, prove took 163 s and fmt 11 s of the 9 minutes of checks (run 41766089451: `setup-smith` 5 min, `fmt` 11 s, `docs` 0 s, `lint` 193 s, `prove` 163 s, `test` 158 s), so the Mac job is about 11 minutes until lint is cached (#2236, #2237). A documents-only change (`docs` scope) builds no Linux artifact, so `docs` and its tests stay on the Mac. Until #1709 these were five jobs (`build`, `mechanical`, `prove`, `test`, `docs`) handing the build over as an artifact; four of them filled four of the five hosted macOS slots the free plan allows, so a second run queued behind the first, and a job that waited past its time limit was cancelled with no test failing. One job takes one slot, so five runs proceed at once, and nothing is packed or downloaded. `test-linux` is 8 hosted shards of `--skip-macos`, each `smith test --shard i/8 --costs .github/shard-costs.tsv`, each restoring the build of the one `build-linux` job (`setup-smith` with `artifact: build-linux`, #1758). A failing test is named in the job summary and as an annotation (`FAIL <name>`). `ci` gathers them and is the one check branch protection and the merge queue name. `ci` also fails a job that was owed and skipped: `full` owes `macos`, `test-linux`, `check-fmt-prove` and `check-lint`, `docs` owes `macos`, and a push to `main` owes no tests (the queue ran them on that commit), so a skipped ancestor can't drop a gate unseen (#1139).

**A queue run whose group left the queue cancels itself** (#2241). When the queue reorders (a jump to the front, a removal, a failure ahead), GitHub deletes the old group's branch `gh-readonly-queue/main/pr-<N>-<sha>` but does not cancel its run, so the stale run kept holding hosted runners (2026-11-04: five stale runs, one with about 11 of the 20 slots, merges fell to 3 to 4 an hour). `concurrency` can't replace it, since an expression can't cut `pr-<N>` out of the ref. No job waits for it (#2256: the polling job held a hosted slot for the whole run, 904 s in #2245's queue run, so a queue run took 12 Linux jobs instead of 11). The composite action `.github/actions/queue-guard` runs in each job of a `merge_group` run (`build-linux`, the test parts, `check-fmt-prove`, `check-lint`, `macos`) right after checkout, before the long steps: it checks once with `git ls-remote --exit-code` that the run's own ref still exists (exit 2 twice, 5 s apart; any other failure is not a miss) and runs `gh run cancel` (`actions: write` on those jobs, nothing else). A dropped group's run is cancelled by the next job to start, within about a minute, since the jobs start one after another. A live group's branch exists until the queue merges or drops it, so a live run is never cancelled. Nobody cancels stale runs by hand.

**What a job's setup restores and builds** (#2242). Run 41766089451 spent 5 minutes in the Mac's `setup-smith`, 71 s of it fetching and building smith; the rest was restoring the 1.5 GB step cache and compiling every test, though the Mac runs only `--macos-only`. So `setup-smith` takes `test-flags`: the `macos` job and the Mac's `warm` pass `--macos-only --shard 1/1 --costs <file>` (a `--shard` is what makes the scan list one part, so the runner and test programs built are those of the part, and the run in `macos_tests` gives the same options so nothing is rebuilt); the Linux jobs build every test once in `build-linux`. The Mac's saved cache then holds what the Mac builds, not the Linux-sized one (the keys were already per OS). A job with `artifact:` (the test parts, `check-fmt-prove`, `check-lint`) restores no step cache, since it compiles nothing. On a hosted Linux runner the first step removes the image's unused toolchains (`/usr/local/lib/android`, `/usr/share/dotnet`, `/opt/ghc`, boost, CodeQL, swift) in the background while the caches restore, and the last step waits for it and prints `disk: <df -h />` in the job summary; this applies to every job that uses `setup-smith` (`build-linux`, the parts, `release-linux`, `warm`, `frontend-coverage`) after a part and `release-linux` died with "No space left on device" (2026-11-04). The numbers after the change are in the PR's runs, not here yet.

**A failure does not end the run.** Every job runs to completion and `ci` (`if: always()`) is red when any job failed or was cancelled; see [ci](ci.md).

**The cache** ([caches](caches.md)). The LLVM pack is `~/.cache/smith/llvm` and `enzyme` under one immutable key, `smith-llvm-<os>-<arch>-<configuration name>`: restoring it takes about 4 s for 194 MB, downloading the pack from its release 12 to 22 s. The compiles of smith and of the tests are the step cache, with the packages (the tree-sitter CLI) and tools: `smith-steps-<os>-<commit>` with the newest entry of the OS as the restore key, 71 MB; `SMITH_CACHE_MAX=1G` keeps it from growing, since a restore carries the whole folder forward. Only `warm` (a push to `main`, one job on macOS and one on Linux: the Linux shards restored no step cache until it saved one) saves it, so there are few entries and every branch and queue entry restores main's (a cache saved on a branch is seen only by that branch). What it buys is small: compiles that go through a precompiled header (`smith.c`, five shims) are never served from the step cache, so a warm `build` still takes about 50 s of the 90 a cold one does. The build graph is not a no-op after a build (the restored tree-sitter object keeps its old mtime and is dirty again, which relinks smith and rebuilds what uses it): see #816.

**Scope.** On a pull request or merge queue entry, the files changed against the base decide: only `LICENSE*`, `CONTRIBUTING.md` and root images (documents no build reads) run nothing and `ci` passes; only those and `README.md`, `knowledge/` and `.agents/` run `build` and `docs`; anything else, a push to `main` and a diff that cannot be read run everything (a push to `main` runs the release jobs).

**What a pull request runs, and what the queue runs** (#754, #2234). A pull request and a queue entry run the same tests: the full suite in 8 Linux parts (`--skip-macos`, `--shard i/8`) and the Linux checks (`check-fmt-prove`, `check-lint`), because from 2026-11-03 the queue was the first place a change was fully tested, 74 of 100 failed queue builds failed in `test-linux`, and each failure fails every build behind it (owner, 2026-11-04). The test mode `--changed` is no longer used in CI. The macOS side is the same too (owner, 2026-11-04): both run `macos` (#1709: lint and the one `--macos-only` part), so a green pull request is a green queue run on both platforms. From 2026-11-03 to 2026-11-04 a pull request had no `macos` job, after 20 runners' pull requests filled the 5 hosted slots and queued jobs were cancelled before their first step; overnight 17 of 44 queue failures were then macOS checks a pull request never ran. The job allows 90 minutes, since its limit counts queued time, and each step has its own limit; when the hosted slots are full, `pick-mac` sends it to the owner's Mac. A change of documents only keeps its scope (nothing, or `docs`), and one that changes only other workflows (`llvm.yml`) runs nothing. A `push` to `main` runs no test part (the queue tested that exact commit, #1139; `test-linux` is skipped, and `release`, `release-linux` and `warm` need only `changes`). Linux is required: `ci` gathers `test-linux` like every other job, with no `continue-on-error`.

Measured (#818, before Linux carried CI): a full run (a workflow change) took 12.0 min to the `ci` verdict with 4 macOS test parts of 6 to 9.5 min; a one-test-file pull request took 6.6 min. On Linux (main's run 41142406495) the build takes 3.5 min and each of the 6 shards 3 to 6 min.

**The split** is `--shard i/n` of the runner ([build-tests](build-tests.md)): a test file stays whole in one part, files go heaviest first to the lightest part, and the weight of a file is the CPU seconds `.github/shard-costs.tsv` gives its tests (0.4 for a test it does not name, so a new test needs no entry). The file holds the tests of 2 CPU seconds or more from a green run's `.smith/log/test.log` (a `test-log-*` artifact of this workflow, which runs with `SMITH_TEST_STATS=1`; `smith build ci-times` reads them): refresh it from there when a part is much slower than the others. The count is chosen with the hosted limit in mind: the organisation gets at most 5 macOS jobs at once, and a job over the limit waits in a queue shared by every pull request, so a run that takes 6 jobs takes the slots of a second run.

**The handoff is an artifact, not the cache, on a hosted runner; on the owner's Mac it is its disk.** Restoring the 376 MB build from the cache took 8 s against 27 s for the artifact, but every job's restore counts against the account's cache egress limit, and a day of runs used it up (2026-10-30: `Egress is over the account limit`, every job that needed the build failed). So the build is uploaded with `upload-artifact` (zip level 1, which takes the 1.1 GB tar to about 0.4 GB: the tree is mostly binaries and a precompiled header; kept a day) as `smith-tree-<os>` and downloaded by each job. The LLVM pack and step caches stay: a restore that fails falls back (`smith build llvm` downloads the pack from its release; a missing step cache only means more compiles).

**Times** (wall clock of one `macos-26` job; numbers from #809): before, every job built smith: `setup` took 2.2 min (fetch 15 to 25 s, build 100 to 120 s) in each of 7 jobs, and a green merge queue run took 21.5 min (mechanical 5.8, docs 4.5, the five test parts 7.5 to 14). Now: `build` 2.4 min with warm caches (restore 14 s, stage0 13 s, smith 57 s, the tests 41 s, pack and save 8 s) and 2.3 to 2.9 min with empty ones (the step cache saves little); a job that takes the build starts its work after 18 s (the caches 12 s, unpack 2 s) and `smith test` then runs a chain of about 55 s before the first test (a build of a just-built tree is not a no-op, #816); `mechanical` 2.9 to 4.8 min; 4 test parts 6.2 to 8.8 min (the runner 261 to 357 s for 440 to 840 tests). The verdict of a run with free slots is about 11.5 min (changes 9 s, build 143 s, the slowest part 528 s), 14.6 min with empty caches and the old runner, against 21.5. The 5-minute target is not reached: 4 parts of about 4.4 min of tests on 3-core runners are the floor of what 5 jobs at once can do, and the tests need either less CPU or more cores. Under load the queue decides: one run waited 16 min for its `build` and 20 min for its last part behind other pull requests' jobs, and the parts differ by 2 min because `.github/shard-costs.tsv` is older than the tests (refresh it from the `test-log-*` artifacts, which this workflow had stopped uploading: `.smith` is hidden).

**How many parts.** Linux parts each add about 1.7 min of start to their share of the tests (about 17 min of runner time in all), so the count changes the latency and hardly the load. The macOS side is one job per run (#1709), so the hosted macOS cap of 5 is five runs at once, not one.

**Not covered by a hosted run:** the debugger tests need a runner that may debug (they do nothing for an account that may not, [debugger](debugger.md)); the editor tests need `nvim`, which the macOS jobs install with Homebrew while the build downloads.

**GitHub's runners come first; the owner's Mac is overflow** (#1141, owner 2026-10-31: "I would prefer to prioritize GitHub runners so that way my MacBook can be off. And if it happens to be on, great, we can use it. But if it's not on, we shouldn't stop working. And also, I would prefer to be able to not have my MacBook fans constantly running"; this replaces #754's Mac-first rule). `changes` outputs `mac`, the `runs-on` of every macOS job (`macos`, and llvm.yml's packs), picked per run by `.github/actions/pick-mac` (`ci.yml` and `llvm.yml` both use it, #1064). The default is `"macos-26"`. It picks `["self-hosted","macOS","ARM64"]` only when both hold: (1) at least one such runner is `online` and not busy (`GET /repos/smith-ai-lab/smith/actions/runners` with the repository secret `RUNNER_STATUS_TOKEN`, a fine-grained token, Administration read-only), and (2) the hosted macOS pool is saturated. The job's own token (`actions: read`; `llvm.yml` declares it) sees that: it lists the repository's runs that are `queued` or `in_progress`, and their jobs with their labels; the pool is saturated when another run has a `macos-26` job `queued` (a job waiting for a slot) or 5 are `in_progress` (the free plan's macOS cap). It cannot see other repositories of the organisation, which share that cap, so the count is a lower bound; a pick made at the start of a run is a forecast, and jobs the run starts later may still queue. It also outputs `"macos-26"` for a `pull_request` whose head repository is not this one (code from outside never runs on the owner's machine), when a token is missing and when a call fails, so a Mac that is off never stalls a run, and the summary of `changes` says which runner was picked and why. Free resources only: no paid runner. Three runners (`Adams-MacBook-Pro`, `...Pro2`, `...Pro3`) share the machine, each with its own `_work` folder and the owner's own `~/.cache/smith`; nothing there is deleted. A runner takes one job at a time, and overflow may use all three runners at once (owner, 2026-10-31, #1141: no cap on the Mac; three runs' `macos` jobs can reach all three); the Mac is the backup, so its fans run rarely. Each macOS job on the Mac gets `SMITH_CORES=5` (16 / 3, rounded down; 3 on a hosted runner, 4 on Linux) so three at once do not oversubscribe it. `release`, `warm`, `release-linux` and `publish` run hosted. The tools (`nvim`, `gtimeout`) are installed with Homebrew only when missing.

**One build is handed to the Linux shards** (#1758). The `macos` job builds and checks in its own checkout and hands nothing over (#1709); `build-linux` packs its tree (zstd) and the shards download it. Storage egress was over the limit 2026-10-30, when 10 shards each downloaded the uncompressed ~1 GB tree: watch it.

**The Mac's Linux runners are overflow too** (#1140, owner 2026-11-02: "I can add Linux jobs to my Mac. That's totally fine with me."). `pick-mac` also outputs `linux`, the `runs-on` of `test-linux`: `"ubuntu-latest"` by default, `["self-hosted","Linux","X64"]` only when such a runner is online and idle and another run has a job queued for `ubuntu-latest` (hosted Linux saturated); a fork, a missing token or a failed call is hosted, so a Mac that is off never stalls a run. The runners are OrbStack containers (already installed, nothing else goes on the Mac), `linux/amd64` through Rosetta, so they use the same LLVM pack as hosted Linux and no `linux-arm64` pack exists. Two of them, 4 cores and 12 GB each, each with its own `_work` and cache folder inside its container: they never see the owner's `~/.cache/smith`. A job on one gets `SMITH_CORES=4`.

Setup by the owner, once per runner (never `sudo`; the token is pasted into the command and nowhere else, since it must not appear in a comment, a file, a log or a transcript, and it expires after an hour):
1. In GitHub, Settings, Actions, Runners, New self-hosted runner, Linux, X64: copy the registration token.
2. Start the container with the token in the command: `orb`/`docker run --platform linux/amd64 --cpus 4 --memory 12g -d --restart unless-stopped --name smith-linux-1 -e REPO_URL=https://github.com/smith-ai-lab/smith -e RUNNER_NAME=mac-linux-1 -e LABELS=self-hosted,Linux,X64 -e RUNNER_TOKEN=<the token> <a runner image that carries the build tools of ubuntu-latest>`.
3. Repeat with a fresh token and `smith-linux-2` / `mac-linux-2` for the second runner.
4. Check Settings, Actions, Runners: both show `Idle` with the labels `self-hosted`, `Linux`, `X64`.
To stop, `docker stop smith-linux-1 smith-linux-2`: CI then runs hosted only.

**The front-end coverage count** (#2073). On every `push` to `main` (scope `release`) the job `frontend-coverage` runs `smith build frontend-coverage -Dall=1 -Dsmith=<smith>` on `ubuntu-latest`, with the smith `setup-smith` builds in that job for the commit (no job of the run hands one over). It is not in `ci`'s `needs` and never fails the run: a count that could not be made logs `unmeasured`. Its job summary has `N of M files pass`, the failures per stage and the top 20 causes, ranked by the files each stops first (the files whose first diagnostic it is, #2247); the artifact `frontend-coverage-<sha>` (kept 30 days) has `output.txt` and `results.tsv`; the step log has one line, `frontend-coverage: <sha> <passed> <total>`, which the lead's watcher reads, followed by 20 lines `frontend-cause: <first> <files> <count> <cause>` (the lead reads them from the job's log with `gh api repos/smith-ai-lab/smith/actions/jobs/<id>/logs`) (`.agents/skills/smith-dev-lead/reference/watch.md`). `timeout-minutes: 20` counts queue time.
