# CI on GitHub's hosted runners, one build and sharded tests

`.github/workflows/ci.yml` (#798) runs on `pull_request`, `merge_group` and `push` to `main`, on hosted runners only (`macos-26` and `ubuntu-latest`), never self-hosted; how a change merges is [ci](ci.md). Nothing runs on a developer's machine on push: there is no git hook. A push to `main` is a commit the merge queue already checked: it runs only `release` and `release-linux` (they publish the stage0 release for each platform, [release](release.md)), `warm` (saves the cache) and `install`. The Linux parts join by themselves once a Linux release exists (#799): without one, stage0 builds smith from source for hours.

**The jobs.** `changes` decides the scope (below) and the matrices. `build` builds smith once and the tests too (`.github/actions/setup-smith`: the stage0 release of the newest ancestor commit fetched by `scripts/stage0.c` ([smith-bootstrap](smith-bootstrap.md)), the LLVM pack, `smith build`, then `smith test --list`, which builds the runner and every test program and runs none), packs everything the build made (git's ignored files, minus the downloaded stage0: `build/`, `.smith/`, the generated headers and parser) into one tar and saves it in the cache under a key of the run (`.github/actions/pack-smith`). `mechanical`, `test` and `docs` start when it ends and each takes the build instead of making it (`.github/actions/use-smith`: the LLVM pack and the build of the run from the cache, unpacked over the checkout with the tracked files made older than it). `mechanical` runs `fmt --dry-run --Werror`, `docs`, `lint` and `prove` (each reported, every one run, a failure ends in `FAIL <stage>`); `test` is a matrix of macOS parts, plus 2 Linux parts when `changes` finds an ancestor release with `smith-linux-x86_64.tar.xz` (it writes both matrices as outputs and says which in the summary), each `smith test --shard i/n --costs .github/shard-costs.tsv`; `docs` runs `smith docs` and `--test readme_test,skills_test`. A failing test is named in the job summary and as an annotation (`FAIL <name>`). `ci` gathers them and is the one check branch protection and the merge queue name.

**The first failure ends the run.** Each job's last step, `if: failure()`, runs `gh run cancel` (the workflow has `actions: write`); `ci` runs whatever happens (`if: always()`), sees a failed or cancelled job and is red at once, instead of after the slowest part. A Linux part (`continue-on-error`) never cancels.

**The cache** ([caches](caches.md)). The LLVM pack is `~/.cache/smith/llvm` and `enzyme` under one immutable key, `smith-llvm-<os>-<arch>-<configuration name>`: restoring it takes about 4 s for 194 MB, downloading the pack from its release 12 to 22 s. The compiles of smith and of the tests are the step cache, with the packages (the tree-sitter CLI) and tools: `smith-steps-<os>-<commit>` with the newest entry of the OS as the restore key, 71 MB; `SMITH_CACHE_MAX=1G` keeps it from growing, since a restore carries the whole folder forward. Only `warm` (a push to `main`) saves it, so there are few entries and every branch and queue entry restores main's (a cache saved on a branch is seen only by that branch). What it buys is small: compiles that go through a precompiled header (`smith.c`, five shims) are never served from the step cache, so a warm `build` still takes about 50 s of the 90 a cold one does. The build graph is not a no-op after a build (the restored tree-sitter object keeps its old mtime and is dirty again, which relinks smith and rebuilds what uses it): see #816.

**Scope.** On a pull request or merge queue entry, the files changed against the base decide: only `LICENSE*`, `CONTRIBUTING.md` and root images (documents no build reads) run nothing and `ci` passes; only those and `README.md`, `AGENTS.md`, `knowledge/` and `.agents/` run `build` and `docs`; anything else, a push to `main` and a diff that cannot be read run everything (a push to `main` runs the release jobs).

**The split** is `--shard i/n` of the runner ([build-tests](build-tests.md)): a test file stays whole in one part, files go heaviest first to the lightest part, and the weight of a file is the CPU seconds `.github/shard-costs.tsv` gives its tests (0.4 for a test it does not name, so a new test needs no entry). The file holds the tests of 2 CPU seconds or more from a green run's `.smith/log/test.log` (a `test-log-*` artifact of this workflow, which runs with `SMITH_TEST_STATS=1`; `smith build ci-times` reads them): refresh it from there when a part is much slower than the others. The count is chosen with the hosted limit in mind: the organisation gets at most 5 macOS jobs at once, and a job over the limit waits in a queue shared by every pull request, so a run that takes 6 jobs takes the slots of a second run.

**The handoff is the cache, not an artifact**: restoring a cache took 3 to 4 s for 194 MB (the LLVM pack) and downloading the artifact of the same build, 378 MB, took 27 s in every job (`download-artifact` 14 MB/s, the cache 60 MB/s), so the build is saved with `actions/cache/save` under `smith-tree-<os>-<run id>-<attempt>` and restored with `fail-on-cache-miss`. Those entries are used for minutes and then idle, so the cache's least-recently-used eviction drops them first; the LLVM and step caches are used by every run.

**Times** (wall clock of one `macos-26` job; numbers from #809): before, every job built smith: `setup` took 2.2 min (fetch 15 to 25 s, build 100 to 120 s) in each of 7 jobs, and a green merge queue run took 21.5 min (mechanical 5.8, docs 4.5, the five test parts 7.5 to 14). Now: `build` 2.3 min with empty caches and 2.9 min with warm ones (restore 14 s, stage0 13 s, smith 66 s, the tests 61 s, pack and save 15 s); a job that unpacks it takes 45 s (4 caches, unpack 7 s) and then `smith test` still runs a chain of about 55 s before the first test (the graph is not a no-op after a build, #816); `mechanical` 2.9 min; 4 test parts 6.2 to 8.6 min (the runner 261 s of 840 tests in one part). The verdict of a run with free slots is about 12 min (changes 13 s, build 175 s, the slowest part 518 s) and 14.6 min with empty caches and the old runner, against 21.5. The 5-minute target is not reached: 4 parts of about 4.4 min of tests on 3-core runners are the floor of what 5 jobs at once can do, and the tests need either less CPU or more cores. Under load the queue decides: one run waited 16 min for its `build` and 20 min for its last part behind other pull requests' jobs.

**How many parts.** The jobs of a run cost `build` + `mechanical` + the parts, each part adding about 1.7 min of start (unpack, the chain) to its share of the tests (about 17 min of runner time in all): with `n` parts the work is about `30 + n` job-minutes, so the count changes the latency and hardly the load. 4 parts with `mechanical` are 5 jobs, the hosted limit, so a single run is as fast as it can be, and the next run's `build` starts in the slot `mechanical` frees (3 min) and its parts follow as the first run's end: two runs overlap, one behind the other. 2 or 3 parts leave slots free but make every run longer by 3 to 6 min.

**Not covered by a hosted run:** the debugger tests need a runner that may debug (they do nothing for an account that may not, [debugger](debugger.md)); the editor tests need `nvim`, which the macOS jobs install with Homebrew while the build downloads.
