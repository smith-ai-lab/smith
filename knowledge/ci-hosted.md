# CI on GitHub's hosted runners, one build and sharded tests

`.github/workflows/ci.yml` (#798) runs on `pull_request`, `merge_group` and `push` to `main`, on `ubuntu-latest` for Linux and, for macOS, on the owner's Mac (three self-hosted runners, `[self-hosted, macOS, ARM64]`; a pull request from a fork runs on hosted `macos-26` instead);  how a change merges is [ci](ci.md). Nothing runs on a developer's machine on push: there is no git hook. A push to `main` is a commit the merge queue already checked: it runs only `release` and `release-linux` (they publish the stage0 release for each platform, [release](release.md)), `warm` (saves the cache) and `install`. The Linux parts join by themselves once a Linux release exists (#799): without one, stage0 builds smith from source for hours.

**The jobs.** `changes` decides the scope (below) and the matrices. `build` builds smith once and the tests too (`.github/actions/setup-smith`: the stage0 release of the newest ancestor commit fetched by `scripts/stage0.c` ([smith-bootstrap](smith-bootstrap.md)), the LLVM pack, `smith build`, then `smith test --list`, which builds the runner and every test program and runs none), packs everything the build made (git's ignored files, minus the downloaded stage0: `build/`, `.smith/`, the generated headers and parser) into one tar and uploads it as an artifact of the run (`.github/actions/pack-smith`). `mechanical`, `test` and `docs` start when it ends and each takes the build instead of making it (`.github/actions/use-smith`: the LLVM pack from the cache and the build of the run as an artifact, unpacked over the checkout with the tracked files made older than it). `mechanical` runs `fmt --dry-run --Werror`, `docs`, `lint` and `prove` (each reported, every one run, a failure ends in `FAIL <stage>`); `test` is a matrix of macOS parts, plus 2 Linux parts when `changes` finds an ancestor release with `smith-linux-x86_64.tar.xz` (it writes both matrices as outputs and says which in the summary), each `smith test --shard i/n --costs .github/shard-costs.tsv`; `docs` runs `smith docs` and `--test readme_test,skills_test`. A failing test is named in the job summary and as an annotation (`FAIL <name>`). `ci` gathers them and is the one check branch protection and the merge queue name.

**The first failure ends the run.** Each job's last step, `if: failure()`, runs `gh run cancel` (the workflow has `actions: write`); `ci` runs whatever happens (`if: always()`), sees a failed or cancelled job and is red at once, instead of after the slowest part. A Linux part (`continue-on-error`) never cancels.

**The cache** ([caches](caches.md)). The LLVM pack is `~/.cache/smith/llvm` and `enzyme` under one immutable key, `smith-llvm-<os>-<arch>-<configuration name>`: restoring it takes about 4 s for 194 MB, downloading the pack from its release 12 to 22 s. The compiles of smith and of the tests are the step cache, with the packages (the tree-sitter CLI) and tools: `smith-steps-<os>-<commit>` with the newest entry of the OS as the restore key, 71 MB; `SMITH_CACHE_MAX=1G` keeps it from growing, since a restore carries the whole folder forward. Only `warm` (a push to `main`) saves it, so there are few entries and every branch and queue entry restores main's (a cache saved on a branch is seen only by that branch). What it buys is small: compiles that go through a precompiled header (`smith.c`, five shims) are never served from the step cache, so a warm `build` still takes about 50 s of the 90 a cold one does. The build graph is not a no-op after a build (the restored tree-sitter object keeps its old mtime and is dirty again, which relinks smith and rebuilds what uses it): see #816.

**Scope.** On a pull request or merge queue entry, the files changed against the base decide: only `LICENSE*`, `CONTRIBUTING.md` and root images (documents no build reads) run nothing and `ci` passes; only those and `README.md`, `AGENTS.md`, `knowledge/` and `.agents/` run `build` and `docs`; anything else, a push to `main` and a diff that cannot be read run everything (a push to `main` runs the release jobs).

**What a pull request runs, and what the queue runs** (#754). `changes` also sets the test mode. On `pull_request` it is `changed`: `build` and `mechanical` (macOS) and one macOS test part, `smith test --changed --base <the base sha>`, with no Linux build; a pull request that changes `ci.yml` or `.github/actions/**` runs the full suite instead (that is how a workflow change is tested), and one that changes only other workflows (`llvm.yml`) runs nothing. On `merge_group` it is `full`: the 4 macOS parts of the whole suite. The 6 Linux parts (advisory, `continue-on-error`, `--skip-macos`, once a Linux release exists) run only on a `push` to `main`, where `build` and `test` run for them alone: they fail until the prover runs on Linux (#820) and each downloaded the build (storage egress); #820 brings them back to every full run (the matrix in `changes`). macOS jobs: a pull request uses 3 (`build`, `mechanical`, 1 test part; 2 for a documents-only one), a queue entry 6. Linux is not yet required: when a queue run passes on Linux, the macOS parts become one `--macos-only` part and the Linux parts required (the edit is the matrix in `changes`).

Measured (#818): a full run (a workflow change) took 12.0 min to the `ci` verdict: `build` 2.5 (macOS) and 1.8 (Linux), `mechanical` 4, the macOS parts 6 to 9.5 min; a one-test-file pull request took 6.6 min (`build` 3.6, the `--changed` part 71 s, `mechanical` 2.5). The 6 Linux parts failed in 2 to 5 min with about 230 failing tests (nearly all `prove_*`, then `autodiff_test`, `smith_lang_test`, `readme_test`, `slots_test`): Linux stays advisory until those are fixed.

**The split** is `--shard i/n` of the runner ([build-tests](build-tests.md)): a test file stays whole in one part, files go heaviest first to the lightest part, and the weight of a file is the CPU seconds `.github/shard-costs.tsv` gives its tests (0.4 for a test it does not name, so a new test needs no entry). The file holds the tests of 2 CPU seconds or more from a green run's `.smith/log/test.log` (a `test-log-*` artifact of this workflow, which runs with `SMITH_TEST_STATS=1`; `smith build ci-times` reads them): refresh it from there when a part is much slower than the others. The count is chosen with the hosted limit in mind: the organisation gets at most 5 macOS jobs at once, and a job over the limit waits in a queue shared by every pull request, so a run that takes 6 jobs takes the slots of a second run.

**The handoff is an artifact, not the cache, on a hosted runner; on the owner's Mac it is its disk.** Restoring the 376 MB build from the cache took 8 s against 27 s for the artifact, but every job's restore counts against the account's cache egress limit, and a day of runs used it up (2026-10-30: `Egress is over the account limit`, every job that needed the build failed). So the build is uploaded with `upload-artifact` (no compression, kept a day) as `smith-tree-<os>` and downloaded by each job. The LLVM pack and step caches stay: a restore that fails falls back (`smith build llvm` downloads the pack from its release; a missing step cache only means more compiles).

**Times** (wall clock of one `macos-26` job; numbers from #809): before, every job built smith: `setup` took 2.2 min (fetch 15 to 25 s, build 100 to 120 s) in each of 7 jobs, and a green merge queue run took 21.5 min (mechanical 5.8, docs 4.5, the five test parts 7.5 to 14). Now: `build` 2.4 min with warm caches (restore 14 s, stage0 13 s, smith 57 s, the tests 41 s, pack and save 8 s) and 2.3 to 2.9 min with empty ones (the step cache saves little); a job that takes the build starts its work after 18 s (the caches 12 s, unpack 2 s) and `smith test` then runs a chain of about 55 s before the first test (a build of a just-built tree is not a no-op, #816); `mechanical` 2.9 to 4.8 min; 4 test parts 6.2 to 8.8 min (the runner 261 to 357 s for 440 to 840 tests). The verdict of a run with free slots is about 11.5 min (changes 9 s, build 143 s, the slowest part 528 s), 14.6 min with empty caches and the old runner, against 21.5. The 5-minute target is not reached: 4 parts of about 4.4 min of tests on 3-core runners are the floor of what 5 jobs at once can do, and the tests need either less CPU or more cores. Under load the queue decides: one run waited 16 min for its `build` and 20 min for its last part behind other pull requests' jobs, and the parts differ by 2 min because `.github/shard-costs.tsv` is older than the tests (refresh it from the `test-log-*` artifacts, which this workflow had stopped uploading: `.smith` is hidden).

**How many parts.** The jobs of a run cost `build` + `mechanical` + the parts, each part adding about 1.7 min of start (unpack, the chain) to its share of the tests (about 17 min of runner time in all): with `n` parts the work is about `30 + n` job-minutes, so the count changes the latency and hardly the load. 4 parts with `mechanical` are 5 jobs, the hosted limit, so a single run is as fast as it can be, and the next run's `build` starts in the slot `mechanical` frees (3 min) and its parts follow as the first run's end: two runs overlap, one behind the other. 2 or 3 parts leave slots free but make every run longer by 3 to 6 min.

**Not covered by a hosted run:** the debugger tests need a runner that may debug (they do nothing for an account that may not, [debugger](debugger.md)); the editor tests need `nvim`, which the macOS jobs install with Homebrew while the build downloads.

**The owner's Mac runs the macOS jobs** (#754, owner 2026-10-30: the hosted limit of 5 jobs at 3 cores is the bottleneck, the Mac has 16 cores, 128 GB and is always on). `changes` outputs `mac`, the `runs-on` of every macOS job (`build`, `mechanical`, `test`, `docs`): `["self-hosted","macOS","ARM64"]`, or `"macos-26"` for a `pull_request` whose head repository is not this one, so code from outside never runs on the owner's machine. Three runners (`Adams-MacBook-Pro`, `...Pro2`, `...Pro3`) share the machine, each with its own `_work` folder and the owner's own `~/.cache/smith`; nothing there is deleted. Each macOS job gets `SMITH_CORES=5` (16 / 3, rounded down; 3 on a hosted runner, 4 on Linux) so three at once do not oversubscribe it. `release`, `warm`, `release-linux`, `publish` and `install` are unchanged. The tools (`nvim`, `gtimeout`) are installed with Homebrew only when missing.

**If the Mac is offline, the macOS jobs wait** (queued until a runner returns; the run times out at 24 h): check `gh api repos/smith-ai-lab/smith/actions/runners`. To fall back, change the Mac's value of `mac` in the `changes` job of `ci.yml` to `'"macos-26"'`.

**The Mac hands the build over on its disk** (storage egress was over the limit again 2026-10-30: 10 shards each downloading the ~1 GB artifact). With `runner.environment == 'self-hosted'`, `pack-smith` writes the tar to `$HOME/smith-ci/<run_id>-<attempt>/<name>.tar` instead of uploading it, after removing folders in `$HOME/smith-ci` older than a day (it never touches `~/.cache/smith` or `~/.local/bin`), and `use-smith` unpacks that tar instead of downloading. Hosted runners (a fork's pull request on `macos-26`, Linux) keep the artifact. All jobs of a run use the same kind of runner, so the two ends always agree.
