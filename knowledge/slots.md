# A host-wide pool of cores limits heavy jobs

Many lanes and two CI runners share one Mac, and its load reached 100 to 170 (#360). A counter of whole runs (#360, #512: cores / 4 slots) bounded the number of runs, not the load: a run of one test waited an hour behind four full runs while the machine's cores sat half idle (#567). So the counter is **cores**: the host has `SMITH_CORES` tokens (default: the core count; `runtime/slots.c`), and a run takes the workers it uses.

**The pool.** A token is one of the files `core-0 ... core-(n-1)` in a folder of the host (`$SMITH_SLOTS_DIR`, else `/tmp/smith-slots-<uid>`; not `$TMPDIR`, which differs between a shell and a launchd service) with an `flock` held by the process; the file holds "pid parent-pid start-time" and "pid verb in folder". There is no daemon: the OS drops the lock when the process ends, however it ends (`kill -9` included). `SMITH_CORES=n` sets the size and also stands for the host's cores in tests; the old `SMITH_SLOTS=n` is read as a size when `SMITH_CORES` is not set, and `SMITH_SLOTS=0` turns the limit off.

**A run takes a token for each worker.** `smith build`, `check` and `test` take one token, the **base**, when the executor starts its first real step (a compile, a link, a test; an up-to-date build, or one whose steps are only functions of build.c such as `friction`, never waits). The first worker of the run rides on it. Every further worker takes one more token when it starts and gives it back when it ends: the executor's jobs and the test runner's workers (`lib/smith/test.smith`, the same files). A run that finds no free token for another worker goes on with the workers it has and asks again, a second later in the runner and at the executor's next wake-up, so a big run never waits for an empty machine and grows as tokens free up. A one-test run takes one token. A job that waits for its base prints `smith: waiting for a core (n of m held: <who>)` to stderr, again every 30 s, and polls every 200 ms. After 4 hours it runs without a token and says so.

**CI goes first.** A job with `SMITH_PRIORITY=ci` (the workflow's Full check step) holds a shared lock on `ci-waiting` while it waits for its base. Any other job checks it before each try and takes no token, base or worker, while it is locked, so the next free token is the CI job's, and the local runs return theirs as their workers end. The check is not atomic: a local job that tested just before the CI job began waiting may still take that token. Once it runs, a CI job holds a shared lock on `ci-held`; while it is held a local run takes another worker's token only if a quarter of the pool (at least one token) stays free, so CI keeps most cores while it runs and the local runs share the rest. Local jobs are not queued among themselves (whichever polls first wins).

**Nesting.** The holder sets `SMITH_SLOT_HELD=<its pid>` in its environment. A smith that finds that variable names a live process takes no base: its first worker rides on the token of the job that runs it (the executor's job that started the test runner holds one), and its further workers take tokens like any other. So `smith check` running `smith build` running the test runner, and the tests that start smith, use the tokens of the outermost job. A dead pid is ignored. The token is held by the smith process, not by its children (the lock is close-on-exec), so a child that outlives it does not hold it.

**A preflight holds its base for the whole run.** `smith build preflight` takes its base token at once, not at its first heavy step, and keeps it: its build, fmt, lint and test are children that ride on it (also the `POSIX_SPAWN_SETSID` ones: the environment is inherited), so it waits for the machine once, at its start, and not between its steps. The workflow's Build smith step is CI's (`SMITH_PRIORITY=ci`), and its timeout counts the wait (a token is held by a process and cannot be taken in a step of its own).

**A dead or orphaned holder loses its token.** A job that finds a token locked reads its file; when that process no longer exists (the lock outlived it in a child), its start time differs (a recycled pid), or its parent is now pid 1 or another than recorded (an orphan: a `smith build wait` left behind by a test held a slot for 10 hours), the job unlinks the file and takes a fresh one; the old holder keeps a lock on a file nobody opens, and is not killed. A holder started directly by launchd (parent 1) is read as an orphan too.

**What the pool gave a run.** A CI run (`SMITH_PRIORITY=ci`), or any run with `SMITH_SLOTS_LOG` set, ends with one stderr line: `smith: pool: waited N ms for the base core; A workers on average, P at most, of C cores; D attempts for another worker found none, W ms wanting a core in all`. It is the measurement of #754: a train run that was slow shows in it whether the time went to waiting for tokens (N and W large: the lanes held the cores) or elsewhere (both small: the machine was loaded by work that draws no token, such as lint, fmt and prove, or by a process that uses several cores). Measured in a pool of 16 with a lane run of 600 steps of 0.5 to 3 s and a CI run of 160 one-second steps: the CI run waited 0.6 s for its base token and had 15 of the 16 cores on average (the lane's own base token is the sixteenth), so the priority holds for steps that end in seconds; a CI run waits as long as the longest step a lane worker is in, because no process is paused or killed.

**A token is one open descriptor, and a fork copies it.** The test runner forks its workers (and, with `--isolate`, a child for each test) after it took the tokens of the jobs running, and a lock lives until the last copy of its descriptor closes, so a worker that kept the copies would hold those cores for as long as it lived, whatever its job did: the runner returned no core after its first batch, found the pool empty for every further test and ran one test at a time, 1.0 tests at any moment of a 20-minute `smith test` on a 16-core Mac while other lanes' runners sat on 15 idle tokens (#754). Every process the runner forks closes all the tokens first (`close_others` in `lib/smith/test.smith`); `test_runner_workers_the_cores_of_ended_tests_go_back_to_the_pool` fails without it. The executor's jobs are `posix_spawn`ed and the token files are close-on-exec, so they hold nothing.

**Tests.** The runner gives each test `SMITH_SLOTS_DIR=<its scratch folder>/slots`, so a smith a test starts counts private slots and never waits for the host's (#627); `tests/slots_test.smith` sets its own.

**Not covered.** `smith lint`, `fmt` and `prove` take no token of their own (lint and prove run `smith build` first, which does); the test runner started by hand, outside `smith test`, has no pool and runs all its workers. `smith --smith-slots PROGRAM` takes a token and runs the program: it is for `tests/slots_test.smith`.
