# From disk (`runtime/import_cache.c`, `front/module_cache.smith`, `shim/cimport.cpp`, #2891)

The tables above last one process; this keeps their entries on disk, so the next process, a CI job or another machine with a smith built from the same sources reads them instead of parsing std and asking clang again.
- **What is cached.** A `.smith` module's parse tree (never a checked module: each file checks the imports itself, as above), and a C header's declarations as the shim's words (`smith_cimport_read`) before `cimport::read` decodes them. A module that does not parse or names itself wrongly is never stored, nor a header clang reported an error for.
- **Where.** `<cache>/smith/imports/<identity>/{h,m}/<key>` (`<cache>` is `$XDG_CACHE_HOME`, or `~/.cache`). `<identity>` is the first 16 hex digits of the import identity `smith build` hashes into the binary (`build_import_identity`, `runtime/import_identity.c`, as the lint identity): every file under `front/` and `lib/std/`, `shim/cimport*`, `runtime/*.c` and `runtime/*.h`, `build.c`, the LLVM pack's identity (`smith-clang.id`), the compile flags and the format's version, each file by name and SHA-256. A smith built from other sources reads none of another's entries, and a format change needs nothing more. A smith with no identity (a build without LLVM, the front end's test runner, which links `tests/front_units/import_cache_off.c`) has the cache off.
- **The keys.** A module: the kind of read (a file, or std embedded in smith), its path and the roots that name it (both relative to the project) and its whole source text. A header: the header as written, `<` or `"`, the importer's folder for a quoted header, and the header flags, with the project folder and clang's resource folder written as tokens so that a checkout elsewhere has the same key. The key is 32 hex digits of a quick 128-bit hash of that text (not cryptographic: the entries come from this machine or from CI). A header entry also lists every file clang read for it, each by its path (the same tokens), size, time and a 128-bit hash of its content: a load checks the size and time and hashes a file again only when they moved, so an edited header (or one a `-D` makes read another file) is a miss; a header whose file changed while it was read is not stored. System headers are absolute and checked the same way, so another machine's SDK is only ever a miss.
- **A module's tree as an image.** The parser's tree is pointers all the way down, so it is stored as memory, not by a walk that would need to know every node: the module is parsed twice (`front/module_cache.smith`), each time with every block taken from a region of its own (`smith_import_region_*`, an `mmap` of 4 GB of address space, committed as it is used) after a copy of the source in it. The two regions hold the same bytes but for the pointers into themselves, which differ by the distance between the bases: those are written as offsets and listed. A word that is the same in both and points at a read-only part of smith's own executable (a literal the parser names, `""`) is written as an offset from the program's load address with the 16 bytes it points at, and a load moves it only where the same 16 bytes are (the identity says the sources are the same, not that the link laid them out the same). Any other difference, or a word that holds another address the process has mapped (`/proc/self/maps`), and nothing is stored (`SMITH_IMPORT_CACHE=why` prints why). A load maps the entry copy-on-write and moves its pointers, and the tree is used in place for the process's life. Linux only for now: on macOS there is no `/proc/self/maps`, so no module is stored (headers are).
- **Never changes a result.** An entry is a head (`SMIC`, the version, the payload's size and a hash of it) and the payload, written beside and renamed. An entry that does not read back whole with its hash, or a header whose files moved, is a miss and is written again; it never fails a compile. The objects of the count's files compiled from the cache are byte-identical to a compile with `SMITH_IMPORT_CACHE=0`, from the same checkout and from a copy of it at another path.
- **Size and pruning.** A full std set (each of std's modules that parses today, 22 of 31, and the 28 headers they import) is 33 MB (3.9 MB gzipped); `std.test` is 13.8 MB of it, its tree about 66 times its source. A hit touches its entry when it is more than a day old. At most once a day (`imports/pruned`) a store removes the folders of other identities unused for 14 days (their `used` stamp) and, past `$SMITH_IMPORT_CACHE_MAX` bytes (default 512 MB; `k`, `M` and `G` suffixes), this identity's oldest entries first.
- **Switches.** `SMITH_IMPORT_CACHE=0` turns it off; `SMITH_IMPORT_CACHE_LOG=<file>` appends `headers <hits> <misses> modules <hits> <misses>` for each process (the line CI adds up); `smith lsp` goes through the same reads (`read_kept`, the shim).
- **Shared (CI and sessions).** A merge queue run's test jobs (`build-linux`'s part, each `test-linux` part, `macos`) and the count's jobs (`frontend-coverage-fix`, each shard) publish their cache as `smith-imports-<os>.tar.gz` in their `test-cache-<sha7>-<job>` prerelease, and each of those jobs restores every set of the newest commit before it builds (`.github/actions/test-cache`, [ci caches](../ci/caches.md)); the nightly restores none, so a key that misses an input fails there. Each job prints `import cache: <n> processes, headers <h> hits <m> misses, modules ...` in its summary. A session restores the same sets with the command in the skill smith-dev-build (The import cache). The test jobs' sets are the dev smith's identity, the count's the release smith's; a smith built from a tree whose front end differs reads none of them.
- **Measured** (`SMITH_TIME=1 smith cc --front-end=new -c`, the count's tree, #2888's six files that import `std.test`, `std.mem`, `std.arena` and `<stdio.h>`, each its own process, the dev build at -O0): with the cache off a cold file imports in 392 to 399 ms (280 ms of it C headers); the first file that fills the cache in 593 to 611 ms (each module is parsed twice and stored); every later process in 36 to 54 ms (11 to 17 ms of it C headers), the 16 modules' images (29 MB) mapped and moved in about 20 ms.
- Gaps: no module image on macOS; std's modules that do not parse in the new syntax yet are parsed by every process; the first process pays the second parse.
- Tests: `tests/cc_import_cache_test.smith` (a second process reads what the first stored, with a generic, reflection and an attribute, and gives the same objects and diagnostics; a header with other defines is another entry; an edited header and a damaged entry are read again; `SMITH_IMPORT_CACHE=0`).
