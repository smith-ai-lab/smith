# Objects and the driver

## front::emit_object (`front/emit_object.smith`, #1134)

`emit_object::write(module, ObjectOptions, path)` writes an LLVM module to an object file and gives `path` back, or an `emit::Error`.
- The target is the caller's (`options.target.triple`, `cpu`, `features`; empty means the triple's defaults); nothing reads the host. It registers every target the linked LLVM has and makes a PIC machine.
- `optimization` 0..3 sets the code generator's level; 1..3 first runs LLVM's `default<O1..O3>` pipeline on the module in place (#1581); 0 runs no pass; checks stay.
- A module whose data layout is not the machine's is refused ("emitted for another target"). Test: `tests/front_emit_object_test.smith` links `add.o` with a `main.c` through `smith cc` and runs it.

## front::compile and front::roots (`front/compile.smith`, `front/roots.smith`, #1221 J2)

`smith cc --front-end=new` reads each `.smith` file of the command line, and `parser`, `types_decl::check_module`, `emit::module` and `emit_object::write` make its object.
- The other arguments go to clang as before with each `.smith` file replaced by its object (`-c` leaves only objects).
- `compile::file(path, output, triple, roots)` does one file and gives a `Report` (ok, diagnostics, nanoseconds per stage); `compile::run` (C name `front_compile_run`) is what `runtime/front_flag.c` calls.
- An import cycle is an error (#2130): before the checker, `compile::file` follows the imports of the file (not `std`) through `load_module`, and each `import` that leads back to the file's own module is reported as `file:line:column: error: import cycle: a -> b -> a` (the column is that of the module's name; `::` between the names in today's syntax, `.` in smith's own). `tests/front_compile_test.smith`.
- A diagnostic is `file:line:column: error: message`; a failing stage stops the next, so a type error writes no object.
- **Keep going and crashes (#2984).** With `SMITH_FRONT_KEEP_GOING` set (the count sets it), a file whose check fails is still emitted when every error is inside a function body of the file itself: those functions become prototypes (`checked_part`), the rest is emitted into a module that is never written, and the emit errors are printed after the check's, so the count's table shows what hides behind a first check error; the file still fails at `check` and no object is written. A plain compile is unchanged. With `SMITH_FRONT_STAGE` set, `runtime/front_flag.c` installs handlers (on an alternate stack) for SIGSEGV, SIGBUS, SIGILL, SIGFPE and SIGABRT that print `<file>: error: the compiler crashed (SIGSEGV) in the <stage> stage[, in the body of `f`, at an expression of kind <k>]` before dying by the signal, from fixed buffers that `front/compile.smith` and `front/emit.smith` keep current.
- **The error trace (#2949).** A diagnostic in the body of a generic's instance, or in an imported module, carries the chain that led to it, innermost first, one `  in ...` line after it: `  in check_part[str], instantiated at <path:line:col>` for each instance (`types::Error.in_instance`/`instance`, `InstanceUse.module` and `outer` give the chain; the emitter's `state::Error` has the same `module`, `in_instance`, `instance`, set by `state::in_module` and `state::in_instance` where it leaves an imported scope or an instance), then `  in module std.test, imported by <path:line:col>` for each import up to the file being compiled (`compile::links_of`, a `compile::Link` per line). A diagnostic whose span is in another module prints that module's path before the position, for the checker and the emitter alike (`lib/std/test.smith:905:16`). `smith lsp` sends each link as one `relatedInformation` entry. The emitter's two catch-alls name what they met: `not emitted yet: a type of kind \`tuple\`` (the `ast::TypeKind`'s name, `state::type_kind_name`) and `this needs the checker's types: ... an expression of kind \`call\`` (`state::expr_kind_name`; "none for the module" when `Options.checked` is null, "the base type ... was not recorded" when the table has no type for the node). In `smith build frontend-coverage` the `results.tsv` position column holds `line:col`, or `path:line:col` when the error is in another module than the file (the `  in ...` lines are in `output.txt` only, since they have no `error:`); the failure list prints such a row as `file (in path:line:col)`.
- **Names in a generic's instance (#2981).** The emitter emits an instance of a generic from another module under that module's prefix (`Emitter.instance_scope`, `std::test::`). A compile-time `if` the checker decided (`types::decided_in`, #1902) emits only its live branch (`decided_if` in `dispatch_statement`), without evaluating the condition. A bare name that is no local resolves under the prefix: a `pub const` integer folds to its value (`instance_global`), a record constructor is found by `emit_call::instance_record`, and a bare type by `emit_memory`'s `leaf_type`. The callee message of an unsupported call names the callee's kind (`not emitted yet: a call whose callee is of kind \`integer\``). `std.test`'s `value_of` picks the Value by a compile-time `if` on the type (`typeof(v) == char`, `is_bool`, `is_integer`), not by `_Generic`, which neither the checker nor the emitter handles. Not yet: a fixed array passed to a `*char` parameter (`snprintf(buf, ...)`) is refused by the checker and the fixer does not write `&buf[0]`.
- **The count's excluded files (#3037).** `scripts/frontend_coverage/excluded.txt` lists the files that leave the count's denominator, one `path TAB reason` per line (`SMITH_COVERAGE_EXCLUDED` names another list; `#` lines and blank lines are skipped). The reason is `error-fixture` (a test expects a diagnostic for the file: the file named by a line of a corpus case's `expect/error`) or `old-form: <form>` (a form the language dropped, decided in `decisions.md` or a smith-dev-syntax skill: preprocessor directives, function-like `#define`, `#pragma`, `#error`, `_Generic`, `goto`). A file whose expected-error file (`<file>.smith.expected` beside a `tests/affine/` file, or `<file>.error` beside a `tests/front/e2e/` file) holds the `smith-affine:` error that names it is an `error-fixture` too (#3234, the rules of #3190 item 33: giving a value away uses it up, and a value from outside a loop cannot be used up inside it; #3323, owner decision 2026-11-12: `tests/front/e2e/result_guard_affine.smith` is the same kind of file); each such file is listed by its own line, and the affine files that fail another way too stay in the count. `summarize` takes those files' rows out before it counts, so `frontend-coverage: P of T files pass` has T without them, and it prints `excluded  <path> [<reason>]` for each and `frontend-excluded: <n>` (T + n is the old total; CI echoes `frontend-excluded: <sha> <n>` next to `frontend-errors:`). An `error-fixture` that compiles is a miss of the front end, never a pass (#3207): it prints one `frontend-excluded-compiles: <path>` line (CI echoes it), its row becomes a failure that stays in the total, and the count is still measured. Two things fail the job, each as an error line that names the file and what to do (CI prints it as the job's error, not as "unmeasured"): an `error-fixture` whose compile ended without a diagnostic (a crash or a kill, `compile ended with status ...`), and a bad line (a reason outside the set, a path twice). An `old-form` file that compiles is good news, not a failure: the count warns with the line to delete and keeps the file in the total as a pass. **To add a file**, show its evidence in the PR: the `expect/error` line, or the line with the dropped form, and the decision that says the form is gone. **Do not add** a file because the front end cannot read it yet (a gap is fixed, not hidden), a form with no ruling (`long double`, `restrict`, `alignas`, `typedef` cases wait for the owner), a file that only fails under a target flag (`*-windows` cases), or library code that uses a dropped form (rewrite it). A file that passes is removed from the list, never left (the warning says which). Tests: `tests/frontend_coverage_test.smith`.
- `smith build frontend-coverage` (#1730, #1922) reads every `error:` line of a failed file, not only the first: the parser reports every error it recorded while it recovered (a file with a lexer or layout error has one, since those stop at the first; on 2026-11-05, 114 of the 213 files that stop at `parse` showed several), the checker reports every error it finds, and emit goes on past a failed declaration (#2982): `emit::module_all` returns every error in the order found (`emit::module` still gives the first), a function that failed to declare gets no body, a failed body is left half-built in a module that is never written, and `front/compile.smith` prints each error with its trace, so a file has one row per failed declaration. A declaration that uses a failed one can add a cascade (`no field ...` after its record failed); the error does not say so (no `after:` mark yet). Recovery after a badly skipped function body can add cascade errors (e.g. `lib/std/slice.smith` after 87:37 repeats `expected an expression` at the end of the file), so trust the first error of a body and re-measure after fixing it. `smith lsp` shows every parse error through the same path. Its summary counts the failed files per stage and the diagnostics per cause (names and numbers replaced), so how much is left after the first cause of each file is fixed can be read from it. `-Dfiles=a.smith,b.smith` (#2309) measures only those files and every module they import transitively, resolved as `load_module` does (the project's source folder, its own or the tree's `lib`, the file's own folder), prints each file's stage and first error with `imports <module>: [stage] <error>` under it for every import that fails, and equals the file's rows in a full run. It runs one fixer or compile per core at once (#2420; `-Djobs=<n>` overrides, `-Djobs=1` is serial), finishing them in file order so `results.tsv` is the same for any `-Djobs`. For the two widest causes it also counts the culprit, the first backticked text of the message (#2413): after the causes table it prints the top 15 names behind `unknown name` and `unknown type` (first-error files, files, occurrences), and the CI log gets one `frontend-name: <first> <files> <count> <unknown-name|unknown-type> <name>` line per name next to the `frontend-cause:` lines. `-Dshard=<k>/<n>` (#2697) measures one shard of the files (by FNV-1a of the path, so a file keeps its shard as files are added) and what they import, writing only the shard's own rows; `-Dmerge=<tables>` joins the eight shards' `results.tsv` (CI's `frontend-coverage-shard` jobs, then the `frontend-coverage` job). The fixer's output is cached in `.smith/frontend-coverage/fixed/<hash>` (keyed by the file, its transitive imports, the tracked C headers and the smith binary), so an unchanged file is not fixed again.
- The parser's warnings of a file in smith's own syntax print as `file:line:column: warning: message` before any error and do not stop the compile.
- The target is the driver's (`--target=` or LLVM's default triple); the checker's pointer width follows the triple. Casts are checked (`Options.checked`).
- Modules are named by path (`front::roots`; owner, 2026-10-31): `src/game/replay.smith` is `game::replay`, `lib/std/ascii.smith` is `std::ascii`. Roots are `src` and `lib`, plus the folder of the file being compiled (`Roots.local`, #2041: `import primes` finds `primes.smith` beside `main.smith`; the file being compiled is not named by it, so its symbols stay plain, and an imported file with a `module` line is still named only by `src` and `lib`); roots from `build.smith` are later. `compile::load_module` tries the three folders, then the source of `std.<name>` embedded in the smith binary (`smith_libraries`, handed over by `runtime/front_flag.c` to `shim/cimport_std.cpp`'s table, read through `smith_std_source`), so `import std.console` resolves outside smith's repository. Linking an imported `std` module into a `smith cc` program is not done yet (the library does not compile through the new front end until #2053).
- A `module` line that disagrees with the path is an error naming both; two files with one name are an error naming both; a file under no root takes its `module` line.
- `build.c` compiles `front/*.smith` (all but `emit_jit` and `cimport_cache`) into smith, with `shim/cimport.cpp` and `shim/cimport_deps.cpp` linked beside the other shims, with `ascii`, `format` and `clock` as plain compile steps. The units runner (`SMITH_CORE`) has no front end.
- `smith prove ... -- --front-end=new` (#1974): a `.smith` source goes through `compile::file` to bitcode, not clang. `file` writes the module as emitted when the output is named `*.bc` (`shim/prove.cpp`, `compile_with_new_front_end`, in a child process), and the prover reads it as it reads clang's. A `.c` file is unchanged. Gaps: `lib/std/contract.smith` is in today's syntax (`[[gnu::always_inline]]`) and does not compile under the new front end yet, and `c::smith_requires` from `import <smith/contract.h>` is not found (an inline function of a header), so a contract cannot be written yet; the test (`tests/prove_smith_test.smith`) proves only that a function reaches the prover by its name.
- `compile::header` spells a run-time array type (`[]f32`, `[, 3]u8`, `*mut []char`, #2183) as `struct smith_array_<element>_<shape>` (`n` a run-time size, one `count` per run-time size), defined once behind an `#ifndef SMITH_ARRAY_...` guard where it is first used; the element must be a scalar (a slice of pointers or structs still reports "no C spelling"). Cases: `slice-header`, `slice-pointer-header`, `slice-dims-header`.
- Gaps: the temporary objects of a link (`<TMPDIR>/<name>.front.o`) are not removed yet; the header cache and `import <header.h>;` are not called by `compile`.
- Tests: `tests/front_join_test.smith` (in process and through `$SMITH_SELF`, goldens `tests/front/join/`) and `tests/front_roots_test.smith`.

## One process, many files (`front/compile.smith`, `front/types.smith`, #2888)

One process that compiles many `.smith` files (a command line with several, `smith lsp`, a test runner) reads and checks what they import once. This is layer 1 of #2888; the disk cache that shares it between processes is #2891.
- **What is shared.** A table of imported modules, keyed by the module's path, the roots that name it (`roots_key`) and its whole source text, all compared whole (never a hash alone): a hit is the parsed, named module; a changed source is a miss. A table of C headers, keyed by the header as written, `<` or `"`, the importer's folder for a quoted header (an angled one does not look there) and the header flags (`$SMITH_FRONT_CIMPORT_FLAGS`); a hit is the declarations `cimport::read` gave. Both live on the system's allocator for the process's life (`enter_shared`), at most 512 entries each; past that a module or header is read for each file again. The embedded std sources are shared the same way.
- **What is not.** The check itself: each file declares the imported modules and headers into its own `types::Table` and `Scopes` (the checker folds nodes in place and names types per table), so each file's diagnostics, IR and object are the ones it gets alone. A module that does not parse or names itself wrongly is not kept, nor a header clang cannot read (clang prints its error for each file that imports it). Everything else a file allocates is bumped from the chunks of a per-file allocator (`file_allocator`: 1 MB chunks doubling to 64 MB, a larger block in a chunk of its own, no table, #3112) and dropped with them before the next file starts (`file_memory_release`), so the last file of a process is never released (#3080: freeing block by block was 19% of a whole-tree pass). `realloc` of the last block grows it in place, which the parser's one-element growth of a list relies on; any other block grows by copy.
- **Each file's own flags.** On a command line with several files, each file's C headers are read with the flags of its own entry in `compile_commands.json` (`front_compile_before_file`, `smith_front_flags_of_file` in `runtime/front_flag.c`), so two files with different `-D` or `-I` read a header each their way and do not share it; before #2888 every file took the first file's flags. A `$SMITH_FRONT_CIMPORT_FLAGS` the caller set is used for every file.
- **When a kept header is checked.** One command line is one generation: its headers are read as it starts and not checked again. Every other entry (`file`, `diagnose`, `hover_at` ...; `enter_file`) starts a new one, and a header kept from an older generation is used only when the files clang read for it (`smith_cimport_deps`, `shim/cimport_deps.cpp`) still have the size and time they had; they are listed on that first use, and a file whose time is not before the header's read drops it.
- **The check of the imports.** Declaring std into a file's tables was most of a file's check once the reading was shared (about 100 ms), so `intern` finds a structural type by a hash of what `same_shape` compares (`Table.shapes`) and `Scopes` keeps a hash index of its names (`ScopeIndex`, from 256 symbols on) that follows `count` before each search: symbols added are put in, and when a scope ends its symbols are taken out newest first, by the hash kept for each. Both are caches that never decide: the result is the one the linear search gave. `declare_headers` declares a header once per check even when several modules import it.
- **Measured** (`SMITH_TIME=1`, the count's tree, six files that import `std.test`, `std.mem`, `std.arena` and `<stdio.h>`, one command line, both smiths built the same way by `smith build`): before (main), every file's import took 843 to 987 ms and its stages 1096 to 1278 ms, 7.3 s for the command; after, the first file's import is 470 ms (345 ms of it C headers) and its wall 526 ms, every later file's import 1.6 to 1.9 ms and its wall 37 to 44 ms, 0.87 s for the command. The first file's check went from 289 to 52 ms with the hashed `types::intern` and scope index. `SMITH_TIME` prints `of which C headers` and `wall (the file, every stage)` for each file.
- **From disk (#2891).** The next section: the same two kinds of entries, kept between processes.
- Gaps: a dropped header's memory is not freed; the shared tables do not shrink, so a long process (the editor) that sees many versions of one module keeps each up to the 512 entries.
- Tests: `tests/cc_shared_files_test.smith` (files compiled together give the objects and diagnostics they give alone, different defines, an imported module's error in each file).

## Speed (#3080)

Where a compile's time goes, measured on main 7d1941a (2026-11-11, 4 cores, the release smith, one core, the import cache warm); the tables, the profiles and the design are in #3080.
- **To measure one file:** `SMITH_TIME=1 smith cc --front-end=new -c x.smith -o x.o` prints the stages (`lex and parse`, `import`, `check`, `emit LLVM IR`, `write the object`, `other`, `wall`) and the command's total. `-o x.bc` writes the module as emitted; `clang -O0 -c x.bc -ftime-report -mllvm -fast-isel-report-on-fallback` (the clang of the LLVM pack) times LLVM alone and names each function that left FastISel.- **A profile:** `valgrind --tool=callgrind smith cc --front-end=new -c x.smith -o x.o`, then `callgrind_annotate --inclusive=yes`; the release smith has its symbols. One stack of a running smith: `gdb -p <pid> -batch -ex bt`.
- **The numbers.** 962 files of the tree (55,034 lines), one process each: 57.1 s, 59 ms a file: check 28%, freeing the file's memory before exit 19%, import 15%, process start 14%, LLVM 12%, parse 0.4%, emit 0.7%. A generated file of 80,053 lines with no imports: parse 0.42 s, check 0.72 s, emit 0.81 s, LLVM at O0 1.94 s, 19,000 lines/s; lex, parse and check together run at 70,000 lines/s and emit at 100,000. LLVM takes 0.22 ms a function. After #3080's three steps the same tree takes 36 s (no free before exit: 57 to 46 s; no clone of a function without `target`: 46 to 36 s).
- **What a file with imports pays.** The checker declares every import into the file's own tables (44 to 52% of a test's compile); `when::uses_when` cloned every imported function to see whether a compile-time `if` would change it (10 to 26%; since #3080 the parser marks a function whose text has no `target` as `no_target` and `when::decided` returns it as it is, which took the tree's check from 15.1 to 5.9 s); each tree node is one `malloc` recorded in a table (22 to 37%); each cached image is hashed whole when it is loaded (6 to 16%).
- **What leaves LLVM's fast path.** A load or store of a whole struct or array makes FastISel fall back to SelectionDAG for the function (57 of 79 functions of `tests/docs_test.smith`); a `[1851 x i8]` loaded whole cost 1.9 s (`tests/resource_test.smith`, #3058).
- **Start-up** is 7 ms and an empty file compiles in 10 ms; the first process on a machine that imports a std module fills the import cache (6.4 s for `std.console`).
- **The fixer** (`smith lint --fix`) runs at about 630 lines/s over the tree and takes 0.75 MB of memory a source line (5 GB on `front/types_expr.smith`). Its cache folder is named by the import identity (`smith_front_std_identity`); before #3080 it hashed smith's own binary on every call, 3.7 s whatever the file.
