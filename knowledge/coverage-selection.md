# Records select the tests a change reaches

The build graph of [changed-tests](changed-tests.md) sees a test that runs smith (`scratch::`) as depending on all of smith, so `--changed` selected 83% of the tests on average. The same is true of a user's end-to-end tests (a CLI's tests run the CLI). A record of what each test actually executed answers it, with no git and no commit keys (issue #456, owner 2026-10-26: "fully general and not coupled to the compiler").

**The record** is `.smith/records/<test>.rec` (or `$SMITH_RECORDS_DIR`), one file per test, rewritten whenever the test runs under coverage (`runtime/record.c`). Text, a tab between fields: `result pass|fail`; `fn <file> <name> <lines> <hash> <first line hash>` for each function the test executed (the hash is 64-bit FNV-1a of the function's lines, and the function is found again by its first line, so moving it changes nothing); `outside <file> <hash>` (the file's code at brace depth 0 that is not a function's opening line: globals, macros, declarations; the lines inside a global's braces are not seen); `input <path> <hash>` (a header the executed files include, and `build.c`); `read <path> <hash>` (files read, see below).

**A test reruns** when its last result failed, a function it executed is not found as it was, an outside or input or read hash differs or the file is gone, or it has no record (a new test). Otherwise it is unchanged. A record from anywhere is valid wherever its hashes match, so shared records are just files in the folder.

**Selecting.** `smith test --changed` reads the records (the folder, else the project's task `coverage-fetch` if its `build.c` defines one: smith itself never runs `gh`), and for any test file selects the tests with a stale record, with their exact names in `--test`; a test file that imports a changed module is still selected by the graph, so records only add (the end-to-end test the graph cannot see) and, for a test that runs smith, replace the graph's "all of smith". A test with no record is selected too where the project makes its records itself (no `build.c`, or one that calls `smith_tests` or `smith_app_tests`); where it does not (smith's own `build.c`: the train records) it falls back to the graph. With no record at all, a project that makes them runs every test once. **A changed file no record names** is placed by the build graph: the tests whose recorded program (the files they executed, children included) imports or includes it, transitively, are selected, with the reason. **If the graph does not place it either (nothing imports it), every test runs:** unknown means run it. Nothing here is specific to smith: smith's own tests fall out of it because their records name the files of the smith program they ran. `build.c` and the other whole-suite files select every test as before. With no records the graph decides, and the message says so.

**Collecting in any project.** `smith test --changed` passes `-DSMITH_RECORD=1` to the build (a build option, not the environment: the smiths a test starts must not be instrumented). With it `smith_tests` and the debug profile of `smith_app` (so the program the tests start) get `-fprofile-instr-generate -fcoverage-mapping` and link with `-fprofile-instr-generate`, and the generated `tests_list.c` is compiled with `-DSMITH_PROFILING` so the runner can reach compiler-rt's functions (`smith_profile` in `lib/smith/test.smith`: they are hidden, so only code linked with them can name them). The test task then runs the runner with `SMITH_COVERAGE_DIR` (`.smith/coverage`), `SMITH_COVERAGE_BINARY` (the runner and the programs the build made, separated by `:`), `SMITH_REPO` and `SMITH_SELF`. The runner (`coverage_begin` and `coverage_end`) sets `LLVM_PROFILE_FILE=<dir>/raw/<test>/%p.profraw` before each test, so every process the test starts, children included, writes there, resets its own counters before the test and writes them after it (a worker runs many tests in one process); when the test ends it runs `smith test --coverage merge <test> <pass|fail>` (`runtime/coverage.c`), which merges the profiles and reads them against the programs inside smith (`shim/coverage.cpp`, what `llvm-profdata` and `llvm-cov export -format=lcov` do: a user has no LLVM tools), makes the record and deletes the raw files. The debug objects of a build that records differ from a plain build's, so alternating `smith test` and `smith test --changed` rebuilds them. A plain `smith test` records nothing and is unchanged.

**The train** records the same way for smith's own tests: `COVERAGE=1 smith build` compiles `smith.c` and the linked `.smith` libraries with the counters, and `test-units` sets the same variables (the runner of the tests is not instrumented, only the smith it starts).

**The table and the report (CI).** `smith test --coverage join <dir> <commit> <table>` makes `coverage.tsv` (a bit per function for each test, and the lines counted and run), and `report <table> <base> <out>` writes `coverage-report.txt`, tab separated: first `coverage`, the commit, `lines`, covered, counted, `functions`, ran, total; then one `uncovered`, file, line, function for each line of `git diff <base>..HEAD` that coverage counts and no test ran; last `changed`, the counted lines changed, how many are uncovered. It flags; it never rejects. The train's check uploads `coverage-<sha>` (table and report) and `smith-records` (the records, 7 days); a clone brings the records in with its `coverage-fetch` task.

**Reads.** The files a test reads (fixtures, read by its children through libc or io) are not recorded yet: `io::Io` is going away (#240), so the recording will go through the files module or an effect handler the runner installs (#239), after it lands. Until then the conservative rule above covers a changed file no record names; a fixture a record does name through no executed function is missed.
