# Records select the tests a change reaches

The build graph of [changed-tests](changed-tests.md) sees a test that runs smith (`scratch::`) as depending on all of smith, so `--changed` selected 83% of the tests on average. The same is true of a user's end-to-end tests (a CLI's tests run the CLI). A record of what each test actually executed answers it, with no git and no commit keys (issue #456, owner 2026-10-26: "fully general and not coupled to the compiler").

**The record** (format 2; a record of format 1 is ignored) is `.smith/records/<test>.rec` (or `$SMITH_RECORDS_DIR`), one file per test, rewritten whenever the test runs under coverage (`runtime/record.c`). Text, a tab between fields: `result pass|fail`; `cpu <seconds>` (the test's cpu time, for `--cheapest-first`); `fn <file> <name> <lines> <hash> <first line hash>` for each function the test executed (the hash is 64-bit FNV-1a of the function's lines, and the function is found again by its first line, so moving it changes nothing); `outside <file> <hash>` (every line of the file that is no part of a function: globals, macros, declarations, the lines inside the braces of a table or a type; written for each executed file and for each `.c` or `.h` file one of them includes, followed through their own includes, so smith.c's `#include "runtime/lang.c"` chain is judged by function and no longer as a whole file; the braces of a C++ namespace are not a depth); `input <path> <hash>` (any other file the executed files include, and `build.c`); `opened 1` (the record lists what the test opened); `read <path> <hash>` and `readdir <folder>/ <hash>` (files opened and folders listed, see Reads).

**A test reruns** when its last result failed, a function it executed is not found as it was, an outside or input or read hash differs or the file is gone, or it has no record (a new test). Otherwise it is unchanged. A record from anywhere is valid wherever its hashes match, so shared records are just files in the folder.

**Selecting.** `smith test --changed` reads the records (the folder, else the project's task `coverage-fetch` if its `build.c` defines one: smith itself never runs `gh`), and for any test file selects the tests with a stale record, with their exact names in `--test`; a test file that imports a changed module is still selected by the graph, so records only add (the end-to-end test the graph cannot see) and, for a test that runs smith, replace the graph's "all of smith". A test with no record is selected too where the project makes its records itself (no `build.c`, or one that calls `smith_tests` or `smith_app_tests`); where it does not (smith's own `build.c`: nothing records in CI) it falls back to the graph. With no record at all, a project that makes them runs every test once. **A changed file no record names** is placed by the build graph: the tests whose recorded program (the files they executed, children included) imports or includes it, transitively, are selected, with the reason. **If the graph does not place it either (nothing imports it), every test runs:** unknown means run it. Nothing here is specific to smith: smith's own tests fall out of it because their records name the files of the smith program they ran. `build.c` and the other whole-suite files select every test as before. With no records the graph decides, and the message says so.

**Collecting in any project.** `smith test --changed` passes `-DSMITH_RECORD=1` to the build (a build option, not the environment: the smiths a test starts must not be instrumented). With it `smith_tests` and the debug profile of `smith_app` (so the program the tests start) get `-fprofile-instr-generate -fcoverage-mapping` and link with `-fprofile-instr-generate`, and the generated `tests_list.c` is compiled with `-DSMITH_PROFILING` so the runner can reach compiler-rt's functions (`smith_profile` in `lib/smith/test.smith`: they are hidden, so only code linked with them can name them). The test task then runs the runner with `SMITH_COVERAGE_DIR` (`.smith/coverage`), `SMITH_COVERAGE_BINARY` (the runner and the programs the build made, separated by `:`), `SMITH_REPO` and `SMITH_SELF`. The runner (`coverage_begin` and `coverage_end`) sets `LLVM_PROFILE_FILE=<dir>/raw/<test>/%p.profraw` before each test, so every process the test starts, children included, writes there, resets its own counters before the test and writes them after it (a worker runs many tests in one process); when the test ends it runs `smith test --coverage merge <test> <pass|fail>` (`runtime/coverage.c`), which merges the profiles and reads them against the programs inside smith (`shim/coverage.cpp`, what `llvm-profdata` and `llvm-cov export -format=lcov` do: a user has no LLVM tools), makes the record and deletes the raw files. The debug objects of a build that records differ from a plain build's, so alternating `smith test` and `smith test --changed` rebuilds them. A plain `smith test` records nothing and is unchanged.

**A run with `COVERAGE=1`** records the same way for smith's own tests: `COVERAGE=1 smith build` compiles `smith.c` and the linked `.smith` libraries with the counters, and `test-units` sets the same variables (the runner of the tests is not instrumented, only the smith it starts).

**The table and the report (CI).** `smith test --coverage join <dir> <commit> <table>` makes `coverage.tsv` (a bit per function for each test, and the lines counted and run), and `report <table> <base> <out>` writes `coverage-report.txt`, tab separated: first `coverage`, the commit, `lines`, covered, counted, `functions`, ran, total; then one `uncovered`, file, line, function for each line of `git diff <base>..HEAD` that coverage counts and no test ran; last `changed`, the counted lines changed, how many are uncovered. It flags; it never rejects. `ci.yml` uploads no coverage records (the check that did is gone, #798), so smith's `coverage-fetch` task finds none, quietly, and `smith test --changed` uses the build graph, as it does with no records.

**Reads (#739).** A test counts as touching every file it opens while it runs, not only the code it calls, so a changed corpus case selects the tests that read it. With `SMITH_READS_LOG` set (the runner sets it per test, to `<coverage dir>/reads/<test>.txt`; every child inherits it) `io::files_read`, `files_map` and `files_list`, and `files::open` (so `read_file`), `map` and `list`, append the real path they open (a folder's ends in `/`; `files` reads the variable through `smith::env` and writes nothing while a files handler is set). Nothing reads a command's text: a test that hands a repository file to a process copies it first with `scratch::copy_tree` (through `io`, so the opens land in the log like any other read; a scratch project's fixture is copied that way too) and gives the process the copy, so no command reads the repository in place. `merge` writes them into the record: `read <path> <hash>` for a file and `readdir <folder>/ <hash>` for a listing (the names in it, so a file added changes it); a record with them says `opened 1`. A test is stale when one of them differs or is gone. **A test file whose tests all have such a record no longer falls back to the rule "its source names the changed data file"** (that rule selected the whole file, 370 tests for a corpus case): the stale records decide, a file no test opened selects nothing. A file with an older record keeps the rule until its records are remade. What is seen: reads through `io` in the runner and in every smith it starts (smith's own file reads outside `io` are not: the in-process lowering opens its named source through `io` first, but not the modules it imports); not a program of the project's own that opens a file (its `fopen`). A copy keeps a symbolic link as a link without reading its target, and files outside the copy are not seen: the repository's generated headers (`-I $SMITH_REPO/.smith/include`, a build output), and the tests that read the whole repository through git or `find` (`generated_files_test`, `neovim_test`, `smith_lang_c_test`'s tree of links) keep reading it in place, so a change selects them only through the rule for a test that runs smith. Cost: with the log on, the heaviest in-process reader (`smith_lang_lowering_test`, 2667 opens) used the same CPU (18.9 s against 18.8 s, user plus system), and without the variable an open adds one `getenv`.

**The front end has no fallback (#638).** `smith.c`, `runtime/lang*.c` and `shim/hook.cpp` (compiled with the counters under `COVERAGE=1`) are judged by function like the rest: the tests that ran a changed function, or whose `outside` hash of a file moved, are selected, and a file no record names (a new file, or code no test ran) still runs every test, with the reason printed. What this can miss, honestly: a test that reaches a function only through a path absent at the base, with no changed function on that path before it (a new branch in an executed function is a change to that function, so it is caught; a data file the code reads at run time is the `Reads` gap above); and the C++ shims other than hook.cpp, which select every test. CI's full check is the net for a miss.
