# What loads a Mac that builds with smith, and what a test may not depend on

**Spotlight.** Measured on macOS 26: `mds` indexes a project's `build/` (75 of its `.o` files were in the index) and does not index a hidden folder (`.smith/`, `~/.cache/smith*`) or the temporary folder (`$TMPDIR`, under `/var/folders`), where smith keeps its scratch and tests' projects. An empty `.metadata_never_index` file in a subfolder is **not** honored (nor `.metadata_never_index_unless_rootfs`, nor the backup-exclusion attribute): files under each were indexed within minutes. A folder whose name ends in `.noindex` is honored. So smith's own folders need no mark; a project that does not want `build/` indexed names its output `build.noindex/` in its `build.c`, or the user adds the folder to System Settings → Spotlight → Search Privacy. smith does not rename `build/`.

**Gatekeeper (`syspolicyd`).** Every executable linked for the first time is assessed once when it first runs, about 10 ms of `syspolicyd` CPU for a small program, whatever its path and content (60 distinct programs: 0.6 s; 60 copies of one: 0.7 s; a rerun: 0). A 235 MB `smith` costs about 0.1 to 0.2 s and 2 s of wall time the first time. A test run therefore pays per executable it builds, and smith reuses an executable that did not change. The user can exempt the programs a terminal or an agent app starts: System Settings → Privacy & Security → Developer Tools, add the app. smith does not change system settings.

**What a test may not depend on.** Under a load of 100 or more, wall time stretches several-fold, so a limit that is wall time ends a test that did nothing wrong. The prover's budget is CPU time; Z3's own timeout (it has only a wall clock) is therefore set to the process's wall backstop, `20 × budget + 30` s, and `with_z3_cpu_limit` ends it at the CPU budget. A test of a CPU limit passes `--wall-timeout` large enough that only the CPU limit can end it. Both were checked at a load of 130 to 250.

**Every pass/fail limit of a test is CPU time (#113).** The runner's `--timeout` is CPU; its default `--wall-timeout` is 600 s and ends a test as a hang ("hung after N s of wall time"), never as a timeout. The `--explain` wait for lldb is 5 s of the explaining child's CPU time (`proc_pid_rusage`, polled every 50 ms) with a 120 s wall backstop ("the debugger hung"). The explaining child itself (`runtime/explain.c`) ends at 5 s of its own CPU time (`ITIMER_PROF`; it was `alarm(30)` of wall time, which killed lldb while attached and left the stopped test stopped for ever: the real cause of #105's 100 s "timeout") and on a wall backstop of 600 s, and on the runner's SIGTERM, each time detaching first so the test runs on. Detach alone was not enough: with 40 tests explained at once, 5 to 16 stayed stopped for ever (the attach's SIGSTOP still pending when lldb let go; a SIGCONT cures every one), which the old 100 s wall limit reported as a timeout and the new 600 s one as a hang. The child therefore continues the test until it has been seen running (0 of 120 stuck after the fix). The DAP and LSP test clients (`tests/cpu_wait.h`) wait for a reply as CPU time of the server they spawned (30 s and 60 s) with a 10 minute wall backstop, and `lsp_client`'s settle (600 ms without a message) restarts whenever the server spends CPU. A test program's `alarm` is a 600 s hang backstop. A CPU measure covers the one process (all its threads), not children it forks; a spinning child is caught only by the backstop. Wall time stays where the wait is the thing under test (`sleeps`, `naps`, `abort_hangs`, `--wall-timeout 1`, the shrink budget) and the test says so. Three full checks started at once on a loaded Mac all pass.

**The release test packages at xz level 1 (#116).** `scripts/release.sh package` xz-compresses the 235 MB smith, one thread: level 6 (the default) costs 56 s of CPU and made `test-release` the longest task of a check (90 s wall under load, 67 s CPU); `tests/release.sh` sets `RELEASE_XZ_LEVEL=1` (9 s), as the test is not about the ratio. A published release keeps level 6. bsdtar ignores `XZ_OPT` and `xz:threads`; only `--options xz:compression-level=N` works.
