# Zero is initialization

**In a module `T t;` and `T t = {};` mean the same thing: every byte of `t` is zero, padding included, and a union across its whole size** (owner, 2026-10-28: "you can write T t; or you can write T t = {}; and that means the same thing"). The skills, README and `templates/new` teach `T t;`; `T t = {};` stays valid, so C code moved into a module needs no change. Go's answer, "make the zero value useful", is the design: reading a variable never written is not an error and not undefined, it is zero.

**The first spelling is a compile flag.** `smith_module_flags` (`runtime/build_runtime.c`) adds `-ftrivial-auto-var-init=zero` to the compile of every `.smith` file with a `module` line, after the profile's flags, so it wins over the debug profile's `pattern`; the optimizer removes the store wherever the variable is written before it is read. The second is C23's empty initializer. The same compile has `-Wno-uninitialized` and `-Wno-conditional-uninitialized`: reading a variable never written is defined, so `i32 total; total += x;` is no error (`templates/new` writes it). A `.c` file, and a `.smith` file without a `module` line, keep the profile's flags (the C rule: giving undefined behaviour a value changes no valid program). `tests/zero_init_test.smith` fills the stack with garbage and checks that both spellings leave no nonzero byte in a struct with padding and a union.

**Every tool sees the zero, not only the compiler.** A flag is codegen only, so the static analyzer (`smith lint`) called a read of `Option(I32) last;` a garbage value. `ZeroLocals` in `shim/hook.cpp` runs where the array-parameter check runs, when the module's translation unit is complete and before any consumer, in the compiler, clang-tidy and clangd alike: each local without an initializer (no parameter, static, extern, variable-length array, incomplete type) gets an implicit value initializer, so `T t;` is `T t = {};` in the AST. `tests/zero_init_test.smith` checks it through `smith lint`. clangd does not run the static analyzer, so the editor never showed the garbage value and has no test of its own; it gets the same AST from the same pass.

**A library type's zero is useful.** `Option(T)`'s first variant is `none` and `Result(T, E)`'s is `error` (`smith_option_header` and `smith_result_header` in `runtime/lang_enum.c`, and `lib/smith/option.smith`, `result.smith`), so their tag 0 is `.none` and `.error` and a forgotten result never looks like success. A type's default is its zero value, never a constructor function.

**Allocations are zeroed already** (`arena::push`, `push_slice`, `mem::alloc`, `alloc_slice`, `try_*`); the opt-outs are `arena::push_uninit` and `mem::alloc_uninit`, for a block the caller writes whole, each with the measurement that justified it in a comment. **A constructor is a constant:** `checkConstants` in `shim/effects_infer.cpp` makes an exported function with no parameters, a returned value and a body that calls nothing (builtins apart), reads no variable and names no function an error saying `constexpr T name = ...;`; a function that calls something (the clock, entropy, the allocator) stays.

**The local opt-out is `T x = undefined;`** (issue #743; owner/lead, 2026-10-28). It lowers to a local with clang's `uninitialized` attribute and no initializer (`T x __attribute__((uninitialized));`; a program never writes the clang spelling): `-ftrivial-auto-var-init=zero` and `ZeroLocals` both skip it. `undefined` is a reserved name in a module and means this only as a local's whole initializer; every other use (an expression, a global, a field, an assignment, a larger initializer, a `static` local) is an error naming the rule. A `.c` file, and a `.smith` file with no `module` line, keep `undefined` as an ordinary name. Each use says in a comment the measurement that justified it, as `push_uninit` does. **A debug build fills the local with 0xAA bytes** (`__builtin_memset_inline(&x, 0xAA, sizeof x)` right after the declaration; the inline form is not the `memset` the `smith-mem` check reports, which is for code a person writes, so a read before a write shows); release leaves it alone. The lowering knows the debug build by the address sanitizer, which the debug profile turns on (`target::address_sanitizer`, the host's `target_fact`); the raw lowering (`smith cc --smith-lower`) has no compiler to ask and writes no fill. A `for` header's `undefined` has no fill. **How it is read:** the `=` is seen only in slice mode, so a file with the word `undefined` is offered every token (the hook's `hasUndefined`, `smith_lang_text_has_undefined`); at a statement's first token `smith_lang_undefined_begin` (`runtime/lang_slice.c`) looks ahead for `T x = undefined ;` and marks the `=`, which `smith_lang_undefined_equals` replaces with the attribute. `tests/zero_init_test.smith` checks that release's AST keeps the local uninitialized and debug's pattern is seen; corpus cases `undefined-local`, `error-undefined`, `undefined-plain` and `tests/smith-lang-c/undefined.c` cover the rest.
