# A stage0 release per merge to main

`smith build release` packages the smith just built and publishes it, so the latest main binary is always one download away and a fresh clone can build from the release of its newest ancestor commit that has one. Nothing in the repository records which release to use, so a release needs no commit.

**What is published.** A GitHub Release tagged `stage0-<full commit hash>` holding, for each platform (`smith-darwin-arm64` and `smith-linux-x86_64`), `smith-<os>-<arch>.tar.xz` (`bin/smith` and the links `smith-cc` and `smith-c++`, nothing else: the embedded files are inside the binary) and its `.sha256` (`shasum -a 256` format). The repository's releases are immutable (a published release takes no more assets), so the release is a draft until every job has added its pair: each platform's job uploads into the draft `stage0-<commit>` (`gh release upload --clobber`, so a re-run replaces its own files), the first creates it, and jobs that race to create it leave two drafts of the tag, of which each deletes all but the oldest. The job `publish` then publishes the draft (`release.sh finish`). A draft has no tag and is invisible to `scripts/stage0.c`'s walk of the git tags, so only a published release is ever used. The full smith is about 235 MB and the tarball about 67 MB (xz, 43 s CPU), far under the 300 MB limit set for this design.

**Where it runs.** Only in CI, on a push to `main` (a commit the merge queue already checked): the jobs `release` (`macos-26`) and `release-linux` (`ubuntu-latest`) of `.github/workflows/ci.yml`, each with `GH_TOKEN` the workflow's `GITHUB_TOKEN` and `permissions: contents: write` on that job alone. Each builds smith from the previous release (the setup of every hosted job) and runs `smith build release`. They are two jobs, not a matrix, so that a failed Linux job does not fail the macOS one: `publish` (`needs: [release, release-linux]`, `if: always() && needs.release.result == 'success'`) publishes the macOS-only release when Linux fails, and `install` needs `publish`. The first Linux release can only come from such a push, and its job builds smith from source (about two hours, [smith-bootstrap](smith-bootstrap.md)); its timeout is 330 minutes (the hosted limit is 360). From then on the Linux job builds from the previous Linux release. A newer push replaces a job still waiting in its queue, so some commits have no Linux release; stage0 walks back to the newest ancestor that has one.

**The guard.** `scripts/release.sh` (the task's one command) refuses by hand unless `HEAD` is on `main` and equals `origin/main`; in CI it accepts only `GITHUB_REF=refs/heads/main` with `GITHUB_SHA` equal to `HEAD`. It also refuses a binary whose `smith version` does not name `HEAD`. A draft that already exists is not created again, so a re-run before `publish` is harmless.

**Pruning.** After publishing, the script lists the `stage0-*` releases and deletes (with `--cleanup-tag`) all beyond the newest 20 except the newest of each ISO week (Monday to Sunday). Other releases and tags are never touched. Both jobs prune, which is safe: only releases beyond the newest 20 (and not a week's newest) go, never the one just published, and a release the other job already deleted is no failure. A failed prune is reported and leaves old releases; it never fails the release. The rule is `release.sh prune`, a function of "tag date" lines.

**Download side.** `scripts/release.sh fetch <tag> <dir>` runs `gh release download`, checks the checksum and extracts `bin/` into `<dir>`. `scripts/stage0.c` picks the tag (the newest ancestor of HEAD whose release has the tarball and checksum of this platform, read with `gh release view`), downloads and checks it itself (`gh release download`, SHA-256 in CommonCrypto, `tar`) and runs it: how a clone with no smith builds ([smith-bootstrap](smith-bootstrap.md)).

**Tests.** `tests/stage0_test.smith` builds `scripts/stage0.c` with the system's clang and tests the choice of the release with a stand-in `gh` (`tests/build_fixtures/stage0`). `tests/release.sh` (task `test-release`) uses no network and no real repository: the package of the smith under test, the pruning rule on fake tags, the guard in scratch git repositories, and publish (create the draft, add a second platform, re-run, `finish`) and fetch against a stub `gh` that keeps releases in a folder. The release step itself runs only on a push to main, so its first real run is the first merge after this change.
