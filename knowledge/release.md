# A stage0 release per merge to main

`smith build release` packages the smith just built and publishes it, so the latest main binary is always one download away and a fresh clone can build from the release of its newest ancestor commit that has one. Nothing in the repository records which release to use, so a release needs no commit.

**What is published.** A GitHub Release tagged `stage0-<full commit hash>` holding, for each platform (`smith-darwin-arm64` and `smith-linux-x86_64`), `smith-<os>-<arch>.tar.xz` (`bin/smith` and the links `smith-cc` and `smith-c++`, nothing else: the embedded files are inside the binary) and its `.sha256` (`shasum -a 256` format). The repository's releases are immutable (a published release takes no more assets), so the release is a draft until every job has added its pair: each platform's job uploads into the draft `stage0-<commit>` (`gh release upload --clobber`, so a re-run replaces its own files), the first creates it, and jobs that race to create it leave two drafts of the tag, of which each deletes all but the oldest. The create is tried three times, 20 seconds apart, because GitHub once answered it with a 403 on a token that could write (#1139). The job `publish` then publishes the draft (`release finish`). A draft has no tag and is invisible to the releases feed and the `releases/latest` redirect, so only a published release is ever used. The full smith is about 235 MB and the tarball about 67 MB (xz, 43 s CPU), far under the 300 MB limit set for this design.

**Where it runs: the queue packs Linux, the push builds macOS and publishes both (#2832, #3052).** The merge queue moves main to the very commit its run tested, so the Linux tarball is packed in that run: the job `release-pack-linux` (`ubuntu-latest`) builds smith's release profile with the setup of every hosted job (the newest stage0), packs it with `release package` and keeps the tarball, its checksum and the release tool as the run's artifact `stage0-<commit>-linux-x86_64`. No queue run builds macOS, so the macOS tarball is built on the push by the job `release` (`macos-26`), by the same steps. `ci` owes the Linux pack in a queue run, so a release that does not build fails the queue run. The artifact is kept 3 days, and a queue run whose `ci` fails deletes its own (so a failed run leaves nothing that looks like a release). On the push to main, `changes` looks the Linux artifact up by the commit's name and takes it only from a `merge_group` run whose `ci` passed; `publish` downloads it, adds it and the macOS tarball to the draft `stage0-<commit>` with `release upload` (guard, each checksum checked) and publishes it, about a minute and a half after the merge instead of about 17. A queue group of several entries is one commit per entry, each with its own run and tarball; the push names main's new head, which is published from its own run's. The job `release-linux` (`ubuntu-latest`) builds the Linux tarball on the push only when the queue left none (a push that did not come through the queue, an expired artifact). Each release job has `GH_TOKEN` the workflow's `GITHUB_TOKEN` and `permissions: contents: write` on that job alone, and builds by the same steps (the release profile in the default folder, then `smith build -DPROFILE=release release`, which publishes that very binary). The Linux artifact carries the tool that uploads, so without it both are built. The Linux fallback has not run on a real push since #3017 (every push since came through the queue with its Linux tarball): it is covered by the stub tests of `release publish` (`tests/release_test.smith`) and by `changes` choosing it whenever no passed queue run left a tarball, so its first real run is the first of its kind and worth a look. The two release jobs are two jobs, not a matrix, so that a failed Linux job does not fail the macOS one: `publish` (`needs: [changes, release, release-linux]`) publishes when either a release job succeeded or the queue run's Linux tarball was there, so the macOS-only release goes out when Linux fails and the Linux-only release when the macOS job fails or times out (#2976: `warm` and the Linux jobs need only the Linux tarball); `publish` says whether the release holds the macOS tarball. The queue-built Linux binary is the commit, profile, LLVM pack and flags the push run would build; it may be built by a stage0 one release older than the push run would have fetched, which today's push timing also varies. The first Linux release can only come from such a push, and its job builds smith from source with the published Linux LLVM pack and lld installed by the job ([smith-bootstrap](smith-bootstrap.md)); its timeout is 330 minutes (the hosted limit is 360). From then on the Linux job builds from the previous Linux release. A push whose commit is not main's head when the run starts still publishes its own release; some commits (the earlier entries of a group that merged together) have no release of their own, and stage0 walks back to the newest ancestor that has one.

**The profile.** The published binary is the release profile (`-O2 -g`, #2684); a plain `smith build` is the dev profile (`-O0 -g`). Under the dev profile `smith build release` first runs `smith build -DPROFILE=release -DBUILD=build/<os>-<arch>-release` (task `release-binary`), so the dev and release objects never mix, and publishes the binary that build made; under `-DPROFILE=release` it publishes the build's own binary. CI builds the release profile in the default folder in every job that releases (the queue's and the push's), so both pack the same build.

**The guard.** `release/publish.smith` (the one program of the release: `publish`, `upload`, `finish`, `package`, `fetch`, `prune`, `prune-old`, `guard`) refuses by hand unless `HEAD` is on `main` and equals `origin/main`; in CI it accepts only `GITHUB_REF=refs/heads/main` with `GITHUB_SHA` equal to `HEAD`. It also refuses a binary whose `smith version` does not name `HEAD`. A draft that already exists is not created again, so a re-run before `publish` is harmless.

**Pruning.** The prune lists the published `stage0-*` releases and deletes (with `--cleanup-tag`) all beyond the newest 20 except the newest of each ISO week (Monday to Sunday); then it deletes, by id, the `stage0-*` drafts older than a day (a draft has no tag, so `gh release delete <tag>` cannot find one: listed with the rest, 449 of them took the prune 5 minutes in run 42877475136, #2832; a younger draft may be one a push run is still adding to). Other releases and tags are never touched. The prune runs as the last step of `publish` (`release prune-old`, the tool from the queue run's Linux artifact); a release built by the fallback is pruned by `release publish` in its release jobs. Both release jobs prune, which is safe: only releases beyond the newest 20 (and not a week's newest) go, never the one just published, and a release the other job already deleted is no failure. The prune checks its outcome, not its commands (#3029): after the deletes it lists the published `stage0-*` releases again and counts those the rule would still delete, and every `gh release delete` that fails (and every failed list) counts too; `release prune-old` exits 1 with the number of problems, so the step is red, and the same text goes to the log. (The first version passed a `take_line` slice's `.data` to `gh`, which read every remaining line as one tag: 422 "release not found" lines in run 42892535935, nothing ever deleted, 371 releases kept, and nobody saw it.) A failed prune leaves old releases and is reported by its step; it never fails the release, because that step is the last one of `publish` and is `continue-on-error`, and `release publish` only prints it. The rule is `release prune`, a function of "tag date" lines (`prune_tags`, which works out the ISO week itself).

**Download side.** `release fetch <tag> <dir>` runs `curl` on the release's public URL (`https://github.com/smith-ai-lab/smith/releases/download/<tag>/<name>`; no `gh` login, no GraphQL, #829), checks the checksum and extracts `bin/` into `<dir>`. A clone with no smith downloads the newest release that has its OS's tarball with the same `curl` calls (the tag from the public releases list, the checksum checked; falls back to an older release when the newest has no asset for this OS, #2796; `.github/actions/fetch-smith` in CI, the README's Install steps by hand) ([smith-bootstrap](smith-bootstrap.md)).

**Tests.** `tests/release_test.smith` uses no network and no real repository: the package of the smith under test, the pruning rule on fake tags, the guard in scratch git repositories, and publish (create the draft, add a second platform, re-run, `finish`), prune-old (the stub answers `release list` with several "tag date" lines as `gh --jq` does, the test asserts each tag reaches `release delete` alone, and a delete that fails makes it exit 1 with the count), upload (the packaged tarballs into the draft, a bad checksum and an empty folder refused) and fetch against a stub `gh` that keeps releases in a folder. The release step itself runs only on a push to main, so its first real run is the first merge after a change.
