# smith-effects, a program touches the world only through capabilities

**`smith-effects` is a clang-tidy check that a program touches the world only through capabilities passed down from
`main`** (`shim/effects.h`, registered in `shim/tidy.cpp` beside `SmithNaming`, so `smith lint` and `smith lsp` both
run it, `.smith` names as written; skill smith-io). `main` makes `io::Io io = io::make(argc, argv)` (`SmithIo io = smith_io_make(argc, argv)` in C), or in a `.smith` file is `i32 main(io::Io *io)`, which the lowering turns into a `static` function and a C `main` that makes, passes and closes the io (issue #52; `io::make` in it is refused), and a function
takes the part it needs, so its signature says what it can do. Decided function by function from the source, with no
lists of files:
- **A raw effect is a call into a system header that is not on the pure allow list** (in `shim/effects.h`, each
  entry with its reason: `<string.h>`, `<math.h>`, `<ctype.h>`, the `strto*` family, `snprintf`, `qsort`...), or an
  Objective-C message to a system framework's class or object. `abort`, `assert`, `__builtin_trap` and smith's failure
  path are not effects.
- **A capability is a record marked `[[clang::annotate("smith::capability")]]`** (`io::Io`, `io::Console`, `io::Files`,
  `io::Clock`, `io::Processes`, `io::Net`, `io::Args` (the live environment), and the handles `io::Op`, `io::Capture`,
  `io::Child` and `io::Connection`, C's SmithIo and the like; not `random::Key` or `arena::Arena`, which are values). Raw effects are allowed in its implementation: the `.smith`
  module that defines it, or the `.c` beside its header (`io.c` with `io.h`; `lib/io.c` with `include/.../io.h`); `smith::io` is itself such a `.smith` module. An
  exported function there that reaches a raw effect must take or return a capability. `io::make` (`smith_io_make`) is marked
  `[[clang::annotate("smith::main_only")]]` and may be called only in `main`; no capability in static storage.
- **Default on, `smith-effects.CFiles` true;** smith's own `.clang-tidy` sets it false, because smith's C is being
  ported to `.smith` (issue #45) and each ported module must be clean from the day it lands. The editor runs it
  because `patches/smith-editor-fast-check.patch` makes clangd treat `smith-*` checks as fast (LLVM `23.1.3-r4`).
- **The stack is solved at the link, from the same summaries.** Each compile to an object asks the backend for frame sizes (`-fstack-usage`, added by `smith_clang_main`, so no LLVM change; for one command that compiles and links the `.su` the driver names after the program is read after each job); the plugin copies them into the object's `.fx` (`S` lines, an `H` line with the opt level and sanitizers; a frame is `dynamic` when the body has a variable-length array or `alloca`, not by the backend's word, which a sanitizer's realigned arrays also earn) and removes the `.su`. The link solves `stack(f) = frame(f) + max stack(callee)` over the merged graph and writes `<program>.stack`: musttail back edges add nothing, other cycles and dynamic frames are `unbounded`, and code with no source is `at least N + unknown (calls: ...)`, never a guessed number (the task runtime, #241, decides what an unknown is). The file records the build's flags because a frame at `-O0` with sanitizers is larger than at `-O2`.
- **The editor uses the same solver** (#246): in clangd's parse the plugin builds the file's summary, merges it with the `.fx` files on disk (its own stale one loses) and reports the link's violations of the file's own functions at their calls. `shim/lsp.cpp` is the layer that tells the plugin the object of each source (`.smith/compile_commands.json`), that a file was saved (its parse then writes the summary) and, when one is written, has the other open files parsed again with a `didChange` that carries `forceRebuild` and no changes. A background pass compiles each stale source with `-fsyntax-only` and `SMITH_EFFECTS_OBJECT` naming the object whose summary it makes.
- **A query is a deferred `static_assert`** (`effects::within(f, mask)` in `lib/smith/effects.smith`, owner decision on #207): the call is an ordinary function that says yes, because an inferred set does not exist while the file is parsed; the plugin reads the `static_assert` after inference and judges it (at once for a function of the file, as a `W` line of the summary for one of another file, judged by the link and the editor's solve), reporting at the assertion with the message and the chain, and a note at the instantiating call. There is no `effects::of` (a value that is an error anywhere but a `static_assert`) and no `effects::pure`; add `of` only when a real use needs it.
- **Promises are listed, not checked.** An effects attribute on a declaration with no source and a function that calls `smith_trusted()` are trusted. The plugin writes each as a `P` line of the summary (kind `e` or `t`, symbol, place, name; a header's declaration once per file); `smith check` runs the default build after its parts (a no-op when fresh), reads the `.smith/effects/*.fx` it left, drops duplicates by place and name and files under `.smith/`, and prints `promises: N`, each one with `-v` (`runtime/verbs.c`, `smith_check_promises`). No count means no promise in the built sources.
- **Inline assembly is read, not assumed `c`** (#396; `shim/effects_asm.h`). The template of a GCC-style `asm` is split by clang, each operand replaced by a register of the target (a constant operand by its value; an explicit register by its own, so `register long x8 asm("x8") = 64` and x86's `"a"` carry their constant), and parsed by LLVM's own assembler (MC, already linked for `.s` files; the host target's asm parser only, so a cross-compile is `c`) into a stream that keeps the instructions. The reading follows the constants moved into registers (`mov`, `movz`, `xor r,r`) and records each system-call instruction (`svc`, `syscall`) with its number and third argument, each call or jump to a symbol the block does not define, and each indirect one. The plugin turns them into edges: a system call is the libc function its number names (`shim/effects_asm.h` has the Linux x86-64, Linux AArch64 and macOS arm64 tables) with that function's table effects, `c` for an unknown number; a named symbol is a function of the file, the table's or `c`; an indirect call is `c`; a block that does none of these is no effect. `code` is the effect of making memory executable (`mmap`/`mprotect` with a constant protection with PROT_EXEC, as a call or a system call); only a constant protection is read, so an unknown protection stays `alloc`. The x86-64 side is written from the instruction names and is not yet run by a test (the host that runs the tests is AArch64).
- **Function pointers, report-only** (#396, the rule is not built): the owner's spelling puts the effects after the parameter list of the function type, `void (*log)(const char *) [[smith::effects(console)]]` (`[[smith::pure]]` there means none; a pointer type without one stays `c`). clang's plugin hook has no type attributes (`'smith::effects' attribute cannot be applied to types`), but `[[clang::annotate_type("smith::effects:console")]]` in that place is kept through a typedef, a field, a parameter and a call, so the plugin can read it from the callee's type until the spelling is lowered to it. Meanwhile `SMITH_EFFECTS_POINTERS=<file>` makes every compile append one line for each call through a pointer (`call`) and each named function made into a pointer (`make`, with the effects it has: the set the pointer's type would have to state), in function bodies and in initializers of globals; it changes no diagnostic.
