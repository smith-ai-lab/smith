# A C header is read through clang's C++ libraries, at one edge file

The new front end (#1112) compiles `.smith` itself, so `import <stdio.h>;` must ask clang what a header declares (#1114, track C). It does so through clang's C++ libraries that smith already links (`clangTooling`, `clangFrontend`, `clangAST`), not libclang's C API, which the LLVM pack does not have: adding it would mean an LLVM rebuild.

- **The edge** is `shim/cimport.cpp`: `smith_cimport_read(request, words, capacity)` parses `#include <h>` or `"h"` with the caller's flags (`-I`, `-D`, `-isysroot`, `-resource-dir`) as C, with `-fsyntax-only`, no code generation and no modules, and walks the translation unit. Only declarations from the header and the headers it includes are read; builtins and implicit declarations are not.
- **The result** is one pointer-free array of 32-bit words in the caller's buffer (a string pool and tables of types, functions, structs, fields, parameters and not-imported entries; the layout is at the top of the file). A buffer that is too small gets the words needed, and the caller calls again. C++ containers stay inside the shim.
- **`front::cimport`** (`front/cimport.smith`, #1124) turns the words into `front::ast` nodes: `Header.decls` holds `Decl`s with `from_c` set, in this order: structs (`Decl.record` with `FieldDecl`s, `opaque` when undefined), typedefs (`type_alias`, one per name) and functions (a prototype, `variadic` as in C). A type is a `TypeExpr`: `Void`, `I32`, `F64` and the like are `named`, a struct or typedef is `named` by its name, `pointer`, `array` with a count, and a C function pointer is `applied { Fn, [function { params, result, variadic }] }`. What smith cannot express is `unsupported_c` with the C spelling. The shim's flat table of types stays private to the module. Nodes are allocated with the allocator in force.
- **Not imported** is a list with a name and a reason, never a guess and never silent: unions, bit-fields, `long double`, `__int128`, volatile, arrays without a size, functions without a prototype, variadic inline functions with a body, and every attribute (nonnull, nothrow, Apple's availability). A declaration that uses such a type is still read, with an `unsupported` type that carries the C spelling, and is also listed. An enum type is its integer type where a declaration uses it.
- **Values (C2, #1127):** a named C enum is `Decl.enumeration` (`underlying` is clang's integer type, each enumerator an integer literal clang folded, `unary negate` below zero); an anonymous enum's enumerators, an object-like macro whose value clang folds to a constant, and a `static const` variable with a constant initializer are each `Decl.variable { is_constexpr, from_c }` with the C type clang gives (`8192` is `I32`, `8192UL` is `U64`, `3.14` is `F64`) and a literal `init` (a string macro is a `Str` with a `string` literal); no macro text survives. The shim first preprocesses the header alone to list its macros, then parses once: the header and one line `static const __typeof__((M)) __smith_m_M = (M);` for each candidate, so clang evaluates the values and an error on a candidate's line is that macro's reason. A function-like macro is listed as "a function-like macro", a non-constant (`#define errno (*__error())`) as "not a constant: <clang's message>". Left out silently as the preprocessor's plumbing: names starting with `__`, empty macros (include guards) and macros of only keywords and punctuation (`#define restrict __restrict`). Predefined macros are not imported. The declarations come in this order: structs, typedefs, enums, functions, then the constants.
- **A slice as C passes it (#3327):** a struct named `smith_array_<elem>_n` or `smith_array_const_<elem>_n` that has exactly `data` (a pointer) and `count` (an array of one `unsigned long`, or `size_t`, as the generated headers write it) is read as the slice `[]mut <elem>` / `[]<elem>` in a field, a parameter and a result. Any other struct stays a record, a third field included.
- **A function's type is read as written** (`getTypeSourceInfo`): the redeclaration of a library builtin such as `strlen` otherwise carries the builtin's type and loses the typedef name `size_t`.
- **A missing header** is an error that names the header and the folders searched, not a crash.
- The test is `tests/front_cimport_test.smith` (a fixture header, whose golden is `ast::dump` of the declarations, and the system's `<string.h>` and `<stdio.h>`, in `tests/front/cimport/`), in the front end's runner.
- **`front::cimport_cache`** (`front/cimport_cache.smith`, #1130) keeps what a header declares so it is read once: `read` has the parameters and result of `cimport::read` and is a hit or a read that is stored. The entry is a compact binary form of the declarations (`round_trip` in the test) under `<cache>/smith/cimport/<clang identity>/<key>`, the key being a hash of the header as written, the importer's folder, the flags that change what clang reads and the format version. In ccache's depend mode, an entry lists every file clang read for the header (`shim/cimport_deps.cpp`, a preprocess-only run) with size, time and content hash, and a hit re-checks them (the hash only when size or time differ), so it is never stale; a corrupt entry is a miss. Not wired into `smith cc`; pruning and `smith cache` come at the join (J2). The test is `tests/front_cimport_cache_test.smith`. `smith cc --front-end=new` keeps headers on disk another way: the shim's words, in the import cache of #2891 ([front-end](front-end.md), "From disk").

## Where the reader finds clang's own headers

Clang's builtin headers (`stddef.h` and the others) live in its resource directory. The reader takes it from a `-resource-dir` line of the flags it is given (`smith cc` writes one into `$SMITH_FRONT_CIMPORT_FLAGS`, `runtime/front_flag.c`); when the flags have none it uses its own default, `smith_cimport_default_resource_dir` in `shim/cimport.cpp`: `<llvm>/lib/clang/<newest version with include/stddef.h>` of the LLVM the program links, the root being `SMITH_CIMPORT_LLVM_ROOT` (set by the build of the front end's test runner, `tests/front_units/build.c`) or else `$SMITH_LLVM`. The same default goes to the body compile (`smith_cimport_bodies`) and the file list of the cache (`shim/cimport_deps.cpp`). A program that links the shim has no clang folder beside it, so without the default a header that includes `<stddef.h>` (`<smith/test.h>`) was unreadable and the fixer kept `import c <smith/test.h>`; a test passed only when another test of its runner process had set `$SMITH_FRONT_CIMPORT_FLAGS` first (#3636).

## Functions a header defines (`static inline`)

A function the header gives a body (`static inline`, a plain `inline`, a `static`) is imported like any other: a name of the module (`c::LLVMInitializeAllTargets`), flagged in the shim's words (function flags bit 1) and `is_inline` on its `from_c` declaration. A call to it needs the body in the object, since a `static inline` function has no symbol of its own: `emit::module_all` collects the names the module calls and, at the end, `call::link_c_bodies` hands them to `smith_cimport_bodies` (shim/cimport.cpp), which has the clang inside smith compile a small unit (the module's headers, a `__typeof__(f) f;` redeclaration so a plain `inline` gets an external definition, and one use of each name) in the module's `LLVMContext` for its target, makes each definition `linkonce_odr` and links it into the module. The body is defined once per module however many instances call it, only the called functions (and what they call) are compiled, and the JIT path and the object path are the same. This is the one way a clang-compiled C body reaches a module (#3284, item 59): a later user (a macro wrapped in a small inline C function, #3338, #3342) calls `smith_cimport_bodies` with the C text it wrote.
